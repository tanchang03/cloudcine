# 剧集 / 影片的「季」与「部」层级设计

> 目标读者：实现者。本文先摆**代码事实**，再给设计。每条设计决定都标了理由，
> 因为这套东西里最危险的不是写不出来，而是「写出来了、编译过了、界面看着对，
> 数据却悄悄分叉」。

---

## 1. 现状：代码里到底有什么

先把三张表和三个服务读清楚，后面所有设计都建立在这上面。

| 层 | 实体 | 已有字段 | 缺什么 |
|----|------|---------|--------|
| 作品 | `MediaWork`（`media_works`） | `key`、`kind`、`category`、标题/海报/简介/评分/`onlineId`… | **完全是平的**，没有任何「季 / 部」结构 |
| 文件 | `MediaItem`（`media_items`） | `season`、`episode`、`episodeEnd`、`dirPath`、`groupKey`… | **没有 `part`**（部/分卷） |
| 解析 | `ParsedMediaName`（`filename_parser.dart`） | **已经解析出 `part`**（`CD1` / `Disc2` / `Part1`） | 这个 `part` **在构造 `MediaItem` 时被丢掉了** —— 解析了但从不落库 |

三个关键机制：

1. **归组**：`ParsedMediaName.groupKey` = 归一化片名（小写 + 只留字母数字汉字），
   电影再拼 `#年份`。剧集**故意不含季号**，所以 `S01` 和 `S02` 落进同一个作品
   （`filename_parser.dart` 第 144-156 行有明确注释）。`WorkSeedBook.add` 按这个键
   累积 `WorkSeed`，`build` 时生成一行 `MediaWork`。
2. **目录名顶替**：`DirectoryTitle.seriesTitleOf(dirPath)` 从末级目录往上找第一个
   「像名字」的目录名。`/动漫/进击的巨人/第一季/…` 会因为「第一季」是容器名而
   上溯到「进击的巨人」→ 整部剧归一个作品。**这是当前跨目录归一的唯一手段。**
3. **详情页**：`WorkDetail`（`library_providers.dart:437`）只是
   `work + items`，`items` 由 `itemsForWork` 按「季 → 集 → 名称」排好。
   `_DetailBody` 把它**平铺**成一列 `MediaItemRow`（`work_detail_page.dart:156`），
   **没有任何层级选择**。5 季 60 集就是 60 行长列表。

### 1.1 用户痛点对应的三个真实缺口

| 用户原话 | 代码缺口 |
|---------|---------|
| 「需要有季和部的概念」 | `part`（部）解析了却丢弃；`season`（季）存了却只在排序里用，UI 上不呈现 |
| 「不同目录刮削到同一影片要归一」 | 归一**只**靠本地 `groupKey`。两个目录若片名不同（`流浪地球2` vs `The Wandering Earth II`）就是两个作品；`onlineId`（TMDB/豆瓣 id）**存了但从不用来合并** |
| 「详情页需要明确的季/部层级选择」 | 详情页是平铺列表，没有选择器 |

## 2. 设计目标与范围

**要做的**

- 作品下支持**可选的**「季」层与「部」层细分，集（文件）挂在最内层。
- 层级**只在数据里真的存在时**才出现（单集电影不出现选择器）。
- 跨目录 / 跨刮削身份的作品能归一，且**归一可回退、可手动**。
- 详情页有明确的层级选择，默认选中「续播那一集所在的层」。

**不做的（本设计不覆盖）**

- 海报墙（列表页）按季拆卡片的形态 —— 一部剧仍是一张卡片。
- 剧场版 / 特别篇独立成作品的规则（它们是 `isSampleOrExtra` 的另一种处理）。
- 音频库（`ScanPolicy.audioOnly`）—— 那套与本设计无关。

## 3. 数据模型

### 3.1 给文件加「部」

```dart
// MediaItem 新增（已存在于 ParsedMediaName，只需接上）
final int? part;        // 部号：第几部 / 第几篇 / Part N / CD N
final String? partLabel; // 部的展示名（非数字部用）："最终季"、"游郭篇"、"上部"
```

- `part` **接上现有的 `ParsedMediaName.part`**（`filename_parser.dart:846` 的
  `_partOf` 已经能认 `CD1 / Disc2 / Part3 / DVD1`）。这是零成本的补齐。
- 再扩 `_partOf` 的识别面，覆盖中文语境：
  `第X部` / `第X篇` / `第X章`（作为**部**而非集）/ `上部`·`下部`·`前篇`·`后篇` /
  `Part.1` / `Season 0`（特别篇另议）。
- `partLabel` 只在**解析不出数字**时才填（「最终季」没有数字）。有 `part` 时展示
  统一用「第 N 部」，避免同一部剧里「第1部」和「Part.1」混着显示。

> **为什么不复用 `season` 塞「部」**：季号会参与 `itemsForWork` 的排序和
> `PlayTarget` 的取舍，把部混进季会让「进击的巨人 S3 Part2」排成「第 3 季的第 2 集」
> 那种错位。两者必须是两列。

### 3.2 作品层**不加**列（v1）

「这部作品有几个季 / 几个部」**从 items 派生**，不落 `media_works`：

- 详情页本来就一次性把 `items` 全查出来（`itemsForWork`），派生是纯内存计算。
- 加冗余列就要维护一致性（增删集时回填），而这是本项目反复踩过的坑
  （见 `MediaWork.itemCount` 那一段「冗余字段」注释的谨慎语气）。

**例外**：若将来列表页要在卡片上显示「3 季」，再考虑加一个只读派生列，届时单开一轮。

### 3.3 归一需要的东西已具备

- `MediaWork.onlineId` 已存在（TMDB `tv/12345`、豆瓣 id）。
- `MediaItem.groupKey` 是作品的关联键。
- 归一**不需要新列**，需要的是「合并两个作品」的仓储方法和一条自动规则。

## 4. 层级规则：季和部谁在外、谁在内

这是整个设计里**唯一有真正歧义**的地方，先讲清楚，再给默认决定。

### 4.1 现实里的三种形态

| 形态 | 例子 | 外层 | 内层 |
|------|------|------|------|
| 只有季 | 美剧《老友记》S01…S10 | 季 | — |
| 只有部 | 国产剧《庆余年》第一部 / 第二部；海贼王「东海篇 / 阿拉巴斯坦篇」 | 部 | — |
| 季 + 部 | 《进击的巨人》第三季 Part.1 / Part.2 | **季** | **部** |

注意第三种：`S03` 下面才是 `Part.1/Part.2`，所以**季在外、部在内**。而
「庆余年第一部/第二部」里「部」是最大的分组，此时**没有季**，部自己就是外层。

### 4.2 决定：**季在外、部在内；某层不存在就不显示**

- 数据里同时有季和部 → 先选季，再选部（进击的巨人场景）。
- 数据里只有部 → 只显示部选择器（庆余年 / 海贼王场景）。
- 数据里只有季 → 只显示季选择器（现有行为，补上 UI）。
- 两者都没有 → 不显示任何选择器（电影、单集剧）。

**为什么这样定而不是反过来**：`season` 是发布组命名的**强约定**（`SxxExx`、
`第x季`），几乎不会认错；而「部」的写法太杂（`第一部`/`Part.1`/`篇名`）。
把强约定放外层，弱信号放内层，认错「部」时的爆炸半径最小 —— 最坏是某个季下面
多出一个「第 1 部」分组，而不是整部剧被拆成两个作品。

### 4.3 「层」的派生规则（纯函数，可单测）

```
levels(items) =
  seasons = items.map(season).filterNotNull().toSet()
  parts   = items.map(part/partLabel).filterNotNull().toSet()

  if seasons.length >= 2 || (seasons.isNotEmpty && parts.isNotEmpty):
      # 季层存在
      if parts.length >= 2: return [SeasonLevel, PartLevel]
      else:                 return [SeasonLevel]
  else if parts.length >= 2:
      return [PartLevel]
  else:
      return []            # 不显示选择器
```

- **`>= 2` 才建层**：只有一季的剧不显示「第一季」这个孤零零的按钮 ——
  一个只有一个选项的选择器是噪音。
- 季存在但只有 1 季、部有多个 → 仍要显示部层（不能因为季只有 1 个就整体不显示）。
- `season == null` 的集（未标季）归入一个隐式的「未标季」桶，排在所有具名季**之前**
  （与 `itemsForWork` 里 `?? 0` 的现有口径一致）。

> 派生结果**不落库**，每次由 items 现算 —— 保证「增删一集后层级立刻正确」，
> 不会出现冗余列过期。

## 5. 跨目录 / 跨刮削身份的归一

分两条路：**自动**（刮削给出同一个身份）与**手动**（用户点「合并到…」）。

### 5.1 自动归一：按 `onlineId` 合并

扫描 / 刮削结束后跑一次**合并遍**：

```
for each (onlineId, kind) with >1 works:
    target = 作品里 itemCount 最大者（并列时 firstSeenAt 最早者）
    for each other:
        items 的 groupKey 全部改写成 target.key   # 或直接改 works 行
        target 的 itemCount/totalBytes/lastModifiedAt 重算
        删掉 other 行
```

三条硬约束（做错就静默坏数据）：

1. **只在 `source == online` 且 `onlineId` 非空且 `kind` 相同**时才合并。
   本地解析出的两个作品（都没刮到）**绝不**自动合并 —— 那正是
   `182.格力空调` 事故的形态。
2. **`source == manual` 的行不参与**（用户手写过的东西不许被算法动）。
3. **合并要写一条 `diag.info`**（哪两个键、按什么 id 合的），否则用户看到
   「两个格子变成一个」时无从追溯。

### 5.2 手动归一：详情页「合并到…」

自动合并不了的情况（本地片名差异大、压根没刮到、刮到两个不同条目但其实是同一部）
只能人来判。入口：详情页一个「合并到…」按钮 → 搜索框列出候选作品 → 选中 →
把**当前作品的所有 item 迁到目标作品**、删当前行、返回目标作品页。

- 迁移是**单向且可解释**的：只改 `groupKey` 指向，不动文件本身。
- 迁完提示「已合并 N 个文件到《目标》」，并给一个**撤销**（记住源 key 与
  item 列表，撤销即改回）。撤销是必须的 —— 合并错一次而不可逆，用户会直接不敢用。

## 6. 详情页 UX

### 6.1 版式（在现有版式上插一行，不动骨架）

```
[返回]                                          [刷新]
┌──────────┬─────────────────────────────────────────┐
│          │  进击的巨人  Attack on Titan            │
│  海报    │  剧集 · 2013 · 87 集 · 9.1  [在线刮削]   │
│  138×207 │  类型标签…                              │
│          │  [▶ 播放]  [刮削] [手动] [自定义] [合并到…]│
└──────────┴─────────────────────────────────────────┘
网盘位置  /动漫/进击的巨人/                           [复制]

  ┌ 季 ─────────────────────────────────────────┐   ← 新增：层级选择器
  │ [第一季 25] [第二季 12] [第三季 22] [最终季 28] │
  └──────────────────────────────────────────────┘
  ┌ 部 ─────────────────────────────────────────┐   ← 仅当当前季有多个部
  │ [Part.1 12] [Part.2 10]                       │
  └──────────────────────────────────────────────┘

  文件  22  共 22 个 · 点任意一行播放
  ▸ 进击的巨人 S03E01 …
  ▸ 进击的巨人 S03E02 …
```

### 6.2 交互决定

1. **选择器用 chip 行，不用下拉**：TV 上（本项目的首要目标）chip 是方向键可达的
   焦点目标，下拉在遥控器上体验差。复用 `library_filter_panel` 里 chip 的做法。
2. **默认选中「续播那一集所在的层」**：与 `PlayTarget.resolve` 同源 —— 用户点开
   一部剧最可能想接着上次看，默认层就该是他上次看的那一季/部，而不是第一季。
   没有播放记录时选**第一层**。
3. **每个 chip 带集数**（`第一季 25`）：一眼看出哪季还没看。
4. **「播放」按钮跟随当前层**：选中「第三季」后点播放，播的是第三季的续播点 /
   第一集，而不是整部剧的第一集。
5. **层级切换不重新查库**：`WorkDetail` 已经持有全部 items，切换只是本地 filter，
   零延迟、零请求。
6. **集号排序在层内**：层内仍按「集 → 名称」排（复用现有排序，只加一层 `part` 比较）。
7. **无层级时不显示选择器**，版式与现在完全一致（电影、单集剧零变化）。

### 6.3 空态与边界

- 某层下一个正片都没有（整季都是花絮）→ 仍显示该层，但列表区显示「本季只有花絮」。
- `partLabel` 与 `part` 同时缺失但文件名有「上部」字样 → 归入「未标部」桶。
- 层级 chip 过多（>8）→ 横向可滚动（`SingleChildScrollView`，**`primary: false`**，
  见 `library_filter_panel` 的坑）。

## 7. 迁移与兼容

- **新列全部 nullable**：老库 `part = null` → 派生不出部层 → 行为与现在一致。
- `schemaVersion` +1，`MigrationStrategy.onUpgrade` 里 `addColumn`。drift 的
  `addColumn` 对 nullable 列是安全操作，不需要回填。
- **`groupKey` 语义不变**，所以历史作品的 `key` 不动，`media_items.groupKey`
  不用重写（合并功能除外）。
- 改 `tables.dart` 后**必须先跑 `build_runner build`** 再编译，否则报的错看不懂。

## 8. 建议的实施顺序（每步可独立提交、可独立回退）

| 阶段 | 内容 | 风险 |
|------|------|------|
| P0 | 接上 `part`：`MediaItem.part/partLabel` + DB 列 + 迁移 + 扩 `_partOf` 识别面 + 单测 | 低（纯补齐） |
| P1 | 派生纯函数 `WorkLevels.of(items)` + 单测（覆盖 4.1 三种形态） | 低 |
| P2 | 详情页层级选择器（chip 行 + 默认选中续播层 + 播放跟随） | 中（UI） |
| P3 | 自动归一（按 `onlineId` 合并遍）+ diag 留痕 | **高**（会删行） |
| P4 | 手动「合并到…」+ 撤销 | 中 |

P0/P1/P2 是用户看得见的收益，P3/P4 是「归一」那半。建议先做 P0–P2 验收体验，
再动 P3。

## 9. 待确认（需要你拍板）

1. **季/部的内外顺序**：默认「季在外、部在内」（4.2）。你的库里如果更多是
   「第 X 部」当大分组（如长篇国漫），告诉我，我把默认反过来或做成按数据自适应。
2. **自动归一是否默认开**：P3 会**删作品行**。默认自动开，还是默认关、只在用户
   点「合并到…」时手动合？（我倾向：**默认开但只限 `onlineId` 相同**，因为那是
   高置信信号。）
3. **剧场版 / 特别篇**：归入所属季的一个「特别篇」部，还是独立成作品？
4. **列表页要不要显示「N 季」**：要的话 P0 之外再加一个只读派生列。
