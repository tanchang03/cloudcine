# 追剧 / 更新提醒 —— 场景设计与实现方案

> 目标：已入库的作品可以「追剧」。当网盘里这部剧的目录下**新出现了文件**（更新了最新集数），
> 应用自动把它增量同步进媒体库，并在海报墙上打「更新 N」角标、在剧集列表里把新集标成 NEW，
> 直到用户看过。
>
> 本文同时覆盖 **macOS/Windows（Flutter PC 端）** 与 **Android TV（原生 Kotlin）** 两套实现。
> 两端共用的只有**数据库 schema** 与**判据口径**，其余各自实现（两个工程互不引用）。

---

## 0. 一句话方案

> 给 `media_works` 加 4 列（`followed` / `follow_started_at` / `follow_checked_at` / `new_item_count`），
> 检查时**只对已追剧作品名下的那几个网盘目录**跑一次「局部发现」（复用现成的 `discover`），
> 再用 `media_items.first_seen_at` 与两个时间戳做差算出「新增了几条」，写进冗余计数列当角标。

不新造扫描器、不新造目录遍历、不新造增量协议 —— 全部复用既有的「局部发现」链路。

---

## 1. 为什么不能靠「全盘扫描」

| | 全盘扫描 `scan()` | 追更检查（本方案） |
|---|---|---|
| 请求量 | 遍历**全部**目录（实测 44+ 目录 / 427 视频，真实库几千文件） | 只列**已追剧作品名下的目录**（去重后通常 1~5 个） |
| 耗时 | 几分钟 | 秒级 |
| 限流风险 | 高（夸克有 QPS 限制，目录超时会跳过） | 低 |
| 副作用 | 写 `scan_cursors`、做 `pruneMissingItems` | **无**（只增不减、不写游标） |
| 触发时机 | 用户手动 | 启动 / 进媒体库 / 手动，可静默跑 |

追剧是个**高频、轻量、可静默**的动作；全盘扫描是**低频、重量、要用户知情**的动作。两者不能混。

**可复用的现成能力**：

- PC：`lib/domain/services/media_discovery.dart` → `MediaDiscoveryService.discoverDirectory(...)`
- Android：`LibraryScanner.discover(rootFid, rootPath, recursive)`（`LibraryScanner.kt:459`）

这两个已经是「只增不减、不写游标、不 prune」的局部发现，**正好是追更需要的东西**，一行都不用改语义。

## 2. 数据模型

### 2.1 新增 4 列（`media_works`）

| 列名 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `followed` | INTEGER NOT NULL | `0` + `CHECK (followed IN (0,1))` | 是否追剧 |
| `follow_started_at` | INTEGER NULL | — | **追剧起点**（Unix 秒）。开启时写一次，之后不动 |
| `follow_checked_at` | INTEGER NULL | — | **上次检查时刻**（Unix 秒）。每次检查成功后推进 |
| `new_item_count` | INTEGER NOT NULL | `0` | 未读新增条数（角标上的数字） |

### 2.2 三条判据（全部基于已有的 `media_items.first_seen_at`）

```
① 「本次新扫到的条」   = media_items.first_seen_at > work.follow_checked_at
② 「追剧以来新增的条」 = media_items.first_seen_at > work.follow_started_at
③ 「这一集还没看过」   = media_items.max_position_ms IS NULL
```

- **①** 驱动 `new_item_count +=`（增量累加，见 §7 红线 7）
- **② ∧ ③** 驱动剧集列表里的 NEW 行标签 —— **播过就自动消失，不需要任何额外写入**

### 2.3 为什么用 `first_seen_at` 而不是 `modified_at` / `episode` 最大值

| 候选判据 | 为什么不用 |
|---|---|
| `media_items.modified_at`（网盘给的修改时间） | **替换文件也会变**。用户换了一版更高码率的同一集 → 误报「有新集」 |
| `episode > MAX(episode)` | 集号会缺失 / 重复 / 花絮带集号；电影、综艺、`kind=unknown` 根本没有集号 |
| `item_count` 变大 | 只知道「多了」，不知道「多了哪几条」，画不出行级 NEW 标签；且删一集加一集会漏报 |

`first_seen_at` 是**「我什么时候第一次见到这个文件」这个历史事实**，只在行首次插入时写，
重扫不刷新（`upsertItems` 的 `skipFirstSeen` 分支 + Android `applyScanItems` 的新行分支，
两端都已经守住了这条）—— 它天然就是「新集」的定义，而且对**所有 kind** 都成立。

### 2.4 迁移

- PC：`AppDatabase.schemaVersion` **16 → 17**，`onUpgrade` 加 v17 分支（4 条 `ADD COLUMN`）
- Android：`LibrarySchema.VERSION` **16 → 17**，`mediaWorks` 加 4 列；
  `LibraryDb.ensureSchema` 是「只补表补列」，自动跟上
- `LibrarySchemaTest` 的逐字比对必须同步更新
- ✅ **v17 不需要回填**：4 列的默认值（`followed=0` / 计数 `0` / 两个时间戳 `NULL`）
  恰好表达「这部作品没在追剧」，与升级前行为完全一致 —— 与 `part` / `intro_start_ms`
  当初的做法同一取向（不需要回填的迁移就不写回填）。

## 3. 检查流程

```
触发（启动 / 进媒体库 / 手动）
  │
  ├─ 1. 节流闸：距 settings.follow_last_check_at 不足窗口 → 直接返回（手动入口无视）
  │
  ├─ 2. 取追剧清单
  │      SELECT key FROM media_works WHERE followed = 1 AND merged_into IS NULL
  │      空 → 直接返回（没人在追剧，一次请求都不发）
  │
  ├─ 3. 反查目录集合（并集口径，含被折叠的源作品名下的文件）
  │      SELECT DISTINCT dir_id, dir_path FROM media_items
  │       WHERE group_key IN (追剧清单) OR group_key IN (折叠进它们的源 key)
  │      → 去重后得到 N 个目录
  │
  ├─ 4. 逐个目录跑局部发现（recursive = true，见 §7 红线 3）
  │      失败（超时 / 限流）→ 记下这个目录，**不推进 follow_checked_at**
  │      成功 → 记下这个目录覆盖到的所有 group_key
  │
  ├─ 5. 回写（一次事务）
  │      for 每个「本次有目录成功」的追剧作品 W:
  │          n = COUNT(media_items WHERE group_key = W.key
  │                          AND first_seen_at > W.follow_checked_at)
  │          new_item_count += n
  │          follow_checked_at = now
  │      settings.follow_last_check_at = now
  │      ⛔ 全程**不写 media_works.updated_at**（见 §7 红线 1）
  │
  └─ 6. UI 刷新：海报墙角标 / 剧集行 NEW / 分类栏「追剧 N」/ 状态行一句话
```

### 3.1 目录集合为什么要**按目录**回写，而不是按「发起检查的那一部」

网盘上的目录不是「一部剧一个目录」：

- `/电影/` 这类目录是**平铺**的，一个目录里有几十部作品；
- 一部剧的 12 集可能全在 `/剧集/黑亚当/` 一个目录里；
- 跨目录归一之后，一部作品的文件可能来自**两个不同目录**。

所以「发现某个目录」这件事的产出必须按 `group_key` 归类，**回写给这个目录覆盖到的每一部追剧作品**。
只回写发起者的话，`/电影/` 里同时更新的另外三部片子就永远收不到提醒。

### 3.2 为什么失败目录不推进 `follow_checked_at`

`follow_checked_at` 是**水位线**。目录列失败（超时 / 限流）时推进它，等于把这批新集
永久划进「已经看过了」——用户再也不会被提醒。

这与全盘扫描那条「有目录列失败就不做陈旧清理」（`LibraryScanner.scan` 的 `failedDirs == 0` 前置条件）
是**同一条思路**：白名单 / 水位线在自身不完整时是有害的，宁可这次不推进，下次重来。

### 3.3 节流零点放在 `settings` 表

作品级的 `follow_checked_at` 是**逐个**的，节流需要一个**全局零点**。
放 `settings` 表（`follow_last_check_at`）的三个理由：

1. 跨端随 `.ccbak` 备份包走（两端同一口径）；
2. `settings` 表**不参与** `libraryModifiedAt` 同步判据 → 不污染同步（见 §7 红线 1）；
3. 与 `remember_position` / `auto_scrape_on_scan` / 刮削四键同一个地方，不新造存储。

## 4. 触发时机

### 4.1 PC（macOS / Windows）

| 入口 | 时机 | 节流 |
|---|---|---|
| 启动静默检查 | App 启动后**延迟 20 秒**（等首屏渲染完，不与首帧抢 IO / 网络） | 沿用窗口 |
| 手动检查 | 媒体库页头「检查更新」图标按钮 | 无视 |
| 定时检查 | 设置项 `follow_auto_check`：`off` / `on_launch`（默认）/ `every_6h` | 沿用窗口 |

完成后：`SnackBar`「2 部剧有更新」+「查看」按钮 → 切到追剧视图。
无更新时**不弹任何东西**（只在按钮上转个圈）。

### 4.2 Android TV

| 入口 | 时机 | 节流 |
|---|---|---|
| 进媒体库静默检查 | `LibraryActivity` 首帧后延迟 **1.5 秒** | 窗口 **30 分钟** |
| 手动检查 | MENU 覆盖层菜单「检查追剧更新」 | 无视 |
| 单作品检查 | 作品简介页动作胶囊「检查更新」（对当前这一部） | 无视 |

- ⛔ **绝不弹对话框**。TV 上弹窗会打断播放、抢焦点、还需要遥控器去点「确定」。
  更新只体现在：状态行一句话 + 海报墙角标 + 分类栏「追剧 N」。
- ⛔ **静默失败**：网络错误只写 `Log` + 状态行一句话，不重试、不打断。
- 零点复用 `StartupSync` 那套思路（`MainActivity.onCreate` 是「本次启动」的唯一信号），
  但追剧检查**不需要**「一个进程一次」这么严 —— 30 分钟窗口本身就是节流。

- 检查中转圈 + 文案「检查中 3/12」；完成无更新则**什么都不显示**（按钮上的转圈本身就是回执）。

> ⛔ **为什么不放页头（2026-10-07 实测）**：桌面页头那一行（`PageHeader` 的

追剧栏为空时**不能**说「这个分类下暂时没有作品」（`libraryEmptyHint`）——
「追剧」是视图不是分类，用户会去分类栏里找一个不存在的入口。单独一支：
「还没有在追的剧集。打开任意一部作品的详情页点「追剧」…」+「去看看全部」。

⚠️ 这一支排在**搜索词 / 面板条件之后**：带条件时确实是「条件太紧，清掉就好」，
排在前面会让用户点「去看看全部」时把自己打的词一起丢掉。

## 6. 跨端一致性

| 事项 | 契约 |
|---|---|
| 4 个新列 | 列名 / 类型 / 默认值两端**逐字一致**（`LibrarySchemaTest` 守着） |
| `user_version` | 两端都是 **17** |
| 判据口径 | 三条判据（§2.2）两端同一套，差异只在 SQL 方言 |
| 节流键 | `settings` 表 `follow_last_check_at`（Unix 秒字符串），两端同键名 |
| 备份包 | 4 列都在 `media_works` 里 → 随 `.ccbak`（原始 db 字节）自动跨端走 |

**跨端场景推演**：电脑上追了《黑亚当》、加了第 13 集、检查出更新 → 备份上传。
电视恢复备份 → `followed=1` / `follow_started_at` / `follow_checked_at` / `new_item_count=1`
**全都带过去**（连同角标）。电视上第一次检查时水位线是电脑写的时间，只会报电脑那之后的新增。✅

> ⚠️ `new_item_count`（角标）会跨端传播，但**清零不会**（清零不写 `updated_at`，同步判据不变）。
> 这是**刻意的**：角标是「这台设备的未读提醒」。电脑上看过 ≠ 电视上看过 ——
> 电视用户本来就是另一个人 / 另一个场景。若将来要改成同步，把清零也写 `updated_at` 即可。

## 7. 红线清单（实现时逐条守住）

1. ⛔⛔ **自动检查的写入不动 `media_works.updated_at`**。
   `libraryModifiedAt` = `MAX(media_works.updated_at)` ∪ `MAX(media_items.first_seen_at)` ∪
   `MAX(media_items.last_played_at)`（两端同口径），它是同步的 LWW 判据。
   检查一次就刷新 `updated_at` 的话，本地永远「看起来更新」→ 下次同步无条件上传 →
   **把另一台设备刚看的进度盖掉**。只有**用户手动开关追剧**才写 `updated_at`（那是真实内容变更）。

2. ⛔⛔ **检查只用「局部发现」，绝不调全盘 `scan()`**。
   `scan()` 会写 `scan_cursors`、会拿「本次见到的 id」当白名单跑 `pruneMissingItems`。
   只看到一棵子树时用它当白名单 = **把库清空**。

3. ⛔ `discover` 的 `recursive = true`。剧集常在 `S01/` 子目录里，只看一层会永远发现不了新集。

4. ⛔ **目录集合必须去重**。12 集同一个目录 → 只发 1 次列目录请求，不是 12 次。

5. ⛔ **按目录回写**，不是按发起者。一个目录可能含多部作品（见 §3.1）。

6. ⛔ **目录失败不推进 `follow_checked_at`**（见 §3.2）。

7. ⛔ `new_item_count` 是**增量累加 `+=`**，不是重算 `=`。重算会把用户清过的角标又算回来。

8. ⛔ 角标清零**只清 `new_item_count`**，不动 `follow_started_at`。
   动它的话，剧集列表的 NEW 标签会跟着一起消失 —— 而用户还没看。

9. ⛔ Android `posterBox` 的新角标**追加在末尾**（现有代码按下标 `getChildAt` 取子控件）。

10. ⛔ 两端 `schemaVersion` 必须**同时**到 17。只改一端 → 另一端 `restore` 后不跑迁移、
    直接 `no such column: followed`，且**不会有任何迁移来兜底**。

11. ⛔ Android 列目录必须走 `PanApi`（`pr=ucpro&fr=pc` 不能漏、`useCaches = false` 不能省）。
    直接复用 `LibraryScanner.listAll` 即可，不要另写一份。

12. ⛔ TV 上检查必须**静默失败**：不弹窗、不重试、不打断播放。

13. ⛔ `customizeWork`（PC）是**整行写**（`_workCompanion(custom)`，不过 `mergeWorkForUpsert`）。
    新 4 列必须显式带上旧值，否则用户点一次「自定义」就把追剧状态整份抹掉。

14. ⛔ `mergeWorkForUpsert`（PC）里 4 列**无条件取旧值**，与 `mergedInto` / `introStartMs` 同一条规矩：
    扫描造出来的新行这 4 列恒为默认值，照抄新值 = 每次重扫都取消追剧。

15. ⛔ Android 恢复备份后必须清设置缓存（`SettingsStore.invalidate()` +
    `invalidate(settingsProvider)`）—— `follow_last_check_at` 在 `settings` 表里，同样受影响。

## 8. 边界与反例推演

| 场景 | 期望 | 为什么成立 |
|---|---|---|
| 库里已有 12 集，用户此刻开启追剧 | **不报更新** | `first_seen_at < follow_started_at` |
| 网盘加了第 13 集，检查 | 角标「更新 1」+ 第 13 集标 NEW | ①=1，②∧③ 成立 |
| 用户进简介页看了一眼就退出 | 角标消失，第 13 集仍标 NEW | 清角标只清 `new_item_count`（红线 8） |
| 用户播了第 13 集 | NEW 标签自动消失 | `max_position_ms` 非空，③ 不成立 |
| 用户换了一版更高码率的第 13 集 | **不报更新** | `modified_at` 变了但 `first_seen_at` 没变 |
| 重扫同一批文件 | 不报更新 | `first_seen_at` 不刷新 |
| 网盘删了第 12 集又加了第 14 集 | 报「更新 1」 | 第 14 集是新 fid → 新行 |
| 取消追剧再重新开启 | NEW 标签全消失，从此刻重新计 | `follow_started_at` 重置 |
| 一部剧横跨两个目录 | 两个目录都检查 | 目录集合取并集 |
| 电脑追剧 → 电视恢复备份 | 状态 + 角标一起过来 | 4 列随 db 字节走 |
| 电视上清了角标，电脑上还有 | 两边不一致（**预期**） | 清零不写 `updated_at`，不参与同步 |
| 追剧 0 部 | 一次网盘请求都不发 | §3 第 2 步提前返回 |
| 检查时目录超时 | 本次不推进水位线，下次重来 | 红线 6 |

## 11. 与现有功能的关系

| 现有能力 | 关系 |
|---|---|
| 全盘扫描 `scan()` | **不改**。追更是它之外的独立轻量通道 |
| 局部发现 `discover` | **不改语义**，直接复用（追更 = 一次「按作品定向」的发现） |
| `StartupSync`（启动备份探测） | **并列**。两个启动探测各管各的，都遵循「静默 / 一个进程一次 / 只读」的取向 |
| 备份同步 `.ccbak` | 4 列随包走；节流零点在 `settings` 表随包走 |
| 跨目录归一 `mergedInto` | 追剧清单只取 `merged_into IS NULL`；目录集合取**并集**（含被折叠源作品的文件目录） |
| 「继续观看」`lastUnfinished` | **语义不同**，不要混：「继续观看」回答「我看到哪了」；追剧回答「有没有新东西」。两者可以同时命中同一部剧 |
| `WorkSort` / `LibraryDb.Sort` | **不新增排序档**。追剧视图内用隐式规则「有更新优先」，避免污染全局排序枚举（那是两端共用的口径） |

## 12. 工作量与风险

**风险最高的三处**：

1. **schema 16→17 跨端同步**（阶段 A）。必须两端同时改、同时测，且 `LibrarySchemaTest` 逐字过。
   漏一端的后果是 `no such column`，且**没有迁移兜底**。
2. **红线 1（不写 `updated_at`）**。写错了不会报任何错，只会表现成「另一台设备的播放进度莫名其妙被覆盖」——
   极难反查。
3. **红线 5（按目录回写）**。写错了表现成「有的剧就是不提醒」，而检查日志上一切正常。

**建议的落地顺序**：阶段 A（两端 schema + 单测）→ 阶段 B（引擎 + 纯决策单测）→
先在 **Android TV** 打通（一个 Activity、一条链路，验证成本最低）→ 再补 PC 的 UI（面更宽）。
