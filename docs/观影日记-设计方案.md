# 观影日记（Watch Diary）—— 功能与交互设计方案

> **目标**：把「我看过哪些剧、看完多少、我给它打几分」变成一份**独立于媒体库的永久日记**。
>
> 媒体库可以清、网盘文件可以删、换设备可以重扫 —— 日记一条都不丢，两端还能自动合并。

---

## 0. 一句话方案

> 新开一个**只装日记的 JSON 文件**（`<应用支持目录>/watch_diary.json`，网盘上同名放在 `云影备份/`），
> 每条记录 = 一部作品的**身份快照 + 完成度快照 + 个人评分**。
> 达标（剧集按集数 ≥ 80%、电影按单片 ≥ 80%）才写入，写入后**冻结**，不再读 `media_items`。
> 同步**挂在播放进度那条通道上**：同一个调度器、同三个触发点、同一套「播种 → 下载 → 逐条合并 → 按需上传」，
> 只是**各存一个文件、各传各的**（为什么不合并成一个文件见 §6.1）。

**不新增数据库表、不改 schema、不碰 `media_works` / `media_items` 的任何一列。**

---

## 1. 先分清四个东西（这是整份设计的地基）

这个项目里已经有三个「和看过有关」的概念，再加一个新的，必须先把边界划死，否则后面每一个判断都会含混。

| | 数据在哪 | 生命跟着谁走 | 会自己消失吗 | 用途 |
|---|---|---|---|---|
| **媒体库作品** | `media_works` / `media_items`（sqlite） | 网盘扫描 | 会。清理 / 重扫 / 删文件就没了 | 「现在能看什么」 |
| **追剧（`followed`）** | `media_works` 四列 | 网盘扫描 | 会 | 「这部还在更新，等新集」 |
| **最近播放** | `media_items.last_played_at` + 视图 | 网盘扫描 | 会 | 「刚才看到哪儿了」 |
| **观影日记（本方案）** | **独立 JSON 文件** | **用户 + 同步** | **不会**（除非用户手动删） | 「我看过什么、我给它几分」 |

### 1.1 为什么日记必须是「快照」而不是「投影」

这是全篇最重要的一句话：

> **日记记录的是「历史事实」，不是「当前状态的查询结果」。**

一个反例最能说明问题。假如日记不存快照，而是存一个 `work_key`，展示时 JOIN `media_works` 拿标题和海报：

1. 用户看完了《漫长的季节》，记入。
2. 用户清理媒体库（或者网盘上的资源被删了，重扫时 `media_items` 被 prune）。
3. `media_works` 那一行没了 → JOIN 不出东西 → **日记列表里那一条变成空白，或者整条消失**。

这正是用户明确要求不能发生的事。所以：

- 标题、年份、海报、类型、集数、完成度 —— 全部在**记入那一刻**抄一份存进日记；
- `work_key` 只作为一个**可选的弱引用**保留，用来「如果资源还在，点进去能播」；
- 资源不在时，日记照常显示，只是详情页少一个播放按钮。

一句话：**媒体库是「现在能看什么」，日记是「我看过什么」。前者可重建，后者不可重建。**

### 1.2 与「追剧」的衔接

`followed = true` 是「等更新」，日记是「已看完」。两者是**同一条时间轴上的前后两段**：

```
入库 ──→ 追剧中（followed=1，等新集）──→ 达标 ──→ 已记入（followed=0）
                                                      │
                                          出新一季 ───┘──→ 提示「有新一季」
```

- 记入时**自动把 `followed` 置 false**（不再提醒更新，否则角标永远挂着）；
- 之后如果网盘又出现新季，扫描发现后日记行打「有新一季」标，提示用户重新加入；
- 这条是 Phase 2，先留字段，不做 UI。

## 2. 五条需求 → 五条硬约束

把用户的话逐条翻译成「实现上不许做什么」。每一条都直接杀死了某种看起来很自然的做法。

| # | 需求原文 | 翻译成约束 | 杀死了什么做法 |
|---|---|---|---|
| R1 | 记录曾经追过的**所有**剧集 | 记录的存在性**不依赖**任何 `media_items` 行 | 存 `work_key` + JOIN 展示（§1.1） |
| R2 | 支持个人评分 | 可反复修改、可追溯、可离线 | 只存一个 `rating` 数字不存修改时间 |
| R3 | PC / 移动端共享 | 两端各自新增的日记要**合并**，不能互相覆盖 | 走 `.ccbak` 整库 LWW（§6.2） |
| R4 | 清理媒体库 / 网盘删资源都**不**清日记 | 日记文件与 `cloudcine.sqlite` 物理分离 | 新建一张 `watch_diary` 表（§4.6） |
| R5 | 必须达到 80% 才能记入 | 门槛是**硬门槛**，手动也绕不过 | 提供「强制记入」按钮 |

> R4 与 R3 是同一个决定的两面：**只要日记活在被整份覆盖的文件里，它迟早会被覆盖掉。**
> 所以它必须活在「逐条合并」的那条通道上。

## 3. 完成度判定

### 3.1 两种形态，两套口径

| 形态 | 判定 | 分母从哪来 |
|---|---|---|
| **电影 / 单文件**（`kind = movie`，或作品下只有 1 个文件） | `maxPositionMs / durationMs ≥ 0.80` | 该文件自己的时长 |
| **剧集 / 多文件**（`kind = tv` 等，作品下 ≥ 2 个文件） | `看完的集数 / 总集数 ≥ 0.80` | **库里已有的文件数**（不是 TMDB 总集数） |

### 3.2 单集「看完」用哪个阈值：95.6%，不是 80%

这一点必须解释，否则会被当成 bug：

```dart
// lib/domain/services/playback_resume.dart
static const Duration finishedTail = Duration(minutes: 2);
static const double finishedRatio = 0.02;
// threshold = total - max(2%, 2min)
```

- 45 分钟的剧：阈值 = 43 分钟 → **95.6%**
- 24 分钟的番：阈值 = 22 分钟 → **91.7%**

**为什么单集不也用 80%**：因为「单集看完」这件事在应用里**已经有定义**了 ——
详情页每一集的进度条打勾、`resumePositionMs` 被清空、自动连播下一集，用的都是 `PlaybackResume.isFinished`。

如果记入判定另立一个 80%，就会出现这种场面：

> 详情页上第 12 集**没有打勾**（因为只看到 85%），但整部剧已经记入了。

用户会认为「记入判错了」。**一致性比统一百分比更重要** —— 而且 2 分钟的尾巴正好覆盖片尾曲，用户看完正片就会跨过阈值，实际体验并不苛刻。

电影则不同：电影片尾字幕常有 5–10 分钟，用户看完正片就退出是常态，所以用用户指定的 **80%** 更符合真实行为。

### 3.3 分母为什么是「库里已有的集数」

不用 TMDB 的总集数，三条理由：

1. **离线可用**：没刮削过的作品没有总集数，而记入判定不能依赖网络；
2. **避免永久卡死**：TMDB 标 24 集，网盘上只有 12 集（下半季还没出）→ 永远到不了 80%；
3. **与「看完了」的直觉一致**：用户说「我看完了这部剧」，指的是「网盘上有的我都看了」。

代价要明确承认：**库里少了集数会让完成率虚高**（删掉 10 集，剩下 2 集看完 = 100%）。
所以 §3.4 的冻结机制是必需的。

### 3.4 记入时**冻结**快照（关键）

```dart
// 记入那一刻算一次，写死进记录，之后永不重算
episodeTotal:   24,     // 记入时库里这部剧有几集
episodeWatched: 20,     // 其中看完了几集
completionRatio: 0.833, // 派生值，也存一份，便于排序/展示，不用每次算
```

**为什么必须冻结**：如果每次展示都拿 `media_items` 重算，那么用户删掉 18 集之后，
剩下 6 集里看了 5 集 → 完成率从 83% 变成 83%（碰巧），但如果是「看了 20 集 → 删掉 15 集没看过的 →
剩下 9 集全看完 → 100%」，日记会显示「9/9 全看完」，而事实是「24 集里看了 20 集」。

日记是历史事实，事实不能因为后来删了文件而改写。

### 3.5 边界情形

| 情形 | 处理 | 理由 |
|---|---|---|
| 时长未知（`durationMs IS NULL`） | **不计入**分子，但**计入**分母 | 拿不到分母，不能判「看完」；但它是这部剧的一集，不能假装不存在 |
| 时长未知且占多数（> 20%） | 判定结果标「完成度不可靠」，仍可记入但 UI 标注 | 宁可记入一个带问号的，也不要因为网盘没给时长就永远不记入 |
| 花絮 / 预告（`isSampleOrExtra = true`） | **不计入分母** | 花絮不该拉低完成率（`media_items` 已有这一列） |
| 特别篇 / SP（有集号但被标成 extra） | 同上 | |
| 一部作品下只有一个文件但 `kind = tv` | 按**电影**口径（80%） | 分母为 1 时，集数口径退化成「这一集必须看完（95.6%）」，反而更严；单文件就是单文件 |
| 重看 | 不改日记，只更新 `lastWatchedAt` | `maxPositionMs` 只增不减，天然支持 |
| 用户看到 80% 但弃剧 | 已记入 → 用户可「移出日记」 | 见 §5.3，移出有墓碑，不会复活 |

### 3.6 判定器（纯函数，可单测）

```dart
// 建议位置：lib/domain/services/diary_eligibility.dart
class DiaryEligibility {
  static const double seriesThreshold = 0.80;   // 剧集：集数完成率
  static const double movieThreshold  = 0.80;   // 电影：单片完播率

  /// 返回 null = 不达标；非 null = 达标，携带要冻结的快照。
  static DiarySnapshot? evaluate(MediaWork work, List<MediaItem> items);
}
```

**它是纯函数**：不读时钟、不碰存储、不发请求。理由与 `PlaybackCompletion` / `PlaybackResume` 一致 ——
这类规则最容易被「顺手加一个 IO」毁掉可测性，而它恰恰是用户最会质疑的地方（「为什么这部没记入」）。

## 4. 数据模型

### 4.1 一条日记记录

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String | **主键**，见 §4.2 |
| `provider` | String | `quark` / `baidu`，用于「资源还在不在」的探测 |
| `workKey` | String? | 弱引用。原作品键，可能失效，**只用于跳转** |
| `title` | String | 快照 |
| `originalTitle` | String? | 快照 |
| `year` | int? | 快照 |
| `kind` | String | `movie` / `tv` / `anime` / `variety` … |
| `category` | String? | 媒体库分类快照（电影/剧集/动漫/综艺） |
| `genres` | List\<String\> | 类型快照 |
| `posterUrl` | String? | 快照（在线海报） |
| `posterFile` | String? | 快照（本地缓存文件名，**关键**，见 §7.4） |
| `posterFaceX` | double? | 人脸锚点快照 |
| `episodeTotal` | int | **冻结** |
| `episodeWatched` | int | **冻结** |
| `completionRatio` | double | 派生值，冗余存 |
| `durationMs` | int? | 电影口径用 |
| `maxPositionMs` | int? | 电影口径用 |
| `addedAt` | int | **首次**记入时刻（Unix 秒），合并时取**较小** |
| `lastWatchedAt` | int? | 最后一次播放，合并取**较大** |
| `rating` | int? | **0–10 的整数**（= 0.5–5 星 ×2），`null` = 未评分 |
| `review` | String? | 短评，≤ 500 字 |
| `tags` | List\<String\> | 个人标签（「神作」「弃了」） |
| `favorite` | bool | 收藏置顶 |
| `updatedAt` | int | **合并判据**（Unix 秒） |
| `deletedAt` | int? | **墓碑**，非空 = 已删除，见 §4.4 |
| `deviceId` | String | 产生这条记录/最后修改的设备，仅排查用 |
| `sourceItemIds` | List\<String\>? | 记入时的文件 id，用于「还能看就跳过去」；可为空 |

### 4.2 主键为什么不是 `work_key`

`work_key` 是**归组键**，它会变：

- 重扫之后文件名解析结果可能变（改了命名规则、刮削补了季号）；
- 用户手动「合并作品」后，`media_items.group_key` 虽然不改写，但目标键可能被选成另一个；
- 换一台设备重扫，`work_key` 由目录/文件名推导，**大概率一致，但不保证**。

如果拿它当主键，跨端同步时同一部剧会变成两条日记，或者一端改名后两端对不上。

**方案**：主键 = `hash(provider + normalizedTitle + year + season)` 的十六进制串。

```
normalizedTitle: 去空格、去标点、全角转半角、转小写、去「第X季」后缀
```

- 同一部剧在两端算出的 id **必须相同**（这是跨端合并的前提）；
- 用户手动改过标题（`CustomizeWorkDialog`）时，id 会变 —— **这是可接受的**：改标题是用户主动行为，
  且此时旧 id 的记录还在（不会被删），只是下次记入会生成新 id。**已知代价，写在 §10**。

> 备选：允许 `id` 与 `dedupeKey` 分离，`dedupeKey` 永不变。这需要额外的「同一 dedupeKey 多条记录 → 合并」逻辑，
> Phase 2 再考虑。

### 4.3 合并规则（照抄 `ProgressEntry.mergedWith` 的思路）

两台设备各改一条，合并时**不是整份覆盖**，而是逐条合并：

| 字段 | 规则 | 为什么 |
|---|---|---|
| `rating` / `review` / `tags` / `favorite` | **`updatedAt` 大者赢**（相等保留自己） | 这是「用户的决定」，后改的说了算 |
| `addedAt` | **取较小值** | 「什么时候第一次记入」是历史事实，不该被另一台设备推后 |
| `lastWatchedAt` | **取较大值** | 「最近一次看」不该倒退 |
| `episodeWatched` | **取较大值** | 同 `maxPositionMs`：只增不减（另一台看得更多，不能抹掉） |
| `episodeTotal` | 跟着 `addedAt` 较早的那一份 | 完成率的分母要在同一时刻定格 |
| `deletedAt` | 参与 LWW（同 `rating`） | 见 §4.4 |
| `posterFile` | 非空优先；都非空取 `updatedAt` 大的 | 本机缓存的海报在另一台机器上不存在，但**文件名**可复用（同一套缓存命名规则） |

⚠️ **`episodeWatched` 取 max 与 `rating` 取 LWW 方向相反是刻意的** ——
与 `ProgressEntry` 里「可加合的量取并集、有状态的量取 LWW」是同一条原则。
把 `episodeWatched` 也交给 LWW，会出现「另一台看了 22 集，被一台只看 20 集的设备改回 20」。

### 4.4 墓碑：删除会「复活」的问题

**这是所有同步设计里最容易踩的坑，必须在第一版就解决。**

场景：A 机器删掉一条日记 → 同步上传（文件里没有这条了）→ B 机器还有这条 → B 上传 → **日记复活**。

**方案**：删除 = 写墓碑，不是移除。

```json
{ "id": "a1b2c3", "title": "漫长的季节", "deletedAt": 1730000000, "updatedAt": 1730000000 }
```

- 合并时墓碑参与 LWW：`deletedAt` 所在的 `updatedAt` 更大 → 这条保持删除；
- 展示时过滤 `deletedAt != null`；
- **墓碑保留 180 天**后由清理任务物理移除（比任何设备的离线时长都长）；
- 「恢复」= 把 `deletedAt` 置 null 并推进 `updatedAt`（比墓碑新，所以会赢）。

### 4.5 文件格式

```json
{
  "v": 1,
  "device": "A1B2-C3D4",
  "updatedAt": 1730000000,
  "records": [
    {
      "id": "7f3a9c21",
      "provider": "quark",
      "workKey": "quark|tv|漫长的季节|2023",
      "title": "漫长的季节",
      "year": 2023,
      "kind": "tv",
      "category": "tv",
      "genres": ["悬疑", "剧情"],
      "posterFile": "w_7f3a9c21.jpg",
      "episodeTotal": 12,
      "episodeWatched": 12,
      "completionRatio": 1.0,
      "addedAt": 1729000000,
      "lastWatchedAt": 1729500000,
      "rating": 9,
      "review": "东北文艺复兴的顶点。",
      "tags": ["神作"],
      "favorite": true,
      "updatedAt": 1729500000,
      "device": "A1B2-C3D4"
    }
  ]

```

**命名**：`watch_diary.json`，与 `playback_progress.json` **同级同风格**（本地同目录、网盘同在 `云影备份/`）。
**落盘**：防抖 + `.tmp` + `rename` 原子替换（照抄 `ProgressStore`，理由见那边类文档）。
**同步**：与播放进度共用调度器，四步流程逐字对齐，见 §6。

### 4.6 为什么不进 sqlite

| 做法 | 后果 |
|---|---|
| 新建 `watch_diary` 表 | ①「清空索引库」如果按表清，要记得加白名单；②**恢复 `.ccbak` = 整文件字节替换**，日记一定被备份里那份旧日记覆盖；③ 要改 schema、跑 codegen、写迁移 |
| 存进 `media_works` 加几列 | 更糟：清理作品时**必然级联删掉**，直接违反 R4 |
| **独立 JSON 文件（本方案）** | 上面三条全都不存在。清理链路碰不到它，恢复备份碰不到它，不需要迁移 |

代价：不能 SQL 查询。但日记规模是**几百条**（一个人一辈子看完的剧集数量级），
全量读进内存 + 内存里筛选排序，比 SQL 更快也更简单。

## 5. 生命周期与状态机

### 5.1 状态图

```
                  ┌──────────────┐
                  │  媒体库作品   │
                  └──────┬───────┘
                         │ 播放中（进度上报）
                         ▼
              ┌─────────────────────┐
              │   未达标（进度累积）  │
              └──────────┬──────────┘
                         │ evaluate() 返回非 null
                         ▼
              ┌─────────────────────┐
        ┌─────│      已记入          │◄──── 手动补录（同门槛校验）
        │     └──────────┬──────────┘
        │                │ 用户评分 / 写短评 / 打标签
        │                ▼
        │     ┌─────────────────────┐
        │     │   已记入 · 已评价    │
        │     └──────────┬──────────┘
        │                │ 移出日记
        │                ▼
        │     ┌─────────────────────┐
        └────►│  墓碑（deletedAt）   │ ──180天──► 物理移除
              └─────────────────────┘
```

### 5.2 触发时机（三个，都不打断播放）

| 时机 | 做什么 | 为什么在这里 |
|---|---|---|
| **播放器退出**（`playback_exit_policy` 之后） | 异步跑一次 `evaluate()` | 进度刚落库，是「刚看完」最准确的时刻；退出时跑不影响播放 |
| **作品详情页打开** | 跑一次，不达标时显示「还差 3 集」 | 用户想知道「为什么没记入」时，答案就在这里 |
| **日记页手动刷新** | 全库扫一遍（几百个作品，一次 SQL） | 兜底：老用户升级上来，历史上看过的剧要补录 |

⛔ **不在播放中每秒检查**：那是热路径，且没有任何收益。

### 5.3 自动记入 + 可撤销（默认），设置可关

**决策**：达标即**自动写入**，并给一条 5 秒的撤销提示；设置里可关（`diary_auto`）。

为什么不用「弹窗确认」：
- 用户的核心诉求是「自动记录我追过的所有剧」，弹窗会让每一部剧都打断一次；
- 门槛是**用户自己定的 80%**，误判概率低；
- 撤销成本极低（一条 SnackBar / 详情页一个按钮）。

为什么不用「完全不提示」：
- 用户需要知道「它记下来了」，否则会怀疑功能没生效；
- 提示条上直接给「去评分」入口，把评分这一步顺势带出来。

### 5.4 记入后 `followed` 置 false

`media_works.followed` 是「等更新」的开关。看完还挂着，角标会永远提醒。
记入时一并置 false，**但不动 `followStartAt`** —— 万一用户移出日记，追剧基线还在。

## 6. 跨端共享（与播放进度同一套机制）

### 6.0 结论：一个调度器，两个同步单元，两个文件

「一并同步」并的是**调度**，不是**文件**。

| | 播放进度（现有） | 观影日记（新增） |
|---|---|---|
| 本地文件 | `playback_progress.json` | `watch_diary.json` |
| 网盘文件 | `云影备份/playback_progress.json` | `云影备份/watch_diary.json` |
| 落盘方式 | 防抖 + `.tmp` + `rename` | **同款**（照抄 `ProgressStore`） |
| 合并方式 | 逐条 LWW + 可加合字段取 max | **同款**（`DiaryBook.mergeFrom`） |
| 上传判据 | 合并结果与远程不同才传 | **同款** |
| 下载失败 | 本轮绝不上传 | **同款** |
| 调度器 | `progressSyncSchedulerProvider` | **同一个**（不新增定时器） |
| 触发点 | 启动 12s / 每 30 分钟 / 退出播放器 | **同三个** |

代码上只做两件事：

1. 新增 `DiarySyncService`（结构照抄 `ProgressSyncService`，四步一模一样）；
2. 在 `progressSyncSchedulerProvider` 的 `run()` 里，**串行**调两个 service。

```dart
// lib/ui/providers/app_providers.dart
final progressSyncSchedulerProvider = Provider<void>((ref) {
  final progress = ref.watch(progressSyncServiceProvider);
  final diary  = ref.watch(diarySyncServiceProvider);   // 新增

  void run(String why) {
    unawaited(_runBoth(progress, diary, why));            // 改这里
  }
  // 三个触发点、两个 Timer、onDispose —— 一行都不用动
});

/// 一轮同步 = 进度 + 日记，串行，**失败互不影响**。
Future<void> _runBoth(progress, diary, String why) async {
  try {
    await progress.syncSilently();
  } catch (e) {
    diag.error('进度', '[$why] 进度同步异常：$e');
  }
  try {
    await diary.syncSilently();
  } catch (e) {
    diag.error('日记', '[$why] 日记同步异常：$e');
  }
}
```

> ⚠️ 外层**不要**再写 `if (service.isRunning) return` —— 每个 `syncSilently()` 内部
> 已经自己判了 `_running`。外层再判一次，会导致「进度正在跑」时**日记被整个跳过**，
> 而表现是「日记偶尔不同步」，极难复现。

### 6.1 为什么不把日记塞进 `playback_progress.json`

看起来更"一并"：一个文件、一次上传、不可能出现"进度同步了但日记没同步"。
**但它会引入一个不可接受的风险，理由写在现有代码里。**

`library_backup_service.dart:571` 那段注释是这么说的：

> ⛔ 代价是「同名覆盖 = 先删后传」中间有一段空窗。进度是**可再生 + 逐条合并**的数据：
> 真丢了也只是这一轮同步白跑，下一轮 30 分钟后会重来。

**日记不是可再生的。** 它是「我看过什么」的唯一记录 —— 丢了就是丢了，重扫网盘、重看一遍都补不回来
（重看一遍只能补上「看过」，补不回「当时打的 9 分」和那句短评）。

把两者放进同一个固定名文件，等于把「可接受的空窗」和「不可接受的空窗」绑在一起：

| | 塞进同一个文件 | 分成两个文件（本方案） |
|---|---|---|
| 上传空窗期 | 进度 + 日记**同时**处于风险中 | 各自独立，互不牵连 |
| 写入放大 | 播放中每 10 秒重写一次**含日记**的整个文件（~50KB → ~250KB） | 日记文件只在记入/改分时写 |
| 类名语义 | `ProgressBook` 变成「进度 + 片头 + 日记」，名字开始撒谎 | 各自一个 `*Book`，名实相符 |
| 老文件兼容 | 要处理「老 JSON 没有 diary 键」 | 新文件，不存在兼容问题 |

第二行是实打实的：`ProgressStore.flush` 在**播放中每 10 秒**跑一次全量重写，
而日记数据一辈子几乎不变。让日记陪着每 10 秒被重写一遍，是把热路径变慢换一个"看起来更一并"的错觉。

> 一句话：**并调度不并文件。** 两者要的是「同一时刻一起动」，不是「住在同一个格子里」。

### 6.2 一轮同步里的执行顺序

顺序不是随便排的，每一步都有原因：

```
触发（启动 12s / 每 30 分钟 / 退出播放器）
  │
  ├─① diary.captureNewlyEligible()      ← 纯本地 SQL，几十毫秒
  │     把刚达标、还没入档的作品写进日记库
  │     返回「本次新记入了哪几部」→ 推给 UI 出提示条
  │
  ├─② progress.syncSilently()             ← 进度先走
  │     播种 → 下载 → 逐条合并 → 回填媒体库 → 按需上传
  │
  └─③ diary.syncSilently()              ← 日记后走
        播种（老用户升级）→ 下载 → 逐条合并 → 按需上传
```

**① 为什么必须在同步之前**：用户刚看完最后一集退出播放器，达标判定要**先**把记录写进日记库，
②③ 才有东西可传。如果先同步再判定，这一轮的日记文件里还没有那条新记录 ——
用户要再等 30 分钟才看到它出现在另一台设备上。

**② 为什么在 ③ 之前**：进度是用户最关心的（"我另一台设备能不能接着看"），
日记晚 1~2 秒无所谓。而且进度文件小、合并快，不会把日记拖太久。

**③ 为什么不能和 ② 并行**：两个都要发网盘请求。夸克有 QPS 限制
（`RequestThrottle` / `token_bucket.dart`），并行会挤在一起，反而更容易被限流。
日记文件只有几十到几百 KB，串行的额外耗时可以忽略。

### 6.3 失败隔离矩阵

这是"一并同步"最容易被写错的地方 —— 一个人把两个 service 包进同一个 `try`，
就会出现「日记下载失败导致进度也不上传」。所以逐格列清楚：

| 情况 | 进度 | 日记 | 用户看到 |
|---|---|---|---|
| 全部成功 | 上传/无需上传 | 上传/无需上传 | 两端一致 |
| 进度下载失败 | 不上传，本地照常回填 | **正常走完** | 进度暂不同步，日记已同步 |
| 日记下载失败 | 正常走完 | 不上传，本地照常落盘 | 进度已同步，日记暂不同步 |
| 进度上传失败 | 本地已合并，下轮重试 | **正常走完** | 同上 |
| 日记上传失败 | 正常走完 | 本地已合并，下轮重试 | 同上 |
| 网盘整个不通 | 失败 | 失败 | 两端都不动，**本地数据完好** |
| 未登录网盘 | 直接跳过 | 直接跳过 | 本地功能不受影响 |

**每一格都是「本地完好 + 下轮重试」**：本地文件是真源，网盘只是副本。
任何一次同步失败都不该让用户丢数据，最多是"晚一点同步过去"。

### 6.4 节流：从「硬挡」改成「尾部补跑」

现有 `ProgressSyncTrigger.request()` 是**硬节流**：20 秒窗口内的请求直接 `return false`。

对进度够用（进度每 10 秒都在变，少传一次无所谓）。但对日记有一个真实场景会丢：

> 用户打开「逐部评分」模式，10 秒内连着给 5 部打了分。
> 第 1 次触发同步（上传了第 1 部），第 2~5 次全被节流挡掉。
> 用户打完就关掉 App → **第 2~5 部的评分没有同步出去**（本地有，但要等下次开 App）。

改法（**尾部补跑**，trailing throttle）：

```dart
class ProgressSyncTrigger extends Notifier<int> {
  DateTime? _lastRequestAt;
  Timer? _pending;                    // 新增

  bool request() {
    final now = DateTime.now();
    final last = _lastRequestAt;
    if (last != null && now.difference(last) < window) {
      // ⛔ 不是丢弃，是**记下来**：窗口结束时补跑一次
      _pending?.cancel();
      _pending = Timer(window - now.difference(last), () {
        _lastRequestAt = DateTime.now();
        state = state + 1;
      });
      return false;
    }
    _lastRequestAt = now;
    state = state + 1;
    return true;
  }
}
```

- 连续改 5 部 → 第 1 次立即同步，窗口结束时补跑 1 次（带上后 4 部）→ **最多丢 20 秒内的最后一次改动**；
- 播放器连续退出（连播模式）→ 仍然是 20 秒一次，不会因为补跑而变密。

⛔ `_pending` 必须在 `onDispose` 里 cancel，与现有两个 Timer 同一条规矩。

### 6.5 首次播种（老用户升级）

`ProgressSyncService` 的第 1 步是「播种」：把 `media_items` 里已有的进度读进进度库。
日记要**同款**，否则老用户升级上来，历史上看完的几十部剧一条都不会出现在日记里。

```dart
// DiarySyncService._run() 第 1 步
var seeded = 0;
try {
  // 遍历媒体库所有作品，跑 DiaryEligibility.evaluate()
  // 达标的写进 DiaryBook，addedAt 用「最后一次播放时间」而不是「现在」
  seeded = await _store.mergeFrom(await _repository.diaryCandidates());
} catch (e) {
  diag.warn('日记', '从媒体库播种日记失败（继续走远程那一步）：$e');
}
```

**两个细节**：

1. `addedAt` 用 `media_works.lastPlayedAt`（最后一次看的时间），不是「现在」。
   否则老用户的 47 部剧全部显示「今天记入」，时间轴完全失真。
2. 播种是**幂等**的：`mergeFrom` 按 `id` 合并，已有的记录不会被覆盖
   （`addedAt` 取 min，评分走 LWW）。跑一百次和跑一次结果一样。

### 6.6 网盘上的目录长什么样

```
云影备份/
├── cloudcine_backup_2026-10-24T12-30-00.ccbak   ← 整库备份（带时间戳，多份历史）
├── playback_progress.json                        ← 进度（固定名，覆盖写）
└── watch_diary.json                            ← 日记（固定名，覆盖写）
```

三个文件，三种策略，各自有理由：

| 文件 | 命名 | 为什么 |
|---|---|---|
| `.ccbak` | 带时间戳 | 用户要能「退回昨天那份」 |
| `playback_progress.json` | 固定名 | 两端要看到同一份当前状态；带时间戳会让目录无限膨胀 |
| `watch_diary.json` | 固定名 | 同上。日记是**当前状态**（含墓碑），不是历史快照 |

> 日记要不要像 `.ccbak` 一样留历史版本？**第一版不要。** 日记里已经有墓碑 + `updatedAt`，
> 逐条合并能覆盖 99% 的恢复需求；留版本会让"哪份才是当前"变成一个需要用户决策的问题，
> 而用户根本不想管这件事。真要防丢，靠的是「本地文件 + 两端副本 + 墓碑」，不是历史版本。

### 6.8 冲突场景表

| 场景 | 结果 | 用户看到 |
|---|---|---|
| 两端各记入不同的剧 | 并集 | 两边都有 |
| 两端都记入同一部剧 | 一条（`id` 相同） | 一条，完成度取高 |
| A 打 9 分，B 打 7 分，A 后改 | 9 分 | 一致 |

| 一端在旧版本（没有日记功能） | 它不碰 `watch_diary.json` | 日记不受影响，进度照常 |

## 7. 与媒体库清理的隔离（逐条核对现有代码）

### 7.2 但文案必须改（两处）

现在 `LibraryBatchDeletePlan.localDataWarning` 写的是：

> 「这些作品的续播进度、播放偏好和自动学到的片头/片尾会一起清掉（网盘文件本身不受影响）。」

加了日记之后，这句话会让用户**担心日记也没了**。必须补一句：

> 「…会一起清掉（网盘文件本身不受影响）。**观影日记和你的评分不受影响。**」

`settings_page.dart` 的「清空索引库」确认框同理。

> 这两处文案是**功能的一部分**：用户判断「要不要按下去」全靠它。少这一句，功能做了等于没做。

### 7.3 作品详情页的「已记入」标识不能靠 JOIN

详情页拿 `work_key` 去日记里查 —— **只在资源还在时有效**。
日记详情页（从日记列表进入）**不查媒体库**，只读快照。两个页面，两套数据源，不要混。

### 7.4 海报：日记必须能独立显示

日记里存 `posterUrl`（在线）**和** `posterFile`（本地缓存文件名）。

- 在线 URL 会失效（TMDB 换图、夸克签名过期）→ 靠本地缓存兜底；
- 本地缓存会被 `PosterCache` 的 LRU 清掉 → 记入时把海报**拷进日记专用目录**
  （`<应用支持目录>/diary_posters/`），不进 LRU；
- 都没有 → 显示占位图（首字 + 渐变色），**不显示破图**。

### 8.2 日记页结构（三种视图）

**「日记」这个名字带来一个结构要求：它必须能按时间翻。** 只有海报墙的话，

| **列表** | 快速扫评分和年份 | |
| **时间轴** | 翻「我什么时候看的、那阵子在追什么」 | |

```
┌─────────────────────────────────────────────────────────────┐
│ 观影日记            [统计条]  共 47 部 · 平均 8.2 分 · 21 部神作 │
│                                                             │
│ [全部] [电影 12] [剧集 28] [动漫 5] [综艺 2]   🔍搜索  排序 ▾   │

```

**时间轴视图**（第三种，按「记入月份」分组）：

```
2026 年 10 月 · 3 部 · 平均 8.8 分
─────────────────────────────────────────────
 24   ┌──┐  漫长的季节                        ★ 9.0
      └──┘  剧集 · 12 集 · 已看完
 19   ┌──┐  漫长的告白                        待评分
      └──┘  电影 · 114 分钟
 03   ┌──┐  繁花                              ★ 8.5
      └──┘  剧集 · 30 集 · 已看完

2026 年 9 月 · 2 部 · 平均 8.3 分
─────────────────────────────────────────────
 28   ┌──┐  狂飙                              ★ 8.0
      └──┘  剧集 · 39 集 · 已离线
```

三条规则：

1. **按 `addedAt` 分组，不按 `lastWatchedAt`** —— 日记记的是「什么时候写下的这一页」。
   重看一部老片不该让它跳到今年；
2. **月份小标题带统计**（几部、平均几分）—— 这是时间轴唯一比海报墙多出来的信息，
   不给的话它就只是「换了个排版的列表」；
3. **时间轴不做多选**。批量操作只在封面/列表视图提供 —— 时间轴是「翻」的，
   不是「管」的。

**卡片上必须有的三样**：封面、标题、评分（未评分显示「待评」的虚线星）。
右上角一个小角标表示资源状态：`可播放` / `已离线`（灰）。

**筛选维度**（与 `LibraryFilter` 同构，但读的是日记不是库）：

- 分类：全部 / 电影 / 剧集 / 动漫 / 综艺 / 其他
- 评分：全部 / 神作(9–10) / 好看(7–8.5) / 一般(5–6.5) / 差评(<5) / **未评分**
- 标签：多选
- 年份：多选
- 排序：最近记入 / 评分最高 / 标题 / 记入时间最早

> **「未评分」必须是一个显眼的筛选**：它的作用是「催你去评分」。这是评分功能的自然驱动力，
> 也是「记录」变成「日记」的关键一步。

```
│  │      │                                                  │

│                                                           │
│  我的短评                                                  │

```

- 「重看」按钮**只在资源还在时出现**（`sourceItemIds` 探测到对应文件行）；
- 资源不在时，那个位置显示一行灰字：「网盘上已找不到这部剧，日记已保留」；
- 完成度显示为「已看完 12/12 集」，**不显示百分比** —— 百分比在这里没有信息量。

### 8.4 评分交互（三端都要能用）

| 端 | 交互 | 关键细节 |
|---|---|---|
| 鼠标 | 悬停星条实时预览，点击落值 | 支持**半星**（星条分 10 段，每段 0.5 分）；点当前分值可清除 |
| 触屏 | 同鼠标，点击落值 | 触控目标 ≥ 44px |
| **遥控器** | **左右键调星，确认键提交** | ⛔ 不能让用户按 9 次右键：**每按一次 +0.5，长按加速**；焦点进入星条时显示当前值 |
| 键盘 | ←/→ 调，Enter 提交，数字键 1–9 直接给分 | 数字键是重度用户的最快路径 |

**保存策略**：改动即存（本地）+ 防抖 2 秒后同步。**不设「保存」按钮** —— 评分是低风险操作，
一个显式的保存按钮只会让人担心「我改的存上了吗」。

**反馈**：星条右侧显示「已保存」→ 2 秒后变成「已同步到云端」，同步失败时变成「待同步」（灰色，不报错）。

### 8.5 记入瞬间的反馈

播放器退出、判定达标时，在媒体库页顶部（不是播放器里）显示一条**非模态**提示条：

```
┌────────────────────────────────────────────────────────┐
│  ✓ 《漫长的季节》已记入观影日记   [去评分]        [撤销] │
└────────────────────────────────────────────────────────┘
```

- 5 秒后自动消失，**但「去评分」的入口留在日记页的「待评分」筛选里**；
- 播放器里不弹任何东西 —— 用户刚看完，情绪还在片子里，弹窗是打扰。

### 8.6 未达标时的引导（详情页）

作品详情页在「已看完 N/M 集」旁边显示：

```
还差 3 集可加入日记 · [查看未看]
```

点击「查看未看」滚动到第一个未看的集。**这是唯一一个「解释门槛」的地方** ——
不给解释的话，用户会以为功能坏了（「我看完了为什么没记入」）。

### 8.7 空态

| 场景 | 文案 | 动作 |
|---|---|---|
| 一条日记都没有 | 「还没有追完的剧。看完一部剧的 80%，它会自动出现在这里。」 | [去媒体库] |
| 筛选后为空 | 「这个筛选条件下没有日记」 | [清除筛选] |
| 全部未评分 | 「47 部待评分」 | [开始评分] → 进入逐部评分模式 |

**「逐部评分模式」**是一个值得做的小功能：一次只显示一部，左右翻，打完直接下一部。
比在墙上一个个点进去快一个数量级，直接决定评分功能的实际使用率。

### 8.8 文案表

| 位置 | 文案 | 备注 |
|---|---|---|
| 侧栏 | 观影日记 | 不用「观看历史」——会与「最近播放」混淆 |
| 记入提示 | 《X》已记入观影日记 | 不写「恭喜看完」，不评判 |
| 未达标 | 还差 3 集可加入日记 | 给数字，不给百分比 |
| 已记入但未评分 | 待评分 | 不用「未评价」，两个字更短 |
| 资源丢失 | 网盘上已找不到这部剧，日记已保留 | 明确「日记已保留」，否则用户会慌 |
| 移出日记确认 | 从日记中移除《X》？你的评分和短评会一起删除。 | 说清代价；删除的是记录，不是文件 |
| 清理媒体库（改） | …观影日记和你的评分不受影响。 | §7.2 |
| 同步状态（正常） | 日记已同步 · 刚刚 | 侧栏一行小字，不打扰 |
| 同步状态（待传） | 日记待同步 | 灰色，不报错 |
| 同步状态（失败） | 日记同步失败，稍后重试 | 不弹窗、不红点 |

### 8.9 同步状态要看得见（但别打扰）

「多端同步」这件事，用户最常问的两个问题是「同步成功了吗」「为什么另一台设备上没有」。
所以状态必须可见，但不能变成一个需要处理的告警。

**三个位置，一处比一处详细**：

| 位置 | 显示什么 | 来源 |
|---|---|---|
| 侧栏底部（PC）/ 设置页（移动） | `日记已同步 · 3 分钟前` / `日记待同步` / `日记同步失败，稍后重试` | `DiarySyncService.lastSuccessAt` / `lastError` |
| 评分区右上 | `改动即保存` → `已同步到云端` → `待同步` | 本地写入成功 / 本轮同步成功 / 同步失败 |
| 设置 → 数据同步 | 进度与日记**各一行**：最后成功时间、条数、上次错误 | 两个 service 的公开状态 |

⛔ **不做红点、不做弹窗、不做 SnackBar**。理由与 `ProgressSyncService` 类文档里
「静默是硬要求」完全一致：同步失败会自己重试，用户此刻什么也做不了 ——
把一件他无法处理的事显示成告警，只会制造焦虑。

⛔ **进度和日记的状态要分开显示**。合成一个「同步正常」的话，
日记连续失败三天的用户会以为一切正常，直到某天在新设备上发现日记是空的。

## 9. 原型

`docs/观影日记-原型.html` —— 可交互，覆盖：

1. PC 日记墙 / 列表双视图 + 筛选 + 排序 + 搜索
2. 点卡片 → 详情 → 打分（半星）→ 「已保存 → 已同步到云端」反馈
3. 「记入瞬间」演示（底部提示条 + 去评分 / 撤销 + 侧栏状态从「待同步」变「已同步」）
4. 「清理媒体库」对比（媒体库 47→6，日记 9→9）
5. 移动端布局（底部 6 个 Tab、3 列海报）
6. 逐部评分模式（一部一部过，选完自动下一部）
7. **同步状态面板**（§6 的可视化）：两个单元各自的文件、大小、状态；
   点「模拟：日记下载失败」→ 日记变红、进度仍绿 —— 失败隔离一眼可见

**怎么看**：右上角演示条可切换 PC / 移动端，以及直接跳到四个演示场景。
也可以带 URL 参数进：

```
?device=mobile            移动端
?view=detail&id=mancheng  打开详情
?view=compare             清理对比
?view=swipe               逐部评分
?view=toast               记入提示
?view=sync                同步状态
?view=sync&fail=1         同步状态 · 日记下载失败态
```

> 原型只表达**布局、状态与文案**，不表达最终视觉细节（颜色取 `AppTheme` 的真实值）。
> 海报是用渐变模拟的占位图 —— 真实卡片会显示刮削到的海报，`FaceAnchor` 裁切规则不变。

## 10. 风险与已定决策

### 10.1 三个口径已定（不再讨论）

| # | 问题 | **决定** | 理由 |
|---|---|---|---|
| 1 | 「所有剧集观看 80%」用哪个口径 | **集数口径**：`看完的集数 / 库里已有的集数 ≥ 0.80` | 与「看到第几集」的直觉一致；时长口径在跳着看时会算出「看了 40% 却已经追完」。两者都写进快照（`episodeWatched/episodeTotal` + `watchedMs/durationMs`），将来要换口径不必重算历史 |
| 2 | TV 顶栏第 6 项会不会溢出 | **先按独立入口实现**；实测溢出则退回「媒体库页内一栏」 | 独立入口的信息架构更清楚，不能因为一个宽度没量就先降级。降级路径已想好（同 `playedOnly` / `followedOnly` 那种视图筛选） |
| 3 | 自动记入默认开还是关 | **默认开** | 用户诉求是「自动记录我追过的所有剧」；门槛是用户自己定的 80%，误判概率低；撤销成本是一条提示条 |

> 三条都已按决定实现，代码里对应 `DiaryEligibility.seriesThreshold` / 导航入口 / `diaryAutoCapture` 设置项。
> 改主意只需要改这三处常量与开关，不影响数据结构。

### 10.2 已知代价（明确承认，不打算在第一版解决）

| 代价 | 说明 | 缓解 |
|---|---|---|
| 用户改作品标题后 `id` 变 | 会多出一条日记 | 合并逻辑（Phase 2）；或记入后标题不再参与 id |
| 跨端 `work_key` 不一致 | 同一部剧两端各自记入成两条 | `id` 用标题哈希，不依赖 `work_key`；真重复时提供「合并日记」 |
| 只看一集就弃剧 → 永远不记入 | 这是**设计意图**（80% 门槛） | 提供「手动补录」入口，但同样校验门槛 |
| 时长全缺失的片子判不准 | 网盘没给 `durationMs` | UI 标「完成度不可靠」 |
| 日记不能 SQL 查询 | 全量内存筛选 | 几百条规模下无感 |

### 10.3 实施顺序（不含代码，只标依赖）

```
① 判定器（纯函数 + 单测）                       ← 无依赖，先做
② DiaryEntry / DiaryBook（纯数据 + 合并 + 单测）  ← 依赖 ①
③ DiaryStore（落盘，照抄 ProgressStore）           ← 依赖 ②
④ 记入触发 captureNewlyEligible（播放退出 / 详情页）   ← 依赖 ①③
⑤ DiarySyncService（照抄 ProgressSyncService）     ← 依赖 ②③
⑥ 接进调度器（_runBoth + 尾部补跑）                  ← 依赖 ⑤，⚠️ 唯一有回归风险
⑦ 日记页 + 详情页 + 评分组件                         ← 依赖 ③
⑧ 文案修改（清理确认 / 清空索引库）                   ← 独立，可随时做
⑨ 移动端导航调整                                    ← 依赖 ⑦
```

**⑥ 的验收标准（必须逐条过）**：

1. 把 `diarySyncServiceProvider` 整个注释掉 → 进度同步**行为完全不变**；
2. 让日记下载抛异常 → 进度**照常上传**；
3. 让进度下载抛异常 → 日记**照常上传**；
4. 20 秒内连按 5 次触发 → 网盘上最终是**最后一次的状态**（尾部补跑生效）；
5. 退出 App 再进 → 没有多出来的定时器（`_pending` 被 cancel）。

①②③ 都是纯逻辑，可以完全脱离 UI 先做并测透 —— 这个功能的正确性全在这三层，
UI 层错了只是难看，这三层错了就是**用户的数据丢了**。

**⑤⑥ 建议在 ①②③ 的合并测试全绿之后再动**：同步是唯一会"把错误扩散到另一台设备"的环节，
它自己出 bug 比日记页排版错位严重得多。
