# 片头 / 片尾自动学习 —— 可行性评估与设计方案

> 需求原文：观看电视剧时，每次都要点进度条跳过片头、到片尾时手动跳到下一集，但没有所有剧集的片头片尾时间点。
> 建议支持按剧集为单位自动学习片头与片尾的时间：每次记录跳过的时间点，学出合理区间。需考虑「拖拽点不在片头片尾」的场景。

**结论：可行。但不能「记录拖拽点求平均」——必须先把拖拽点过滤成「有效落点」，再做跨集聚合。**
其中片尾的判定比片头难一档，建议片尾只做「提示 + 一键跳下一集」，不自动跳。

---

## 一、现状盘点

| 能力 | PC 端（Flutter） | Android/TV 端（Kotlin） |
|---|---|---|
| 片头区间识别 | ✅ `IntroMarkerDetector` 认文件章节 | ❌ 无 |
| 片头跳过 | ✅ `IntroSession` + `IntroSkip` | ❌ 无 |
| 手标区间 | ✅ `MediaWork.introStartMs/introEndMs`（作品级） | ❌ 无（列在库里，但没用） |
| 片尾 | ❌ 完全没有 | ❌ 完全没有 |
| 学习 | ❌ 完全没有 | ❌ 完全没有 |

关键文件：`lib/domain/services/intro_marker.dart`（区间模型 + 章节解析 + 判定纯函数）、`intro_session.dart`（一次播放的状态机）、`lib/domain/entities/media_work.dart:188`（手标两列）、`lib/ui/providers/settings_providers.dart:141`（`skipIntro` 开关，`SettingKeys.skipIntro = 'skip_intro'`，默认 `true`）。

现有优先级链是 **文件章节 > 手标**，学习应当插在中间：**章节 > 手标 > 学习**。

### 两个必须知道的前提

1. **Android 端读不到章节。** Media3/ExoPlayer 不暴露容器章节（`MediaMetadata` 里没有 chapter 字段），PC 端读章节靠的是 mpv 的 `chapter-list` 属性。所以 TV 端**天生只能靠手标或学习** —— 这让「学习」在 TV 端的价值远大于 PC 端。
2. **两端 schema 必须相等。** `AppDatabase.currentSchemaVersion` 与 `LibrarySchema.VERSION` 当前都是 **17**，且 `LibraryBackupService` 会拒绝 `schemaVersion` 更高的备份。加表 / 加列 = 两端一起升到 18。

## 二、为什么不能直接记录拖拽点

用户在进度条上拖一次，**动机是多义的**。同一个 `(from → to)` 至少能对应六种意图：

| 场景 | 落点特征 | 该不该学 |
|---|---|---|
| 跳片头 | 起播后不久，前进到 30s~2min | ✅ 片头正样本 |
| 跳片尾 | 接近末尾，前进到末尾 / 触发下一集 | ✅ 片尾正样本 |
| 拖到中间看剧情 | 落点在 20%~80% | ❌ 丢弃 |
| 回看刚才那段 | `to < from`（后退） | ❌ 丢弃，可能是负样本 |
| 找位置 / 拖错了 | 短时间连续多次 seek | ❌ 丢弃（只留最后停下的那次） |
| 跳前情提要 / 广告 | 落点很小但 > 0 | ⚠️ 需要靠「最小长度」挡掉 |

直接对 `to` 求均值，会被「随便拖」严重污染，学出一个并不存在的片头，然后**自动跳过去** —— 用户莫名其妙丢了内容，且没有任何提示。这比不跳糟得多。

所以第一层必须是**过滤**，不是记录。

## 三、核心概念：有效落点（Watch Anchor）

**只有「停下来连续观看」的落点才有信息量。**

定义：一次 seek 之后，若满足全部条件，则 `to` 记为一个**有效落点**：

1. **稳定观看**：从 `to` 起连续自然播放 ≥ `STABLE_MS`（建议 15000），期间**没有新的 seek**；
2. **前进**：`to - from ≥ MIN_DELTA_MS`（建议 3000）—— 防抖、防误触；
3. **倍速 = 1.0**：`rate != 1.0` 时「位置」的语义变了（用户用倍速扫剧），锚点不可比；
4. **时长已知**：`duration > 0`。

「拖来拖去」会被第 1 条自动过滤：中间那些落点都因为「很快就又 seek 了」而不成立，只有最后停下来的那一次成为锚点。

这条规则同时解决了「拖拽点不在片头片尾」里最麻烦的一类噪声 —— **探索性拖拽**。

---

## 四、两类锚点与各自的判据

### 片头锚点

- 前提：本集是**从头起播**的（起播位置 < 30s）。续播（从上次位置继续）不产生片头锚点 —— 那是从中间开始的，`0 → to` 这个区间根本不成立；
- 落点 `a` 落在 `[15s, 180s]`；
- 记录 `(0 → a)`，即候选片头区间 `[0, a]`；
- 存**绝对时间** `a`。

### 片尾锚点

片尾的关键差异：**用户跳过片尾的动作不是「拖到末尾」，而是「从某个位置直接切下一集」**。

- 信号 A（最强）：在位置 `a` 触发了「下一集」/ 退出播放；
- 信号 B：从位置 `a` seek 到 `≥ duration - 5s`，且之后 30s 内没有继续观看。

两种信号都指向「从 `a` 起我就不想看了」，`a` 即片尾起点候选。

- 落点 `a` 落在 `[duration - 300s, duration - 10s]`；
- 存**距末尾的偏移** `d = duration - a` —— 各集片长不同，绝对时间跨集不可比，偏移可比。

⚠️ **「拖到接近末尾然后继续看完」不是片尾锚点，是负样本。** 落点在片尾窗口内、但之后自然播放一直走到 `duration`，说明用户想看那段内容，那里不是片尾。

## 五、跨集聚合

「按剧集为单位」的落点粒度是**作品级**（同一部剧各集片头位置高度一致），但**样本按集存**，以便后续做集级覆盖。

聚合用**中位数 + MAD（中位绝对偏差）**，不用均值 + 标准差：

- 拖错一次产生一个离群点，均值会被拽偏、标准差会被拉爆；中位数与 MAD 对离群点免疫。
- MAD 是「紧致度」的直接度量：它小，说明各集落点真的聚在一起。

判定门槛（**初值，需 P0 观测期用真实数据校准**）：

| 项 | 门槛 |
|---|---|
| 最小样本数 | `n ≥ 3`（至少 3 集 / 3 次） |
| 紧致度 | 片头 `MAD ≤ 8s`，片尾 `MAD ≤ 10s` |
| 片头中位数 | `M ∈ [15s, 180s]` |
| 片尾中位数偏移 | `D ∈ [10s, 300s]` |
| 区间长度 | 片头 `≥ 5s`（沿用 `IntroMarkerDetector.minLength` 的口径） |

不满足就**什么都不做**（`null`），而不是勉强取一个值。这一点与 `IntroMarkerDetector.detect` 的现有取舍完全一致：认不出来宁可不生效。

## 六、误判防护（四层，逐层收窄）

用户特别关心的「拖拽点不在片头片尾」，靠四层叠加解决：

### 第 1 层 · 样本过滤（§三）
稳定观看 + 只取前进 + 倍速排除 + 时长已知。挡掉探索性拖拽、回看、倍速扫剧。

### 第 2 层 · 时间窗 + 长度约束（§四）
落点必须落在片头 / 片尾窗口内；片头区间长度必须 ≥ 5s。挡掉「跳前情提要」（落点太小）与「拖到中段」（窗口外）。

### 第 3 层 · 聚合紧致性（§五）
中位数 + MAD + 最小样本数。单个离群点进不了簇；「每集片头位置差异很大」的剧（动画 OP 位置漂移、纪录片无片头）会因 MAD 超标而**拒绝建立**，这是期望行为。

### 第 4 层 · 负样本与用户裁决

- **回拖 = 负样本**：用户拖到 `a` 之后又回拖到 `< a` 并继续看 ⇒ `a` 不是片头结束，该锚点作废；
- **看完片尾 = 负样本**：见 §四；
- **撤销 = 最强负样本**：跳过后给出「已跳过片头 0:00–1:32 · 撤销」提示。用户点撤销 ⇒ 该锚点立刻作废，并且**该作品的置信度清零重学**；
- **手标永远压过学习**：用户手动标过区间的作品，学习结果不生效（`章节 > 手标 > 学习`）。

## 七、落库与同步

### 样本表：`skip_samples`（本地专用）

```
id TEXT PK · item_id TEXT · work_key TEXT · kind TEXT(intro|outro)
anchor_ms INT · duration_ms INT · offset_ms INT · negative INT
created_at INT · device TEXT
索引：(work_key, kind)
```

**不进 `.ccbak`、不参与 `libraryModifiedAt`** —— 理由与 `playback_progress.json` 同一条：高频写、本地行为数据、无长期价值。写它绝不能污染同步判据（`libraryModifiedAt` 已经为 `last_played_at` 做过同样的摘除）。

### 结论列：`media_works` 新增 6 列（进备份、进同步）

```
learned_intro_start_ms · learned_intro_end_ms
learned_outro_start_ms · learned_outro_end_ms
learned_at（毫秒时间戳，LWW 用）· learned_samples（参与聚合的集数）
```

**为什么不复用现有的 `intro_start_ms/intro_end_ms`**：那两列是「用户手标」语义，`mergeWorkForUpsert` 有专门的保护分支（扫描不许覆盖）。学习结果混进去会：
1. 让手标与推断无法区分，UI 上没法显示「这是你自己标的 / 这是自动学的」；
2. 逼迫 `mergeWorkForUpsert` 的保护逻辑改判定条件，改动面更大、更容易漏。

新增列 + 独立优先级链，手标那一套**一行都不用动**。

### 跨设备合并

两个设备各学各的，结论列会 LWW 冲突。建议：**取 `learned_samples` 更大的一方**（样本多的更可信），而不是取时间更新的 —— 简单、可解释、不需要额外时钟同步。

## 八、生效策略

**先提示，再自动。** 分两步走，因为「静默误跳」的伤害不可逆：

- **P1 阶段（建议先做）**：学出区间后只在 UI 上显示「已识别片头 0:00–1:32」，由用户点一下确认。确认后写入手标列（`introStartMs/introEndMs`），此后走现有链路。**零新增生效路径，零误跳风险。**
- **P2 阶段**：自动跳 + 撤销提示。撤销入口是安全阀，不能省。

播放页 / 详情页需要的新 UI：
- 详情页：一行「片头 0:00–1:32 · 片尾 距末尾 1:20 · 来自自动学习（3 集样本）」，带「清除学习」按钮；
- 设置页：一个总开关 + 「清空全部学习数据」（与 `SettingKeys.skipIntro` 并列）。

## 九、分阶段实施

| 阶段 | 内容 | 风险 |
|---|---|---|
| **P0** | PC 端加锚点采集，**只写日志不落库**。跑一两周，用真实数据校准 §五 的阈值 | 零 |
| **P1** | 加 `skip_samples` 表 + 聚合纯函数（带单测）+ 结论列（schema 18）+ **只提示不自动跳** | 低 |
| **P2** | 自动跳片头 + 撤销提示 | 中 |
| **P3** | 片尾（一键跳下一集，不自动） | 中 |
| **P4** | Android 端对齐：需要先补一套 Kotlin 版 `IntroMarker`/`IntroSession`（目前**零基础**），再加学习 | 高 |

### 工作量粗估

- PC 端 P0：采集点 + 日志，约 1 天
- PC 端 P1：聚合算法（纯函数 + 单测）+ 落库 + 迁移 + UI，约 3 天
- PC 端 P2/P3：约 2 天
- Android 端 P4：**3~5 天**（要从零建跳片头基础设施，且 ExoPlayer 读不到章节，只能吃手标 + 学习）

### 新增的守卫测试

- `AnchorFilterTest`：稳定观看 / 前进 / 倍速三条过滤（纯函数）
- `AnchorClusterTest`：中位数 + MAD 聚合，含离群点与 MAD 超标的拒绝路径
- `OutroAnchorTest`：负样本（拖到末尾但看完）必须不产生锚点
- `IntroSessionTest` 扩展：学习区间与章节 / 手标的优先级

## 十、风险与未解问题

1. **片尾天然比片头难。** 片头有「起点 = 0」这个强锚，片尾没有；「跳过片尾」与「快进看结局」在信号上高度相似。**建议片尾只做提示 + 一键跳下一集，不做自动跳。**
2. **每集片头位置漂移的剧会被拒绝建立。** 这是设计上的期望行为，但用户会疑惑「为什么这部没学出来」。需要 UI 上说明「样本差异过大，未识别」。
3. **多设备结论合并**用「样本数大的赢」是启发式，不是严格正确。若将来要更严谨，需要把样本表也纳入同步（代价：同步体积与冲突面变大）。
4. **样本表不备份 ⇒ 换设备后无法再聚合**，只能吃已固化的结论列。可接受，但要写进文档。
5. **`STABLE_MS` 的取值需要实测。** 15s 是估计值：太短挡不住探索性拖拽，太长会让「跳完片头马上又跳片尾」的连续操作互相干扰。**这是 P0 观测期最需要校准的一个参数。**

---

## 十一、结论

- 需求**可行**，且与现有 `IntroMarker` / `IntroSession` 架构天然兼容 —— 学习只是给「区间来源」加了一条支路，判定与生效链路可以完全复用。
- 最大的技术风险不在算法，而在**片尾的信号歧义**与 **Android 端零基础**。
- 建议路径：**P0 先埋点观测（零风险）→ P1 只提示不自动 → P2 自动跳片头 → P3 片尾 → P4 Android 对齐**。
- 最该守的一条红线：**宁可不生效，也不勉强生效。** 认不出来的剧就让它空转，用户手动拖一次的成本，远低于被自动跳到错误位置的成本。
