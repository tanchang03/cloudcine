> [`AndroidTV-4K-丢帧-夸克对标.md`](./AndroidTV-4K-丢帧-夸克对标.md)（下称「4K 文档」）。

## 0. 目标与验收判据

**目标**：4K 原画（3840×2160）在 MiTV-MFTP0（Android 9 / 4 核 / 显示层
`1920×1080@60`）上**不丢帧、音画同步**，同时不牺牲 mpv 现有的格式覆盖
（MKV/AVI/TS/RMVB）、内嵌 ASS 渲染、音效与缓冲调优。

验收**只看三个数**（口径与 4K 文档 §5 一致）：

| # | 指标 | 目标 | 读法 |
|---|---|---|---|
| 1 | `[解码]` **显示丢帧** | 从 4K 基线 **20%~44% / 21s** 降到 **≈810p 的 1.3%** | `[解码]` 行 |
| 2 | `[资源]` **进程 CPU** | 从 **225%~326%**（单核口径，4 核折合 56%~82%）明显下降 | `[资源]` 行 |
| 3 | **画面** | 4K 有画面、音画同步 | 人眼 |

⚠️ 跨会话比 `显示丢帧` 之前**先确认起播条件一致** —— 冷启动 / 换集 / 双 seek
都会污染这个数（4K 文档 §5 已踩过）。

## 1. 事实基础（2026-10-05 源码复查）

> 本节全部是**读源码得到**的结论，不是推测。凡标 ⚠️ 的才是待验证项。

### 1.1 fvp 上游**已经实现** SurfaceView 输出

`fvp-0.39.0` 是 pub.dev 上游原包（全包文件 mtime 一致 = `pub get` 时刻；
`pubspec.lock` 为 `source: hosted / url: pub.dev`），**我们没有改过它**。
它自带的东西：

| 上游已实现 | 位置 |
|---|---|
| `FvpVideoView implements PlatformView, SurfaceHolder.Callback` | `FvpVideoView.java:32` |
| 内部 `new SurfaceView(context)`，`getView()` 返回它 | `FvpVideoView.java:53,63-65` |
| `holder.setFixedSize(videoWidth, videoHeight)`（**视频分辨率**，不是 view 尺寸） | `FvpVideoView.java:54-58` |
| `surfaceCreated` → `nativeSetSurface(player, surfaceId, surface, w, h, tunnel)` | `FvpVideoView.java:68-74` |
| `surfaceId = -1000L - viewId`（负空间，**避免与 texture id 撞**） | `FvpVideoView.java:52` |
| tunnel 分支：`setDecoders(Video, {"AMediaCodec:dv=1:image=0:surface=<ptr>"})` | `fvp_plugin.cpp:89-98` |
| 非 tunnel 分支：`updateNativeSurface(surface, w, h)`（GL 渲染器画进 ANativeWindow） | `fvp_plugin.cpp:99-103` |
| 释放时**先** `setDecoders(Video, {})` **再** `updateNativeSurface(nullptr)` | `fvp_plugin.cpp:67-76` |
| hybrid composition：`PlatformViewLink` + `initExpensiveAndroidView` | `video_player_mdk.dart:542-568` |
| view factory 注册：`registerViewFactory("fvp/video-view", ...)` | `FvpPlugin.java` |

其中 `fvp_plugin.cpp:67-76` 那段注释特别重要：

```cpp
if (player->directSurface) {
    // Release the codec BEFORE the surface dies, or it wedges
    // (dequeue -10000) and the stream is marked decode-error, so
    // the next surface never shows a frame. Empty list, not a
    // surface-less re-open: that costs ~600ms of codec restart
    // and pipeline re-prime, here on the UI thread inside
    // surfaceDestroyed.
    player->setDecoders(mdk::MediaType::Video, {});
}
```

⇒ **「下一个 surface 永不出帧」这个失败模式，fvp 作者在 native 层已经处理了。**
「4K 看不到画面」**不是这条路的设计缺陷**。

### 1.2 两轮失败的机制（不是「路线不通」，是两个参数没配）

| 轮次 | 配置 | 用户反馈 | 机制（源码级） |
|---|---|---|---|
| A | 只加 `viewType: platformView` | 「更卡、音画不同步」 | 不开 tunnel 时 `w,h` 由 `maxWidth/maxHeight` **钳**（`video_player_mdk.dart:394-417`）。**我们没设这两个值** → `w,h` = 原生 `3840×2160` → Java 侧 `setFixedSize(3840,2160)` → **GL 渲染器在 4K 上渲染**。上游注释原话：*"full 4K RGBA can push SurfaceFlinger into GPU composition on weak GPUs"* |
| B | A + `tunnel: true` | 「4K 看不到画面，只有声音」 | `fvp_plugin.cpp:97` 走 `AMediaCodec:dv=1:image=0:surface=<ptr>`。**`dv=1` 是强制杜比视界解码器档位**，在一台非 DV 的 MiTV 上嫌疑最大 ⚠️ |

**两轮都不是「这条路不通」。** 而且组合 `platformView` + **不开** tunnel +
`maxWidth/maxHeight = 1920/1080` **从来没有试过**。

### 1.3 关键参数在哪一层（⚠️ 之前记错过一次，这里是核实过的）

| 参数 | 位置 | 性质 |
|---|---|---|
| `platforms` | `registerWith(options:)` | **全局**（进程级） |
| `maxWidth` / `maxHeight` | `registerWith(options:)` | **全局**（`video_player_mdk.dart:175-176`） |
| `tunnel` | `registerWith(options:)` | **全局**（`video_player_mdk.dart:178`） |
| `viewType` | `VideoPlayerController.networkUrl(..., viewType:)` | **每个 controller** |
| `maxWidth/maxHeight` 的**钳制逻辑** | Dart 侧 `video_player_mdk.dart:392-417` | **不在 native** |
| `tunnel` 的**生效点** | `fvp_plugin.cpp:89-103` | native |

两条推论：

1. **阶段 1 的修法只是加注册参数 + 一个 `viewType`，不用改任何 native 代码。**
2. ⛔ **`tunnel` 是全局项 ⇒ macOS 的 DV 路（必须 `false`）和 TV 的 4K 路（想要
   `true`）不能在同一进程同时满足。** 必须按平台条件注册
   （`'tunnel': Platform.isAndroid`）。
   （texture 路给 `tunnel` 是无效的 —— `updateTexture` 那里源码留着
   `// FIXME: set tunnel too late`。）

### 1.4 `viewType` 的传递链（顺带核实，用于排查「没生效」）

```
VideoPlayerController.networkUrl(viewType: ...)          // video_player.dart:404
  └─ VideoCreationOptions(viewType: viewType)            // video_player.dart:462-465
      └─ createWithOptions(...)                          // video_player.dart:473
          └─ MdkVideoPlayerPlatform.createWithOptions    // video_player_mdk.dart:296
              └─ Platform.isAndroid ? options.viewType : textureView   // :300
```

⛔ 注意：`VideoPlayer` **widget** 调的是
`buildViewWithOptions(VideoViewOptions(playerId: _playerId))`
（`video_player.dart:906-907`），而 `VideoViewOptions` **只有 `playerId`**
（`video_player_platform_interface:543`）—— **widget 不传 viewType**。
所以「有没有走 platformView」只看 controller 那一个参数，**不看 widget**。

## 2. 目标架构

### 2.1 数据路径对比

```
【夸克 TV】
  MediaCodec ──直写──▶ SurfaceView（独立硬件显示层）──▶ SurfaceFlinger 合成上屏
  拷贝次数：0

【云影 · 现在（mpv 纹理路）】
  MediaCodec ──拷回 CPU──▶ mpv 帧缓冲 ──上传──▶ GL 纹理 ──▶ Flutter SurfaceProducer
                                                              └─▶ Flutter/Impeller 再合成
  拷贝次数：2 + 1 次全屏合成        ← 4K 一帧 YUV ≈ 12.4 MB，24fps ≈ 600 MB/s

【云影 · 目标（fvp platformView，阶段 1）】
  MediaCodec ──AImage──▶ GL 渲染器（画进 SurfaceView 的 ANativeWindow，钳到 1080p）
                                              └─▶ HWC 合成上屏
  拷贝次数：0 次 CPU 回读（GL 直接采样解码器输出）

【云影 · 目标（fvp tunnel，阶段 2）】
  MediaCodec ──直写──▶ SurfaceView 的 BufferQueue ──▶ HWC 合成上屏
  拷贝次数：0（无 GL、无 EGLConfig、无 GPU 拷贝）
```

### 2.2 分层改动

```
┌─ 业务层 ─────────────────────────────────────────────────────────────┐
│ player_page.dart（内置页） · player_window_app.dart（独立窗口）        │
│   ⚠️ PlaybackSurface 的调用点要挪出「每拍 position tick 都重建」的子树 │
├─ 渲染分派 ───────────────────────────────────────────────────────────┤
│ playback_surface.dart                                                │
│   + platformView 分支；− AspectRatio 包裹；= 保留 null 守卫            │
├─ 引擎契约 ───────────────────────────────────────────────────────────┤
│ playback_engine.dart                                                 │
│   EngineCapabilities + 「输出方式」能力位（HDR / 截图 / codec）        │
├─ 选内核 ─────────────────────────────────────────────────────────────┤
│ playback_engine_router.dart                                          │
│   时机：从「开播后可能中途换」→「挂载前定死，一次播放内不再变」         │
│   规则：+ 第二条触发线（TV 4K）                                       │
├─ 内核实现 ───────────────────────────────────────────────────────────┤
│ fvp_playback_engine.dart（升格为 TV 4K 专用）                         │
│ main.dart（注册参数） · app_providers.dart（装配）                    │
├─ 原生 ───────────────────────────────────────────────────────────────┤
│ fvp FvpVideoView / fvp_plugin.cpp —— **上游已自带，不动**             │
│ media_kit —— **不动**（VideoOutput.java 硬编码 createSurfaceProducer）│
└──────────────────────────────────────────────────────────────────────┘
```

## 3. 分阶段落地

> **原则：先验证、后架构。** 阶段 1/2 都是零架构改动的真机验证；
> 只有验通了才做阶段 3，避免重犯「先落地再验」的错。

### 阶段 1 · 验「platformView + 钳到 1080p」（零架构改动）

改动只有两处：

**① `lib/main.dart`** —— 注册范围加 `android`，并带上钳制值：

```dart
if (Platform.isMacOS || Platform.isAndroid) {
  fvp.registerWith(options: <String, Object>{
    'platforms': <String>['macos', 'android'],
    // ⚠️ 全局项。TV 的显示层只有 1920×1080，不钳的话 GL 渲染器会在 4K 上
    // 渲染（上游注释：full 4K RGBA can push SurfaceFlinger into GPU
    // composition on weak GPUs）。
    'maxWidth': 1920,
    'maxHeight': 1080,
    // ⛔ tunnel 先不开。它是全局项，一旦为 true，macOS 的 DV 路也会带上
    // （texture 路无效，但注册时是共享的）。
  });
}
```

**② `lib/data/playback/fvp_playback_engine.dart:207`** —— 加 `viewType`：

```dart
final controller = VideoPlayerController.networkUrl(
  Uri.parse(media.url),
  httpHeaders: media.headers,
  viewType: VideoViewType.platformView,   // ← 新增
);
```

⚠️ 注意 `viewType` 是**每个 controller** 的，不是全局的；`MdkVideoPlayerPlatform`
只在 `Platform.isAndroid` 时尊重它（`video_player_mdk.dart:300`），所以
macOS 上写不写都退回 `textureView`，安全。

**这一步的判据**（只要这一条成立就继续）：

```
adb logcat -s FvpPlugin
→ FvpVideoView surfaceCreated, video 3840x2160, tunnel false
```

- 出现 → platformView 真的建起来了，进阶段 1 的观感判据（§0 三个数）。
- ⚠️ **没出现不能当反证** —— `I/chatty` 会按 uid 过期日志行（实测一次
  `uid=10050 expire 2183 lines`），主缓冲区也会轮转。要看就看
  `logcat -d` 全量 dump 到文件，别用 `-s` 盯屏。

### 阶段 2 · 再验 tunnel 零拷贝

前提：阶段 1 出画面了、但还是卡。

改动：注册里加 `'tunnel': Platform.isAndroid`。

⚠️ **先把 `dv=1` 单独拆出来查。** `fvp_plugin.cpp:97` 的硬编码是
`AMediaCodec:dv=1:image=0:surface=`；`dv=1` 强制杜比视界档位，而目标机是
非 DV 面板。若开 tunnel 后仍然无画面，第一个要试的是把 `dv=1` 去掉
（需要给 fvp 打补丁，或者先用 `'video.decoders'` 注册项覆盖）。

**判据**：`[资源]` CPU 从 225%+ 掉下来；`[解码]` 显示丢帧不再每 21 秒涨 44。

### 阶段 3 · 才动架构（§4 的 5 层）

前提：阶段 1 或 2 至少一条验通。

### 阶段 4 · 仅在 1、2 都失败时才考虑

自建 ExoPlayer / ijkplayer 内核（照抄夸克）。代价见 §5 —— 等于重写整个

## 4. 阶段 3 的详细改动清单

### 4.1 `lib/ui/widgets/playback_surface.dart`

现在 fvp 分支（`playback_surface.dart:79-100`）返回
`ColoredBox > Center > AspectRatio > vp.VideoPlayer`。三条硬约束：

- ⛔ **不能再套 `AspectRatio`**：platform view 的尺寸由原生 `setFixedSize` +
  Flutter 给的 rect 两边协商，外面再套一层会让 hybrid composition 算错。
  要么 `SizedBox.expand` 铺满，要么自己算 letterbox 给固定尺寸。
- ⛔ **必须保留 `controller == null → 黑底` 的守卫**（现在在 `:85`）。
  否则 `buildViewWithOptions` 会拿 `playerId = kUninitializedPlayerId` 去查
  `_platformViewParams`，查不到就退回 `Texture(textureId: -1)`
  （`video_player_mdk.dart:530-533`）—— 又一个无效纹理。
  ⚠️ 配套事实：`player_page.dart:808` 在 `await _controller.open(...)`（`:834`）
  **之前**就 `_ready = true`，所以这条守卫是**必需**的，不是可选。
- ⛔ **必须与高频重建隔离**：platform view 是 hybrid composition（每个 view
  一次额外合成），而 `player_page.dart:1384` 把它放在 `if (_ready)` 下的 Stack
  里，每拍 position tick 都可能重建。钉 `ValueKey(engine)` / `RepaintBoundary`，
  或抽到只依赖 `engine` 的子树。

> 📌 修正 4K 文档 §4 P1 里的一句旧话：那里写「`PlaybackSurface` 已经按引擎
> 分派，**不用改**」—— 对 `textureView` 成立，对 `platformView` **不成立**。

### 4.2 `lib/domain/services/playback_engine_router.dart`

**这一条比渲染改动更重要，因为它直接对应我们看到的崩溃。**

崩溃链（`logcat -b crash`，**四个不同进程**都中，且**与 `viewType` 无关**）：

```
FinalizerDaemon → SurfaceTextureWrapper.release → SurfaceTexture.release
                → ConsumerBase::onLastStrongRef
```

这是 Flutter 引擎侧对 `SurfaceProducer` 的**二次释放**。成因：
`selectFor` 在 `open()` 之前异步探测、**可能中途换内核**，而换的时候
`previous.stop()` 只停播放，**不释放 `VideoController`** —— 那个纹理输出还活着
等 GC finalize。

**架构解法（不是加 try/catch）：**

> **引擎在 `PlaybackSurface` 挂载之前就是终态，一次播放内不再变。**

具体：

- 把「这条流用哪个内核」提前到**点播放的那一刻**（`PlayTarget.resolve` /
  取直链时顺手探头部字节），结论随 `StreamTicket` 传进播放页；
- 没被选中的内核，本次播放**从头到尾不碰视频输出**（不 `open()`、不建
  SurfaceProducer）。

附带好处：platformView 的 `playerId` 是**原生 handle**
（`video_player_mdk.dart:386` `final id = player.nativeHandle`），换内核 = 换
handle，`PlatformViewLink` 必须整体重建 —— 提前定死就完全避开。

代价：探测从「进播放页后」挪到「点播放时」，多几百毫秒等待。值得。

**规则**：恢复第二条触发线 —— **TV 上「≥4K 或 DV」→ fvp；其余 → media_kit**。
⛔ 不要 TV 全量替换（会丢掉 mpv 的格式覆盖 / ASS 渲染 / 音效 / 缓冲调优）。

### 4.3 `lib/domain/services/playback_engine.dart`

`EngineCapabilities`（`:248-289`）现在建模的是「哪些功能没有」。走 platformView
会**新增**几条取舍，必须变成**可查询的能力位**、由 UI 置灰，别静默失效。

⛔ 现有 5 个布尔位（`audioEffects` / `networkSpeed` / `rawLog` / `chapters` /
`rawProperty`）**不够表达**「同一个内核、两种输出方式」的差异 ——
`FvpPlaybackEngine` 的 `capabilities`（`fvp_playback_engine.dart:110`）现在是
`static const mdk`，而 tunnel 开不开是**运行时**才知道的。
⇒ 要么把 `capabilities` 从常量改成实例方法，要么新增一个 `surfaceOutput` 维度。

### 4.4 `lib/ui/providers/app_providers.dart`

- `alternateAvailable`（`:218`）现在 `= Platform.isMacOS`，要加回 TV；
- `dolbyVisionEngine`（`:225`）的工厂现在只在 `alternateAvailable` 时非空 ——
  第二条触发线要用同一个工厂，别建两个 `FvpPlaybackEngine` 实例
  （每个都占一份解码器配置）。

### 4.5 `test/domain/services/playback_engine_test.dart`

上一轮删掉的那组 `group('高分辨率换内核的判据（Android TV）')`（6 例）**要加回来**
—— 判据回来了，测试就要跟着回来。原处现在留着一条注释说明「不要加回来」，
实施时一并改掉。

### 4.6 已核实的硬约束汇总（避免踩坑）

| # | 约束 | 出处 |
|---|---|---|
| 1 | platformView 要求 `player.textureSize` 有效，否则报 `video size error` | `video_player_mdk.dart:375-385` |
| 2 | `tunnel` 全局，不可 per-controller | `video_player_mdk.dart:178` |
| 3 | texture 路给 `tunnel` 无效（`set tunnel too late`） | `video_player_mdk.dart:432` |
| 4 | `_platformViewParams` 为空时静默退回 `Texture` | `video_player_mdk.dart:530-533` |
| 5 | `surfaceId = -1000 - viewId`，不要自己算 id | `FvpVideoView.java:52` |
| 6 | 释放必须走 `nativeSetSurface(0, id, null, ...)`，不能只 dispose Java 对象 | `FvpVideoView.java:99-105` |

## 5. 取舍与代价

| 能力 | 现在（mpv 纹理路） | platformView 不开 tunnel | 开 tunnel |
|---|---|---|---|
| 零拷贝 | ✗ 实测 `mediacodec-copy` | 半：GL 采样，无 CPU 回读 | ✓ 解码器直写 Surface |
| HDR tone mapping | ✓ | ✓ | ✗ |
| 帧回读 / 截图 | ✓ | ✓ | ✗ |
| codec 覆盖 | 最全（mpv） | 少 | 少（最少） |
| 音效（`af`） | ✓ | ✗ | ✗ |
| 实时速率读数 | ✓ | ✗ | ✗ |
| 缓冲调优属性 | ✓ | ✗ | ✗ |
| 字幕样式 | Flutter 层可控 | libass 烧进画面 | libass 烧进画面 |
| **4K 面板直出** | ✗（UI 层 1080p 封顶） | ✓ | ✓ |

「HDR / 截图 / codec 变少」三条是 fvp 文档原文
（`fvp.dart:30`）：

> *"Maybe more efficient, but some features are not supported, e.g. HDR tone
> mapping and frame readback (snapshot), and fewer codecs."*

⚠️ 而 `audioEffects` / `networkSpeed` / `rawProperty` 是**只要离开 mpv 就永久
失去** —— 这也是「fvp 只做按需路由、不做 TV 全量替换」的理由。

## 6. 明确不做的事

| 想法 | 为什么不解决问题 |
|---|---|
| 继续调 mpv 的 `hwdec` 参数 | P0 已被真机证伪两次（4K 文档 §4）；`media_kit_video` 的 `VideoOutput.java` **硬编码** `createSurfaceProducer()`，mpv 在 Android 上**结构上**拿不到零拷贝 |
| 给 media_kit 打补丁加 SurfaceView | 代价与自建内核相当，收益不如直接用 fvp |
| 自建 ExoPlayer / ijkplayer 内核 | 等于重写整个 `PlaybackEngine` 实现（音轨 / 字幕 / 章节 / 缓冲 / 倍速 / 逐影片偏好全要重来），且 §5 里 mpv 独有的能力**全部失去**。**只在阶段 1、2 都失败时**才讨论 |
| 把 `fvp.registerWith` 的 `platforms` 开成全平台 | 会连带影响 macOS；且 `tunnel` 全局项一旦为 true，DV 路也带上 |
| 只改 `tunnel` 不改 `maxWidth/maxHeight` | 正是第二轮失败的做法（tunnel 分支 `/* native size, no clamp */`，`setFixedSize` 拿到 3840×2160） |
| 写死 `hwdec=mediacodec`（不带逗号回退） | 配不上就只剩软解，4K 直接不能看 |

---

## 7. 风险与回退

| 风险 | 缓解 |
|---|---|
| platformView 引入 hybrid composition 开销，可能「更卡」 | 阶段 1 用 `maxWidth/maxHeight` 钳到 1080p；`[资源]` 行是判据 |
| tunnel 打开后无画面 | 第一个要试的是去掉 `dv=1`；不行就退回阶段 1（不开 tunnel） |
| 换内核触发 `SurfaceProducer` 二次释放崩进程 | 阶段 3 的「引擎提前定死」是解法；**阶段 1/2 期间不要中途换内核**（验证时直接进 4K 片源） |
| platform view 在高频重建下闪烁/错位 | 阶段 3 的隔离改动；阶段 1 先看观感 |
| 阶段 3 落地后回归 | 逐文件回退清单见 4K 文档 §4.5「回退落点」，本轮实施时**同步更新那份清单** |

**回退落点**（本轮若实施，结束时要保证这四处能一句话回退）：

- `main.dart` 的注册块
- `fvp_playback_engine.dart` 的 `viewType`
- `playback_engine_router.dart` 的第二条触发线
- `app_providers.dart` 的 `alternateAvailable`
