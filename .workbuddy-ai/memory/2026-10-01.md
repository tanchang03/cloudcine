## 播放缓冲优化：增大 demuxer 缓存 + 预读目标

### 问题
原画高码率影片播放时周期性卡顿（播一会停一会），带宽没跑满。

### 根因
media_kit 默认 `demuxer-max-bytes`=32MB、`demuxer-readahead-secs`=1秒。
40Mbps 4K 下 32MB 只有约 6.4 秒缓存，且 mpv 只预读 1 秒就停止拉流 →
播放追上缓存后又卡，循环往复。

### 改动
1. 新建 `lib/core/utils/player_buffer_config.dart`：共享配置，
   `bufferSize`=1GB（设 demuxer-max-bytes/max-back-bytes），
   `readaheadSecs`='9999'（设 demuxer-readahead-secs via NativePlayer.setProperty，≈2.7小时覆盖绝大多数片长，等于一直往前缓存）。
2. `PlaybackController.player`：`mk.Player()` → `mk.Player(configuration: PlayerConfiguration(bufferSize: ...))`
   + 构造函数里 `unawaited(PlayerBufferConfig.apply(player))`。
3. `player_window_app.dart` `_ensurePlayer()`：同样加 bufferSize + apply()。
两个播放器共用同一份配置，避免只改一个。

### 效果预期
- 8Mbps：1024秒缓存（17分钟），预读一直拉到片尾
- 40Mbps 4K：205秒缓存（3.4分钟），预读持续拉流
- 80Mbps：102秒缓存（1.7分钟）
- 配合 media_kit 硬编码 cache-on-disk=yes，超额落盘，内存可控

### 阻塞原因一：`LANG` 未设 → CocoaPods 的 unicode_normalize 崩

工作区路径含中文（`网盘媒体库播放器`），CocoaPods 的
`Config#installation_root` 会做 `Dir.pwd.unicode_normalize`。
`LANG` 未设时 Ruby 默认外部编码是 US-ASCII，`Dir.pwd` 拿到非 ASCII 路径就退化成
`ASCII-8BIT`，`unicode_normalize` 抛
`Encoding::CompatibilityError: Unicode Normalization not appropriate for ASCII-8BIT`。

症状：`pod install` 在 `verify_podfile_exists!` 阶段就崩，但**看起来像"pod install 很慢"**。
手动 `cd macos && pod install` 能立刻看到 Ruby 栈。

修：`export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8`。

### 阻塞原因二：safe-delete shim 拦了 Flutter 自己的 `rm -rf`

`podhelper.rb` 用的是 `system('rm', '-rf', symlink_dir)`（**不走 FileUtils**）。
工具链给 `rm` 挂了安全删除 shim，阈值 50；`.symlinks/plugins` 下 11 个目录符号链接
递归统计后 55 个 → `rm` 被拒 → 紧接着 `File.symlink(...)` 撞 `Errno::EEXIST`
→ `[!] Invalid Podfile file: File exists @ syserr_fail2_in`。

非交互（后台跑构建）时 shim 等不到确认 → 永久挂起。

**决定性证据**在 `pod install --verbose` 的日志里：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":55,"threshold":50,"scope":"turn",...}
[!] Invalid `Podfile` file: File exists @ syserr_fail2_in - .../.symlinks/plugins/desktop_multi_window
```

修：`macos/Podfile` 里新增 `cloudcine_clear_plugin_symlinks`，在
`flutter_install_all_macos_pods` 之前用 `FileUtils.rm_rf` 清掉 `.symlinks`
（FileUtils 走 unlink 系统调用，不经过 `rm`，不会被拦）。
语义与 Flutter 自己一致（它本来就要删掉重建），幂等。

### 两个踩坑记录（方法论）

- **`ps` 在本沙箱里返回 0 行**（`ps -Ao pid,comm | wc -l` = 0）。
  我据此误判"没有编译进程"，**误杀了一次正在 pod install 的构建**。
  判断构建活性只信文件 mtime。
- **`flutter build macos` 的工具状态可能是 `failed` 而实际成功**：
  沙箱会对 `~/.swiftpm/security` 报一次 `file-write-unlink` 拒绝，
  把整条命令判为失败。以日志末尾的 `✓ Built ...` 和 `exit=0` 为准。

### 可复用的判据

- **修好后 `pod install` 只要 1.7 秒**。超过一两分钟就是出问题了，别干等。
- `flutter build macos` 的完整前置组合：

## 分辨率改用夸克实测值（§6 候选第 1 条落地）

### 做了什么

1. 把夸克的 `video_width` / `video_height` 一路打通到媒体库：实体 → 夸克解析 →
   drift 两列（schema **v3 → v4**）→ 仓储读写 → `MediaItem.fromEntry` 改为实测优先。
2. 新增 `VideoFormats.resolutionFromDimensions()` 做实测尺寸归挡。
3. 补 8 个单元测试钉住归挡规则，全量 **400 例通过**。
4. 压缩 `MEMORY.md`（17136 → 10946 字节），把操作手册类内容拆到 `HOWTO.md`。

### 归挡规则：长边 + 短边，取较高的那档

第一版只按长边（依据是 40% 宽银幕裁切按高度会低估一档）。自查时发现两个反例：

- **只按长边会漏掉 4:3**：`720x576`（PAL DVD）的长边只有 720，低于最低档 sd480 的
  854 → 返回 `null`，一部 DVD 时代的老剧连分辨率角标都不显示；`960x720` 会被说成 480P。
- **第二根轴不能用「高」**：竖屏的「高」就是长边。取高的话 `1080x1920` 会被读成
  1440P、`720x1280` 读成 1080P —— 手机拍的竖屏内容全部虚高一到两档。

所以第二根轴用**短边**（横竖屏下都是那条短轴，两个方向共用一套档位表），两根轴各算
一遍取较高的：长边兜住宽银幕，短边兜住 4:3。顺带把 `resolutionFromName` 里 `宽x高`
的写法也改成取较小值（`1080x1920` 的第二个数不是「高」），`_byHeight` 更名
`_byShortAxis` 让名字与实现一致。

16:9 与竖屏在两条轴上结论一致，所以「取较高」只在宽银幕和 4:3 两类内容上起作用，
不会抬高正常内容。

## 排查「媒体库没有封面」

用户反馈媒体库里的媒体没有封面。查了运行中的真实产物（数据库 + 日志 + 缓存目录），
结论是**封面链路本身没坏，坏在「拿到的不是海报」和「卡片形状把画面裁没了」**。

### 实测证据

| 检查项 | 结果 |
|---|---|
| 海报缓存目录 | 30 个文件，全部今天 10:54 下载，HTTP 200（6–16 KB） |
| 作品封面地址覆盖率 | `poster_url` **145/145**；条目 `thumb_url` 2689/2881 |
| `poster_file` 列 | 全为 NULL（没有任何代码写回，符合已知设计） |
| 缓存图真实格式 | **WebP 640×360（16:9）**，内容是带**硬字幕 + bilibili 水印**的剧中帧 |
| 卡片形状 | `childAspectRatio: 0.56`（竖版）+ `BoxFit.cover` → 只保留约 **31%** 画面宽度 |
| TMDB 连通性 | `api.themoviedb.org` / `image.tmdb.org` **超时**；`www.themoviedb.org` 200、`api.github.com` 200 |
| 刮削器命中统计 | 289 次 `local 命中`，**0 次 `tmdb 命中`/`tmdb 未命中`** |
| 数据库升级时间 | 日志：`2026-10-01 10:33:29 索引库已升级到 v3（缩略图地址 + 媒体分类）` |

### 三条结论

1. **「一直没封面」的直接原因**：缩略图两列是**今天 10:33 才随 v3 迁移建出来的**，
   在那之前库里根本没有地址，海报墙只能是首字占位块。今天的重扫补上了地址，
   10:54 起封面开始正常下载。
2. **「封面不像封面」的原因**：夸克给的是剧中帧（带硬字幕/水印），
   而卡片是 0.56 竖版 + `BoxFit.cover`，把 16:9 源图裁成 202×360 的竖条再放大
   → 字幕被切一半、画面认不出。用 `sips` 复现了这个裁切效果作为证据。
3. **真海报这条路当前走不通**：TMDB 的 API 与图片 CDN 在本机都不可达（DNS 污染），
   所以即使配了 Key、开了在线刮削也永远拿不到结果。
   ⚠️ 且 `online_scrape=true` + 有 Key 会让每次扫描为每部作品白等 12s 超时。

### 做了什么

2. **方案 2（可配地址）**：新增 `tmdb_api_base` / `tmdb_image_base` 两个设置项，
   经 `SettingsStore` → `AppSettings` → `buildScanService` → `TmdbScraper(baseUrl:,
   imageBaseUrl:)`；设置页加「API 与图片地址」两项 + 「测试连接」探针
   （区分「连不上」/「401 Key 被拒」/「HTTP n」）。
3. **熔断**：`TmdbScraper` 连续 3 次**网络层**失败即判定不可达，之后一次请求都不发。
4. **挖出一个静默 bug**（见下），并补 20 个单元测试。

### 静默 bug：TMDB 的响应形状 ≠ 夸克信封

`_searchOne` 用 `res.dataListItems` 取搜索结果，而那个 getter 读的是 `json['data']['list']`
（夸克信封）。TMDB 返回 `{page, results:[…], total_pages, total_results}` ——
**没有 `data` 也没有 `list`**。`whereType` 在「键不存在」时不抛，只返回空列表，
于是每部作品都走进「TMDB 没搜到」分支。`_loadGenres` 同样读 `dataMap['genres']`，
而 `/3/genre/{movie,tv}/list` 的 `genres` 也在顶层。

**为什么一直没暴露**：网络本来就不通，`TmdbScraper` 从来没真正跑通过一次 ——
这个 bug 与 DNS 污染叠在一起，谁都没机会发现。**必须先修它**，否则就算用户填了可达地址，
依然一部都刮不到（而且症状和「地址不对」一模一样）。

核对方式：读官方文档的 200 示例（`/reference/search-movie`、`/reference/genre-movie-list`），
不是猜。修法：新增私有 `_resultsOf(res)` 读 `res.json?['results']`，类型表读
`res.json?['genres']`，夸克那边的 `dataListItems` / `dataMap` 一概不动。

### 测试里踩到的两个小坑（写测试时）

- `_baseUrl` 自带版本段（`https://api.themoviedb.org/3`），所以 `Uri.parse(url).path` 是
  **`/3/search/movie`** 而不是 `/search/movie`。用 `startsWith('/search/')` 过滤会得到空列表。
- `expect(iterable, contains('/search/tv'))` 的 `contains` 匹配的是**整个元素**，
  不是子串 —— 要断言子串得用 `anyElement(contains(...))`。

## 刮削源调研（TMDB 境内不可用，找国内替代）

**结论：不存在「国内版 TMDB」；VidHub 也没换源，它换的是解析方式 —— 而且实测修错了层。**

- VidHub（`/Applications/MediaCenter.app`，包名 `MediaCenter`）二进制里刮削源**只有 TMDB**
  （`image.tmdb.org/t/p/{w200,w400,w500,original}`）+ TVDB/IMDb/Trakt 互查 ID。
  境内对策是 `DNSResolver`（阿里 DoH `https://223.5.5.5/resolve?...&uid=&ak=&key=&ts=`）
  + `TMDBRequestModifier` + `testTmdbImageLoadingSpeed`/`isTmdbImageAccessSlow` 探针。
  远端配置 `api.7littlemen.com/Vidhub/native_config.json` 实测**只有版本与内购 ID**。
- **实测三种封锁模式（关键）**：
  | 域名 | 结果 |
  |---|---|
  | `api.themoviedb.org` | DNS 污染（本地给 bit.ly 段、阿里给 31.13.64.7、doh.pub 给 31.13.95.17、360 给 69.171.227.37） |
  | `image.tmdb.org` | **DNS 干净**（CNAME→b-cdn.net 真 IP），但 **TLS ClientHello 后被 RST = SNI 阻断** |

- **并发会消耗豆瓣额度**（低优先级的结果可能用不上但请求已经发出）。当前接受，
  因为豆瓣搜索只由详情页按钮按需触发、一次最多 2 个词。真要省就把并发改串行。
- **自动刮削默认关**：全盘自动刮对豆瓣必然中途耗尽额度，而耗尽后是**整批失败**。

### 「原画没有画面」：原画取的是纯音频流

4. `_Inherited` 把祖先的 `resolution` / `original` 传给子层；

**证据**：`play/info` 的 `video_list` 实测**只有** super/high/low

### 「播放器不支持空格暂停 / 方向键跳转」

**症状**：用户要求「空格暂停、左右调进度」。

**根因**：**代码里早就写了** —— `PlayerPage` 的 `CallbackShortcuts` 里

而 `player_window_app.dart` 的键位表里只有 `F` / `Esc`。两个播放器各写一套，

**改法**：

1. 独立播放窗口补上 空格 / ← / →（步长 10 秒），`F` / `Esc` 保留。
   Esc 抽成 `_onEscapeKey`，两张表共用，分支顺序（先退全屏、再退诊断页）不变。
2. 抽 `lib/core/utils/playback_seek.dart` 的 `clampSeekTarget(target, total)`，
   `PlaybackController.seek` 与窗口 `_seekBy` 共用（两处各写一遍必漂移）。
3. **控制栏整块 `ExcludeFocus`**（两个播放器都做）。
4. 诊断页用另一张只含 Esc 的键位表 —— 那一页有手输直链的输入框，
   空格必须留得住。
5. 播放/暂停按钮的 tooltip 补上「（空格）」，键位至少有个能看见的地方。

**实测证据**（三条都是本轮真跑的，不是印象）：

| 探针 | 结果 |
|---|---|
| 焦点给 `Slider(value: 0.5)` 后按 → | `onChanged` 收到 `0.55` —— **滑块确实吃掉方向键** |
| 同一滑块包在 `ExcludeFocus` 里 | `canRequestFocus=false`，方向键不再改值 |
| 焦点给 `IconButton` 后按空格 | `onPressed` 没触发、`CallbackShortcuts` 命中 —— 空格**不**受影响 |

→ 所以 `ExcludeFocus` 是**为方向键**加的，不是为空格；别当成「顺便防按钮」。

**测试边界（重要）**：`flutter test` 里 `Player()` 直接抛
`Exception: Cannot find Mpv.framework/Mpv. Please ensure it's presence in the
Frameworks folder of the application.`（跑在宿主 Dart VM 上，libmpv 不在 rpath）
→ `_player` 永远是 null，**没有进度条可点、没有播放状态可切**。
所以「空格真的暂停了吗」这类断言**写不了**，只能：

## 播放器补齐「字幕 / 音轨」两条能力（用户提的三个问题之 2、3）

### 用户要什么
> 2. 播放器中缺少字幕加载和选择按钮，内嵌字幕，加载外部字幕，互联网加载字幕等功能
> 3. 播放器中缺少音轨选择和识别能力

通过提问确认的口径：字幕**四路全要**（内嵌轨 / 网盘同目录 / 本地文件 / 互联网搜索），
音轨要**完整菜单**（语言 + 编码 + 声道 + 采样率 + 码率，可切换），在线字幕源用 **OpenSubtitles**。

### 交付（全部落在 macOS 真正用的那个窗口 `player_window_app.dart`）

**音轨菜单**（`_AudioDialog` + `_showAudioMenu`）
- 数据源是 `player.stream.tracks`（**持续听**，不是 `open()` 后读一次 —— 容器没解析完时它是空的）。
- 必须过 `TrackLabels.realTracks` 剔掉 media_kit 硬塞的两条合成轨（id 是 `auto`/`no`）。
- 「识别」那一半靠 `TrackLabels.audioTitle/audioDetail`：`中文` / `AAC · 立体声 · 48 kHz · 320 kbps`。
- **选中态不在点击时乐观更新**：以 `player.stream.track` 回报为准。切轨可能失败，乐观更新会让菜单在错的那条上打勾而用户毫无察觉。

**字幕菜单**（`_SubtitleDialog` + `_showSubtitleMenu`）四组 + 两个「动作」入口：
`关闭字幕` → `网盘字幕` → `内嵌字幕` → `在线字幕` → `本地文件` → `从别处加载：搜索在线字幕… / 选择本地字幕文件…`

四个来源的**加载方式**用一个枚举穷举（`_SubtitleKind`）而不是几个可空字段 ——
漏一种的表现是「点了没反应」：
- `embedded` → `player.setSubtitleTrack(SubtitleTrack('$sid', null, null))`
- `cloud` / `online` / `local` → **先拿到正文文本**，再 `SubtitleTrack.data(text, …)`
- 打勾口径：**有外挂字幕挂着时内嵌轨一律不打勾**。mpv 认不出我们后挂的外挂字幕是哪一条，
  它只会把「有字幕轨被选中」报成一个数字，靠那个数字高亮会在错误的内嵌轨上打勾。

### 四个来源各自的「取正文」路径（这才是这次真正的工作量）

| 来源 | 谁去取 | 为什么不能就地取 |
|---|---|---|
| 内嵌轨 | mpv 自己 | 不需要取，切轨即可 |
| 网盘同目录 | 主窗口 `fetchSubtitleText` | 夸克直链缺 Cookie 一律 412，而 `SubtitleTrack.uri/.data` **都没有请求头参数** |
| 在线 | 主窗口 `searchOnlineSubtitles` + `fetchOnlineSubtitle` | Api-Key 在设置里、HTTP 客户端在主窗口 |
| 本地文件 | 播放窗口自己读 | 用户刚在系统选择器里选中，沙箱已授权，不需要绕 |

**编码必须走 `decodeTextBytes`（先严格 UTF-8、失败再 GBK）**，三处都一样。
中文外挂字幕大量是 GBK，`readAsString()` / mpv 自动探测会得到满屏乱码，而且**不报错**。

**只传文本、不传字节**：`fast_gbk` 在主窗口那一侧，播放窗口刻意不背这类依赖（本地文件那一路例外 ——
它必须自己读，所以顺带把 `text_encoding.dart` 引进来了；它是纯 Dart，无平台通道）。

### 过程中挖出来的两个坑（都写进 HOWTO 了）

1. **`PlatformException` 是跨引擎通道唯一认识的错误形状。**
   主窗口的 `onSearchOnlineSubtitles` 原来 `rethrow` 一个 `OpenSubtitlesException`，
   而框架对非 `PlatformException` 的兜底是 `code='error'`、`message=<整段 toString>` ——
   用户看到的提示会变成 `OpenSubtitlesException(notConfigured, 还没填…)` 这种内部类型名。
   改成显式拆三段：`code = 'opensubtitles/${failure.name}'`（进日志）、`message = 人话`（直接显示）。
   **这条比想象中重要**：搜索失败与「搜不到」混起来，用户会以为这部片没字幕，
   而实际要去做的是去设置页改 Key。

2. **`pod install` 在本机（路径含中文）必须先设 locale。**
   直接跑必炸 `Unicode Normalization not appropriate for ASCII-8BIT (Encoding::CompatibilityError)`
   —— CocoaPods 用 `Encoding.default_external` 读路径，而当前 shell 的 `LANG` 不是 UTF-8。
   正确姿势：`LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 pod install`。
   （`flutter run` 自己会处理，所以一直没暴露。）

### 为什么 git 救不回来

`git clean` 只删**不在索引里**的文件，所以：

| 状态 | clean 后 | 能救吗 |
| --- | --- | --- |
| 已 commit | 不动 | 本来就在 |
| `git add` 过 | **不删** | 在 |
| 改过但没 add | **不删**（tracked） | 在 |
| 从没 add 过（`??`） | 删 | **不能** —— 内容从没进过对象库 |

实测确认：`git fsck --dangling` 只有 20 个悬空 blob，全是更早的东西（PNG、
`tables.dart`、几个 md），**没有一个是被删的文件**。`git stash list` 空，

### 现象

`flutter build macos --release` 构建成功（`✓ Built … cloudcine.app`），

```
Termination Reason: Namespace CODESIGNING, Code 1, Taskgated Invalid Signature
```

### 关键读法（先记这三条，能省一小时）

`"Runner" requires a provisioning profile.`


- entitlements：删 `keychain-access-groups`；`app-sandbox` 改 **`false`**；

  `DebugProfile` 保留 `get-task-allow`/`allow-jit`。
- `SecureCredentialStore`：`useDataProtectionKeyChain: true → **false**`，
  accessibility 改 `first_unlock_this_device`。
  （用户截图里那个 `-34018 A required entitlement isn't present` 就是它报的。）

## ⚠️ 事故：排查钥匙串时在用户机器上弹出授权框（17:28）

**我做了什么**：为了验证「`SecAccessCreate` + `SecTrustedApplicationCreateFromPath(nil,…)`
建出来的 ACL 是不是真的『任意程序可读』」，在 `/tmp` 与 `~/cloudcine_kc_probe` 下编译了多个
Swift 探针（`kcs_probe` / `kcs_write_probe` / `probe_a` / `probe_b` / `abc1..abc3` / `kcs_diag`），
让「程序 A 建条目、程序 B/C 去读」。**这触发了 macOS 的钥匙串授权弹框**（要求输入登录钥匙串密码），
用户看到后一头雾水。**教训：不要在用户机器上跑会触发钥匙串授权的探针** ——
授权框是系统级 UI，弹出来用户根本不知道是谁在要权限。

**已清理**：探针二进制、源码、临时文件、`~/cloudcine_kc_probe` 全部删除；无残留进程（`pgrep` 已确认）。
遗留钥匙串条目（**惰性，无程序会读**，用户可在「钥匙串访问」里搜 `cloudcine` 删掉）：
`com.cloudcine.cloudcine.credentials.selftest` / `.selftest3` / `.abcprobe`。

### 复测结论（已定论，17:33）

**用打包好的 .app（`open` 启动、正常 GUI 会话）复测，plan B 兑现不了「零弹框」。**

探针做法：搭一个最小 `.app`（ad-hoc 签名，`LSUIElement`），行为逐字复刻
`KeychainChannel` 的 `read`/`write`（先删后建）。建条目 → **原地重新构建**
（cdhash 从 `6c1d9c6e…` 变成 `d61f0379…`，路径不变）→ 再启动。

| 步骤 | 首次（创建者） | 重建后（身份变了） |
|---|---|---|
| `read` | `0` | **`-128 errSecUserCanceled`，且阻塞了 3.2 秒** |
| `write.delete` | — | `0`（删除反而放行） |
| `write.add` | `0` | `0` |
| 再 `read` | `0` | `0` |

**3.2 秒的阻塞 = 确实弹了模态授权框。** 两种 ACL 写法都试过、都不行：
- 受信程序 = `SecTrustedApplicationCreateFromPath(nil, …)`（「任意程序」）
- 受信程序 = `SecTrustedApplicationCreateFromPath(bundlePath, …)`（app 自己的路径）

**机制**：macOS 只认「创建这个条目的那一份代码签名」。ad-hoc 签名的身份是 cdhash，
重建即变 → ACL 永远对不上 → 每次重建后第一次读都要授权。
「任意程序」那一条对 **ad-hoc 签名**的条目根本不生效
（连 Apple 自带的 `/usr/bin/security` 去读也拿到 `-128`）。

**plan B 的真实收益**（不是零，但确实改善）：
`write()` 是「先删后建」，**删除是放行的**，所以重新登录后条目会被重建、
重新绑定到当前这份构建 → **从「每次启动都弹」变成「每次重新构建后弹一次」**。
`flutter_secure_storage` 之所以「每次启动都弹」，是因为它用 `SecItemUpdate`，
条目修不回来。

**真正能做到零弹框的只有两条路**：
1. **签名身份稳定**（Developer ID）—— 兄弟项目 `夸克音乐播放器` 就是这么做的：
   `build_macos.sh --release <TeamID>` 把证书写进 `Signing.local.xcconfig` 再
   `flutter build macos --release`，产出的 `cloudtune.app` 实测是 Developer ID 签名
   （`TeamIdentifier=7TXGZ3BSQC`），所以它不弹。⚠️ 我上次是用**手动 `codesign`**
   试的（报 `errSecInternalComponent`），**没试过走 `flutter build macos`** —— 那条路可能本来就是通的。
2. **不用钥匙串**：凭证加密落文件，密钥由本机 + 本用户推导（混淆级）。

**踩坑**：`security add-generic-password -A` 与 `security delete-generic-password`
在本机间歇性静默失败（exit 1、无输出）；同一个 `swiftc` 有时也静默失败。
**看不懂就先重跑一次。**

## 凭证代码复查（17:58）

对着 `secret_cipher.dart` / `secret_backend.dart` / `secure_credential_store.dart` 逐行审了一遍。

**密码学部分：没找到缺陷。** HKDF extract(`HMAC(salt, ikm)`) / expand(`T(i)=HMAC(prk, T(i-1)‖info‖i)`) 与 RFC 5869 一致；
密钥流 `HMAC(key, nonce‖be32(counter))` 每块输入唯一，与 CTR 等价；`open()` 严格**先验 MAC 再解密**；
常量时间比较不提前返回；每次 `seal` 同时换盐和 nonce，所以即便 nonce 撞了密钥也不同（双保险）。

**发现并修掉一处真实脆弱点：密钥材料掺了易变的环境值。**
原 `localKeyMaterial()` = `[IOPlatformUUID, Platform.localHostname, $USER, $HOME].join('\n')`。

→ 改成：**拿到 UUID 就只返回 `platform-uuid\n<uuid>`**，拿不到才退回 `fallback\n主机名\n用户\nHOME`。
（`credentials.enc` 此刻还不存在，所以这次改动**不会让任何已存凭证失效**。）
测试新增 2 条（`credential_store_test.dart` 的「密钥材料（localKeyMaterial）」组），定向测试 **48/48 全过**。

## 修掉 read-modify-write 竞态：给 EncryptedFileSecretBackend 加串行队列（18:06）

这是**我自己写出来的**代码里的真实缺陷，不是猜测。整个文件是**一个**加密块、里面一张
`key → value` 表，于是每次写都是「读全表 → 改一项 → 写全表」—— 典型的 read-modify-write：
两个并发写各自读到同一份快照、各自加自己的键、各自写回整表，**后写的把先写的键整个抹掉**。
表现极隐蔽：文件完好、能解密、日志一个字都没有，用户只会看到「另一个网盘莫名其妙要重新登录」。

**做法（顺序很重要）**：
1. **先只加测试、跑一遍确认它红**。结果是 `+27 -1` / `+27 -2` 双红 —— 证明竞态真实存在、
   测试也确实守得住东西。不然写完修复再跑绿，你不知道那条测试是不是本来就绿。
2. 再加 `_serialized()`（`Future` 链式队列）：`read`/`write`/`delete` 全部排进队列，
   保证本后端任意两次操作永不交错。**顺带**也解决了 `_store` 里固定名 `.tmp` 的抢占问题
   （不重叠就不会有两个写入者盯同一个临时文件）—— 一个机制收两个 bug。
3. 异常处理的关键：失败要**原样交给调用方**（`write` 的失败要让上层记日志），
   但**绝不能让队列断掉** —— 队列一旦带着错误往下走，后续每次操作都会收到上一次的异常，报的还不是真因。

## 文件夹模式改造：数据源换成网盘实时目录 + 局部发现（19:0x）

用户诉求原文：「对于文件夹模式，不是将已扫描的媒体库作为数据来源而是直接读取网盘目录结构，
并支持将指定目录或文件进行发现媒体文件加入到媒体库，比如新加入了电影，但不像整体扫描
媒体库来发现新的电影，通过文件夹直接发现新的媒体文件」。

**为什么要改**：原实现是从 `MediaItem.dirPath` 重建 `FolderTree`（「已扫描的媒体库」的投影）。
后果是文件夹视图只能显示**扫过**的东西 —— 用户新传一部电影进去，点进目录什么也看不到，
而他并不知道「要先跑一次全盘扫描」。改成直接列网盘目录后，视图与网盘同源，新文件立刻可见，
「入库」变成一个可选的叠加状态（行上标「已入库 N」）。

### 抽出的三份唯一实现（全盘扫描与局部发现共用）

这三件事原本都只存在于 `ScanService` 的遍历循环里。局部发现若照抄一遍，两条路径的行为会随时间漂移
—— 而漂移的表现是「同一个文件走扫描进了动漫、走发现进了电影」，用户根本无从理解。所以先抽出来：

- `domain/services/media_entry_classifier.dart`：`classifyEntry(entry) → EntryRole`。
  顺带修掉一个死代码：原来的 `isDiscImage` 判定写在 `isVideoFile` **之后**，
  而 `.iso`/`.img` 不在视频扩展名表里 → 那个分支永远走不到。现在镜像判定提前，
  索引结果不变（本来就不入库），但日志/分类变准确。
- `domain/services/work_builder.dart`：`WorkSeed`（公开化的原 `_WorkSeed`）+ `WorkSeedBook`
  （分组种子累积器，含 `queries` / `buildDirty` / `markClean`）。归组、累加体积、封面锚点成对，全在这里。
- `domain/services/request_throttle.dart`：`RequestThrottle`，语义是「请求**起点**之间的最小间隔」
  （不是终点后固定 sleep）。注入时钟以便测试。

### 新增 `domain/services/media_discovery.dart`

`MediaDiscoveryService.discoverDirectory(provider, dirId, dirPath, recursive, cancel, onProgress)`
与 `discoverFile(provider, entry, dirPath)`。三条**与全盘扫描刻意的区别**，每条都写进注释与 `reason`：

1. **绝不清理陈旧记录**：不调 `deleteItemsNotIn` / `deleteSubtitlesNotIn`。
   局部视野只看到一棵子树，拿它去算「库里多余的」会把子树外的东西全删掉。
2. **绝不写续扫游标**：续扫游标是「整个盘扫到哪了」的状态，局部发现写它会让下一次全盘扫描
   从半截开始、静默漏掉一大片。
3. **深度从本次目标算第 0 层**：用户的「只发现这一层」指的是他点的那个目录这一层，
   不是相对于网盘根的第 N 层。

另外：`_knownIds(rootPath)` 在开始前取一次快照，用来区分「新增 / 已有」；`_active` 做重入守卫
（页头「发现本目录」与目录行「只发现这一层」可能被连点两次，两次并发列目录会让实际 QPS 翻倍，
而两边各自的节流器都以为自己守住了 3 QPS）。`discoverFile` 会额外列一次父目录来配同目录字幕，
失败只 warn 不上抛（除非 `needsReauth`）。

列表却是空的，却找不到那第二个条件在哪。唯一出路是「清空筛选」，
把另外那个还想留的条件一起抹掉。

→ 把这类项也画出来，标「无结果」（灰字、仍是打勾态、**照样可点**），
所以能被**单独**取消。同时有已选项时**不再**说「还没有带年份的作品」——
两句话同时出现会自相矛盾（用户正看着一颗勾着的「1990 年代（无结果）」）。

### 缺口四：空态按钮写「清空筛选」，实际执行 `clear()`

`library_page.dart` 的空态原本是「提示语按条件分两种，按钮一律 `clear()`」。
而 `clear()` 是**全部复位**（分类、排序、搜索词、面板两组）：只打了搜索词的
用户点「清空筛选」，连分类栏选的位置和排序都一起丢掉 —— 他不会把
「我的栏目没了」和「我刚点了个清空按钮」联系起来。

→ 抽出纯函数 `libraryEmptyHint(filter)`（`@visibleForTesting`），按**当前
实际在用的条件**分派「提示语 + 按钮标签 + 该清什么」，四种情形：

| 在用的条件 | 按钮 | 清掉什么 |
|---|---|---|
| 年代/类型 + 搜索词 | 清空筛选条件 | 两者，保留分类 |
| 只有年代/类型 | 清空筛选 | 面板两组，保留分类 |
| 只有搜索词 | 清空搜索 | 搜索词（走 `_clearSearch`，输入框里的字也要清） |
| 都没有（只切了分类） | 回到全部 | 全部复位 |

第二个「为什么」值得记下来：**要清就清掉全部在用的条件**。按钮的用途是让
用户重新看到内容；同时设了搜索词与年代却只清一个，列表很可能还是空的 ——
用户会认为这个按钮坏了。

## 新增排序策略：按网盘文件修改时间倒序（默认）

用户要求「全部影片增加排序策略，默认为按网盘文件修改时间倒序」。

### 方案

作品（`MediaWork`）下可能有多个文件（剧集）。取所有文件 `modifiedAt`
（网盘文件修改时间）的**最大值**作为作品的排序依据 —— 新增一集或替换一集时，
这个值会变大，整个作品就会浮到前面。这比 `updatedAt`（入库时间）更能反映
「用户刚在网盘上动过」这件事。

### 改动清单

1. **`WorkSeed`**（`work_builder.dart`）：加 `lastModifiedAt` 字段，
   在 `addItem` 时取 `max(当前值, item.modifiedAt)`。
2. **`MediaWork`**（`media_work.dart`）：加 `lastModifiedAt` 字段，
   更新 `copyWith`。
3. **`MediaWorks` 表**（`tables.dart`）：加 `lastModifiedAt` 列（nullable）。
4. **`mergeWorkForUpsert`**：永远取 incoming 的新值（重扫就是为了更新它）。
5. **`_workCompanion`** / **`_toWork`**：映射新字段。
6. **`WorkSort` 枚举**：加 `recentModified('最近修改')`，排第一位（默认）。
7. **`listWorks` 排序**：SQL 侧 `OrderingTerm.desc(t.lastModifiedAt)`；
   内存侧同样的 NULL 垫底逻辑。
8. **默认值**：接口参数 / `LibraryFilter` / `isDefault` 全部改为 `recentModified`。
9. **UI 排序菜单**：已经用 `WorkSort.values` 循环，自动包含新选项。

## 补迁移：v6 `media_works.lastModifiedAt`（真机报错 no such column）

上一轮给 `tables.dart` 加了列就收工，**忘了写 migration** → 用户在老库上
一打开媒体库就报 `no such column: last_modified_at`。

### 教训（下次改 schema 必须一起做的三件事）
1. `tables.dart` 加列。
2. `app_database.dart` 的 `schemaVersion` **+1**。
3. `onUpgrade` 里 `addColumn`。
**编译期完全发现不了**：drift 编译期只认 `tables.dart`，磁盘上的旧库它管不着。
→ 唯一能兜住的是拿一个**旧版本库文件**真跑一遍迁移（见下面的测试套路）。

### 这一列必须回填，不能「等下次扫描」
它是**默认排序** `WorkSort.recentModified` 的唯一依据。留 NULL = 整库按
tie-breaker 乱序，用户第一眼就是「更新把功能做坏了」。
而前几版（`posterFaceX`/`videoWidth`…）只是显示细节，缺了不影响列表能不能用 ——
**所以「能不能等下次扫描」要看这一列是不是查询/排序的依据，不是一刀切。**
好在能回填且不碰网络：`media_items.modifiedAt` 里就有，取每个 group 的 MAX：
```sql
UPDATE media_works SET last_modified_at = (
  SELECT MAX(mi.modified_at) FROM media_items mi WHERE mi.group_key = media_works.key)
```
口径与 `WorkSeed.add()` 一致 —— **`add()` 不过滤 sample/extra**，所以 SQL 也不加过滤。

### 顺手修的遗留不一致
`InMemoryMediaRepository.listWorks` 的默认 `sort` 还是 `recentAdded`，
接口和 drift 实现已经是 `recentModified`。**接口默认值只是文档，真正生效的是
实现上的默认值**；不显式传 sort 时两个实现会给出不同顺序，而单测通常都显式传
sort → 看不出来。已改成三处一致。

### 迁移测试套路（可复用）
`test/data/db_migration_last_modified_test.dart`：
**不手写老版建表 SQL**（等于抄一份 schema，漏更新只会让测试假装通过）。
反过来做：按当前 schema 建库 → 塞数据 →
`ALTER TABLE media_works DROP COLUMN last_modified_at` +
`PRAGMA user_version = 5` → close → reopen。
它就是一个货真价实的 v5 老库，reopen 时 drift 必走 `onUpgrade`。
（依赖 SQLite ≥ 3.35 的 DROP COLUMN，本机 ok。）

### 验证
- `flutter analyze lib test` → No issues found
- 全量 `flutter test` → **1000 例全过**（+5 迁移例）
- 用户**不需要重扫**就能看到正确的「最近修改」排序（已回填）。
