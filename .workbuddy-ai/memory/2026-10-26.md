# 2026-10-26

## 百度网盘：文件夹页 / 媒体库删不掉资源 —— 根因与修复

**现象**：百度对接后，文件夹页「多选 → 删除」点了只得到一句「该网盘不支持删除文件」；
媒体库批量删除里百度的文件被算成「删不了」，勾「一并删网盘」也不会动它们。

**根因（两条，叠在一起）**：
1. `BaiduAdapter` 当时是纯只读接入，`deleteFiles` 走基类默认实现抛 `unsupported`；
2. 唯一的写能力位 `Capabilities.canWrite` 把「上传 / 建目录 / 删除 / 移动」绑成一个布尔，
   而百度只做了删除 —— 用 `canWrite` 判删除必然判错（百度能删却不能写）。

**修复**：
- `BaiduAdapter.deleteFiles` 实装：`POST /api/filemanager?opera=delete&async=2&onnest=fail`
  + 表单体 `filelist`（**路径** JSON 数组）。百度按路径寻址，所以先做 fid → path 翻译：
  优先 `_pathByFsId`（列目录白捡），未命中走**一次批量** `xpan filemetas`（`fsids=[1,2]`，
  不是逐条问 —— 逐条 100 个文件就是 50 秒）。响应里的 `info[].errno` 逐条核对，
  被拒的从返回值摘掉；`async` 只回 `taskid` 时按「请求已受理」回报全部。
- **新增 `Capabilities.canDelete`**（默认 true）。`canWrite` 收窄为「上传 / 建目录 / 移动」。
  百度：`canWrite: false, canDelete: true`。`library_removal._canDelete` 改判 `canDelete`。
- 记账修正：两个批量删除控制器都按「`chunk.length - ok.length`」把**逐条被拒**的差额
  算进失败数（之前只按异常记失败，百度那种部分拒绝会被报成「全删干净」）。
- 文案修正：`DriveDeletePlan` 增加 `provider`，不可逆警告按家分岔（不再在百度的盘上
  说「夸克侧按永久删除处理」）；`folder_browser` 的「移动」按钮按 `canWrite` 置灰
  （百度移动没实现，留着就是同一个「点了才报错」的坑）。
- 媒体库删百度文件时用 `primeFilePath(item.fileId, item.netdiskPath)` 预热路径缓存，
  省掉那次 `xpan` 解析（该端点还可能被账号风控 9019 挡着）。

**⚠️ 未验证**：`/api/filemanager` 这条删除请求**没有真实账号实测过**（本机没有可用
BDUSS）。证据是两个独立来源：2018 年一篇抓包分析给的完整 URL；AList 的 `manage()`
（走官方 `xpan/file`，`filelist` 同样是**路径 JSON 数组**）。首次真机验证时看诊断日志
「接口」那一栏的响应体即可（失败时会把原始 body 截断打出来）。

**测试**：`test/data/baidu_adapter_test.dart` 新增 deleteFiles 组（表单形状 / 逐条 errno /
全部被拒 / 只回 taskid / 路径翻不出来 / 缓存失效 / 批量解析只发一次）；
`library_removal_controller_test` 增加「能删但不能写（百度现状）照样删」的回归用例；
`drive_cleanup_controller_test` 增加「返回比发出去少 ⇒ 差额算失败」。
全量 `flutter test` 2916 个用例通过。

**顺带修掉的过期表述**：README 支持矩阵（百度已接入）、`auth_page` 底部说明、
`app_database` / `app_providers` / `library_removal_providers` 里把百度称作「只读」的注释。

## 追加二：部分失败那句「为什么」按网盘分岔

原来两个 `*Message` 都硬写「多半是限流，可以再试一次」。这在夸克上成立
（整批 429 → 一批全算失败），在百度上是**错的**：`opera=delete` 逐条 `errno`，
常见原因是目录里还有删不掉的子项（`onnest=fail`）或文件被别的客户端占用 ——
让人去重试，重试一百次也不会成功。

- `DriveDeletePlan._failedHint` / `DriveMovePlan._failedHint`：`switch (provider)`
  → 夸克「多半是限流」；百度删除「目录里还有删不掉的子项 / 文件被占用，反复失败看
  诊断日志里的 errno」、百度移动「最常见是目标目录已有同名文件（重试也一样，得先改名
  或换目录）」；`aliyun || null` → 中性「可以再试一次」。
- `DriveMovePlan` 新增 `provider`（可空，与 `DriveDeletePlan.provider` 同一套 null 语义），
  由 `drive_move_dialog._planFor` 用 `ref.read(browseProvider)` 填。
- 文案只改括号里那半句，保留「N 项失败」字样 —— 既有断言不用跟着改。
- 新用例：删除/移动各三条（夸克说限流、百度不说限流且给出可操作原因、null 中性不指名）。

## 追加四：⛔ `primeFilePath` 不许覆盖已有映射（本轮唯一能造成**误删**的路径）

上一轮为了省掉一次 `xpan` 解析，在媒体库删除前加了
`primeFilePath(item.fileId, item.netdiskPath)` 预热。但当时的实现是
**无条件 `_pathByFsId[fileId] = path`**，而两边的「新旧」方向恰好相反：

- 缓存里那条可能刚由 `listDirectory` 从服务端拿回来（几秒前的事实）；
- 调用方给的是库里持久化的 `dir_path + name`（**可能是几天前的扫描**）。

覆盖方向反了，拿到的就是一条陈旧路径。取链时它报「文件不存在」（用户以为
文件丢了）；**删除时更糟 —— 若那条旧路径上现在住着另一个文件，删掉的是它**。
常见触发顺序：用户在文件夹页看过那一层（缓存被填满）→ 再去媒体库删同一个文件。

改成 `if (_pathByFsId.containsKey(fileId)) return;`（只填空位）。
缓存里没有时间戳，所以「谁更新」无从判断；但「不覆盖」至少保证一次都不会
把服务端刚说的话改成库里那句旧话。契约层
（`CloudDriveAdapter.primeFilePath` 文档）也写明了「它是**垫**，不是**改**」，
并说明「纠正一条已知错误的映射是适配器自己的事，不该由外部调用方代劳」。

新用例：先 `listDirectory` 填 `/归档/a.mkv`，再用旧记录 prime 成 `/电影/a.mkv`，
断言删除请求发的是 `/归档/a.mkv`。

另外在验证清单里补了一小节「撞上 `-9` 时先别改代码」：路径有两个来源
（会话缓存 / 库里的 `dir_path`），
「媒体库删失败但文件夹页删同一个文件成功」这个组合指向库里 `dir_path` 陈旧，
重扫即可，不是删除实现的问题。

## 追加五：请求侧也进日志（唯一未验证那一步的取证补全）

删除/移动是这套代码里唯一没真机验证过的接口，而原来只记**响应**体
（`_logBody`）。形状不对时服务端只回 `errno=2`，光有响应分不清是「我们发错了」
还是「它不认这个字段」，而从代码反推「发了什么」不可信（代码随时会改）。

- `_post` 里加一行 `diag.debug('接口', '百度$path 请求体：…')`。放在 `_post`
  而不是两个调用点：它俩共用的就是那个出口，将来任何新 POST 都自动带上。
- 抽出 `_clip` + `_logBodyLimit = 300` 与 `_logBody` 共用。300 是实用值：
  100 项的 `filelist` 有几 KB，整条打进日志页会让那页卡住，而前 300 字符
  足够回答「数组还是对象、字段名对不对」。
- 新用例断言删除后日志里有 `请求体：filelist=`。
- 验证清单的「每步看哪几行日志」补上这一行，并写明**请求侧与响应侧必须
  一起看**。

## 追加七：`Capabilities` 第一次有了直接单元测试

查 `test/domain/` 时发现这个值对象**一条直接用例都没有**，而这一轮恰好给它

它的判错方式是**全静默**的：备份挑错网盘、媒体库分账错、按钮莫名灰掉，

## 追加九：删除按钮从来不查 `canDelete`（工具条两个按钮不对称）

查 `folder_browser` 的多选工具条时发现的：**移动按钮按 `canMove` 置灰，
删除按钮只看「有没有勾选」**：

```dart
onPressed: selection.isEmpty ? null : () => _delete(context, ref),   // 旧
```

后果比「按钮灰着」糟：一个 `canDelete == false` 的网盘上，用户勾选 → 点删除 →
读一遍「删除后不可撤销」→ 按下确认 → **什么都没发生**。一次不可撤销的确认
换来零结果，比一开始就灰着伤人得多。`canDelete` 这个位当时只被媒体库那边
（`LibraryBatchDeletePlan.undeletableFileCount`）用着，文件夹页从没用过。

修法：
- 把能力位的读取收敛成**一次** `capabilities` 查询，再派生出 `canMove` /
  `canDelete` —— 两处各查一遍的话，写法迟早分叉，而「一个按钮按新判据、
  另一个按旧判据」正是这一页反复出问题的形状。
- 删除按钮提成局部变量 `deleteButton`（内联在 `children` 里就没法像移动那样
  包 `Tooltip`），不支持时置灰 + `Tooltip('该网盘不支持删除文件')`。
- 取不到适配器（账号刚被移除）时按「能」处理：那时整页本来就在报错，

**验证有牙齿**：把判据改回 `selection.isEmpty` 单条件，该条立刻变红；

## 追加十：删目录之后的索引子树 —— 追到底，是对的（不必再查）

按「用户会走的路径」补完最后一步：文件夹页删**目录**之后，本地索引里那几十集
会不会变成死索引。结论：**处理正确**，链路上三道都有人守：

1. `DriveCleanupController._purgeLibrary` 用 `crumb.child(entry).path` 算前缀，
   **不用 `entry.path`** —— 列目录拿到的 `DriveEntry.path` 常是 null，
   用它做前缀会**静默**一条都匹配不到（注释里已写明这个坑）；
2. `crumb.child()` 走 `normalizeDrivePath`，产出的前缀**不带**结尾斜杠；
   而 `listItems(pathPrefix:)` 内部用 `drivePathWithTrailingSlash` 补齐后
   才做 `LIKE`，所以 `/电影` 不会带出 `/电影2`（`media_repository_impl`
   里那段注释解释了为什么必须补）；
3. 失败批次**不清索引**（`deletedIds` 只含服务端确认的那批），
   方向也对：清早了的代价是下次扫描重建，清晚了的代价是用户点到死卡片才发现。

测试覆盖：`drive_cleanup_controller_test` 的「删掉一个目录会连它子树里的索引
一起清掉」（含兄弟目录不受影响）、「删除失败的条目不清索引」；
`media_repository_list_items_test` 的「前缀必须按**整段**比」；
`drive_paths_test` 的 `drivePathIsUnder('/电影2', '/电影') == false`。

**这一处不需要改。** 记下来是为了下次不必重走。

```
10:08:27.395 DEBUG [接口] 百度删除文件响应体：{"errno":8001,"request_id":3732219969458013}
10:08:27.396 ERROR [接口] 百度删除文件业务失败 | unknown code=8001 http=200
```

三条**排除性**结论：

1. **形状是对的**。形状错（`filelist` 给成对象数组、`Content-Type` 给成
   `text/plain`）服务端回 `errno=2`。回 `8001` 说明请求体已被解析，拒绝在业务准入层。
   所以别再动 `filelist` / `Content-Type` / `opera` / `onnest`。
2. **不是夸克那条成功案例可类比**。日志里 `已删除 1 个文件` 出现两次
   （09:05:36、10:08:31），但那是 `drive-pc.quark.cn/.../file/delete` —— **夸克**。
   百度删除整份日志只调用过**一次**，就是那个 8001。别被「删除成功过」误导。
3. **`bdstoken` 一次都没取过**。`grep 'gettemplatevariable|get/template|已取到'`
   零命中。

### 根因（设计缺陷，不是参数写错）

`_ensureBdstoken()` 只在 `_request` 捕获到 `-6`（unauthorized）时才触发。
但**缺令牌在读写两条路上回不同的码**：

| 端点 | 缺 `bdstoken` | 后果 |
|---|---|---|
| `/api/list`、`/api/account/uinfo`（读） | `-6` | 自愈能触发 |
| `/api/filemanager`（写） | **`8001`** | 自愈等不到，**永远**自愈不了 |

于是每次删除都发一个不带令牌的请求 → 8001 → 用户看到「未知错误」→ 重试同样失败。
这就是「改了还是删不掉」的全部原因。

### 修法

- `BaiduAdapter._ensureWriteToken(what)`：写操作**先取后发**。取不到也照发
  （不把「取令牌失败」升级成「功能不可用」——一次网络抖动不该让删除按钮永久失效），
  但日志留一句。**未授权时直接返回 null**，让 `_request` 先报「请重新授权」，
  而不是先发两条 401 噪音。
- `deleteFiles` / `moveFiles` 在 `_post` 之前 `await _ensureWriteToken(...)`。
- `BaiduErrorCode.writeRejected = 8001` → `permissionDenied`，文案同时给出
  「缺 bdstoken」与「去网页版过验证」两条出路（8001 的官方释义**没拿到**，
  不谎称权威）。
- `_post` 新增 `查询参数：opera=… & bdstoken=有|缺` 一行日志（**只报有无，不报值**）。
  这次排查最贵的一步就是「令牌带没带」只能从代码反推，而 `_post` 在令牌为空时
  是**静默省略**该参数的。

测试：`baidu_adapter_test` 76 例（新增 6 例：写操作带令牌、移动带令牌、
8001 报成可处置错误、取不到令牌照发、未授权不取令牌、查询参数进日志）。
全量 2949 例通过。

### 待复验（下次真机）

日志应出现 `百度删除文件是写操作，先取 bdstoken` → `已取到 bdstoken（来源 …）`
→ `查询参数：… & bdstoken=有`。若**仍然** 8001，下一个嫌疑是 `async=2` 与
`onnest=fail` 的组合（这两个值只来自抓包，从未本机实测）。

另：同会话 `xpan/multimedia` 一直 `9019 need verify`（账号风控）。若
`gettemplatevariable` 也被 9019 挡住，就取不到令牌 → 仍 8001，那时该做的是
让用户去网页版过验证，而不是继续改代码。这是两个独立变量，别混为一谈。
