3. 按 README 协议 **BACK 退出播放页**（中继活着；实测退出后 curl 仍 206）。
4. `am start -n com.cloudcine.kuake/.PlayerActivity --es url "http://127.0.0.1:<port>/s1"`

### ★★ 三个必须记住的结论

1. ⛔ **`Source error` 的真判据不是「首帧总时长 > 8s」** —— 原型首帧 **12.3s 却完全没报错**。
   `DefaultHttpDataSource` 的 readTimeout 是**单次 socket 读**的空闲上限：2 MiB 中继 ~2.8s
   就出首字节（curl 实测 TTFB **2.81s**），socket 一直在收；8 MiB 中继**整块读完才发第一个字节**，
   >8s 零字节 ⇒ 必炸。**推翻了我 10-05 的表述，记入 MEMORY.md。**
2. ⛔ **云影在 Android TV 上本来就已经是 ExoPlayer + 硬解直通**（HUD 实证 `内核 ExoPlayer` /
   `解码 硬解(直通)`）⇒「换原型方案」的实际落点是
   **渲染面（真 SurfaceView vs Flutter 纹理）+ OSD 实现 + 每拍 rebuild 纪律**，**不是换引擎**。
3. ⛔ **LMK 会杀掉后台的云影，中继随之消亡**：原型起播 42s 后就
   `ConnectException: Failed to connect to /127.0.0.1:43409`。
   08:03:12 `lowmemorykiller: cache 288772kB below limit 200000kB / Free memory is -3308kB above reserved`。
   ⇒ **「云影当中继 + 原型播放」这条路只有 2~3 分钟窗口**；先 `am kill-all` 腾内存。
   ⇒ 也说明 **RSS 658 MB → 205 MB** 这条不只是性能，还是**存活率**（这台机器只有 2.5 GB）。

### ⛔ 错在哪
- 云影 `DebugOverlay`（`lib/ui/widgets/debug_overlay.dart:80`）用

  实测 OSD 关着 `FPS 2`、OSD 开着 `FPS 10`（**这个数 ≈ 每秒整页 rebuild 的次数**）。
- 原型 `StatsOverlay` 用 `Choreographer` **主动每帧重新 post**，等于持续请求 vsync，
  所以永远报满帧（113~121）。**两者语义不同，横向比毫无意义。**
- ⇒ 唯一可比的是 **「按键→下一帧」**，而云影侧原先**根本没有这条埋点**。

### 这次重测拿到的硬读数（云影，同一路 4K，OSD 打开）
| 读数 | 值 | 来源 |
|---|---|---|
| 进程总 CPU | **178%** | `/proc/<pid>/stat` 前后差，4 秒窗口 |
| **主线程（= Dart UI）** | **70%** | `/proc/<pid>/task/<pid>/stat` —— **未饱和，还有 30% 余量** |
| DartWorker 合计 | 2% | 同上（先前 top 里看到的 50%+ 是瞬态/误读） |
| RSS | 747 → **910 MB** | HUD |
| 网络↓ | 1~163 KB/s | HUD |
| HUD | `内核 ExoPlayer` `解码 硬解(直通)` | HUD |

- ⛔ **Flutter 的 Dart isolate 就是 Android 主线程**：`/proc/<pid>/task/*/comm` 里
  **没有 `1.ui`**，主线程名就是进程名。所以「主线程 70%」≈「Dart 代码占 70% 一个核」。
- ⛔ **中继里没有任何 `Isolate`/`compute`**（`local_stream_relay.dart` 全文零命中）：
  上游 TLS 握手、TLS 记录解密、HTTP 解析、分块拷贝**全在 Dart 主线程上**。
  这是「中继吃主线程」的结构性证据，也解释了 10-05 那次 VM service 采样为什么
  命中的是 `secure_socket.dart` / `http_parser.dart`。

### ★ 根因：中继把「起点越界的 Range」回成了「200 + 整文件」
现场日志（`凡人` 4K，3.13 GiB，fid `5cade084…`）：
```
08:54:54.578 读取器 #5：GET /s1（Range: bytes=5014520206-）   ← 问 3.13GiB 的流要第 5.01GB
08:54:54.585 读取器 #5 → 200 bytes 0-3358116481/3358116482    ← 回了整文件从 0 开始
08:54:54.587 播放位置跳到块 0（约 0 MiB）：预取窗口改锚…缓存已清空
—— 之后再无任何日志（>7 分钟），loopback 稳定 2.1 MB/s，画面停在「正在加载…」
```
机制：HTTP 上「对带 Range 的请求回 200」=「我不支持区间，这是完整资源」。
播放器（media3 `DefaultHttpDataSource`）于是**把响应体前 `position` 个字节丢掉**
去对齐它要的偏移；偏移 5.01 GB > 流长 3.13 GiB ⇒ 它把整部片子读完丢掉才报 EOF。
按 2.1 MB/s 算要 ~26 分钟 —— 用户看到的「一直加载」就是这一段。

**为什么以前没人发现**：`parseRangeHeader` 用**一个 `null`** 同时表达
「没要求区间」（→200 整文件）和「起点越界」（→必须 416）。调用方
`clampRange(requested ?? ByteRange(0, total-1), total)` 只能三选一，选了整文件，
于是 416 分支**是死代码**。⚠️ `test/core/http_range_test.dart` 里那条
`'起点超过文件长度返回 null —— 交给 416'` 的**注释写着「交给 416」**，
但调用方从没走到 —— **契约的两半分家**，测试因此一直是绿的。

## ★★★ 原型复测（10-06 10:25~10:34）：「原型 fps 很高」是**指标幻觉**

用户问「为啥 fps 依然只有个位数」+「之前跑原型 fps 很高，帮我再测一下原型，我确认一下」。
**两个问题其实是同一个答案：两边的 `fps` 分母不一样，都不能当流畅度看。**

### 原型确实跑到 100 fps —— 但它自己的视频只有 26 fps
原型真跑起来后的读数（`adb logcat -s KuakeProto | grep 统计`）：
```
片源 3840x2160 · 25.00fps · avc1.640033 · 解码器 OMX.MS.AVC.Decoder
渲染 26.0 fps · 丢帧 0 ｜ 进程CPU 5~12%（折合 4 核 1.2~3.0%）· 内存 124 MB
UI 100~101 fps · 最大帧间隔 10~15 ms ｜ 按键→下一帧 0.3~3.9 ms（n=6）
```
- **同刻 100 fps（UI） vs 26 fps（渲染）** ⇒ 那个 100 不可能是视频。
- SurfaceFlinger 真值印证：`SurfaceView - …kuake.PlayerActivity#0` = **24.9 fps、中位 40ms**。

### ⛔⛔ 那个 100 fps 是「自己驱动 vsync」数出来的，不是性能
`prototype/kuake/…/StatsOverlay.kt`：
```kotlin
override fun doFrame(frameTimeNanos: Long) {
    framesThisWindow++
    ...
    choreographer.postFrameCallback(this)   // ← 第 104 行：自己把自己再排一次
}
uiFps = framesThisWindow.toDouble()
```
回调**每帧重新 post 自己** ⇒ 每个 vsync 都被叫到 ⇒ `uiFps` **永远≈刷新率**。
源码自己的注释（:36-40）也认了：「帧回调是**自续**的…所以它会持续请求 vsync…
**待机时**会让它多烧一点电」。
- **硬证据**：原型还没出第一帧时（`渲染 0.0 fps · 已解码 0`，且
  `--latency` 的 128 帧**全是 0 0 0**，一帧都没上过屏），`UI` 就已经报
  **98~121 fps** 了。
- ⇒ 那个数是**屏幕刷新率**，不是「原生更快」。

### 云影那边为什么是个位数（同一个道理，反向）
`debug_overlay.dart:80,92,142`：`addPersistentFrameCallback` 只数**引擎真的出帧**。
视频在独立 SurfaceView 图层自渲染 ⇒ Flutter 没东西要画 ⇒ OSD 关着报 1~3、开着报 ~10。
**≈「每秒整页 rebuild 了几次」**。（`player_diag.dart:34-39` 早就这么写了。）

### ★★ 写代码时踩到的两个真 bug（都在并发上，**单测才逼出来**）
1. **`releaseIfDrained` 只在消费者路径上 ⇒ 死锁。**
   消费者可能**在生产者还在 `FILLING` 时**就把这一块读干净了 —— 那时 `releaseIfDrained`
   因「还没 SEALED」跳过，而消费者**再也不会回头看这个槽位**（已前进到下一块＝另一个槽位）。
   槽位永远停在 `SEALED`，对应 worker 永远等不到 `FREE`。
   ⇒ 修法：生产者置 `SEALED` 时**必须再查一次**是否已读干净（`sealSlot`）。
   ⛔ 但 `produced == 0`（上游 416 / 立刻 EOF）时**故意不交还** —— 消费者要靠「SEALED 且 0 字节」判 EOF。
2. **EOF 判据用「块号越界」是错的 ⇒ 永久挂起。**
   读完整块后 `readPos` **恰好**落在文件末尾，算出的块号仍是**合法的最后一块**，
   而那一块早已读干净、槽位已交还 ⇒ 判据为假、继续等一个不会再被填的槽。
   实测症状：**线程栈里一个 `cc-range-` 都没有**（8 条 worker 全退休），
   消费者孤零零挂在 `awaitNanos`，CPU 0%，挂 5 分钟以上。
   ⇒ 修法两条：① `pastEnd()` 改用**绝对偏移**（`readPos > limit` / `readPos >= 总长`）；
   ② 加 `workerDone[]` —— 负责该槽位的 worker 已退休 ⇒ 再也不会有字节来 ⇒ EOF。
- 另加：`@get:Rule Timeout.seconds(30)` 兜底，避免以后死锁把整个构建挂住。
- 顺手补的两处健壮性：`openFollowingRedirects`（`HttpURLConnection` 只跟同协议跳转，
  `DefaultHttpDataSource.setAllowCrossProtocolRedirects(true)` 干的事要自己补）；
  上游**短读**（合法但比请求的块短）必须**抛出去重试**，不能当 EOF —— 否则流从这里静默截断。

### ★★ 新发现：暂停后不缓冲 —— 是**后缓冲吃光了字节预算**
现象（15:36:48~15:37:12 密集采样，用户暂停）：
`[控制栏] 01:58 / 1:46:08 · 已缓冲+2s · 速率 0 KB/s · 已暂停 · 已缓冲 2s` —— **30 秒一个字节都不读**。
播放中则是锯齿：`15.35 MB/s → 983 KB/s → 3.00 MB/s → 12.79 MB/s → 0 KB/s`，前向缓冲**始终只有 2~7s**。
- 片源：原画 DV `22.82 GiB / 6368s = 3.67 MiB/s`（`dvhe.05.08`，`OMX.MS.DOLBY_VISION.DVHE.STN.Decoder`）。
- **机制**：`setTargetBufferBytes(48 MiB)` 是「前向 + 后向」**共用**的总预算，而
  `setBackBuffer(30_000, true)` 在后缓冲上保留最多 **30s** 媒体 = 3.67 × 30 = **110 MiB**，
  是总预算的 **2.3 倍** ⇒ 后缓冲把额度吃光，前向只剩 2~7s。
  播放中：播放头前进 ⇒ 旧样本被回收 ⇒ 腾出额度 ⇒ 突然读一批（15 MB/s 突发）⇒ 又满 ⇒ 0 KB/s。
  **暂停时：播放头不动 ⇒ 后缓冲样本永不被回收 ⇒ 分配器恒满 ⇒
  `DefaultLoadControl.shouldContinueLoading` 恒为 false（`targetBufferSizeReached`）⇒ 一个字节都不读。**
  ⇒ 屏幕上是「已暂停 · 已缓冲+2s」卡死。判据：**暂停时速率恒 0 且 `已缓冲` 完全不动**。
- 代码注释**早就预言过**这件事，只是算错了档位：
  「⛔ 但**别给到 60s**……4K 下 60s 就是 165MB，会把 48MiB 的额度全吃光、前向缓冲饿死。
  30s 在超清档下才 4MB，完全放得下。」—— 超清放得下，但**原画 30s = 110MB 同样饿死**。
  ⇒ 10-04 的「48 MiB 上限」与更早的「30s 后缓冲」在**原画档下互斥**，当时没在 4K 原画上暂停过所以没暴露。
- **附带结论**：`maxBufferMs = 120s` 对原画档**不可达** —— 48 MiB ÷ 3.67 = **13.1s** 就是前向能拿到的全部。
  要 120s 需 440 MiB，而 Java 堆只有 192 MiB，**物理上做不到**。
  低码率档（超清 0.31 MB/s，48 MiB ≈ 150s）才是 `maxBufferMs` 先撞到的那个 —— 需求在低码率档下仍成立。
- **待定修法**（已抛给用户选）：后缓冲按**字节**而非秒约束。
  `setBackBuffer(2_000, true)` → 原画后缓冲 7.3 MiB、前向 ~40 MiB ≈ 11s（比现在 2~7s 好得多），代价是回拖 >2s 要重下；
  或 `setBackBuffer(0, false)` → 48 MiB 全给前向 ≈ 13s，但任何回拖都重下。
- **现场可验证**：在**片头 0:00 立刻暂停** —— 那时后缓冲还没积累，若前向能涨到 ~13s 即证实本诊断。

### 磁盘缓冲方案评估（16:00，实测数据）

用户问「能一直缓冲吗？不 OOM 吗？比如写本地磁盘？」

实测（`adb shell df` / `dd`）：

| 项 | 实测值 | 说明 |
|---|---|---|
| 电视 `/data` 可用 | **12 GB**（总 20G，已用 8.3G） | `/dev/block/mmcblk0p37` |
| 内部存储连续写速 | **131.6 MB/s**（200MB/1.593s） | 需求仅 3.85 MB/s，**写盘不是瓶颈** |
| 整集原画体积 | **22.82 GiB ≈ 24.5 GB** | ⛔ **12 GB 装不下一整集** |

- ⇒ 磁盘方案**只能做「滚动缓存最近 N 分钟」**，做不了「整片缓存」。
  12 GB ÷ 3.67 MiB/s ≈ **55 分钟**（若限 6 GB 上限则约 27 分钟）。
- **内存方案的天花板**：48 MiB ÷ 3.67 = **13.1s**（改完后前向能拿到 ~9.8s，改前只有 2~7s）。
- ★ **关键结论：光把 `DefaultHttpDataSource` 换成 `CacheDataSource` 解决不了「暂停不缓冲」**
  —— `CacheDataSource` 仍在 loader 路径上，下游还是 `SampleQueue`，
  队列满了 `shouldContinueLoading` 还是 false。**必须「旁路预取」**：
  独立线程用已有的 `ParallelRangeReader` 顺序读 → 写进 `SimpleCache`，
  播放器的 `CacheDataSource` 只是顺带命中。
- 旁路预取的关键细节（待实施）：
  1. `SimpleCache` 必须**单例**（一个目录只能一个实例），生命周期跟 Application 走；
     放 Activity 里第二个实例会抛 `IllegalStateException`。
  2. 写入方**只留预取器一个**：播放器侧 `CacheDataSource.Factory.setCacheWriteDataSinkFactory(null)`
     —— 只读缓存不写，否则两边争同一个 span 会 `Another writer is already locked`。
  3. 淘汰用 `LeastRecentlyUsedCacheEvictor(N)`，别用 `NoOpCacheEvictor`（会撑爆 12 GB）。
  4. 缓存目录用 `context.cacheDir`（⛔ 别用 `getExternalFilesDir`，会被「清除数据」连带删）。
  5. 预取要有**停止条件**（下到 N 分钟/N GB 就停），别把 12 GB 填满。
  6. `CacheWriter.cache()` 是阻塞调用，放后台线程；`onDestroy` 要 `cancel()`。
- ⚠️ **代价**：持续写 eMMC。按每天看 3 小时原画算 ≈ 41 GB/天写入量，
  对电视 eMMC 寿命是真实影响 ⇒ 要不要上、缓存上限给多少，需用户拍板。

## ★ 16:30~16:40 落地：预取器跟随跳转 + 磁盘层多段显示 + 调试面板三行

用户问「拖了进度条以后，磁盘缓存是否从当前播放位置重新开始？」⇒ **原来不会**。

- 根因：`DiskPrefetcher.nextPositionBytes` **只前进、从不回锚**；`loop()` 里
  「领先太多就等播放头」那段只会**等**、不会**回看**；而且**没有任何 seek 回调**
  通知过预取器。⇒ 往前跳到预取前沿之外后，它继续下**用户刚跳过的那一段**。
- 修法（`DiskPrefetcher.reanchor(positionBytes)`，**只往前锚**）：
  - 由 `Player.Listener.onPositionDiscontinuity(reason == DISCONTINUITY_REASON_SEEK)`
    触发（**唯一**通知点；只认 SEEK，不认 `SEEK_ADJUSTMENT`/`AUTO_TRANSITION`）。
  - 用 `@Volatile pendingAnchorBytes` 登记、由循环在**块与块之间**消费 ——
    ⛔ 不能直接改 `nextPositionBytes`：in-flight 块结束时 `nextPositionBytes = from + actual`
    会把它**覆盖回旧位置**。
  - 同时 `writer.cancel()` + `source.close()` 打断当前块（否则最多等 12 秒）。
    ⚠️ 被打断的 span **不 commitFile**，那部分数据丢弃（最多一整块 = 128 MiB）。
  - `catch` 里靠 `pendingAnchorBytes > 0` 区分「主动打断」与「真失败」，
    打断时**不退避 2 秒**；`sleep()` 也会被锚点提前唤醒。
  - `startLock` 串起 start/cancel/restart：`reanchor` 与线程收工的 `finally`
    都可能看到「有锚点但线程已收工」，各判各的会**同时拉起两条线程**。
- ⛔ **磁盘层必须画成多段**：跳转后盘上是 `[片头,旧前沿] ∪ [新锚点,新前沿]`，
  中间是**真空洞**。画成「从片头连到新前沿」等于骗用户。
  ⇒ 新增 `DiskCachePlan`（纯函数）+ `DiskCacheSnapshot`，数据源是
  **`Cache.getCachedSpans(key)`**（⛔ 不是 `nextPositionBytes` —— 一个点表达不了两段）。
  - `CacheSpan` 里**未提交**的 `isCached = false` 且 `length = C.LENGTH_UNSET(-1)`，
    必须过滤（否则画出「起点在终点右边」的负宽度矩形）。
  - ⛔ 单测抓到一个真 bug：`rangesToRatios` 只写 `totalBytes <= 0.0` 时
    **NaN 会穿过去**（`NaN <= 0` 是 false），最后 `coerceIn` 也拦不住 NaN。
- 顺带修掉一个**同类的误判源**：`速率 0 KB/s · 磁盘 3.3 GiB`（实测日志）。
  播放器几乎总从磁盘缓存命中、不碰网络，而**预取器的流量根本没进计数器**
  （`startDiskPrefetch` 传的是裸 `parallel`）⇒ 用户看到 0 就以为「不缓冲了」。
  ⇒ 改传 `countingParallel`；且**网速只留一个采样入口**（`PlayerActivity.rateSupplier`），
  控制栏 500ms 那一拍负责采样，调试浮层读缓存值 —— 两处显示同一个数。
- **调试面板（`StatsOverlay`）新增三行**：`缓冲 内存`（+Ns / 后缓冲 / **占用 x/y MiB**）、
  `磁盘 本片`（字节 / 段数 / 到 HH:MM:SS / 目录 x/y MiB / 盘剩）、
  `预取`（第 N 块 / 领先 / 上限 / **网络速率**）。
  - ★ `占用 x/y MiB` 是**精确值**：自己建 `DefaultAllocator(true, C.DEFAULT_BUFFER_SEGMENT_SIZE)`
    交给 `DefaultLoadControl.Builder.setAllocator()`（与默认**逐字相同**、行为零变化），
    于是能读 `getTotalBytesAllocated()` —— 那正是 `setTargetBufferBytes` 管的数。
    ⛔ 不这么做就只能「已缓冲秒数 × 估算码率」反推，会跟预算对不上账。
  - `Fmt`（新，纯函数）统一 `time/bytes/speed/mib`：控制栏与浮层**同屏**，
    两边各写一套必然漂移。字节一律 `GiB/MiB/KiB`（1048576 进制）。
- 单测 59 例全过（`DiskCachePlanTest` 26 / `FmtTest` 10 / `BufferPlanTest` 12 / `DiskSpaceTest` 11）。

## ★ 16:47~17:20 线上事故：拖进度条 OOM 崩溃 → 定位 + 修复（真机验证）

### 崩溃事实（`logcat -b crash`）
```
FATAL EXCEPTION: cc-range-5
java.lang.OutOfMemoryError: OutOfMemoryError thrown while trying to throw OutOfMemoryError; no stack trace available
```
伴随 `art`：`Clamp target GC heap from 200MB to 192MB` /
`Alloc concurrent copying GC freed 0(0B) AllocSpace objects, 0(0B) LOS objects, 0% free, 192MB/192MB`。
⇒ **`freed 0(0B)` 是关键**：GC 一个字节都回收不掉，说明那些内存**全部强可达**，
是「瞬时分配速率打满堆」，不是泄漏。

### 根因（证据链）
1. 遥控器 `←→` 是**自动重复**的（约 20 次/秒），而 `seekBy` **每次都真发 `seekTo`**。
   实测一次拖拽 2 秒内发起 **28 次 seek**（日志 `跳转 → 31s/41s/51s/…/301s`，步进 10s）。
2. 每次 `seekTo` ⇒ ExoPlayer 拆掉当前 load、**重开数据源** ⇒ 新建一个
   `ParallelRangeReader`，它 `init` 里**一次性**分配 `slots = Array(8){ ByteArray(2 MiB) }`
   = **16 MiB**。28 × 16 MiB = 448 MiB 的分配churn，而旧数组要等 worker 退出才可回收。
3. ⇒ 堆被打满 ⇒ OOM。**不是解码、不是网络、不是泄漏。**

### ⚠️ 更正一条旧判断：**读取器没有泄漏**
一度以为「启动 33 次 / 关闭 25 次 ⇒ 漏了 8 个」。加了存活计数（见下）后实测：
每次关闭后 `存活 0`、启动后 `存活 1`，**配平正确**。那 8 个只是**采样时刻还在途**。
⇒ ⛔ **判据必须是「存活是否随时间单调上涨」，不是「累计建 vs 累计关」的差值。**

### 修法（`prototype/cloudcine`，已真机验证）
- **`SeekPlan.kt`（新，纯函数）**：`step()` 累加+夹取；`multiplier()`/`acceleratedDelta()` 加速档位。
  - ⛔ 基准必须是**待提交目标**而不是 `currentPosition`（否则「按 10 次只走 10 秒」）。
  - ⛔ 时长未知（`C.TIME_UNSET = -1`）**不能拿去 `coerceIn`** ⇒ 抛 `IllegalArgumentException`。
  - ⛔ 溢出兜底两行：不加会「按快进却翻成负数→夹到 0→跳回片头」。
  - 加速档位（按 20 次/秒估算，2 小时片约 9 秒到底）：
    `0~2s ×1`（**前 2 秒严格不加速**，留给精确落点）`2~4s ×2` `4~6s ×4` `6~9s ×8` `9s+ ×12`。
- **`PlayerActivity`**：
  - 按键只累加 `pendingSeekMs` + `controls.showPendingSeek(target)`（UI 立刻跟手），不 seek。
  - `seekToPosition(target, source)` 是**唯一**落点，`source` 进日志（`触摸`/`快进`）——
    ⛔ 曾经因为日志分不清触摸还是按键，把一个「松手前就提交」误判成别的原因。
  - **提交时机**：`ACTION_UP`（松手）**只把窗口缩短**到 `SEEK_RELEASE_MS = 150ms`，
    **不是立刻提交**。兜底窗口 `SEEK_FALLBACK_MS = 800ms`。
    ⇒ 长按/连点/单击**都只提交一次**；直接提交的话「连点」会退化成 seek 风暴。
  - ⛔ 原窗口 400ms **小于部分遥控器的重复间隔**（约 500ms）⇒ 按住时每按一下提交一次，
    这正是用户说的「**拖动过程中会触发影片进度调整，实际上并没有释放拖动按钮**」。
- **`SeekBarView`**：加 `beginExternalScrub()/endExternalScrub()`（遥控器快进时屏蔽 ticker 回写）。
- **`ParallelRangeReader`**：加 `created/live` 计数，启动/关闭日志尾追 `累计建 N · 存活 M`。
- **`AndroidManifest.xml`**：加 **`android:largeHeap="true"`**。
  本机 `heapgrowthlimit=192m` / `heapsize=512m` / `low_ram=true` ⇒ 上限 192 → **512 MiB**。
  ⚠️ 副作用可控：`bufferBytes = min(heapMax/4, 64 MiB)` 从 48 → **64 MiB**（有上限封顶）。
- **`seekToRatio` 的 `inBuffer` 恒真 bug 已修**：`bufferedPosition` 必须在 `seekTo` **之前**读
  （之后会被夹到 ≥ target ⇒ 恒真 ⇒「磁盘缓存命中」那支成死代码）。真机已确认日志能正确说
  「两处都没命中，需缓冲」。

### 实测结果
- 20 次连点 → **1~2 次提交**（原来 20 次）；`存活` 全程 1，无堆积；**无崩溃**。
- `Java 堆 94/512 MB` 稳态；`渲染 61 fps · 丢帧 3`（杜比视界 4K 原画）。

### ★★ 磁盘缓存**跨会话不可复用**（用户提问，已用实验证实）
**结论：不能。重启后同一部片 `磁盘 本片 0 B`，而盘上有 4.9 GB 缓存。**
- 实验：记录 `本片 972 MiB · 8 段`（61 个 span 文件）→ `am force-stop` → 重开 → 播同一部片
  ⇒ `磁盘 本片 0 B`，且缓存目录**多出两个全新的键前缀**（`13`/`14`，原来只有 `2~12`）。
- 机制：`CacheKeyFactory.DEFAULT` 的键 = **URI 字符串**；而 `api.resolve(fid)` 每次起播都
  重新取一次夸克直链（**带签名的临时地址**）⇒ URI 变 ⇒ 键变 ⇒ 旧数据**一个字节都命中不了**。
- 文件命名可直读键：`<哈希>.<位置>.<uid>.v3.exo`，分片目录 = 哈希首字符；
  预取器写的位置都是 **128 MiB 的整数倍**（`CHUNK_BYTES`），可直接据此辨认。
- **修法（待用户批准，未动）**：给 `CacheDataSource.Factory().setCacheKeyFactory(...)` 与
  `DiskPrefetcher` 注入**稳定键** `"quark:<fid>:<quality.id>"`。
  ⛔ **必须带画质档 id**：原画与转码档是**不同的字节流**，只按 `fid` 做键会**串数据**（解码出乱码）。
  ⛔ 这样会让现有 4.9 GB 缓存全部失效（键变了），属预期。
