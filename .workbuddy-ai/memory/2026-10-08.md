## 修 CI：`folder_browser_test.dart` 3 条用例红（PC 端 Flutter）

**现象**：`flutter test` 里 `test/ui/widgets/folder_browser_test.dart` 的「点了就播」那一组
3 条红（另 2 条绿）。报错栈指向 `play_action.dart:179` 的 `ref.read(mediaRepositoryProvider)`，
抛的是 `UnimplementedError: appSupportDirProvider 必须在 main() 里用 ProviderScope.overrides 注入`。
表现极具误导性：**点一下行就抛异常、页面根本没导航**，于是下游断言报「找不到 `播放页：…`」，
看失败信息完全看不出缺的是测试的 override。

**真因**：`d7be641`（跨环境同步播放进度）把进度写透接进了仓储 ——
`mediaRepositoryProvider` 现在 `progress: ref.watch(progressStoreProvider)`，
而 `progressStoreProvider` 挂在 `appSupportDirProvider` 上（后者在 `main()` 之外一律抛）。
`pumpBrowserWithRouter` 只 override 了 `databaseProvider`，没补这一项。
`pumpBrowser`（前 4 条用例）不受影响，因为那几条不点行 ⇒ 不碰仓储。

**修法（测试侧，最小改动）**：`pumpBrowserWithRouter` 的容器里加
`mediaRepositoryProvider.overrideWithValue(DriftMediaRepository(db))`。

- 为什么不用 `appSupportDirProvider.overrideWithValue(tempDir)`：那会挂上一个**真的
  `ProgressStore`**，`markPlayed` → `recordPlayed` → `_markDirty()` 留下一个 2 秒防抖
  `Timer`，测试结束时那个挂着的 Timer 会让用例以「A Timer is still pending」失败。
- 为什么不改生产代码：`appSupportDirProvider` 在生产里恒被注入，抛异常是刻意的；
  且 `DriftMediaRepository` 的 `progress` 本就**可空**，类文档明说
  「单测里大量用例只关心库本身，不该被迫造一个进度文件」。
- 同款先例：`settings_page_test.dart` / `tv_pages_layout_test.dart` 也是
  `mediaRepositoryProvider.overrideWithValue(DriftMediaRepository(db))`。

**验证**：`flutter analyze` = No issues found；`flutter test` 全量 **2529 passed / 0 failed**；
单跑该文件 8 passed。

### 百度两条路线（关键约束，已查官方文档 + AList）
| | 官方开放平台 OAuth | 自用 Web 接口（BDUSS） |
|---|---|---|
| 前置 | 需注册应用 + 审核 | 无 |
| 可访问范围 | **默认只有 `/apps/{应用名}/`**；权限外目录禁访问 | 全盘 |
| 频率 | 未过审 **10 次/小时**、10 用户；过审白名单制 | 有风控，自用无硬限 |
| 直链 | `xpan/multimedia?method=filemetas&dlink=1`，**8 小时** | `/api/download?sign=&timestamp=&fidlist=` |
| 与夸克同构度 | 低（token 模式） | **高**（cookie 模式，AuthMode 全复用） |

- ⛔⛔ **官方 dlink 必须带 `User-Agent: pan.baidu.com`**，否则 `31326` 命中防盗链；
  AList 实测**下载 >20MB** 就要带。官方文档另说 >50MB 不允许浏览器直接下（需原生 App）。
- ⛔ AList 已把**非官方 Crack 接口标记为「似乎已无法使用」**，且报 `31119`/`31329`
  「hit black userlist」⇒ 百度直链比夸克脆弱得多。
- ⛔ 官方接口**非会员限速**（AList 原话「速度慢 (SVIP 速度快)」）⇒ 这是**产品级硬风险**。
- 上传：**30s 内必须完成单分片**、不允许空文件、上传域名要动态获取。

### 设计要点
1. **ID 语义不对称（最容易埋雷）**：夸克 `listDirectory(fid)`，百度 `listDirectory(dir=path)`；
   而 `scan_service.dart:396` / `media_discovery.dart:404` 传的是 `dir.id`。
   → 给 `listDirectory` 加**可选** `dirPath` 参数（扫描器已有 `dir.path`，见 `PendingDir`），
   夸克忽略、百度用它。`DriveEntry.id` 百度用 `fs_id`（取直链 `fidlist=[fs_id]` 需要它，主键才稳定）。
2. **推荐主链路 = BDUSS 自用接口**（与夸克同构、零前置、能扫全盘）；官方 OAuth 仅适合
   「把 `.ccbak` 写进 `/apps/`」这类受限场景，且配额也不够。
3. **转码档**（**已解决，见下方逆向结论**）：夸克有 `video_list` 多档（4K 卡顿的解药）；百度 web 也有，
   入口 `/api/batch/streaming?check_blue=1&type=<档位>`，档位枚举 `360P=0…4K=5/帧彩映画=6`，
   但**切档是超级会员特权**、非会员默认锁 480P ⇒ 播放策略要按会员等级分流。
4. **登录**：百度走 passport `getqrcode` → `unicast` → `qrbdusslogin`（与夸克 CAS 完全不同的链路）；
   兜底用 `AuthMode.manualCookie` 粘贴 `BDUSS`/`STOKEN`/`bdstoken`。

## 逆向百度网盘 Mac 客户端：授权方案 + 扫码可行性（**仅调研，未动代码**）

**问题**：逆向百度网盘 App，最佳授权方案是什么？是否支持扫码授权？
**结论**：**支持扫码，而且有两套完全独立的扫码方案，均已实测存活。但「官方扫码」受目录限制，对本产品不可用；「客户端同款 BDUSS 扫码」才是可用路线。**

### 取证方法（可复用）
- 官方下载配置接口（**公开、免登录**）：`GET https://pan.baidu.com/disk/cmsdata?do=client`
  → JSON，键 `mac` 即当前 Mac 客户端（**实测 = V8.8.8**，463.6MB，
  `https://pkg-ant.baidu.com/issue/netdisk/MACguanjia/8.8.8/BaiduNetdisk_mac_8.8.8_x64.dmg`）。
  ⛔ 旧路径 `issuecdn.baidupcs.com/issue/netdisk/MACapk/BaiduNetdisk_mac_4.48.2.dmg` 已 302→403；
  ⛔ 直连 pkg-ant 不带 `Referer: https://pan.baidu.com/download` 会回 **`31326 anti hotlinking`**。
- asar 解析用自写脚本（Chromium pickle 头：`[UInt32 4][UInt32 size]` 外层 +
  `[UInt32 paddedSize][UInt32 jsonLen][json]` 内层，**4 字节对齐**）；踩坑过程见当日会话。
- 8.8.8 的 JS 在 `Contents/Resources/core.asar`（`renderer.js` / `main.js` / 编号 chunk），
  `app.asar` 主要是 `node_modules`。
- ★ **接口 URL 的找法（可复用，别直接搜 URL）**：客户端全部接口走 `Ad(key)` = `getUrlbyKey`：
  先查远程配置 `app.$getAppConfByKey("url", key)`，兜底查**内置表**
  `{[常量]:\`https://${host常量}/api/…\`}`，host 来自 `{host_pan:"pan.baidu.com", host_d_pcs:"d.pcs.baidu.com",
  host_wenku:"wenku.baidu.com", …}`。**常量名与 URL 是分离的** ⇒ 正确姿势 = 先搜
  `常量="方法名"` 拿到短名（如 `Mi="video_preload"`），再搜 `` `[Mi]:` `` 拿 URL，两处对齐。
  ⚠️ 同一个短名（`Ad`/`kd`/`vt`）在**每个 chunk 里都是重新分配的**，不能跨文件套用。

### ★★ 结论 1：官方开放平台「设备码模式」= 官方认证的扫码方案，实测存活
- `GET https://openapi.baidu.com/oauth/2.0/device/code?response_type=device_code&client_id={AppKey}&scope=basic,netdisk`
  （**需 `User-Agent: pan.baidu.com`**）→ 实测返回：
  `{device_code, user_code, verification_url:"https://openapi.baidu.com/device",
    qrcode_url:"https://openapi.baidu.com/device/qrcode/<id>/<user_code>", expires_in:300, interval:5}`
- `qrcode_url` **实测返回 1000×1000 真 PNG**（1-bit grayscale）；二维码内容按文档规则拼
  `https://openapi.baidu.com/device?display=mobile&code={user_code}`。
  文档原话：「用户授权有两种方式：一种是**扫描二维码方式**，另一种是输入用户码方式」。
- 轮询换 token：`GET https://openapi.baidu.com/oauth/2.0/token?grant_type=device_token&code={device_code}&client_id={AppKey}&client_secret={SecretKey}`
  **间隔必须 ≥5s**；返回 `access_token`（30 天）+ `refresh_token`（**有效期 10 年**）。
- 刷新：`grant_type=refresh_token&refresh_token=&client_id=&client_secret=`。
  ⛔ `refresh_token` **单次有效**，刷新后必须换用新值；刷新失败则旧值作废 ⇒ 只能重新授权。
- 端点行为已刻画：垃圾 `client_id` → `{"error":"invalid_client"}`（**确实校验应用身份**，
  文档里的示例 AppKey `EVaI5x0U6lEmP125G0Su55ROEXZtItdD` 是真实注册应用）；
  错 `response_type` → `{"error":"invalid_response_type"}`；**缺 `scope` 也能成功**。
- ⛔⛔ **致命限制（官方文档 2026-08-03 更新，原文）**：「为进一步保障用户网盘数据安全…**2026年6月3日后
  在平台创建的应用**，以下接口**仅支持访问 `/apps/{appname}` 目录下的文件**：
  `xpan/file?method=download`、`xpan/multimedia?method=listall`、`xpan/file?method=filemanager`、
  `xpan/file?method=precreate`、`xpan/file?method=meta`、`xpan/file?method=move`」。
  下载文档另有总括句：「第三方应用在网盘**只能拥有一个文件夹**用于存储、上传和下载文件，该文件夹必须位于
  `/apps` 目录下」；`check_blue=1` 固定值 = **开启路径合规校验**，错误码 **`20011` 路径不在允许访问范围内**。
  ⇒ **官方路线拿不到用户媒体库里既有文件的直链**（`list` 未列入名单、但 `list` 的错误码 `-7` 也写了「应用目录范围」，
  存在口径不一致，落地前必须实测）。个人认证应用限 **10 个用户**、只给 **1 个应用**。
- 其他实测/文档要点：`dlink` **必须拼 `&access_token=`**、**必须 `User-Agent: pan.baidu.com`**（否则 `31326`）；
  `dlink` **8 小时**过期（`31360`，可重试）；`31362` = 签名错误（**不许截断 dlink**）；
  **>50MB 不允许浏览器直接下**（需原生 App）；支持 `Range`（可 seek）；错误码 `-6` 未登录 / `-7` 无权 / `-9` 不存在。

### ★★ 结论 2：Mac 客户端（8.8.8）的登录 = 扫码，而且**只有**扫码

### 关键设计决定（附理由）
- **`extends` 而非 `implements`**：基类默认实现表达「此能力可能不支持」，写 4 个抛异常的壳是噪音。
- **路径缓存 `_pathByFsId` 而不是改契约**：百度的目录标识是**路径**（`dir=/电影`），而契约用的是 id。列表响应自带 `path` ⇒ 父目录列表顺手收下子项路径，BFS 先父后子 ⇒ 命中率≈100%；未命中回退一次 `filemetas`。**改契约要动 8 个测试替身**，不值。
- **`activeDrive` 单一真源**：原先 6 处散落硬编码 `DriveProvider.quark`。接第二家网盘时漏改一处的表现是「登录成功了，但列表/扫描/播放还在问夸克」——**不报错，只是空**。落库到 `SettingKeys.activeDrive`，用 `AsyncNotifier`（不在 `main()` 里读，避免再加一条「必须在 main 里 override」的隐式约定——已经有两条了：数据库、app-support 目录）。
- **authorize→切网盘的重建竞态**：`_handoffAccount`/`_handoffProvider` 单槽位，避免切换触发 rebuild 时短暂回到 `loading`（路由会闪一下启动页）。`signOut` 里清掉，防止已登出的账号被复活。
- **驱动必须是工厂不是 `family`**：`family` 会缓存实例 ⇒ 第二次进页面复用旧 `sign`。
- **诊断行 `reveal` 参数化**：脱敏责任放驱动里，而不是页面里一句口头约定。泄漏形态是「用户截图里的凭证」。

### 扫码三跳的坑
- `channel_v` 是**被二次编码的 JSON 字符串**，不是对象。当 Map 用 ⇒ `status` 永远 null ⇒ 现象「扫码确认了但页面一直转圈」而**不报错**。
- 长轮询无事件时挂约 30 s，HTTP 超时走 `isNetworkFailure` ⇒ **必须映射成 `Waiting` 而不是失败**（否则页面「连续失败 3 次报错」在用户还没掏手机时就触发，而百度取码**有次数限制** `errno=50000`）。
- `status`：`1`=已扫待确认（**只有百度有这一态**）、`0`=已确认、`2`=取消。
- 换票判据 `errInfo.no == 0 || data.errno == 0`；凭证在 `Set-Cookie: BDUSS=` ⇒ ⛔ **不跟重定向**。v5 失败降 v4；`400023` 风控**不降级**（换路由只会掩盖真实错误）。
- ⛔ 原画哨兵**必须**用 `kOriginalQualityId`（`'origin'`）。写错 ⇒ `QualityLabels.isOriginal` 静默 false ⇒ 默认播转码流而**不报错**。

## Bug：`添加百度网盘` 点下去没反应 / 看不到二维码

**现象**（日志 `cloudcine-2026-10-08.log`，用户已连夸克）：点了「添加百度网盘」页面不切到授权页、看不到二维码；日志里**完全没有**百度或任何扫码取码的 HTTP 请求。

**真因**：`lib/ui/router/app_router.dart` 的 `redirect` 里有一行单网盘时代留下的守卫：
`if (authorized && atAuth) return '/library';`。
`atAuth = location.startsWith('/auth')`，而「添加百度网盘」走的是 `/auth/qr?drive=baidu`。
用户已连夸克 ⇒ `isAuthorized == true` ⇒ 导航一发起就被这条 redirect 弹回 `/library`，
授权/扫码页根本没机会渲染，自然也没有取码网络请求。**这正是「点了没反应」的根因**。

## Bug：百度扫码页打开了，但二维码图片加载失败

**现象**（接上一步修完路由之后）：进得去 `/auth/qr?drive=baidu` 了，页面拿到
`sign` / `gid` / `imgurl`，但 `_loadQrImage` 抛错（被页面 `catch (_)` 静默吞），
结果框里显示「二维码加载失败，点击重试」。
日志里 `GET(bytes) ://passport.baidu.com/v2/api/qrcode → 请求未完成` —
注意 URL **没有 `https` scheme**（对比能成功的 `GET https://passport.baidu.com/v2/api/getqrcode`）。

**真因**：`BaiduQrLoginClient.start()` 在补 scheme 时只判
`imgRaw.startsWith('//')`，但百度 `getqrcode` **实测**返回的 `imgurl` 是
`passport.baidu.com/v2/api/qrcode?sign=…`（**没前导 `//` 也没 scheme**）——
旧代码漏判 ⇒ `Uri.parse` 得到一个没 scheme 的 URI ⇒ `getBytes` 拿不到 host ⇒ 请求失败。
测试夹具 `baidu_qr_login_test.dart:148` 当时用的 `//passport.baidu.com/…` 形
态与真实响应**不一致**，所以单测全绿、生产炸。

**修法**：
1. `baidu_qr_login.dart`：抽出 `_normalizeImgUrl(raw)`，先 `Uri.tryParse` 判
   `hasScheme`；没 scheme 的两种形态（`//host/...` / `host/...`）统一补
   `https://`。`BaiduQrSession.imgUrl` 的注释也同步更新成「两种形态都见过」。
2. `baidu_qr_login_test.dart`：`qrOk` 改用**实测主形态**
   `passport.baidu.com/...`（无 `//`），新增 `qrOkProtocolRelative` 保留对
   `//host/...` 的兜底测试。原先那条「协议相对补成 https」改名为
   「host 相对补成 https（实测主形态）」。
- 验证：`baidu_qr_login_test` + `baidu_adapter_test` + `auth_qr_login_page_test`
  **87 例全过**；`dart analyze` 干净。未提交。
