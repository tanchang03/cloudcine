## 12:2x · 修 Windows MSI「需要 Windows 10 或更高版本」误报（只改 1 行判据）

用户报：「windows 安装包在 windows 11 上安装时提示需要 windows 10 或更高版本」。

### 根因：不是包坏了，是判据写反了

`windows/packaging/cloudcine.wxs:59` 的启动条件是 `VersionNT >= 1000`。
**Windows Installer 把 VersionNT 钳在 603**（= Windows 8.1），Windows 10 与
Windows 11 上读出来都是 **603** —— 于是 `>= 1000` 在**任何**真实 Windows 上都不成立，
这条 LaunchCondition **永远失败**：不是「Win11 特别装不上」，是**谁也装不上**
（Win7=601 / 8.1=603 / 10=603 / 11=603，全都 `< 1000`）。

- 出处 1：微软 **KB3202260**《VersionNT value for Windows 10, Windows Server 2016,
  and Windows Server 2019》——「the VersionNT value is 603 … This version numbering
  is by design. To maintain compatibility…」。
- 出处 2：**Advanced Installer** 文档（qa-OS-dependent-install）——「By default,
  Windows 10 and Windows 11 set the VersionNT property to 603」；他们家自己的包会把它
  改写成 1000 / 1100，那是**安装包生成器额外做的**，裸 WiX 没有这一步。
- 对照：**WindowsBuild 是真实构建号、不被钳制** —— Win7=7601 / 8.1=9600 /
  10=10240 起 / 11=22000 起。`WindowsBuild >= 10240` 恰好等价于「Windows 10 或更高」。

### 改动

`windows/packaging/cloudcine.wxs` 一行：

```
- <Condition Message="…">VersionNT &gt;= 1000</Condition>
+ <Condition Message="…">Installed OR WindowsBuild &gt;= 10240</Condition>
```

- `Installed OR` 是必须的：启动条件在**所有**安装模式下都会被求值（含维护/卸载），
  少了它，已装好的机器在卸载时会被自己这条条件挡住。
- ⚠️ **MSI 条件语法不支持括号**，多条件只能靠优先级 —— 比较运算符优先于 OR，
  这个写法没有歧义（别顺手加括号，那会让 candle 报错）。
- 顺手把那段的注释扩写成「为什么不能写 VersionNT」+ 两处出处（这文件本来就是
  注释密度很高的风格）。
- **没改提示文案**（「需要 Windows 10 或更高版本」本身是对的），也没动 `build_package.ps1`。

- ✅ 已做：解析 `cloudcine.wxs` 确认 XML 仍良构、条件表达式与文案按预期（python 校验）。

## 23:15 日志分析：切换影片经常卡死 / 显示播放报错（`logs/cloudcine-log-android-20261005-231252.txt`）

`local_stream_relay.dart` 的 `_fetchChunk` 是「整块读完才 `cache.put` + `_settle`」，

同一份日志里的 A/B 证据（同机、同批 4K 片源、同引擎同路径，只差块大小）：

| | 2 MiB（≤22:17） | 8 MiB（≥22:55） |
|---|---|---|

| 结果 | 连续播 8~13 分钟（20:14/20:30/20:40/20:53/21:02） | **零成功**，每次 `Source error` → 回退 → `Failed to open` |

`会话开始` = 新进程：23:04:51、23:11:30，**6.7 分钟内两次**，与用户「卡死崩溃」吻合。

1. router 切到 ExoPlayer 时日志写的是「切到 **fvp（libmdk）** 内核」
   （`playback_engine_router.dart:199` 文案写死）—— 排查时会被带偏，我自己就被带偏过一次。

### 为什么是**独立工程**而不是云影里加个 Activity
只要 Flutter 引擎还在同一进程，「每秒 10 次整页 rebuild」这个变量就撇不干净 ——
而它恰恰是要验证的对照组。所以 `prototype/kuake/` **不引 Flutter、不引云影任何代码**。

  ⛔ 故意去掉三样：圆角**裁剪**、blur 阴影、隐式动画 —— 这三样就是要验证的差异。

### 构建踩的坑（都记下来了）
1. **首次构建必须联网**：Media3 1.5.1 的两条传递依赖不在本机缓存 ——
   `androidx.annotation:annotation-jvm:1.6.0`（新版 KMP 命名，缓存里只有老的
   `annotation` 1.2/1.3/1.5/1.6/1.8/1.9）与 `androidx.lifecycle:lifecycle-runtime:2.3.1`。
   `--offline` 会卡在 `:app:checkDebugAarMetadata`。拉过一次后 `--offline` 才行。
2. **Media3 1.5.1 的 `DecoderCounters` 计数器全是 `int` 不是 `long`**，且
   **没有 `inputBufferCount` 字段**（那是 ExoPlayer 2.x 的名字）—— 用
   `javap androidx.media3.exoplayer.DecoderCounters` 实测得到：`renderedOutputBufferCount`
   / `droppedBufferCount` / `queuedInputBufferCount` 都是 `public int`。
3. `StreamSpec.fromIntent` 里写成 `intent?.getStringExtra(...)` 之后，编译器只能推出
   「url 非空」推不出「intent 非空」→ 必须**先** `if (intent == null) return null`。
4. `KeyEvent.ACTION_MULTIPLE` 已 deprecated，且遥控器长按在 TV 上是一串独立
   `ACTION_DOWN` → 只认 `ACTION_DOWN`。
5. ⚠️ **同一文件的多条 Edit 并行发会互相覆盖**（三条 Edit 只有最后一条落盘，
   前两条静默丢失、工具还报成功）。→ **同文件必须串行改，改完 `sed -n` 复核。**

### 补：取流的「公平对照」协议（查证后写进 README 第三节）
原型要从中继取流，而**中继跑在云影进程里**，所以两边会互相干扰。查证结论：
- ⛔ `PlaybackController._releaseRelay()` **只在 `dispose()` 里调**（`:1628`），
  `stop()` 不碰它（`:1113-1148`）⇒ 暂停 / 停止 / 切后台**都不会**关中继会话。
- Android 上**退出播放页会调 `stop()`**（`player_page.dart:721-724`，
  `PlaybackExitBehavior.stopAndRelease`）→ 释放 4K 解码器、关掉 mpv 的连接。
- ⇒ **正确协议：按返回键退出播放页，再拉起原型。**
  ⛔ 不能「一边播着一边切」（两边同解一路 4K，CPU/丢帧全被污染）；
  ⛔ 也不能「暂停后切」—— mpv 的 HTTP 读取器**还挂在会话上**，而预取锚点由
  「最新到达的、范围够长的读取器」决定（`relay_reader_arbiter.dart:104/109`），
  锚点会被按在云影的暂停位置，原型的预取跟着跑偏。
- 端口来自 `HttpServer.bind(loopbackIPv4, 0)`（`:204`）**每次启动都不同**；
  token 是 `s1`/`s2` 递增序号（`:162/178`）。日志那行 `｜入口 $uri` **逐字可用**。
- ⛔ **诊断页的「中继状态」面板看不到入口 URL** —— `RelayStats` 里不含 uri，
  公开成员只有 `configure/open/statsOf/primaryContentLength/close/dispose`。
  所以电视上只能去**诊断页的日志**里读那行。
- 中继判「谁在放片子」的阈值 = `prefetchChunks × chunkSize` =
  **128 × 2 MiB = 256 MiB**（`:64/784`）。ExoPlayer 的 Range 短于此只会被当
  「探索引」：请求照样立刻被服务（规则 ④）但**不推动预取窗口**。
  只要云影的读取器已退出，规则 ⑤ 仍会让原型接管锚点。
