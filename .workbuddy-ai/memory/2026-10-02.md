### 现象
设置页点「上传备份」失败：
`DriveException(unknown, code=43001, http=400, 完成上传: request cpp error[complete file failed!])`

日志（`~/Library/Application Support/com.cloudcine.cloudcine/logs/`）显示：
pre → hash → 3 片 PUT 全 200（ETag 都拿到了）→ `/file/upload/finish` → **400**。

### 根因
夸克的上传收尾是**两步**，上一版只做了第二步（而且第二步的参数也错了）：

1. **向 OSS 提交 `CompleteMultipartUpload` XML**（带 `x-oss-callback`）——
   让对象存储把分片真正合并成一个对象；
2. **再调 `/1/clouddrive/file/upload/finish`**，body 只要 `{task_id, obj_key}`
   —— 通知夸克把该对象登记成文件。

只做第 2 步 → 服务端找不到可合并的对象 → `43001 complete file failed!`。
上一版还把 finish 的 body 写成了 `{task_id, part_info_list}`（错的字段）。

### 两条「错了不报错」的细节
- **ETag 在 XML 里必须带双引号**：`<ETag>"abc"</ETag>`。OSS 要求原样回填
  PUT 响应里的值（含引号），不带引号会被判成分片不匹配。
- **分片必须按 `part_number` 升序**排列。

两者都做进纯函数 `QuarkAdapter.buildCompleteMultipartXml`，用 6 例测试钉死
（`test/data/quark_upload_complete_test.dart`）。

### 参考实现
`RemyYYZ/QuarkPan`（Python，58 commits）的
`complete_multipart_upload` + `finish_upload` 两步法，与
`imeiming/quark-drive` 的 OSS callback 写法一致。
`file/upload/auth` 的 `auth_meta` 字段顺序必须与真实请求头一致，签名才算得对：
```
POST\n{contentMd5}\napplication/xml\n{ts}\n
x-oss-callback:{cb64}\nx-oss-date:{ts}\nx-oss-user-agent:...\n
/{bucket}/{objKey}?uploadId={uploadId}
```

### 新增 `HttpClientLike.postBytes`
`putBytes` 只够分片；完成合并要 POST 原始 XML，所以加了 `postBytes`
（`DioHttpClient` 实现，返回响应体字符串）。6 个测试替身都补了空实现。

## 修复：缓冲时显示「≈1.0 GB/s」（口径错误，不是单位换算）

现象：缓冲浮层的网速经常跳到 1 GB/s，而用户带宽远不到。

结论：**换算链每一环都是对的** —— media_kit `real.dart:1544` 的秒→微秒、
`倍速 × (体积÷时长)` 的量纲、`formatBytes` 的 1024 进制字节，全部正确。
错的是**测的位置**：

- media_kit 硬编码 `cache=yes` / `cache-on-disk=yes`（`real.dart:2400-2401`），
  于是 mpv 的缓存是**两层且互相解耦**的：
  `网络 → stream cache（字节，后台预读）→ 解复用 → demuxer cache（秒）`。
- 界面只能量到第二层 `demuxer-cache-time`，而它的数据来自**本地**
  （内存，或 `cache-on-disk` 的落盘文件），速度是 CPU / 磁盘量级 ——
  一次几百 MB 的块填充几十毫秒就能灌完，换算出来就是 GB/s。
- 我们又设了 `demuxer-readahead-secs=9999`，demuxer 一路往前冲，加剧了这个现象。
- 两个放大项：`CacheSpeedMeter._minSpanSeconds=0.4` 允许 0.4 秒的跨度（块填充直接成尖峰）；
  `_cacheRate` 在 `rate == null` 时**保留旧值** ⇒ 尖峰被**冻结在界面上**，
  这才是「经常看到」的直接原因。
- 反证：40 Mbps 原画要算出 1 GB/s，8 秒窗口内 `demuxer-cache-time` 得涨 1640 秒
  ≈ 8.2 GB，而缓存上限只有 1 GB ⇒ 不可能，故必然是窗口退化成了两点差分。

修复（4 文件，243+ / 23-）：

1. `PlayerBufferConfig.disableStreamCache = true`：`apply()` 里在 `open()` **之前**
   `setProperty('cache','no')`，让 demuxer 直接吃网络 ⇒ 测出来的才等于真网速。
   安全性：夸克原画是支持 Range 的 seekable HTTP、转码档是 HLS，都不需要 stream cache 回读；
   `bufferSize`(1 GB) 同时给 `demuxer-max-bytes` / `-back-bytes`，回看与抗抖动照旧；
   还省掉一层 1 GB 的字节缓存。
   ⚠️ **待真机实测**：若开播变慢或 seek 后重新缓冲，把 `disableStreamCache` 改回 `false`
   （代价只是网速重新变成估算值）。
2. `CacheSpeedMeter._minSpanSeconds` 0.4 → 1.5（挡住块填充尖峰）。
3. 新增纯函数 `cacheBytesPerSecond()`（与 meter 同文件）：换算 + 护栏
   `defaultMaxCacheBytesPerSecond = 256 MB/s`（≈2 Gbps；超过就返回 null = 这一拍不显示速度）。
4. `player_window_app`：新增 `_cacheRateAt` / `_currentCacheRate`（5 秒过期，不再冻结尖峰）；
   `_cacheBytesPerSecond()` 改为委托纯函数。

测试：`test/domain/cache_speed_meter_test.dart` 15 例（原 9 + 新 6）；
全量 `flutter test` **1050 例全过**（与上面那次同数，说明我的 6 例已含在里面）。

### 追加：网速改成直接读 mpv（不再估算）

上面那版还是「估算 + 护栏」。查证后发现有更好的源：

- **`NativePlayer.getProperty` / `observeProperty` 其实是公开的** —— HOWTO 里

## 教训：不要对仓库文件跑 `dart format`

## 修复：同步的新旧判定拿错了时间（读代码发现，不是测试报的）

### 症状（潜在数据丢失，尚未被用户撞上）
新机器装好后点「同步」，**会把远程那份好备份覆盖掉**；本地空库也照样「胜出」。

### 根因
`BackupManifest` 只有 `createdAt`（**备份包被创建的时刻**），旧 `sync()` 拿它比大小
⇒ 刚导出的包时间戳永远最新 ⇒ `localNewer` **恒为 true** ⇒
**同步永远只会「上传」，永远不会「下载」**。

### 修法（4 文件）
1. `library_backup.dart`：`BackupManifest` 加 `libraryModifiedAt`（可空）；
   派生 `effectiveModifiedAt => libraryModifiedAt ?? createdAt`、
   `hasLibraryContent => libraryModifiedAt != null`；`isNewerThan`/`conflictsWith` 改用它；
   `toJson`/`fromJson` 处理新字段。
2. `media_repository.dart`：抽象加 `Future<DateTime?> latestLibraryChangeAt()`；
   `InMemoryMediaRepository` 实现（空库返回 null；取 `updatedAt`、
   `lastPlayedAt ?? firstSeenAt` 的最大值）。
3. `media_repository_impl.dart`：用 drift 聚合实现
   （`mediaWorks.updatedAt.max()` / `mediaItems.firstSeenAt.max()` / `mediaItems.lastPlayedAt.max()`）。
4. `library_backup_service.dart`：`exportBackup` 把 `modifiedAt?.toUtc()` 写进 manifest；
   `sync()` 重写 —— 先判两个「空」守卫，再判冲突，最后比 `effectiveModifiedAt`。

## 补测：上传的**编排**（原先只有 XML 形状的测试）

### 为什么补
`quark_upload_complete_test.dart` 只钉 XML 的**形状**；真正出 43001 的是**编排**
（谁先谁后、每个端点收到什么 body）。这类错误**不抛异常、只静默失败** ——
而上传是「用户点一下、结果只有成/败」的路径，没有测试就只能靠真机撞。

### 新文件 `test/data/quark_upload_flow_test.dart`（7 例）
假 `HttpClientLike` 按 `post` / `putBytes` / `postBytes` **三类分别记账**，断言：
- `post` 路径序列必须是 `pre → hash → auth×N → auth(合并) → finish`；
- `finish` 的 body **恰好**是 `{task_id, obj_key}`，且**不含** `part_info_list`；
- 分片 PUT 的 `partNumber` 升序、每片带 `Authorization`；
- OSS 合并**必须发生一次**，带 `x-oss-callback` / `Content-MD5` / `Content-Type: application/xml`，
  XML 里 ETag 重新带上双引号、PartNumber 升序；
- 秒传命中（hash `finish=true`）→ 直接返回 fid，**零** PUT、**零** OSS 合并；
- 缺 `bucket`/`obj_key`/`upload_id` → 动分片**之前**就抛 `malformedResponse`；
- 缺 `callback` → 合并阶段抛错（不是静默成功）；
- `onProgress` 逐片递增、末次等于总大小。

`part_size` 由用例给（默认 4 字节），所以 10 字节的小文件就能造出 3 片，
不必真造 MB 级数据。

### 按项目约定验了「测试不空转」
临时把 `finish` 的 body 改回旧 bug（`part_info_list`）→ 测试**确实变红**
（`+0 -1`，diff 显示 `Actual: {'part_info_list': [...]}`），随即还原并确认全绿。
这说明断言不是恒真的摆设。

### 顺手修了一处**会误导人**的文档
`QuarkEndpoints.uploadFinish` 的注释还写着「请求体：`{task_id, part_info_list}`」——
正是 43001 的成因。改成 `{task_id, obj_key}` 并注明「不是 part_info_list」，
免得下次有人照注释「修回去」。
