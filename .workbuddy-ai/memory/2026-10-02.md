### 现象
设置页点「上传备份」失败：
`DriveException(unknown, code=43001, http=400, 完成上传: request cpp error[complete file failed!])`

日志（`~/Library/Application Support/com.cloudcine.cloudcine/logs/`）显示：
pre → hash → 3 片 PUT 全 200（ETag 都拿到了）→ `/file/upload/finish` → **400**。

### 根因
夸克的上传收尾是**两步**，上一版只做了第二步（而且第二步的参数也错了）：

1. **向 OSS 提交 `CompleteMultipartUpload` XML**（带 `x-oss-callback`）——
   让对象存储把分片真正合并成一个对象；
2. **再调 `/1/clouddrive/file/upload/finish`**，body 只要 `{task_id, obj_key}`
   —— 通知夸克把该对象登记成文件。

只做第 2 步 → 服务端找不到可合并的对象 → `43001 complete file failed!`。
上一版还把 finish 的 body 写成了 `{task_id, part_info_list}`（错的字段）。

### 两条「错了不报错」的细节
- **ETag 在 XML 里必须带双引号**：`<ETag>"abc"</ETag>`。OSS 要求原样回填
  PUT 响应里的值（含引号），不带引号会被判成分片不匹配。
- **分片必须按 `part_number` 升序**排列。

两者都做进纯函数 `QuarkAdapter.buildCompleteMultipartXml`，用 6 例测试钉死
（`test/data/quark_upload_complete_test.dart`）。

### 参考实现
`RemyYYZ/QuarkPan`（Python，58 commits）的
`complete_multipart_upload` + `finish_upload` 两步法，与
`imeiming/quark-drive` 的 OSS callback 写法一致。
`file/upload/auth` 的 `auth_meta` 字段顺序必须与真实请求头一致，签名才算得对：
```
POST\n{contentMd5}\napplication/xml\n{ts}\n
x-oss-callback:{cb64}\nx-oss-date:{ts}\nx-oss-user-agent:...\n
/{bucket}/{objKey}?uploadId={uploadId}
```

### 新增 `HttpClientLike.postBytes`
`putBytes` 只够分片；完成合并要 POST 原始 XML，所以加了 `postBytes`
（`DioHttpClient` 实现，返回响应体字符串）。6 个测试替身都补了空实现。

## 修复：缓冲时显示「≈1.0 GB/s」（口径错误，不是单位换算）

现象：缓冲浮层的网速经常跳到 1 GB/s，而用户带宽远不到。

结论：**换算链每一环都是对的** —— media_kit `real.dart:1544` 的秒→微秒、
`倍速 × (体积÷时长)` 的量纲、`formatBytes` 的 1024 进制字节，全部正确。
错的是**测的位置**：

- media_kit 硬编码 `cache=yes` / `cache-on-disk=yes`（`real.dart:2400-2401`），
  于是 mpv 的缓存是**两层且互相解耦**的：
  `网络 → stream cache（字节，后台预读）→ 解复用 → demuxer cache（秒）`。
- 界面只能量到第二层 `demuxer-cache-time`，而它的数据来自**本地**
  （内存，或 `cache-on-disk` 的落盘文件），速度是 CPU / 磁盘量级 ——
  一次几百 MB 的块填充几十毫秒就能灌完，换算出来就是 GB/s。
- 我们又设了 `demuxer-readahead-secs=9999`，demuxer 一路往前冲，加剧了这个现象。
- 两个放大项：`CacheSpeedMeter._minSpanSeconds=0.4` 允许 0.4 秒的跨度（块填充直接成尖峰）；
  `_cacheRate` 在 `rate == null` 时**保留旧值** ⇒ 尖峰被**冻结在界面上**，
  这才是「经常看到」的直接原因。
- 反证：40 Mbps 原画要算出 1 GB/s，8 秒窗口内 `demuxer-cache-time` 得涨 1640 秒
  ≈ 8.2 GB，而缓存上限只有 1 GB ⇒ 不可能，故必然是窗口退化成了两点差分。

修复（4 文件，243+ / 23-）：

1. `PlayerBufferConfig.disableStreamCache = true`：`apply()` 里在 `open()` **之前**
   `setProperty('cache','no')`，让 demuxer 直接吃网络 ⇒ 测出来的才等于真网速。
   安全性：夸克原画是支持 Range 的 seekable HTTP、转码档是 HLS，都不需要 stream cache 回读；
   `bufferSize`(1 GB) 同时给 `demuxer-max-bytes` / `-back-bytes`，回看与抗抖动照旧；
   还省掉一层 1 GB 的字节缓存。
   ⚠️ **待真机实测**：若开播变慢或 seek 后重新缓冲，把 `disableStreamCache` 改回 `false`
   （代价只是网速重新变成估算值）。
2. `CacheSpeedMeter._minSpanSeconds` 0.4 → 1.5（挡住块填充尖峰）。
3. 新增纯函数 `cacheBytesPerSecond()`（与 meter 同文件）：换算 + 护栏
   `defaultMaxCacheBytesPerSecond = 256 MB/s`（≈2 Gbps；超过就返回 null = 这一拍不显示速度）。
4. `player_window_app`：新增 `_cacheRateAt` / `_currentCacheRate`（5 秒过期，不再冻结尖峰）；
   `_cacheBytesPerSecond()` 改为委托纯函数。

测试：`test/domain/cache_speed_meter_test.dart` 15 例（原 9 + 新 6）；
全量 `flutter test` **1050 例全过**（与上面那次同数，说明我的 6 例已含在里面）。

### 追加：网速改成直接读 mpv（不再估算）

上面那版还是「估算 + 护栏」。查证后发现有更好的源：

- **`NativePlayer.getProperty` / `observeProperty` 其实是公开的** —— HOWTO 里
  「`real.dart` 里有但没暴露到公开类」的旧笔记**是错的**（`analyze` 能编译通过就是证据）。
- 但 `setProperty` **丢掉 mpv 的返回码**（`mpv_set_property_string` 调完直接返回）
  ⇒ 属性设不上是**完全静默**的。所以 `apply()` 里加 `_confirmStreamCacheOff()`：
  读回 `cache` 并记诊断日志，让「关没关掉」在诊断页里看得见。
- **`demuxer-cache-state.raw-input-rate` 就是真实输入速率（字节/秒）**，不用乘码率
  ⇒ 顺带消掉了「转码档码率对不上」那个偏差。字段名**直接在随包的 libmpv 二进制里核对过**
  （`strings .../Mpv | grep -Fx raw-input-rate`，mpv 0.36.0）—— 比翻文档可靠，文档抓不全。
- 新增 `core/utils/mpv_cache_state.dart`（纯函数 `rawInputBytesPerSecond`，8 例测试）
  + `player_window_app` 里 1 Hz 轮询 `getProperty('demuxer-cache-state')`。
  **拿不到就退回原估算**，两条路共用同一道 256 MB/s 护栏。
  ⚠️ 计时器起在 `_ensurePlayer()` **之后** —— 起在 try 外面的话，播放器建不出来时
  （`flutter test` 里必然如此）会留下「A Timer is still pending」。

## 教训：不要对仓库文件跑 `dart format`

⛔ 本仓库的文件**不符合 dart format**（既有状态，不是这次弄坏的）。
顺手跑一次 `dart format`，把 `player_window_app.dart` 从 **5 处改动**膨胀成
**62 个 hunk / 563 行**（全是换行与缩进重排），diff 当场没法 review。

## 修复：同步的新旧判定拿错了时间（读代码发现，不是测试报的）

### 症状（潜在数据丢失，尚未被用户撞上）
新机器装好后点「同步」，**会把远程那份好备份覆盖掉**；本地空库也照样「胜出」。

### 根因
`BackupManifest` 只有 `createdAt`（**备份包被创建的时刻**），旧 `sync()` 拿它比大小
⇒ 刚导出的包时间戳永远最新 ⇒ `localNewer` **恒为 true** ⇒
**同步永远只会「上传」，永远不会「下载」**。

### 修法（4 文件）
1. `library_backup.dart`：`BackupManifest` 加 `libraryModifiedAt`（可空）；
   派生 `effectiveModifiedAt => libraryModifiedAt ?? createdAt`、
   `hasLibraryContent => libraryModifiedAt != null`；`isNewerThan`/`conflictsWith` 改用它；
   `toJson`/`fromJson` 处理新字段。
2. `media_repository.dart`：抽象加 `Future<DateTime?> latestLibraryChangeAt()`；
   `InMemoryMediaRepository` 实现（空库返回 null；取 `updatedAt`、
   `lastPlayedAt ?? firstSeenAt` 的最大值）。
3. `media_repository_impl.dart`：用 drift 聚合实现
   （`mediaWorks.updatedAt.max()` / `mediaItems.firstSeenAt.max()` / `mediaItems.lastPlayedAt.max()`）。
4. `library_backup_service.dart`：`exportBackup` 把 `modifiedAt?.toUtc()` 写进 manifest；
   `sync()` 重写 —— 先判两个「空」守卫，再判冲突，最后比 `effectiveModifiedAt`。
   `app_providers.dart` 注入 `localModifiedAt: () => ...latestLibraryChangeAt()`。

### 两个「空」守卫（对称，缺一个就会互相覆盖）
- 本地空库（`!localManifest.hasLibraryContent`）⇒ **拉远程**，绝不推。
- 远程空包（`!remoteManifest.hasLibraryContent`）⇒ **推本地**，绝不被它覆盖。

⚠️ 中间写错过一版：拿「`fileNames` 里有没有 `posters/`」判空 —— 但海报是**打进 payload**
的，不在 `fileNames` 里，于是判空**恒为 false**。被新增测试逮住，换成 `hasLibraryContent`。

### 测试

  含回归例「createdAt 更晚但库更旧 → 不算更新」。

## 补测：上传的**编排**（原先只有 XML 形状的测试）

### 为什么补
`quark_upload_complete_test.dart` 只钉 XML 的**形状**；真正出 43001 的是**编排**
（谁先谁后、每个端点收到什么 body）。这类错误**不抛异常、只静默失败** ——
而上传是「用户点一下、结果只有成/败」的路径，没有测试就只能靠真机撞。

### 新文件 `test/data/quark_upload_flow_test.dart`（7 例）
假 `HttpClientLike` 按 `post` / `putBytes` / `postBytes` **三类分别记账**，断言：
- `post` 路径序列必须是 `pre → hash → auth×N → auth(合并) → finish`；
- `finish` 的 body **恰好**是 `{task_id, obj_key}`，且**不含** `part_info_list`；
- 分片 PUT 的 `partNumber` 升序、每片带 `Authorization`；
- OSS 合并**必须发生一次**，带 `x-oss-callback` / `Content-MD5` / `Content-Type: application/xml`，
  XML 里 ETag 重新带上双引号、PartNumber 升序；
- 秒传命中（hash `finish=true`）→ 直接返回 fid，**零** PUT、**零** OSS 合并；
- 缺 `bucket`/`obj_key`/`upload_id` → 动分片**之前**就抛 `malformedResponse`；
- 缺 `callback` → 合并阶段抛错（不是静默成功）；
- `onProgress` 逐片递增、末次等于总大小。

`part_size` 由用例给（默认 4 字节），所以 10 字节的小文件就能造出 3 片，
不必真造 MB 级数据。

这说明断言不是恒真的摆设。

正是 43001 的成因。改成 `{task_id, obj_key}` 并注明「不是 part_info_list」，

- ⚠️ **OK 键 ≠ `enter` ≠ `space`**。Android TV 遥控器中心键的键码是 **23**，映射到 `LogicalKeyboardKey.select`（见 `keyboard_maps.g.dart`）。`WidgetsApp._defaultShortcuts` 把 `select`/`enter`/`space`/`gameButtonA` **四个都**映射到 `ActivateIntent`，所以只绑 `space` 的自定义快捷键**收不到遥控器**。

## 13:15 「182.格力空调显示E6如何维修.mp4」被刮成希腊纪录片 —— 归因与规则评估

用户问：为什么 `/来自：分享/姜松《家电维修视频教程》/182.格力空调显示E6如何维修.mp4`
被刮成《1821: Οι Ήρωες》(2021)，以及「目录名什么时候才是系列名」的界限在哪。

**复现链路**（写临时探针跑 `dart run` 确认，跑完已删；日志 `cloudcine-2026-10-02.log:318/327/328`）：
1. 解析出 `title="182 格力空调显示"`、`latinTitle="182"`、`kind=episode`（**`E6` 被当第 6 集**）、`conf=true`；
2. `_alternateOf` 把 `latinTitle="182"` 当备用词（**不看有没有字母**）；
3. TMDB 用 `"182"` 模糊搜 → 返回 `1821: Οι Ήρωες`；
4. 闸门：主名 `182 格力空调显示` 判 **0.3636 reject**（对），备用词 `182` 判 **0.9125 accept**（错）——
   因为 `titleSimilarity` 前缀档下界 `0.65 > strongSimilarity 0.6`，**短的是长的前缀就必然无条件通过**。
   年份闸门这次是空的（`y=null`）所以没兜住。

**三个独立缺陷**：①备用词可以是纯数字；②前缀/包含档对纯数字过宽（实测 `1`→`127 Hours` 0.69、`2`→`2012` 0.74、
`10`→`10000 BC` 0.75，全部 accept）；③`E\d+` 前置守卫 `(?<![0-9a-z])` **汉字不算边界** → `显示E6` 被当集号，
`conf` 被顶成 true，于是**同一目录里 5/7 个文件各自建成独立作品**（`7.冰箱不制冷…` 那类 `conf=false` 反而不建）。

**目录名界限的结论**：界限**不在目录名里，在「文件夹的文件集合形状」里**。
`/我的电影/01.流浪地球2.mp4` 与 `/姜松《家电维修视频教程》/182.xxx.mp4` 的**文件名形态完全一样**，
只有兄弟文件能区分 → **判定单元必须是文件夹**，而现在的 `parse(fileName, dirName:)` 是逐文件纯函数，结构上修不了。
另外 `dirName` 兜底只在 `title` 为空时触发（`filename_parser.dart:214`），本例提出了垃圾片名 → 兜底**根本没跑**。

### P1-2（`library_filter_panel.dart`）
`MenuAnchor` 是 `OverlayPortal` **不是路由**，唯一关闭绑定是 `escape: DismissIntent()`

- 面板底部常驻一个「关闭」`TextButton`（**不做平台判断**，否则桌面测不到）；
- 外层包 `PopScope(canPop: !_open, onPopInvokedWithResult: ...)`。
⚠️ `MenuController` 是普通类**不是 `ChangeNotifier`**，`_open` 只能用 `onOpen`/`onClose` 同步。
⚠️ `find.byType(PopScope)` 会 `Bad state: No element` —— `PopScope<T>` 是泛型，
   要用 `find.byWidgetPredicate((w) => w is PopScope)` + `hasLength(1)`。
测试 17 例（新增 3 例「关得掉：TV 上没有 Esc」）。

## 目录名作为系列名 —— 从事故归因到落地（13:15 起）

**用户报的现场**：`/来自：分享/姜松《家电维修视频教程》/182.格力空调显示E6如何维修.mp4`
被自动刮成 **《1821: Οι Ήρωες》(2021)**（希腊纪录片）。用户的判断很准：
「重点是文件所属目录的目录名有可能才是影片系列的名称，但是不知道这个界限是什么」。

**归因（四步，每步都写了 5 行探针实测，用完即删）**：
①`E6` 被当成第 6 集（`(?<![0-9a-z])` 不把汉字当边界）→ `latinTitle="182"`；
②`_alternateOf` 只要求两种文字都非空 → 备用词 `"182"`；
③TMDB 模糊搜索 `"182"` → `1821: Οι Ήρωες`；
④闸门主名 0.3636 **拒（对的）**、备用词 0.9125 **过（错的）** —— 前缀档下限 `0.65 > strongSimilarity 0.6` ⇒ 短串是长串前缀**恒过**。
**所以不是「刮错了」，是「备用词把一道本来有效的闸门绕过了」。**

**界限的答案**：不在目录名里，在**文件夹的文件集合形状**里。
`/姜松《家电维修视频教程》/182.xxx.mp4` 与 `/我的电影/01.流浪地球2.mp4` 文件名形态**一模一样**，

### 播放器三个菜单改成「贴着按钮正上方划出」（同日稍后）

**用户反馈**：画质 / 字幕 / 音轨三个菜单全不对 —— 字幕与音轨是**屏幕正中**的 `AlertDialog`，
画质之前改成 `CompositedTransformFollower` 后**跑到屏幕左上角**。要的是「在点击按钮的上方划出，
跟随按钮相对定位，类似下拉框的上划弹出」。

**根因**：`CompositedTransformFollower` 靠图层树里的 leader/follower 配对；按钮在路由里、
浮层插在 Overlay 顶层这种跨层组合下不稳，找不到 leader 时就退回自己 `Stack` 的左上角 ——
正好就是用户看到的「左上角」。这条机制**不可靠，别再回去用**。

**新做法**：新增 `lib/ui/widgets/anchored_menu.dart`：
- `globalRectOf(context)` 拿按钮的全局矩形（元素已失效时在 debug 下会断言，所以调用前必须判 `mounted`）；
- `anchoredMenuOffset(anchor, screen, menu, gap, edgePadding)` —— **纯函数**，算菜单该摆哪儿：
  ①底边落在按钮顶边之上 gap 处 ②右沿对齐按钮右沿 ③两边夹进屏幕 ④上方放不下就翻到下方；
- `showAnchoredMenu<T>(navigator:, anchor:, builder:)` —— 推一个 `PopupRoute`（遮罩 / 点外部关闭 /
  Esc / 无障碍语义都由它兜住），170ms「上划 14px + 淡入」；
- `AnchoredMenuPanel` —— 圆角深色面板（`title` + 可滚动 `children`），面板自己吃空白处点击，
  否则点标题会把菜单关掉。

**收 `NavigatorState` 而不是 `BuildContext`** 是刻意的：字幕菜单搜完在线字幕会**重开**，
那时手里只该有一个不依赖元素生命周期的 navigator。

**两处调用点**：
- `player_window_app.dart`：删掉 `_qualityLink` 与 `_QualityPopupLayer`；三个按钮各套一层 `Builder`
  拿自身 context；`_QualityPopup`/`_AudioDialog`/`_SubtitleDialog` → `_QualityMenuPanel`/
  `_AudioMenuPanel`/`_SubtitleMenuPanel`（`AlertDialog` → `AnchoredMenuPanel`，行照旧
  `Navigator.of(context).pop(value)`，所以 `@visibleForTesting` 那两个入口的语义没变）。
- `player_page.dart`：四个 `PopupMenuButton`（画质/字幕/音轨/倍速）换成 `_MenuButton`（`Tooltip`+
  `InkWell`）+ `_openAnchoredMenu` 帮助函数；新增 `_MenuTile` 包住 `_MenuRow`；`_MenuRow` 去掉写死的
  `width: 240`（改成撑满面板）。**用 `InkWell` 而不是纯装饰**是为了 TV 遥控器那条路不断（控制栏只走焦点链）。

**实测确认（写了一次性探针，跑完即删）**：菜单开着时，底下那层 `CallbackShortcuts` 收不到
space（0 次）、收不到 escape（0 次），Esc 正常关掉菜单 —— `ModalRoute` 的 `FocusScope` 会接管焦点，

设计文档 `docs/季与部-层级设计.md` 5.1 的原方案是：把源作品的
`media_items.group_key` 改写成目标的 key，**然后删掉源作品行**。

落地时改了，理由是那条路**合并错了就回不去** —— 用户看到两个格子变成一个，
既不知道发生了什么，也没有任何按钮能还原，从此不敢用自动归一。而设计文档
自己就写着「合并错一次而不可逆，用户会直接不敢用」（那句本来是讲手动合并的）。

改成 `media_works.merged_into`（v11）打标记：

| 事 | 怎么办 |
|----|--------|
| 列表 / 角标 | `WHERE merged_into IS NULL`（加在 `_workConditions` 一处，`listWorks`/两个计数共用） |
| 详情页文件 | `itemsForWork` 取并集（`IN (子查询)`） |
| 撤销 | 清 `merged_into`，一条 UPDATE，零风险 |
| `media_items.group_key` | **永不改写** → 「item.groupKey 一定等于某个 work.key」这条不变量继续成立 |

观感与「删掉」完全一致，但可逆。已在设计文档 5.1 与实施顺序表里补了注。

### 两个踩到的坑

### 四个交互决定（与「手动刮削」**刻意相反**，别照抄那边）

| # | 决定 | 为什么与那边不同 |
|---|------|------------------|
| 1 | 预填当前片名，**且一打开就搜** | 手动刮削不预搜是因为**每次搜索花一次豆瓣额度**；这里是**纯本地内存过滤**，零成本 |
| 2 | 零匹配不说「没找到」，说「把搜索框清空可以看到全部 N 部作品」 | 这条通道最常见的用法恰恰是「两个片名完全不一样」，用户最容易的结论是「库里根本没有那一部」 |
| 3 | 点候选**只是选中**，再点「合并」才生效 | 合并会改掉两部作品在列表里的可见性，不该在用户只是「看看有哪些」的时候发生 |
| 4 | 不能合的行**点不动** + 原因写在行上 + 按钮同时变灰 | 让用户选中一个马上会被否掉的目标，是最没必要的一次往返；等点了才弹错，看起来就像应用坏了 |

### 三条拦截全为**防链**

判据只在 `manualBlocker`（**对话框与 `mergeInto` 用的是同一个函数** ——
两边各写一遍迟早出现「按钮亮着、点了却没反应」）：①自己并自己；②目标已是
别名行；③**源自己还折着别的作品**（真会撞上：自动归一刚把两部合到《X》，
用户又想把《X》并进《Y》）。

第③条**不做「连坐迁移」**（把 X 的源一起改指 Y）—— 那样撤销就无法精确还原：
X 的那些源原本指向 X，撤完却会变成独立的根。正确动作是先「拆开」再合。
「目标已经有源」**不拦**：只是又多一个兄弟，不成链。

## Android TV P2-4：`SelectableText` 是焦点陷阱（16:05–16:30）

### 先纠正自己的一个错判

上一轮我在文档里写 P2-4「`SelectableText` 与普通 `Text` 视觉完全一样，改它收益≈0，
所以未动」。**这个判断是错的**，而且错得不轻。

按本项目的规矩（「测相似度/打分别猜数值，先写脚本跑」）先写了个探针：
在 `SelectableText` 上下各放一个按钮，从上面那个连按 4 次 ↓ ——

| 组件 | ↓ 轨迹 |
|---|---|
| 裸 `SelectableText` | `[text, text, text, text]` —— **停在原地，出不去** |
| `TvSelectableText` | `[after]` —— 一下穿过 |

`focusNode.canRequestFocus` 实测 `true`。机理：`SelectableText` 内部是
`EditableText(readOnly: true)`，而 `EditableText` **自带 `FocusNode`** ——
`readOnly` 只管「能不能改」，不管「能不能聚焦」。

所以它是**有害**不是**没用**：走进一段长文本就出不来，按 OK 毫无反应、方向键也不动，
用户只会得出「遥控器坏了」。而这 5 处恰好都在**诊断页 / 登录页** ——
用户是在出问题的时候才来这里的。

⚠️ **教训**：凡是「这个控件在 TV 上有没有意义」的问题，一律先写探针。
本项目已经栽过三次同类（`Tooltip` 等于不存在、`focusColor` 被海报盖住、
`Slider` 吃掉方向键），共同点是**错了不报错**，只表现为「用户觉得功能坏了」。

### 修法

新增 `lib/ui/widgets/tv_text.dart` 的 `TvSelectableText`：TV 上返回 `Text`，
**其余平台原样返回 `SelectableText`**。接线 5 处：`common_widgets`（`KeyValueRow`）、
`diagnostics_page`（`LogPathRow` + `_LogLine`）、`auth_qr_login_page`（`_MonoBlock`）、
`player_window_app`（自检列表；这处是 PC-only，走包装只为口径一致）。

三条不可动摇：
1. ⛔ **非 TV 分支不许也换成 `Text`** —— 桌面/手机划选是刻意的设计
   （`LogPathRow` 注释：「即使不点按钮，也能用鼠标划走」）。按平台分工，不是统一简化。
2. **探针同时钉两件事**：裸的确实卡住（包装存在的唯一理由）＋ 包装确实不卡（修复没白写）。
   只钉后者，「为什么要有这个包装」就只存在于注释里了。
3. `focusNode` 只在非 TV 上透传 —— TV 上**故意**不留落点。

**播放列表提不出集号时改显「剧名-文件名」（20:3x）**
- 反馈：剧集播放（独立窗口）右侧剧集列表里，文件名不符合集数命名规则的条目
  全显示同一个剧名，分不出是哪一集。
- 根因：`desktop_play.dart` 的 `_episodeLabel` 在 `item.episode == null` 时退回
  `displayTitle`（= 片名）。而这批条目正是「目录名作为系列名」规则**刻意清掉
  季集号**的那些（`MediaFilenameParser.parse` 目录级归组：
  `182.格力空调显示E6如何维修.mp4` 里的 `E6` 是故障代码不是第 6 集）。
- 改法：退回 `剧名-文件名`（文件名去扩展名）。剧名取**作品行** `MediaWork.title`
  （刮削后的名字），没有作品行时退回条目自己的 `title`；文件名已含剧名
  （折叠掉标点后 `startsWith`）时不重复拼前缀。`_buildPlaylist` 新增
  `workTitle` 参数，由 `buildPlayRequest` 传入。
- 同步 `PlaylistEntry.title` 的契约注释；新增 3 例（前缀取作品行 / 文件名自带
  剧名去重 / 无作品行兜底）。`flutter test` 全量 1522 例全过
  （数量与并发会话的 1627 不同，是两边同时在加用例）。
- 改动文件：`lib/ui/windows/desktop_play.dart`、`lib/ui/windows/player_protocol.dart`、
