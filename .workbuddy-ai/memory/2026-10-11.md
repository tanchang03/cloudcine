## 「flutter build apk 报 v1 embedding」—— 不是 bug，是命令用错

**现象**：在仓库根跑 `flutter build apk --release` ⇒
`Build failed due to use of deleted Android v1 embedding.`

**根因**：仓库根是 Flutter 工程（`pubspec.yaml` + `.metadata` 里
`platform: android`），`flutter` 工具于是把 `android/` 当自己的 Android 宿主目录，
去清单里找 v2 嵌入标记 `flutterEmbedding`。但 `android/` 是**独立原生 Kotlin 工程**：

- `android/settings.gradle.kts` 只有 `include(":app")`，**没引 Flutter Gradle 插件**；
- `android/app/src/main/AndroidManifest.xml` 里 `grep flutterEmbedding|io.flutter`
  **零命中**，`MainActivity` 也不是 `FlutterActivity`；
- `android/app/build.gradle.kts` 的 plugins 只有 `com.android.application` +
  `org.jetbrains.kotlin.android`。

找不到 v2 标记 ⇒ Flutter 报「v1 embedding 已被删除」。**跟代码无关，改多少行都不会好。**

**正确构建方式**（已实测通过）：

```bash
cd android
export JAVA_HOME=/Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home
export ANDROID_HOME=/Users/tandy/Library/Android/sdk
./gradlew :app:testDebugUnitTest :app:assembleRelease   # 发版；debug 用 :app:assembleDebug
# 或：android/tool/adb_tv.sh build [debug|release]
```

本次实测：`assembleDebug --offline` 8s 成功；`testDebugUnitTest + assembleRelease
--offline` 20s 成功（release 产物 UP-TO-DATE，未重建）。与 `release.yml` 的
`build-android` job 完全同一条命令（该 job `working-directory: android`、JDK 21、**不装 Flutter**）。

**产物**：`android/app/build/outputs/apk/release/app-release.apk`
+ `branded/cloudcine-<ver>-b<code>-android.apk`（`brandReleaseApk` 任务产出）。

⚠️ 本机 `android/keystore.properties` **不存在** ⇒ release 包退回 **debug 签名**
（`keytool -printcert` 显示 `CN=Android Debug`）。能侧载自测，对外发布前必须配密钥。

## 用户报的两条（PC 全屏快捷键 / 跨环境「最后播放集数」）

两条都**不是「功能没做」，而是「做了但走不到」**——与 2026-10-01 那次
「用户报『不支持空格暂停』，实际是播放器有两套实现」同一类。

### ① PC 全屏下空格 / ← / → 全失灵

`player_window_app.dart` 的 `_playbackShortcuts` 里这三条一直都在（有用例钉着），
所以问题不在键位表，而在**事件走不到表上**：`CallbackShortcuts` 是往**焦点链**
里插一个节点，而 macOS 的原生全屏（`NSWindow.toggleFullScreen`）会把窗口搬到
另一个 Space，切换过程中 Flutter 这侧的主焦点被丢到根 scope ⇒ 整张表**同时**
失灵且**不报任何错**。同根因见 flutter/flutter#166237（至今未修，P3）。

修法（两条都做，分别覆盖两种失效方式）：
- **Dart**：兜底挂在 `HardwareKeyboard` 上（它不看焦点）。⛔ 必须有
  `_rootFocus.hasFocus` 这道闸 —— `HardwareKeyboard._dispatchKeyEvent` 是
  「**所有处理器都调一遍**」、不因某个返回 true 就提前结束，不挡就是**一次按键
  被处理两次**（空格 = 按了没反应，→ = 跳 20 秒）。
- **原生**：`windowDidEnter/ExitFullScreen` + `windowDidBecomeKey` 里
  `makeFirstResponder(FlutterView)`（全屏切换后第一响应者不再是 Flutter 视图）。
- 另加 `_rootFocus`（自有节点）在 `_onFullScreenChanged` 后抢回焦点。

### ② 跨环境「最后播放集数」不同步

用户以为缺字段。**逐条进度（`r`/`m`/`p`）早就在整份同步**，缺的是**上传时机**：
PC 主窗口的进度同步只有「启动 +12s / 每 30 分钟 / 内置播放页 `dispose`」三处，
而**第三条在 PC 上永远走不到**（PC 播放跑在独立窗口那个引擎里）。Android 早在
`onActivityResult(REQ_PLAYER)` 后 2 秒就同步一次 ⇒ 两端时机不对等。

修法：
- 新增 `PlayerBridgeMethod.playerClosed`（播放窗口 → 主窗口），
  `_releasePlayer()` 开头 `_notifyClosed()`（**幂等**，只发一次）；
  `player_bridge_host.dart` 收到后走 `progressSyncTriggerProvider.request()`
  （自带 20s 节流 + 「上一轮没跑完就跳过」）。
- 顺手修 `WorkDetail.primary`：它曾是 `features.first` = **永远第一集**
  ⇒ PC 详情页点播放与电视简介页（走 `PlayTarget.resolve`）口径分裂。
  现在统一走 `PlayTarget.resolve`，并给 `WorkDetail` 补 `resumePositions`
  （画进度条用 `maxPositions`、算该播哪一集用 `resumePositions`，**不能混**）。

## 评估：为什么「拖到已缓冲区间内还要缓冲」

用户原话：「影片播放过程中，缓冲了大量的缓存进度，此时拉动播放进度并且进度在
缓冲进度范围内，依然会有一个加载缓冲过程，这个看起来之前的缓存并没有发挥作用呢？」

**结论：不是错觉，但也不是「缓存没生效」——是三件事叠在一起。** 完整分析已
写入 `HOWTO.md` §11，这里只留结论。

1. **前提被纠正**：`PlayerControlsView` 头注释说「落在已缓冲区间内 ExoPlayer 直接
   从 `SampleQueue` 出帧、不碰网络」——**只对一半**。去 media3 源码核对
   （`ChunkSampleStream.seekToUs`）：只有落在队列保留窗口内的跳转才 `seekTo` 移
   读指针；窗口之外走 `// We can't seek inside the buffer, and so need to reset.`
   ⇒ `resetSampleQueues()` ⇒ **从数据源重读**。窗口 = 前向
   `min(字节预算, maxBufferMs=120s)`（原画 64 MiB ÷ 3.67 MiB/s ≈ 17s）、
   后向 `BufferPlan.backBufferMs`（钳 [2s, 30s]）。
   ⇒ **内存里已缓冲的那段，seek 之后一律作废。**

2. **盘上「有」也不等于「读得到」**：
   - `DiskPrefetcher.CHUNK_BYTES = 128 MiB` 且 `CacheDataSink` **没开**
     `setFragmentFileSize` ⇒ 一个 span 只在**整块读完**才 `commitFile`；
     在此之前 `isCached=false`，淡蓝不画它、播放器读它 = **未命中回网络**。
     按媒体时间：原画档 ≈ 35 s，低码率档（0.24 MiB/s）≈ **9 分钟**。
   - `reanchor()` 开头就 `currentWriter?.cancel()`，被取消的 span **不 commit**
     ⇒ 用户每拖一次进度条，盘上就留一个**真空洞**。而淡蓝那层看着还是一大片。
   - `.setCacheWriteDataSinkFactory(null)` ⇒ **播放器只读缓存**，它自己读过的
     字节一个都不落盘（代价比注释里写的「起播头十几秒重复下载」大得多）。

3. **已实测确认的独立缺陷：续播时预取器从字节 0 爬。**
   `startPlayer` 的顺序是 `setMediaItem → prepare → seekTo(续播点) → playWhenReady
   → startDiskPrefetch(...)`，续播那次 `onPositionDiscontinuity(SEEK)` 打过来时
   `prefetcher` 还是 null ⇒ `reanchor` 空操作；而 `startPositionBytes = 0L`，
   `reanchor` 又**只在用户跳转时**才调。实测（模拟器，`01.mp4` 续播 1880s）：
   ```
   17:45:05.327  续播：起播跳到 1880s（库里记的续播点）
   17:45:05.331  磁盘预取：已启动（键 quark:e631c05f…:origin · 码率 0.24 MiB/s）
   17:45:06.328  … 磁盘 本片 0 B … 预取 第 0 块 · 领先 0 B
   ```
   ⇒ 预取器在灌用户**已经看过**的前 31 分钟。

**定性靠一行日志**：`跳转提交[触摸/快进] → Xs（…内存区间内 / 磁盘缓存命中 /
两处都没命中）`。⚠️ 但它用的是**估算字节**（时间 × 平均码率），VBR 片源上可能错，
只当线索；判据看 `磁盘 本片 X MiB` 与 `预取 第 N 块`。

**修复清单（按性价比，尚未实施）**：① 预取器的 `CacheDataSink` 加
`setFragmentFileSize(8 MiB)`；② `startDiskPrefetch` 后补
`prefetcher?.reanchor(estimatedBytes(startMs))`；③ `CHUNK_BYTES` 降到 8~16 MiB
或让 `reanchor` 补完当前块再跳；④ 让播放器也写缓存（需先解决与预取器撞 span）。

**本次顺手改的**：两处**已经与代码矛盾**的注释（都在假设「播放器会写缓存」）——
`DiskPrefetcher` 类注释的「与播放器的分工」、`PlayerActivity.startDiskPrefetch`
的「70% 留给播放器自己写的那部分（已播段）」。`./gradlew :app:testDebugUnitTest`
复跑通过。

**顺带发现**：模拟器（`android-34;android-tv;arm64-v8a`）**解不了 HEVC 10bit**
（`MediaCodecVideoRenderer error … format_supported=NO_EXCEEDS_CAPABILITIES`，
`c2.android.hevc.decoder` Error 0xe）⇒ 想在模拟器上做播放类实测，得挑 H.264/8bit
的片源，否则一到 `setMediaItem` 就报错、拿不到缓冲读数。

## 续：「拖进已缓冲区间还要缓冲」**已按最佳方案修复并真机验证**（2026-10-11 晚）

**实施**（改的是上面清单的 ①②，另加「首块=文件头」这一条）：
- 新增 `PrefetchPlan.kt`（纯决策层：`chunkSpan` / `jumpAfterHead` /
  `resumeAnchorBytes`）+ `PrefetchPlanTest`（12 例）+ `PrefetchWiringTest`（4 例静态守卫）。
- `DiskPrefetcher`：加 `jumpAfterHeadBytes` 形参；块长走 `PrefetchPlan.chunkSpan`；
  `CacheDataSink` 开增量提交；首块下完调 `PrefetchPlan.jumpAfterHead` 登记锚点。
- `PlayerActivity.startDiskPrefetch`：算 `resumeAnchor` 并传下去。
- 单测：相关 3 类 20 例绿；红检 1 例（去掉 `setFragmentSize` ⇒ 恰好 1 红）；全量 47 类 / 610 例绿。

**⛔ API 名踩坑**：media3 1.5.1 里那个方法叫 **`setFragmentSize(long)`**，
**不是** `setFragmentFileSize`（ExoPlayer 2.x 的老名字）。写错是**编译错**，
`javap -classpath <aar 里抽出的 classes.jar> 'androidx.media3.datasource.cache.CacheDataSink$Factory'` 可当场验。

**真机（模拟器 `emulator-5554`）验证**——用 `assets` 之外自造的 H.264 baseline 片
（300s / 56.1 MiB），经一个**支持 Range** 的本地 HTTP 服务喂进去（`python -m http.server`
**不支持 Range**，会毁掉并行取块与缓存，必须自己写）：

| 现象 | 日志 |
|---|---|
| 续播锚点算对并传下去 | `首块 8 MiB 后跳到续播点 30 MiB` |
| 首块**只下文件头** | `预取第 1 块：0 → 8 MiB（8 MiB）`（修前是 128 MiB） |
| 跳转逻辑真的触发 | `预取首块（文件头）已落盘 ⇒ 跳到续播点 30 MiB` |
| 从锚点续下、**不回 0 重灌** | `预取第 2 块：30 → 56 MiB（26 MiB）· 累计 34 MiB` |
| 盘上是**两段**、都已提交 | 统计行 `磁盘 本片 34 MiB · 2 段` |
| 二次打开纯盘上读 | `缓存 34 MiB`（不增长）+ 统计 `网络 0 KB/s` |

**⚠️ 测试片伪影（不是缺陷）**：直连路径没有 `PlayInfo` ⇒ `assumedBitrateMibps()`
回落到 `BufferPlan.ASSUMED_BITRATE_MIBPS = 3.0`，而自造片真实码率仅 0.19 MiB/s
（差 16 倍）。于是 `跳转提交[…]` 的「内存/磁盘命中」判定（走**估算字节**）会给出
`两处都没命中`、`到 00:18` 这类**看起来不对**的读数。真机网盘路径的
`requiredMbPerSec` 来自实际档位，不存在这个偏差。**要复现「磁盘缓存命中」那一路，
测试片的真实码率必须≈3.0 MiB/s**（例如 45s / 135 MiB）。

## CI 发版版本号不一致 —— 整改（18:30–19:10）

**现场**：tag `v0.1.6` · `pubspec.yaml` `0.1.1+2` · 设置页 `_kAppVersion` `0.1.0` ·
`android/app/build.gradle.kts` `versionName 0.1.1 / versionCode 2`。
⇒ Release 标题 `v0.1.6`，产物名 `cloudcine-0.1.1-macos.dmg`，应用内显示 `0.1.0`。

**结论**：macOS/Windows 的版本是构建期从 pubspec 自动派生的（Info.plist
`$(FLUTTER_BUILD_NAME)` / Runner.rc `FLUTTER_VERSION` / MSI 名读 pubspec），**从来不漂**；
会漂的只有**手写的两处 + 人为约定的 tag**，且没有任何机器守卫。

**改动**（全部落地并验证）：
- 新增 `tool/version.dart`：解析三处（+ 可选 tag），`--check` / `--print` / `--set` / 默认同步。
  `versionCode = x*10000 + y*100 + z`，与 pubspec 的 `+build` 同值 ⇒ 天然单调递增，
  不用再维护「上次用到几了」的计数器。
- 三处版本号统一到 `0.1.6`（pubspec `0.1.6+106` / 设置页 `0.1.6` / Android `0.1.6` + `106`）。
- `release.yml` 新增 `version-guard` job（三个构建 job 都 `needs` 它，排在造产物之前）；
  release job 增加「产物文件名版本 == tag 版本」正反两向断言；
  build-android 的版本号改取 `needs.version-guard.outputs.version`（不再自己 sed 一遍）。
- 新增 `test/core/version_consistency_test.dart`（本地守卫，`flutter test` 里跑）。
- ⛔ 刻意**不让 Gradle 去读仓库根的 pubspec** —— `android/` 是独立原生工程，
  那样会把两条构建链路重新焊死；所以是「手写字面量 + 机器守卫」。

**验证**：`flutter analyze` → `No issues found!`；新单测 `+4 All tests passed!`；
`--check --tag v0.1.5` 故意用旧 tag ⇒ 退出码 1；`--tag main` ⇒ 跳过 tag 项；
`./gradlew :app:assembleRelease --dry-run` 通过。

**踩坑**：① `repoRoot` 不能靠 `Platform.script` 推（被单测 import 时指向 flutter_test 宿主）；
② CLI 第一版只认 `--set=x`，`--set x` 被**静默忽略**且退出码 0 —— 已改成两种写法都认。
