### 2. 抓到并修掉 TV 页头横向溢出 145px（complaint ③ 的真根因）

`PageHeader` 的 TV 分支原来是 `Row(children: actions)`。媒体库页头那一行有
**六个**控件（视图切换 / 搜索框 / 排序 / 筛选 / 选择 / 刷新），而 TV 上页面只

  **两者必须在测试里分开给**。

### 5. 面板开关的路由抽成纯函数 `resolveTvPanelKey`（+7 条测试）

`_handleTvPanelKey` 原来是**方法**，而同一个文件里 `resolveRemoteKey` 的文档
明写「路由判断本身在纯函数里，`_onRemoteKey` 只负责执行」—— 那我自己加的那段
就违反了这条约定，而且一行测试都没有。抽成 `resolveTvPanelKey` 并补 7 条：

- **必须在 `resolveRemoteKey` 之前判**：后者「沉浸模式下任何认识的键 →
  `showControls`」会把菜单键吃掉，沉浸时按菜单键只会叫回控制栏、面板打不开。
- 菜单键不挑焦点，开 / 关同一个键。
- ↑ 只在「面板关着 **且** 焦点真在画面上」时接管。
- ⛔ **↓ 绝不接管** —— 咽喉所在：↓ 是画面 → 控制栏的唯一通路，而控制栏上有
  「设置」按钮，那是**没有菜单键的遥控器上唯一一条进面板的路**。

顺手确认了两件之前只是**假设**的事：
① `select` → `ActivateIntent` → `InkWell.onTap` 靠 `WidgetsApp` 默认快捷键表成立
（所以电视上「按 OK 选一集」是通的）；
② Dart 3 的 `switch` 语句**不穿透** —— `_activate` / `PlayerTvPanel` 里那些
不写 `break` 的 `case` 是安全的（我那条「↑ 从第一行绕到最后一行」的断言顺带
证了它：若穿透，结果会是 `[6, 0]` 而不是 `[6]`）。

另外顺带审了一遍「遥控器够不到」的常见成因：全 `lib/ui/` 里只有 4 处
`GestureDetector`（播放器画面手势层 ×2、`anchored_menu` 吃点击 ×1、
`player_page` 沉浸点击 ×1），**主界面没有任何 tappable 是 `GestureDetector`**；

（前三者已包 `TvFocusable`）。所以「够不到」不是这个原因造成的。

### 新文件 `test/support/focus_reach.dart`（共用判定）
- ⛔ **判据不能是 `Focus.of(...).hasFocus`**：`TvFocusable` 是
  `Focus(canRequestFocus: false)` **只观察**，真正吃焦点的是里面的 `InkWell` ——
  `Focus.of` 拿到观察者，**永远 false**，会得到一直红的假警报。
  正确做法：从 `FocusManager.instance.primaryFocus` 出发**往上走祖先链**找目标。
- **目标方向要挑对**：`TvFocusable`/`TvIconLabel` 包着 `InkWell` → 用它们；
  文件夹的行是**裸 `InkWell`**，行里那段文字是它的**后代** → 得用
  `find.ancestor(of: 文字, matching: InkWell).first`。
- 走 **Tab** 而不是方向键：方向键依赖几何（网格 ↓ 落哪一格取决于间距），
  换个 `posterAspect` 就飘。

## DV 片源颜色错乱：根因锁定在 libmpv 没编译 libplacebo（11:18 用户报）

用户报：`/来自：分享/D 笗峸猎讻/4K DV杜比视界 高码率/01.mkv`，
夸克自带播放器颜色正常，云影偏绿/偏紫。**只做分析，没改代码。**

### 结论（三层，每层都有本机产物证据）

1. **Dolby Vision 不是 YCbCr**。Profile 5 的像素是 Dolby 私有的 **IPT-PQ-C2**，
   播放器必须读 HEVC 里 type 62 的 **RPU** 元数据再做 IPT→RGB。mpv 里**只有
   libplacebo 会做这件事**（`pl_map_avframe` + `PL_COLOR_SYSTEM_DOLBYVISION`，
   入口是 `vo=gpu-next`）。跳过 RPU = 把 IPT 当 YCbCr BT.2020 PQ 解 → 颜色全错。

2. **media_kit 两份 libmpv 都禁用了 libplacebo**（实测，不是推测）：
   - macOS `media_kit_libs_macos_video 1.1.4` 的
     `macos/Frameworks/Mpv.xcframework/macos-arm64_x86_64/Mpv.framework/Versions/A/Mpv`
     → `strings` 读出 **`mpv 0.36.0`**，waf 配置行写着
     `-Dlibplacebo=disabled -Dvulkan=disabled`（同时有 `-Dgl=enabled
     -Dgl-cocoa=enabled -Dvideotoolbox-gl=enabled`）。
   - Android `media_kit_libs_android_video 1.3.8` 的 `android/build.gradle`
     写死下载 `media-kit/libmpv-android-video-build` **v1.1.7**；该 tag 的
     `buildscripts/scripts/mpv.sh` 同样是
     `-Dvulkan=disabled -Dlibplacebo=disabled`。**v1.1.8 / v1.1.11 也没改**。
   - **判据**：`strings Mpv | grep -c "gpu-next"` = **0**。二进制里根本没有这个
     vo，`VideoControllerConfiguration.vo` 传 `gpu-next` 进去也是静默无效。
   - 源码级旁证：mpv v0.36.0 `meson.build:932-939` —— `vo_gpu_next.c` 只在
     `features['libplacebo']` 且 `libplacebo >= 5.264.0` 时才编进 sources。

3. **为什么只有 DV 片源炸、HDR10 片源正常**：mpv 0.36 的
   `video/out/gpu/video.c`（legacy `vo=gpu`）**不 include libplacebo**，是自带
   GLSL 的渲染器，`--tone-mapping` / `--hdr-compute-peak` 都在。
   `-Dlibplacebo=disabled` 只砍掉 `vo=gpu-next`，**没砍掉 HDR10 的色调映射**。

### 本项目现状：一处都没配（改颜色目前无旋钮）

- 桌面 `playback_controller.dart` / `player_window_app.dart` 都只写
  `VideoControllerConfiguration(enableHardwareAcceleration: true)` → 默认
  `vo=libmpv` + `hwdec=auto`（`media_kit_video` 的
  `native_video_controller/real.dart:119-122`）。
- Android 默认 `vo=gpu` + `opengl-es=yes` + `gpu-context=android` +
  `hwdec=auto-safe`（`android_video_controller/real.dart:186-208`）。
- `lib/` 全树 grep `'vo'|gpu-api|gpu-context|tone-mapping|target-prim|target-trc|hwdec`
  → **零命中**。

### 症状轻重由 profile 决定（别混为一谈）

| profile | 无 DV 支持时的表现 |
|---|---|
| **P5**（单层 IPT） | 颜色彻底错 → **就是本症状** |
| **P8.1**（HDR10 兼容基底） | 退化成 HDR10，颜色大致对 |
| **P7**（UHD 蓝光双层 FEL/MEL） | 只解 BL，HDR10 观感，非 DV |

⚠️ 本机库里同批 DV 片源大多是 WEB-DL 的 `DV.HDR`（P8.1 面大），
但用户报的这份在 `4K DV杜比视界 高码率` 目录下、且**尚未入库**（库里
`dir_path like '%杜比视界%'` 查不到它）—— 说明是从**文件夹页直接播**的。
**profile 没验，属未证实**。下一步该先验 profile 再谈修法。

### 修法（按代价排，都还没做）

1. 自编译带 **libplacebo ≥ 5.264** 的 libmpv → `vo=gpu-next`。
   macOS 可行：mpv 0.36 的 `video/out/gpu_next/context.c` 里有
   `#include <libplacebo/opengl.h>` + `pl_opengl_create()` →
   **OpenGL 后端就能跑 gpu-next，不必上 MoltenVK**。
   ⚠️ `media_kit_libs_macos_video` 最新就是 1.1.4，**升级包没用**，得换 framework。
2. HDR10 兜底：对 P8.1/P7 有效，**对 P5 无效**。
3. 只告知用户「DV P5 不支持」——诚实但不解决。

### 怎么验 profile（下次第一步，别先猜）

- `ffprobe -show_streams` 看 `side_data_list` 的 `Dolby Vision configuration`。
- libavcodec 会打 `Found Dolby Vision config record: profile %d level %d`
  （本机 Mpv 二进制里**确实有这个字符串**）。⚠️ 但它是 **verbose** 级，而两个
  播放器的 `PlayerConfiguration.logLevel` 分别是 `warn`（独立窗口）/
  默认 `error`（内置页）→ **当前收不到**，要看得临时抬级。
- mpv 0.36 只暴露 `video-params/primaries`、`/gamma`、`/colormatrix`、
  `/colorlevels`（**没有 DV 专用属性**）。

## 一次「排查完发现没问题」的审计 + 补上「看得见焦点」这条断言

顺着「PC 交互模式在 TV 上体验不好」这条诉求，把 TV 上可能**没有对应物**的交互
逐个查了一遍。结论：**没发现新 bug**，只有一处设计取舍。写下来免得下次重查

|---|---|

### 补了一条断言：够得到 ≠ 看得见
原来的可达性用例只证明焦点**走得到**。而「走得到但看不见焦点在哪」在电视上和

所以「焦点环没出现」可能是「焦点没到位」、也可能是「档位还没翻」，只有断言分得清。

  （grep 可证），而它与焦点环由**同一个** `_showRing` 控制。
- ⛔ 先断言「还没按键时 `findsNothing`」（反空转）：少了它，在「焦点环压根没接
  highlightMode」时断言照样绿 —— 而那正是桌面上「鼠标点过的卡片留一圈环」的成因。
- 实测：`tester.sendKeyEvent` 在 `flutter test` 里**确实会让 highlightMode 翻档**
  （`walkReachability` 发的 Tab 就够了），不用手工改 `highlightStrategy`。
- 反向对照：把 `focusScale` 改成 `1.0` → 红，报「焦点环没画出来…」。

## 诉求② 找到另一半：**卡帧有两条独立的路，上一轮只修了一条**

上一轮为「原画卡帧 / 音画不同步」做的只有**缓冲参数**（缓存 256MB、预读 60s、

### 事实链（每条都可复现）
1. **mpv 的 `hwdec` 默认是 `no`** —— 纯软件解码。
2. **media_kit 不设它**：`media_kit-1.2.6/lib/src/player/native/player/real.dart`
   约 2389–2416 行那张默认 `properties` 映射里有
   `scale / dscale / dither / cache / cache-on-disk / hr-seek / ao /
   subs-fallback / …`，**没有 `hwdec`**（grep 整个包零匹配）。
3. **本项目也不设它**：全仓 grep `hwdec` 零匹配。
4. `PlayerConfiguration` **没有**任意属性 map（只有 `vo/osc/bufferSize/libass/
   title/muted/pitch/…`），所以只能走 `PlayerBufferConfig.apply` 的 `setProperty`。

⇒ 电视盒子一直在**软解**高码率原画，而那颗 SoC 通常只够软解 1080p。
   解码跟不上音频 → mpv 跳帧追主时钟 → 正是用户描述的「卡帧 + 音画不同步」。

### 关键区分：两条路不能互相代替
| 症状 | 原因 | 谁负责 |
|---|---|---|
| 卡帧 | 数据没到位（网络抖动 / eMMC 抢带宽） | 缓冲参数 |
| 卡帧 **+ 音画不同步** | **解码跟不上** | **`hwdec`** |

### 改法：只给 TV，取值 `auto-safe`
- ⛔ 不能用 `auto`（会试不安全的 API，崩溃 / 花屏）、不能写死 `mediacodec`
  （直通路径，渲染端配不上就是**黑屏**）。
- `auto-safe` 只用安全列表（Android 上解析成 `mediacodec-copy`：硬解 + 帧拷回
  内存再上屏），配不上**回落软解** —— 最坏情况等于没改。
- 桌面返回 **`null`（不下发）**，不是 `'no'`：下发 `'no'` 也是改桌面行为
  （把默认显式化，且挡住将来给桌面开硬解）。专门一条用例钉「null vs 'no'」。
- 策略日志那行加了 `hwdec=`。

### ⚠️ 没做到的那一步（诚实记一笔）
日志记的是**请求值**，不是**实际生效**的解码器。要知道真的有没有启用，得读 mpv 的
**`hwdec-current`**，而它**必须在起播之后**读（`apply` 那一刻还没开始解码）。
这需要给播放控制器挂一个起播后的钩子 —— 这轮没做。

- ⚠️ **只能真机验证**：`auto-safe` 在用户盒子上解析成哪个 API、有没有真的启用、

### 根因：**scope 隔离**，不是几何

侧栏那 6 项的位置**完全符合** `←` 的筛选条件（`node.rect.center.dx <= target.left`，
侧栏 tile 的 InkWell 是 `(60,100.5,276,151.5)`，内容区从 `x=288.5` 起）。
真正的原因是 `StatefulShellRoute.indexedStack` **给每个分支一个独立 `Navigator`**，
于是每个分支页有自己的 `FocusScope`；而 `FocusTraversalPolicy.inDirection`
（`focus_traversal.dart:1070`）只在 `currentNode.nearestScope.traversalDescendants`
里找候选，**找不到就返回 false，不向上冒泡到父 scope**。侧栏是分支页的**兄弟**，
在外层 scope 里。

探针打出来的两条硬证据：
1. 焦点在内容区时 `nearestScope.traversalDescendants` **只有 1 个节点**（它自己）；
   焦点在侧栏时同一个方向键就通 —— **同一个键，结果只取决于焦点在哪一边**。
2. 祖先链：`c0 → _ModalScopeState FocusScope(分支) → Navigator → FocusTraversalGroup
   → _ModalScopeState FocusScope(壳) → Navigator → …`。侧栏在**外层**那个 scope。

⚠️ **Tab 两个方向都能跨**（`_moveFocus` 会爬 scope 边界），**但真机遥控器没有 Tab**。
所以「Tab 能到」不能当作「遥控器能到」—— `test/support/focus_reach.dart` 开头那段
「Tab 只当可达性代理」的说法在这里**失效了**，这条得改（见下）。

#### ① 方向键进不去 → 壳层兜底（`lib/ui/shell/app_shell.dart`）

判据链条（**顺序不能换**）：

1. `_arrowDirectionOf(event)` —— 只认**裸**方向键。`event is KeyDownEvent || KeyRepeatEvent`；
   ⛔ **`HardwareKeyboard.instance.isControlPressed` 时必须返回 null**：框架默认表里

3. 只有它返回 false（=「最近那个 scope 里确实没有」）才走几何兜底

   `canRequestFocus && !skipTraversal && context != null` 且**在侧栏子树内**的节点，
