## 追加：两个实测问题的根因与修复（同日 17:20 前后，**未 git 提交**）

### 问题 A：mp4 4K「有声音、进度条正常、没画面」

**两个独立原因叠加，而且都不报错：**

**A1（真凶）`VideoController` 绑错了 Player** —— `playback_controller.dart`：

```dart
final mk.Player player = mk.Player();
final VideoController videoController = VideoController(mk.Player(), ...);  // ← 新建的实例！
```

给 `VideoController` 传的是**新建的** `mk.Player()`，不是真正在播的 `player`。
于是「解码」和「出画面」落在两个互不相干的 mpv 实例上：`player` 解码音频
（声音、进度条都正常），但它**从来没有视频输出端**，画面永远空。

修法：在**构造函数体**里 `videoController = VideoController(player, ...)`。
两个约束都不能省：
- 不能写成字段初始化器 —— Dart 实例字段初始化器不允许访问 `this`；
- 不能改成 `late final` 惰性初始化 —— 播放页是在 post-frame 回调里才 `open()`，
  惰性初始化等于把正确性押在「UI 恰好先 build 过一次」的时序巧合上。
  **mpv 必须在 `open()` 之前就拿到视频输出端。**

**A2（放大伤害）错误遮罩盖住画面** —— `player_page.dart` 的 `_ErrorOverlay`
是 `AppTheme.cinema.withValues(alpha: 0.88)` 的**全屏**遮罩，只要 `error != null`
就铺满 stage。于是任何非致命错误都会让画面消失、声音照常。

修法：新增 `_notice` 通道（控制器）+ `_NoticePill`（贴顶小药丸、可关闭、不遮挡）。
非致命的事（字幕没挂上、选的档位服务端没给地址）走 notice；
`_error` 只留给「播放真的死了」的情况。

### 问题 B：「内嵌字幕缺少轨道号」

**根因**：media_kit 在 `track-list` 前面**硬塞两条合成轨**。
`media_kit-1.2.6/lib/src/player/native/player/real.dart:1713`：

```dart
final subtitle = [SubtitleTrack.auto(), SubtitleTrack.no()];
```

它们的 `id` 是字符串 `'auto'` / `'no'`（`models/track.dart` 里写死），
**不是 mpv 轨道号**。老代码遍历 `tracks.subtitle` 时把这两条也当真实内嵌轨 →
`int.tryParse('auto')` = null → `embeddedTrackId == null` → 报错。
更糟的是自动选字幕取 `all.first`，而合成轨**永远排第一** → 每次播放必错。

**实测铁证**：日志 `内嵌轨更新：字幕 2 条、音轨 2 条、视频 2 条` ——
每一项**正好是 2**，就是那两条合成轨；那个 mp4 根本没有内嵌字幕。

修法：新增 `PlaybackController.realTracksOf<T>(tracks, idOf)`（`@visibleForTesting`
静态纯函数），剔除所有 id 不是整数的轨道，视频/音频/字幕三处共用。
抽成静态是为了能脱离 mpv 单测 —— media_kit 的轨道基类 `_Track` 是**私有**的，
没法写 `T extends _Track`，所以用 `idOf` 把「怎么取 id」传进来。

### 问题 C（用户第 1 条）：扫描中媒体库里看不到已发现的媒体

**根因**：作品行只在遍历**全部结束之后**由阶段二创建。大库要遍历几千个目录、
跑几十分钟，这期间 `media_works` 恒为 0，而媒体库页读的正是这张表 →
空态文案还是「媒体库还是空的，点『扫描』…」，与事实相反。

修法：
- `scan_service.dart` 新增 `dirtyWorkKeys` + `flushWorks()`，在**每个目录边界**
  （以及遍历收尾）把新出现的分组建成作品行。与阶段二走同一个 `upsertWorks`
  入口，所以 `mergeWorkForUpsert` 的「保护已有元数据」规则照常生效。
- `library_page.dart` 的 `_NeverScannedState` 区分两种空：扫描进行中 →
  「正在扫描网盘… 已遍历 N 个目录、发现 M 个媒体文件」。

### 结论（对「云影」的可借鉴点）

1. **夸克的「播放窗口独立」= 独立进程 + Flutter 窗口**，不是「同一进程里的第二个窗口」。
   代价换来的是：播放崩溃不拖垮主界面、退出即整进程回收（天然满足 Android TV「返回即释放」）。
2. **预热 + 单例复用**（`PreCreatePlayerWindow` / `GetOrCreatePlayerWindow` / `sys.warmupPlayer`）
   是消除「点击到出画」延迟的关键，且只在 Windows 侧启用；macOS 侧只有 `OpenFlutterModuleWindowUTF8`。
3. **跨语言传参用 `--key=value` 扁平字符串数组**，反向回调用 `--base-pointer` 传函数指针 ——
   避免结构化 IPC 的序列化开销。本项目若走多窗口，可直接照抄这个约定。
4. **VidHub 的「最小化时自动暂停」开关**是本项目「返回后还在播」的现成产品答案；
   而「Android TV 返回即释放」本项目已实现。
5. **VidHub 用 libmpv render API 自绘**，与本项目 media_kit 的 `VideoController` 同路 ——
   说明当前技术选型方向正确，差距在**字幕/渲染调优项**（deband/dither/icc/tone-mapping/HDR、
   `enableOverwriteAssStyle`、字幕编码探测、图形字幕 OCR、双字幕）。
6. 本项目若要「PC 端真独立窗口」，最贴近夸克形态的是 `multiview_desktop`（单引擎多窗口），
   但它要求 Flutter ≥3.38.2，当前 3.29 不兼容。

## PC 端独立窗口：决策依据核实（2026-09-30 晚，pub.dev 实测）

用户目标明确：**PC 端播放器要独立窗口播放**。核实结论：

| 包 | 最新版 | 发布 | `environment` | 引擎模型 |
|---|---|---|---|---|
| `multiview_desktop` | 1.2.2 | 2026-09-01 | `sdk >=3.10.0 <4.0.0`、`flutter >=3.38.2` | **单引擎单 isolate**（Flutter multi-view API），`runMultiApp` |
| `desktop_multi_window` | 0.3.1 | 2026-08-26 | `sdk >=3.5.0 <4.0.0`、`flutter >=3.0.0` | 每窗口独立引擎 |
| `window_manager` | 0.5.2 | 2026-07-04 | `sdk >=3.0.0 <4.0.0`、`flutter >=3.3.0` | — |

本项目现状：Dart `^3.7.0`、Flutter 3.29，**pubspec 里没有 window_manager，也没有任何多窗口包**。
macOS Runner 是标准模板（`MainFlutterWindow.swift` 里 `FlutterViewController()` + `RegisterGeneratedPlugins`；
`AppDelegate.swift` 里 `applicationShouldTerminateAfterLastWindowClosed → true`）。

### `desktop_multi_window` 0.3.1 实测能力（读 pub.dev README + dartdoc 得到）

- macOS 集成**只需改 `MainFlutterWindow.swift` 两行**：
  `import desktop_multi_window` + `FlutterMultiWindowPlugin.setOnWindowCreatedCallback { RegisterGeneratedPlugins(registry: $0) }`。
- **自带 `WindowMethodChannel` 双向通信**（`setMethodCallHandler` / `invokeMethod`），跨引擎可用。
- `WindowController.create(WindowConfiguration(hiddenAtLaunch: true, arguments: '...'))`
  → **支持隐藏启动 = 预热窗口**（对应夸克的 `PreCreatePlayerWindow`）。
- `WindowController` 只有：`hide()` / `show()` / `invokeMethod()` / `setWindowMethodHandler()` /
  `create()` / `fromCurrentEngine()` / `getAll()`；**没有尺寸/位置/标题控制**。
- `WindowConfiguration` 只有 `arguments`(String) + `hiddenAtLaunch`(bool) 两个字段 → **尺寸/标题必须靠
  `window_manager` 或自写插件**。
- 官方 README 明确写 *"Each window created by this plugin has its own dedicated Flutter engine.
  Method channels cannot be shared between engines, so plugins must be manually registered for each new window."*
- 官方 example 里列了 *"Plugin registration for video playback"* → 子窗口播视频是已验证用例。
- README 建议 `window_manager` 用 fork（`boyan01/window_manager` ref `6fae92d2…`）；
  但 `window_manager` 0.5.0 changelog 已有 `feat: Add getId method for retrieving window ID on macOS and Windows`
  与 `fix: Crash when using window_manager by multi engine on Windows platform (#546)` ——
  **该修复只标注 Windows，macOS 子窗口控制能否正常工作必须实测**。

### 已向用户给出的建议

**推荐 `desktop_multi_window`，不为该功能升 Flutter。** 理由：
1. `multiview_desktop` 需 Flutter 3.29 → ≥3.38.2（Dart 3.7 → ≥3.10），连带 `go_router` 14→1x、
   `flutter_riverpod` 2.6→3.x、`drift`、`flutter_secure_storage` 9→10、`flutter_inappwebview`、
   `media_kit` 全家桶与 macOS 构建链（entitlements / 部署目标 / mpv 符号链接）全部重验。
   用一个 9 个版本的地基大跳换一个 UX 功能，风险收益不成比例。
2. `desktop_multi_window` 兼容当前 SDK，且自带跨窗口通道与隐藏启动预热。
3. **关键设计**：把「播放」与「媒体库」解耦本身是对的架构 —— 引入 `PlayerHost` 抽象作为**唯一切换点**，
   桌面实现 = `WindowMethodChannel` 跨引擎，电视实现 = 同进程直连。将来若升 Flutter 到 multiview_desktop，
   只换实现，播放器 UI 一行不改 —— 这活儿不会白做。

### 该方案的已知代价（已如实告知用户）

1. 播放窗口成为自包含迷你应用：自己建 `Player`，经通道拿参数、回报进度。
2. 需设计双向协议：`open` / `refreshTicket` / `switchQuality` / `progress` / `closed`。
3. **夸克 ticket 有时效** → 协议里必须包含「播放窗口向主窗口请求刷新 URL」的回路（最易被低估）。
4. 尺寸/标题/全屏需 `window_manager` 或自写约 120 行 macOS 窗口插件。

### 附带收益

- 「返回后还在播」的怪异状态消失：PC 上关掉播放窗口即停止释放，媒体库窗口的返回不再影响播放。
- 语义统一：PC「关窗即停」≡ Android TV「返回即停」；`PlaybackExitBehavior` 里桌面的
  `keepPlaying` 可以退场。
- Android TV 不受影响（单窗口 + `stopAndRelease` 保持不变）。

### 建议的落地顺序（每阶段独立可验证）

1. 装 `desktop_multi_window` + 改 `MainFlutterWindow.swift` → **开一个空白第二窗口跑通**
   （验证引擎创建 / 插件注册 / 双向通道 / media_kit 在子窗口能出画）。**纯验证，不改现有代码。**
2. `PlayerHost` 抽象 + `WindowPlayerHost`；`playbackControllerProvider` 改为由 host 提供。
3. 播放窗口复用 `player_page.dart` 舞台层。
4. 进度回报 + 关窗释放（复用已实现的 `stop()`）。
5. ticket 刷新协议。
6. 尺寸 / 标题 / 全屏 / 置顶。

**本轮未改动任何项目代码**，只做调研与建议。等用户选定路径再动手。

### 排掉的最大未知数：子引擎能不能出画 → **能（静态证据充分）**

- `MediaKitVideoPlugin.register(with:)` 用的是 `registrar.textures`（**每引擎各自的**纹理注册器），
  每次注册都 new 一个 `VideoOutputManager(registry:)`，method channel 绑在 `registrar.messenger`。
  **没有任何全局单例。** 所以 `MainFlutterWindow.swift` 里那句
  `setOnWindowCreatedCallback { RegisterGeneratedPlugins(registry: controller) }`
  确实能给子引擎一份独立纹理注册器 → `Video(controller:)` 在子窗口能出画。
- `MediaKit._initialized` 是 **per-isolate 静态字段**（不是进程级单例），所以两个引擎各调一次
  `MediaKit.ensureInitialized()` 是**必须的**，不是冲突。它在 `main.dart` 里放在分流**之前**是对的。
- `asset:///assets/x.mp4` 的解析链已逐行核对：`normalizeURI` → `AssetLoader.load` →
  `encodeAssetKey` 会**去掉前导斜杠** → key `assets/player_selftest.mp4` → macOS 落到
  `Contents/Frameworks/App.framework/Resources/flutter_assets/assets/...`（该文件已确认存在）。
- 原生参数契约再确认：`project.dartEntrypointArguments = ["multi_window", windowId, config.arguments]`。

### 修掉一个「会白跑一轮实测」的假故障

**`ChannelMode.bidirectional` 的调用方自己也必须在配对里。** 原生
`ChannelRegistry.getTarget(for:from:)` 第一步是
`guard candidates.contains(where: { $0 === window }) else { return nil }`。

我原来的 `PlayerWindowApp._runSelfCheck()` 直接 `invokeMethod(ping)`，但子窗口**从未注册过**这个
通道 → 必然拿 `CHANNEL_UNREGISTERED`，而且自检页会把它显示成「跨引擎通道不通」——
看起来像插件不支持，其实是调用方没入场。

修法：把处理器提到 `player_window_bridge.dart` 的顶层 `handleMainWindowCall(MethodCall)`
（协议归属地，且该文件已 import `services.dart`），自检里先
`setMethodCallHandler(handleMainWindowCall)` 再 ping，并单独加一行「通道入场（本窗口）」的检查。

### 新发现的一个真实缺陷：关窗不通知 Dart（阶段四必须解决）

插件 macOS 侧 `FlutterWindow.init` 观察 `NSWindow.willCloseNotification`，但回调里**只做**
`MultiWindowManager.shared.removeWindow(windowId:)` —— **不销毁引擎、不通知 Dart**。
加上 `CustomWindow.isReleasedWhenClosed = false`，`contentViewController` 没有任何地方被释放。

后果（两种可能，都指向同一个 bug）：
1. 引擎活着 → `PlayerWindowApp.dispose()` **不执行** → mpv 原生线程继续出声；
2. 引擎被销毁 → 也不跑 `dispose()` → mpv 句柄泄漏，原生线程照样出声。

即 **「关掉播放窗口，声音还在放」**。这正是「返回后还在播」那个问题在 PC 上的新形态。

- 判定手段已埋好：`dispose()` 里加了一行 `diag.info('播放窗口', '播放窗口已释放（dispose 执行了）')`。
  关窗后去诊断页搜「播放窗口已释放」——搜不到就是情况 2。
- 可预测的连带故障：若引擎不销毁，它的 `WindowChannel` 也不 deinit → 不 unregister →
  再开一个播放窗口会撞 `CHANNEL_LIMIT_REACHED`（bidirectional 上限 2）。
  这条如果出现，等于同时证明了「引擎没销毁」。
- 修法方向：原生侧关窗钩子（自写约 30 行，或子窗口用 `window_manager` 的
  `onWindowClose` + `setPreventClose`）。**阶段六本来就要 `window_manager`**，可合并解决。
- 另一个已确认的正面事实：`window_show` 会 `NSApp.activate(ignoringOtherApps: true)`，
  所以「复用已有窗口并置前」是有效的。

### 阶段二的设计修正（未实施）

读 `PlaybackController`（763 行）与 `app_providers.dart` 后，原计划的「`PlayerHost` 镜像整个
controller API」**不是最合适的形状**。更贴合的切分是：

- **主窗口**保留适配器 / 凭证 / 数据库 / 取链（`adapter.resolveStream`）—— 鉴权相关的东西留在一处；
- **播放窗口**只拿 `{url, headers, title, 字幕, 起播位置}` 出画，不碰网盘凭证；
- 回报方向：播放窗口 → 主窗口（进度 / 状态 / 错误），主窗口负责 `markPlayed` 落库；
- 阶段五的 ticket 刷新天然落成「播放窗口向主窗口要新 URL」，与夸克 `sys.openVideoPlayer` 同形。

也就是边界是**一个播放请求 DTO + 一条回报流**，而不是把 controller 的 30 个方法镜像过去。
这比原计划小得多，且 `PlaybackController` / `player_page.dart` 基本不用改（Android TV 路径原样保留）。

**待用户实测后再动这一步** —— 若四项自检有任一项红，这个设计要重估。

## 阶段四/六部分落地：窗口标题尺寸 + 关窗释放（2026-09-30 晚）

### 自写极小原生窗口通道，不引入 `window_manager`

`macos/Runner/MainFlutterWindow.swift` 里新增 `ChildWindowController`（约 90 行）：

- 在 `setOnWindowCreatedCallback` 里 `ChildWindowController.attach(to: controller)`，
  从 `controller.view.window` 拿子窗口 —— **此刻才是正确时机**（插件已把
  `contentViewController` 装好并 `orderFront` 了）。
- `applyDefaults()`：`title = "云影 · 播放器"`、`setContentSize(1200×675)`、
  `minSize 640×360`、`center()`。
  ⚠️ 用 `setContentSize` 而不是 `setFrame`：后者算的是含标题栏的外框，
  直接给 1200×675 会让**画面区域**矮掉一个标题栏的高度。
- 通道 `cloudcine/window`：`setTitle` / `close`。
- `windowWillClose` → `channel.invokeMethod("onClosing")` 通知 Dart 释放 mpv。
- **强引用表 `instances` 必须有**：`NSWindow.delegate` 是 weak 的，只赋给 delegate
  的话实例立刻被回收，`windowWillClose` 再也不触发。

**为什么不用 `window_manager`**：它在多引擎下的 macOS 行为没被验证过（多引擎修复
只标注 Windows），而这里只需要三件事。为三件事引入行为未知的大依赖不划算。

### 为什么用 `windowWillClose` 而不是 `windowShouldClose`

后者返回 false 能取消关闭、等 Dart 回话再关，握手更可靠 —— **但它在退出应用时也会
被调到**，一旦因等不到 Dart 回话而返回 false，就变成**应用退不掉**。那比「声音还在
放」严重得多。所以选非阻塞通知。

确定性的那条路放在 UI 上：播放窗口新增 **「停止并关闭」** 按钮 —— 先
`_releasePlayer()`（stop + dispose）再 `closeChildWindow()`，不依赖通知时序。

### 释放幂等

`_releasePlayer()` 幂等（关窗通知与 `dispose()` 常前后脚发生，重复 dispose 一个已释放
的 `Player` 会抛），且**不调用 `setState`**（可能从 `dispose()` 里被调到）。

### 踩到的坑

`MethodChannel.setMethodCallHandler` 返回 **`void`**，不像 `desktop_multi_window` 的
`WindowMethodChannel.setMethodCallHandler` 返回 `Future` —— 写 `await` 会报
`use_of_void_result`。已修。

## 阶段四落地：进度回报 + 诊断页「复制路径」（2026-09-30 晚）

### 修掉自己引入的回归：「最近播放」在独立窗口播放时不更新

接上独立窗口后，播放发生在**另一个引擎**里，主窗口的 `PlaybackController`
根本没被 `open()` 过 → 它的 `onPositionTick` 永不触发 → 而 `markPlayed`
正是挂在那个回调上。

⚠️ 措辞纠正：`MediaRepository.markPlayed` **只写 `lastPlayedAt` 时间戳**
（`media_repository_impl.dart:273`），库里**没有**续播位置字段。
所以丢的不是「续播位置」，是「最近播放排序与已看标记」。

修法：**播放窗口每 10 秒把位置报回主窗口，由主窗口落库**。

- `PlayRequest` 加 `itemId`（本地行号，不是凭证；只为回报用）。
- 新增 `PlaybackProgressReport{itemId, position, duration}` + 畸形输入返回 null
  （**没有 itemId 就没有意义**，主窗口拿到也不知道更新哪一行）。
- 新增 `ProgressThrottle`：**整十秒边界**节流（与
  `PlaybackController._maybeTickPosition` 同一套办法，但**各自独立实现**是有意的 ——
  它们跨了引擎边界，一边改粒度不该牵连另一边）。
  - `<=0` 秒不报（刚打开就报会把上次进度覆盖成 0）；
  - 同一个整十秒只报一次（mpv position 是 ~100ms 一条的高频流）；
  - **换片必须 `reset()`** —— 否则新片恰好停在上一部片报过的那个整十秒上时，
    那次回报会被当成重复吞掉。
- `player_window_bridge.dart` 加全局 `onPlaybackProgress` 回调 + `reportProgress`
  分支。回调**必须由 UI 层装上**（`playbackProgressReporterProvider`）——
  这个文件在 `main()` 里就被调用，那时还没有 Riverpod 容器。
- 新增 `lib/ui/windows/playback_progress_reporter.dart`；`lib/ui/app.dart` 加
  `ref.watch(playbackProgressReporterProvider)`。
- `player_window_app.dart`：`_subs` 订阅表（`position` 流）、`_currentItemId`、
  `_reportProgress`；`_releasePlayer()` **先取消订阅再 stop+dispose** ——
  否则 dispose 过程中还会发一条指向已释放播放器的消息。

## 阶段五落地：刷新过期直链（2026-09-30 晚）

网盘直链是**带签名的临时 URL**，几十分钟就过期。播放窗口手里只有一条死链，
它没有（也不该有）重新取链的能力 —— 取链要凭证、要走四路由降级，那套东西
留在主窗口。所以补一条「播放窗口 → 主窗口」的回路。

### 触发时机：让它在坏的地方修，不做提前刷新

**过期只在「下一次真正发起请求」时暴露**，最典型的是拖进度条（mpv 会重新发
Range 请求）。已建立的连接通常还能继续读 —— 签名是请求时校验的。
所以：

- **不做定时提前刷新**：那要么没有触发时机，要么得打断正在播的流（更糟）。
- **唯一触发点是 `player.stream.error`**：与内置播放页同一套过滤
  （`failed` / `error`）。

### 协议

- `PlayRequest` 加 **`qualityId`**（机器可读的档位标识）。原来只有
  `qualityLabel`（人话标签）—— 刷新时只带 label 的话，主窗口只能退回
  「设置里的默认档位」，**用户手选的档位会在一次刷新后静默跳回默认**。
- 新增 `TicketRefreshRequest{itemId, qualityId, position}`。
  **刻意不带 URL** —— 主窗口只需要知道「哪一项」，把旧链带回去只会让人忍不住
  去复用一条已经失效的链。
- 新增 `PlayerBridgeMethod.refreshTicket`，返回 `PlayRequest.toJson()` 或 null。
- 新增全局 `onTicketRefresh` 回调（与 `onPlaybackProgress` 同样的理由必须由
  UI 层装：`main()` 阶段还没有容器）。

### 新增 `TicketRefreshGuard`：防死循环 + 防一次用满

很容易写出 `mpv 报错 → 刷新 → 重开 → 还报错 → 再刷新` 的死循环，而**非时效性**
的失败（文件损坏、编码不支持、网盘侧删了）刷新多少次都不会好。所以：

- `maxAttempts = 3` 上限；
- 但光有上限太脆 —— 一部长片撞两三次过期是正常的，用满后整场都不能再刷。
  所以要能判定「这次刷新有效」并清零。
- **判定口径不能是「open 没抛异常」**：失效的直链照样会被 mpv 接受，然后在
  解复用阶段才报错，那时 `open` 早就返回了。用两个条件同时成立：
  1. 从刷新那一刻起墙钟过了 ≥ 30s（期间没再报错）；
  2. 位置确实往前走了 ≥ 30s。
  条件 2 单看有假阳性（用户往后拖进度条会让位置一次跳很远），条件 1 排除它。
- 时钟由调用方注入，否则只能靠 `sleep` 测。

### 拆 `_play` / `_openStream`：一个容易写死的坑

刷新必须能绕过 `_play` 的重入闸。**直链过期导致的报错经常在上一次 `open()`
还没返回时就到了**，那时 `_busy` 是 true —— 走 `_play` 会被静默吞掉，
表现就是「刷新功能明明写了却从不生效」。所以：

- `_openStream` —— 真正 `open`，**无闸**；
- `_play` —— 带闸的入口（用户 / 主窗口发起）；
- `_refreshTicket` 直接调 `_openStream`；
- 另设 `_refreshing` 防刷新之间的重入，与 `_busy`（给按钮看的）分开。

### 顺手修掉一个隐蔽 bug：自检视频会污染「最近播放」

原来自检视频 / 手输直链直接调 `_play`，**没有清掉条目上下文**。先播库里的
第 102 项、再点「播放内置自检视频」，`_currentItemId` 还指着 102 ——
自检视频播到 10 秒就把进度报成了 102。

修法：把 `_currentItemId` 换成 **`PlayRequest? _currentRequest`**（一个对象，
避免「清了 itemId 忘了清 qualityId」这种半有效状态），新增 `_playRaw` 专门播
没有库记录的流并清掉上下文。

### 其他改动

- 新增 `lib/ui/windows/player_bridge_host.dart`（`playerBridgeHostProvider`），
  把进度落库与刷新取链两个回调收在一处；**删掉** `playback_progress_reporter.dart`
  （它只装一个回调，名字会变得不准）。
- `desktop_play.dart`：`buildPlayRequest` 的 `WidgetRef` 参数换成
  `ProviderReader` typedef（`WidgetRef` 与 `Ref` 都有 `read`，但 Riverpod 没有
  暴露公共父类型）—— 这样 provider 层能复用**同一份选档规则**，否则刷新会刷出
  与当前播放不同的档位。加 `startPosition` 参数。
- `player_window_app.dart`：错误监听、`_onPosition`（喂刷新闸 + 回报进度）、
  `_refreshTicket`、手动「重新取链并续播」按钮、`_toast`。

### 验证

`flutter analyze` 无问题；单元测试 **234 例全过**（+25）。
新增 `test/ui/windows/ticket_refresh_test.dart`（20 例）。

   回路本身通不通）；

## 阶段六落地：全屏 / 置顶（2026-09-30 晚）

### 先核实了插件不会挡路

`desktop_multi_window` 的 `CustomWindow` 就是个标准 `NSWindow`：
`styleMask [.miniaturizable, .closable, .titled, .resizable]`（`.resizable` 在，
全屏可用）、`collectionBehavior` 未设（默认允许全屏）、**没有设 delegate**
（所以我方设 `window.delegate` 不冲突；插件自己用 NotificationCenter 监听
`willClose`）。

### 原生侧（`ChildWindowController`）

- 通道加 `setFullScreen` / `setAlwaysOnTop`。
- `setFullScreen` **只在状态真要变时才 toggle**：`toggleFullScreen(_:)` 是无参
  开关，无脑调用会在「已经全屏、再要求全屏」时把它关掉。
- 置顶用 `.floating` 而不是 `.statusBar`：floating 已能盖住普通窗口，
  又不至于连系统面板都压住。
- **新增 `windowDidEnterFullScreen` / `windowDidExitFullScreen` → 回调
  `onFullScreenChanged`**。这是必须的：macOS 的全屏能由**系统**退出
  （Esc、绿灯、三指手势），那些路径不经过我们的通道。Dart 只信自己设的值
  就会出现「已经退出全屏，界面还以为在全屏」—— 全屏布局里的退出栏继续挂着。
  用 `Did`（动画结束后）而不是 `Will`：Dart 拿状态是用来切布局的，
  动画途中切会让画面先跳一下。

### Dart 侧：`setMethodCallHandler` 是覆盖式的

`registerChildWindowClosingHandler` 改名成 **`registerChildWindowHandlers`**，
一次装完「关窗」与「全屏变化」两件事。**分两次装会让先装的那个静默失效**
——在这里就是「关窗后 mpv 不释放」，很难查。已加用例钉住这个行为。

`setChildWindowFullScreen` / `setChildWindowAlwaysOnTop` 返回 `bool` 而不是
`void`：调用方要据此**回滚**自己那份乐观状态。不回报的话，原生没接上时界面会
显示「已全屏」而窗口纹丝不动，用户只会觉得按钮坏了。

### 播放窗口：加了真正的全屏布局

- `_fullScreen` 状态**以原生回调为准**，本地只做乐观更新（按钮立刻有反应，
  全屏是动画）。
- 全屏布局不复用 `_buildStage` 的 `AspectRatio(16/9)`：全屏下窗口是屏幕的形状
  （笔记本 16:10），锁死 16:9 会凭空多出上下黑边。交给 `Video` 自己 `contain`。
- 全屏下加一条**半透明控制栏**（片名 + 播放/暂停 + 退出全屏）。
  系统虽然认 Esc，但用户不一定知道；而且全屏下没有任何面板，没有这条栏就
  没法暂停 —— 所以它是必要的，不是装饰。
- 快捷键 `F` 切换、`Esc` 退出，用 `CallbackShortcuts` + `Focus(autofocus: true)`
  （没有那个 `Focus` 收不到事件：`CallbackShortcuts` 只在自己处于焦点链上时
  生效，而这个窗口里没有别的可聚焦控件）。
- 新增 `_playing`（订阅 `stream.playing`）：不订阅的话全屏那个按钮会永远显示
  「播放」，语义正好反过来。
- 窗口化形态的按钮组加「全屏（F）」与「窗口置顶 / 已置顶」。

## 18:40–19:00 修用户实测反馈的三条问题（窗口形状 / 调试信息 / 双击全屏报错）

用户实测反馈（带截图）：① 窗口高度算错，播放控制按钮只露出一半；
② 拖大窗口后底部露出大量调试信息与调试按钮；③ **双击视频进全屏报错**。

### 根因（三条，都已定位到具体代码）

1. **控制按钮只露一半**：窗口建出来写死 1200×675（16:9），片源是别的比例时

2. **底部一堆调试信息**：诊断页（自检 + 出画验证）原来**常驻在**窗口化形态里，
   画面被夹在中间；窗口一小就全挤出来。
3. **双击进全屏报错**（`Looking up a deactivated widget's ancestor is unsafe`）：
   `media_kit_video` 自带控制栏的 `AdaptiveVideoControls` 双击走
   `enterFullscreen(context)` → 它在窗口**内部** push 一个 Navigator
   `PageRouteBuilder`（不是真 macOS 全屏），而那条路由的
   `fullscreen_inherited_widget.dart` 用
   `PopScope(onPopInvokedWithResult: (_, __) => onExitFullscreen(context)?.call())`，
   对已失活的 element 做 `VideoStateInheritedWidget.of(context)` → 抛。

### 修法

- **`Video(controls: NoVideoControls, fit: BoxFit.contain)`**（`NoVideoControls
  = null`，见 `media_kit_video_controls/src/controls/no.dart`）。**已核对源码**：
  `video_texture.dart:461` 是 `if (videoViewParameters.controls != null)` 才构建
  控制栏 —— 传 null 后 media_kit 的双击手势与全屏路由**都不会被安装**，报错源头
  是被摘掉而不是被绕过。`onEnterFullscreen` / `onExitFullscreen` 只是被控制栏
  调用的回调，同样变死代码。
- **全屏只留自写那一套**：双击 → `_setFullScreen(!_fullScreen)` → 原生
  `toggleFullScreen`。
- **窗口形状跟视频走**：新增 `setChildWindowAspectRatio(double?)` + 原生
  `setAspectRatio`，锁 `contentAspectRatio`，并在锁的同时主动 `setContentSize`。
- **诊断页默认隐藏**（`_showDiagnostics`），控制栏一个图标进入、Esc 返回。
- **控制栏改为浮在画面底部**（`Stack` + `Positioned(bottom: 0)`）—— 这是

1. **只设 `contentAspectRatio` 不会立刻改变窗口形状**，它只约束**以后**的拖拽。

2. **竖屏片源**（比例 < 1）按当前宽度反算高度会高过屏幕，标题栏被顶出可视区、

- `FontFeature` **不需要** `import 'dart:ui'` —— material 已经透出来了，显式

## 19:00–19:20 阶段五收尾：直链过期检测的**盲区**（不是口径宽窄的问题）

原问题是「确认 mpv 对 403 的措辞，决定是否收窄刷新触发口径」。查下来发现
问错了方向：**那条措辞根本到不了我们手里**。

### 证据链（查源码 / 产物得来，不是猜的）

1. `media_kit-1.2.6/lib/src/player/native/player/real.dart:2069-2123`：mpv 的
   `MPV_EVENT_LOG_MESSAGE` 转成 `Player.stream.error` 时**筛掉一大批** ——
   只有 `level == 'error'` 且 `prefix` ∈ {`file`, `ffmpeg`, `vd`, `ad`,
   `cplayer`, `stream`} 才放行，而且 `ffmpeg` 前缀**还额外要求 text 以
   `tcp:` 开头**。
2. 产物 `Avformat.framework` 里 ffmpeg 报状态码的格式串只有一条：
   `HTTP error %d %s`。
3. 产物 `Mpv.framework` 里的 log prefix 字面量：`cplayer` / `ffmpeg` /
   `demux` / `lavf` / `http` / `file` —— **`lavf` 与 `http` 都不在 media_kit
   的白名单里**。
4. 于是 403 的原文（`http: HTTP error 403 Forbidden`）**以 `http` 打头，不满足
   `tcp:`** → 被 media_kit 丢掉。
5. 能到达 `stream.error` 的只剩 mpv 自己的 `[cplayer] Failed to open <url>.`
   —— 二级症状，**只在「打开时就已过期」时才有**；播到一半才过期（拖进度条才
   炸，也就是最常见的那种）它不会出现。

**结论：「放宽 stream.error 的口径」是无效的 —— 消息根本没进来，放宽也够不着。**

### 修法：从 `Player.stream.log` 拿被丢掉的那条

`PlayerStream.log` 是**公开**的 `Stream<PlayerLog>`（`player_stream.dart:97`），
而 `logController.add(...)` 发生在过滤**之前**，所以它是全量的。

- 新增纯函数 `isHttp4xxLog(text)`：匹配 `http error 4\d\d`。**按内容匹配而不是
  按 prefix** —— mpv 给 ffmpeg 日志挂什么 prefix 取决于 av_log 的 context 名
  （可能是 `ffmpeg` 也可能是 `http`），按 prefix 判会漏。
- 只认 4xx 不认 5xx：4xx 是「请求不被接受」（签名过期 401/403、夸克缺 Cookie 回
  412、资源被拒 404/410），重取一条链有救；5xx 是服务端自己的问题，重取链解决
  不了，交给 mpv 的 reconnect。
- 两条路**刻意不重叠**：`stream.error` → `_onPlayerError` 管 `Failed to open`；
  `stream.log` → `_onTicketExpiryLog` 只管 `stream.error` 看不到的 HTTP 4xx。

### 已验证订阅不是死代码

`PlayerConfiguration.logLevel` 默认 `MPVLogLevel.error`（`platform_player.dart:529`）
→ `mpv_request_log_messages(ctx, 'error')`（`real.dart:2505`），而
`HTTP error %d %s` 正是 error 级。项目里没有覆盖 logLevel。

### 顺带修掉一个**签名泄露**

`_onPlayerError` 原来直接把 mpv 原文写日志（`diag.warn('mpv 报错：$message')`）。
而 mpv 的二级报错是 `Failed to open %s.`，那个 `%s` 是**完整 URL** —— 夸克直链的
签名就在查询串里，于是它会**落进诊断日志文件**，而那个文件是给用户复制粘贴用的
（诊断页还专门做了「复制日志路径」按钮）。这与 `_openStream` 里「日志不打 url」
是同一条规矩，区别只是那条报错**不是我们拼的**。

新增 `redactUrls(message)`：把 `https?://\S+` 换成 `scheme + host + /…（直链签名
已抹去）`，保留主机名（有诊断价值：能看出哪个 CDN 节点），抹掉路径与查询串。
`_onPlayerError` / `_onTicketExpiryLog` / `_refreshTicket` 的原因字段都先过它。

### 配套改动：冷却窗口

一次 seek 失败不会只报一条 403 —— ffmpeg 的 http 层带 reconnect 重试，mpv 又可能
在 demux / cplayer 两层各报一次，这些是**同一次故障的回声**（间隔毫秒级）。
不去抖的话 3 次额度会在几百毫秒内被烧完。

`TicketRefreshGuard` 加 `minInterval`（默认 10s）：
- `begin()` 在冷却内返回 false，且**不计数**；
- 调用方用 `exhausted` 分辨「用满」（要弹提示）与「冷却」（只是一次去抖，
  **不该弹提示**，否则一次故障弹好几条）；
- `reset({DateTime? now})`：手动刷新传 `now` **重新起冷却**（手动刷新同样会招来
  旧流那批回声）；换片调 `reset()` 不传 → 冷却一并清掉。

### 验证

`flutter analyze` 无问题；单元测试 **270 例全过**（+16：冷却 6 例、`isHttp4xxLog`
5 例、`redactUrls` 5 例）。既有用例里「用满 maxAttempts」那条要调整 —— 它原来用
同一个 `t0` 连调两次 `begin`，现在会被去抖挡下；已改成两次调用拉开 30 秒

## 19:50–20:10 实测 mpv 对 HTTP 403 的真实日志 —— 推翻了我上一轮读源码的结论

上一轮我说「403 那条消息被 media_kit 的**前缀过滤**丢掉」。方向对，但**原因错了**，
而且错得关键 —— 按那个理解写出来的代码在默认配置下**根本收不到消息**。

### 怎么测的（可复现）

产物里捆了 `libmpv`，可以直接 dlopen 起来跑：

```python
FW = ".../cloudcine.app/Contents/Frameworks"
# ⚠️ 必须设 DYLD_FRAMEWORK_PATH 指向 FW，否则 dlopen 报
#    Library not loaded: @rpath/Ass.framework/Versions/A/Ass
lib = ctypes.CDLL(f"{FW}/Mpv.framework/Versions/A/Mpv", mode=ctypes.RTLD_GLOBAL)

class MpvEventLogMessage(ctypes.Structure):
    _fields_ = [("prefix", c_char_p), ("level", c_char_p),
                ("text", c_char_p), ("log_level", c_int)]
class MpvEvent(ctypes.Structure):
    _fields_ = [("event_id", c_int), ("error", c_int),
                ("reply_userdata", c_uint64), ("data", c_void_p)]
```

流程：`mpv_create` → `mpv_set_option_string`（`vo=null`、`ao=null`、`idle=yes`、
`terminal=no`）→ `mpv_initialize` → `mpv_request_log_messages(b"v")` →
`mpv_command(["loadfile", url])` → 循环 `mpv_wait_event`，打印
`event_id == 2`（`MPV_EVENT_LOG_MESSAGE`）的 prefix/level/text。
配一个本地 `http.server`，任何请求都回 403。

### 实测结果（403）

```
level='v'     prefix='ffmpeg'  text='Opening http://…'
level='warn'  prefix='ffmpeg'  text='http: HTTP error 403 Forbidden'
level='error' prefix='stream'  text='Failed to open http://… .'
level='v'     prefix='cplayer' text='Opening failed or was aborted: http://…'
```

### 三条结论，每条都跟读源码的推断不一样

1. **`HTTP error 403` 是 `warn` 级，不是 `error` 级。**
   `mpv_request_log_messages(level)` 的语义是「该级别**及以上严重**才发」，
   而 media_kit 默认请求 `error` → **这条消息根本不会被发到 Dart**，
   连它的前缀过滤都轮不到。所以我上一轮加的 `stream.log` 订阅按原配置
   **是死代码**。
   → 修法：`Player(configuration: PlayerConfiguration(logLevel: MPVLogLevel.warn))`。
   抬到 warn 只影响 `stream.log` 的流量，`stream.error` 不受影响
   （media_kit 仍只挑 `level == 'error'` 的）。
2. 真正到达 `stream.error` 的是 `prefix='stream'` 的 `Failed to open <url>.`
   —— **prefix 是 `stream`，不是我猜的 `cplayer`**（`cplayer` 那条是 `v` 级，
   同样收不到）。而且它只在**打开阶段**失败时出现。
3. 正文带 `http: ` 前缀（mpv 把 av_log 的 context 名拼进了 text）。

### 没能复现的：播到一半才过期

想测「流已建立、拖进度条才 403」。试了两版都没成：
- 首个请求回整段 → mpv 一次把 32KB 读进缓冲，seek 直接命中缓存，**不再发请求**；
- 首个请求回 `206` + 只给前 8KB（声明总长 32981）→ 仍然没发第二个请求。

`assets/player_selftest.mp4` 只有 3 秒 / 32KB，太小。**要复现得换足够长的素材。**
不过这不影响结论：warn 是 error 的**超集**，抬到 warn 只多不少。

### 验证

`flutter analyze` 无问题；单元测试 **283 例全过**；`flutter build macos` 成功。
`isHttp4xxLog` 的用例里换成了**实测原文**（`'http: HTTP error 403 Forbidden'`），
注释里写清它是跑出来的、级别是 warn。

### 教训

**「读源码推出的行为」不等于「实测的行为」。** 这一轮读源码得到的「被前缀过滤丢掉」
和实测的「因级别不够根本没发」指向同一个修法（另接一条流），但**默认配置下前者能
工作、后者不能** —— 没实测的话，这个功能会带着「看起来对、实际收不到」的状态
交付出去。

## 20:10–20:35 复现「播放途中才过期」—— 补上整条链最后一块

上一轮没能复现（自检素材只有 3 秒 / 32KB）。这轮换了素材就成功了。

### 造素材

本机有 `/opt/homebrew/bin/ffmpeg`（**不在 PATH**，要用绝对路径）：

```
ffmpeg -f lavfi -i "testsrc2=size=320x240:rate=10:duration=180" \
  -c:v libx264 -preset ultrafast -g 10 -pix_fmt yuv420p -movflags +faststart out.mp4
```

得到 9.8MB / 180 秒。**素材必须足够大** —— 否则 mpv 一次就读完、seek 命中缓存，
根本不会再发请求（前两版就是栽在这上面）。

### 怎么逼出「流建立之后又收到 4xx」

试了三种服务端形态，只有第三种逼出来了：
1. 首个请求回整段 → mpv 全读进缓冲，不再发请求 ✗
2. 首个请求回 `206` + 只给一段（声明总长）→ mpv 拿到就停在那儿等，也不发 ✗
3. **首个响应声明完整长度（`Content-Length: 9799538`）但只写 64KB 就断线** ✓
   —— 这是 CDN 中途掉线的形态，mpv 的 http 层必然重试，那时回 403。

### 实测结果（播放途中 403）

```
level='warn'  prefix='ffmpeg'         text='http: HTTP error 403 Forbidden'
level='warn'  prefix='ffmpeg'         text='http: Will reconnect at 65536 in 0 second(s), error=Input/output error.'
level='error' prefix='ffmpeg'         text='http: Stream ends prematurely at 65536, should be 9799538'
level='error' prefix='ffmpeg'         text='Seek failed (to 8162141, size -78)'
level='error' prefix='ffmpeg/demuxer' text='mov,mp4,m4a,3gp,3g2,mj2: stream 0, offset …: partial file'
```

### 关键结论：这个场景下 `stream.error` **一条都收不到**

逐条对 media_kit 的规则：`ffmpeg` 前缀要求 text 以 `tcp:` 开头，而它们要么以
`http:` 开头、要么以 `Seek` 开头；`ffmpeg/demuxer` 不在白名单里。
**唯一通路就是 `stream.log` + 抬到 warn 的日志级别** —— 少了那行配置，
用户实际会遇到的那种过期一次都检测不到。

（上一轮「播到一半才过期时 `Failed to open` 不会出现」的推断，到这里被证实。）

### 另一个收获：一次 403 会连出十几条

ffmpeg 的 reconnect 退避是 0s / 1s / 3s / 7s…，实测一次故障刷出 **16 个请求**。
这是冷却窗口存在的直接理由（没有它，3 次额度几秒内被同一批回声烧完）。

据此把 `_onTicketExpiryLog` 的日志级别从 warn 降到 **debug**：逐条打 warn 会把诊断
日志刷爆，而真正有信息量的是 `_refreshTicket` 那行「请求刷新直链：… 原因：…」
—— 一次故障只打一条，且同时说了「发生了什么」和「打算怎么办」。

### 新增的负例（价值很高）

把实测到的**同一次故障的其它日志**加成负例，尤其是：
`'http: Will reconnect at 65536 in 0 second(s), error=Input/output error.'`
—— 它同时含 `http` 和 `error`，如果匹配逻辑写成「含 http 且含 error」就会误触发。
按 `http error 4\d\d` 精确匹配才挡得住。

### 验证

`flutter analyze` 无问题；单元测试 **284 例全过**；`flutter build macos` 成功。

## 20:20–20:40 修用户实测反馈两条：拖拽抖动 / 续播失效（两条都有实测证据）

### 问题 2：续播每次从头开始 —— 根因是「open 之后 seek」被 mpv 丢掉

**先用用户机器上的真实数据定位，不猜**：

- 索引库里续播位置**确实存下来了**（`user_version=2`，`resume_position_ms` 有 3 行：
  10s / 120s / 280s）。所以落库这一环是好的。
- 日志里主窗口也**确实算出了续播点**：

  ```
  20:23:08.143 [窗口] 续播：斩神2 S02E01 从 130s 开始
  20:23:08.152 [播放窗口] open → 斩神2 S02E01（4K）
  20:23:20.637 [播放] 播放窗口回报进度：… @ 10s      ← 从 0 开始播了
  ```

  即丢在「播放窗口应用起播位置」这一步。同一现象在 20:17 换清晰度时也出现过
  （续播 20s → 40 秒后位置只有 4s）。

**根因**（读 media_kit 源码 + 跑真 libmpv 双重确认）：`Player.open()` **不等待文件
加载完成** —— 它只发 `loadlist` 再设 `playlist-pos`（`real.dart` 的 `open()` 全文里
没有任何等待），紧跟其后的 `seek()` 落在解复用器就绪之前，被 mpv 丢掉。

**探针结果（脚本写法见 `本机构建环境` 新增条目）**：

```
A) 设 start=20 → loadfile cc_a  → 文件=cc_a 位置=23.0s   ✅ start 有效
B) 不设 start  → loadfile cc_b  → 文件=cc_b 位置=23.0s   ⚠️ 也从 20s 起播（start 残留）
C) 显式 start=0 → loadfile cc_a → 文件=cc_a 位置=3.0s    （残留被清掉）
D) 不设 start  → loadfile cc_b  → 文件=cc_b 位置=3.0s
E) loadfile cc_a 后**立刻** seek 20 → 位置=3.0s          ⚠️ 这次 seek 被完全忽略
```

**两条结论**，第二条是想都没想过的：
1. 起播位置只有 `Media(start:)` 这一条可靠路径；`seek` 只用于**播放中**的跳转。
2. **`start` 会残留到下一个文件**。media_kit 只在 `start != null` 时设这个属性，而
   mpv 加载完并不清掉它 → 下一个不设 start 的文件会沿用上一个的位置。所以
   「不续播」也必须**显式写 0**，不能传 null。（差点写成一个新 bug：只在续播时传
   start，就会变成「播过一部续播的片子之后，别的片子也从中途开始」。）

**修法**：新增 `lib/domain/services/playback_media.dart`（`PlaybackMedia.build`），
`startAt` 默认 `Duration.zero` 而**不是 null**，两处共用：
`player_window_app.dart` 的 `_openStream`（续播 / 换档 / 刷新直链三条路都走它）与
`playback_controller.dart` 的 `_loadIntoPlayer`。

⚠️ 内置播放页的 `switchQuality` 原来也是「open 之后 seek」→ **切清晰度必然回片头**，
同一个根因，一并修掉。另外内置播放页**完全没有**续播（不存也不读），属缺口不是回归，
留给用户定夺。

### 问题 1：拖拽窗口抖得厉害 —— 逐帧报 delta 在 macOS 上自激振荡

原实现：`onPanUpdate` 把 `details.delta` 报给原生，原生 `setFrameOrigin(origin + delta)`。

**振荡回路**：`PointerMoveEvent.position` 是**窗口内**坐标 → 窗口一移动，同一个鼠标
位置在窗口里的坐标就反着变成 `-dx` → 窗口在光标底下移动时 macOS **会补发
mouseDragged**（不补发的话光标矩形/悬停态就永远是错的）→ 我们收到 `-dx` 再加一次反向
位移 → 窗口被推回原位 → 循环。

**修法**：「锚点 + 绝对鼠标位置」。原生 `beginWindowDrag` 记 `NSEvent.mouseLocation`
（**屏幕**坐标）与窗口原点；`updateWindowDrag` 算
`origin = anchorOrigin + (now - anchorMouse)`。绝对量不受窗口移动影响，误差不累积。
再补一条 `if origin == window.frame.origin { return }` —— `setFrameOrigin` 会发
`NSWindowDidMoveNotification`，那又是回路的燃料，鼠标没动就断在那里。
Dart 侧只报「开始 / 继续」两件事，**不带任何参数**。

**不用 `NSWindow.performDrag(with:)` 的理由**：跨通道调用发生在事件派发之外，
`NSApp.currentEvent` 多半是 nil；而且它会吞掉后续鼠标事件 → Flutter 侧的单击暂停 /

### 补：HLS 那条（原本留给用户实测的，离线验掉了）

本地 `ffmpeg -f hls` 出 VOD 切片（a.m3u8 60s / b.m3u8 30s，带 `EXT-X-ENDLIST`），
本地 HTTP 提供，同一套探针跑四步，各步等 5 秒：

```
A) 设 start=20 → loadfile a.m3u8  → 24.9s  ✅ start 对 HLS 有效
B) 不设 start  → loadfile b.m3u8  → 24.8s  ⚠️ 残留同样成立
C) 显式 start=0 → loadfile a.m3u8 → 4.9s   （残留清掉）
D) loadfile 后**立刻** seek 20     → 4.9s   ❌ seek 照样被丢
```

与本地 mp4 **四条结论完全一致**。夸克 `play/info` 签的就是 `media.m3u8`，
所以这条是硬指标，不再是「待实测」—— 看门狗那条兜底方案**不需要**了。

**这套探针的三个坑**（下次直接避开）：
- **`MPV_EVENT_LOG_MESSAGE = 2`，不是 26**。写错时表现是「一条日志都收不到」，
  很容易误判成 mpv 没加载文件。
- **本机代理会把 `127.0.0.1` 也拦掉**：urllib 拿到 `HTTP 502 Bad Gateway`
  （curl 因为有 `no_proxy` 反而正常）。跑探针前必须
  `unset http_proxy https_proxy all_proxy HTTP_PROXY HTTPS_PROXY ALL_PROXY`。
  ffmpeg 的 http 协议是认 `http_proxy` 环境变量的，mpv 走它就会连不上本地服务。
- **后台 HTTP 服务跨不过 Bash 工具的一次调用**：上一条命令里 `nohup ... &`
  起的 server，到下一条命令就死了（mpv 报 `Connection refused`）。
  必须把「起服务」和「跑探针」放进**同一次** Bash 调用。

## 晚上这一轮：切集进度 / 集数面板改版 / 缓冲指示

用户三条反馈，都改完了（未提交）。

### 1. 不关窗口直接切集 → 进度不落库，切回来无法续播

根因是**顺序**：播放窗口切集时直接向主窗口要新链，主窗口要**读库**算续播点，
而当前这一集的进度还只在播放窗口内存里（10 秒一报的节流还没到点）。
关窗再开之所以没问题，是因为关窗那条路本来就会报一次。

改法两处，缺一不可：
- `_requestFreshTicket` 开头 `await _reportProgress(..., force: true)`
  —— 放在这里而不是三个调用点各写一遍：切集/切画质/直链过期续播都是「换流」；
- 通道回调 `onPlaybackProgress` 改成 `Future<void> Function`，`handler(report)`
  **必须 await**（原来 fire-and-forget）。不等写完就读库，读到的还是旧值。

### 2. 集数面板：控制栏图标 → 右侧边框隐藏按钮 + 滑入 + 挤压画面宽度

- 布局从 `Stack`（面板压在画面上）改成 `Row`：`Expanded(画面)` + 面板。
  ⚠️ **`crossAxisAlignment: CrossAxisAlignment.stretch` 是必须的** ——
  默认 center 会把子项高度压成 0（`Stack` 只有 `Positioned` 子项时按最小
  约束取尺寸），画面直接消失。
- 两层动画**同时跑、同时长**：外层 `AnimatedContainer` 宽度 0→320（画面让位），
  内层 `AnimatedSlide` 把面板从 +320 平移进来（真·滑入）。只有第一层是「擦除」，
  只有第二层面板会压在画面上。
- 入口是画面区右边缘一条 26×66 的竖长条，平时 `opacity 0` + `IgnorePointer`，
  鼠标进窗口才淡入。放在**画面区**里（不是窗口最右）→ 面板展开后它跟着挪到
  面板左边缘，收起按钮永远在面板边上。
- 面板**不能一直挂在树上**：宽度为 0 的面板照样被 `find.text` 查到、被朗读功能
  读到，等于「收起了但还在」。用 `_playlistMounted` + 一个等滑出动画跑完的
  `Timer` 摘掉它。
- ⚠️ **首次展开必须分两帧**：隐式动画只在第二次 build 时才开始插值。
  面板刚上树那一帧 `AnimatedSlide` 会把 offset 直接设成终值 → 滑入根本不发生。
  所以先 setState 挂上（宽度 0、在右外侧），post-frame 再 setState 展开。
  测试里对应的代价：`openPlaylist` 要 **pump 三拍**（挂树 / 起步 / 跑完），
  两拍时列表项还在 x≈919（800 宽窗口之外），`tester.tap` 报「不会命中」。

### 3. 开播缓冲时黑屏 → 加载指示 + 缓存进度 + 速率

- mpv 侧能拿到的只有两个量：`demuxer-cache-time`（缓存到播放头前面多少**秒**，
  media_kit 的 `player.stream.buffer`）和 `cache-buffering-state`（初始填充
  0~100，`player.stream.bufferingPercentage`，**填满后停在 100 不再变** →
  进度条只在 0<x<100 时显示，否则退回不确定态）。
- **没有字节数**。media_kit 不暴露任意 mpv 属性（`Player` 上没有 `getProperty`），
  所以 KB/s 只能靠估算：`文件大小 ÷ 时长 = 平均码率`，再乘「每秒缓存多少秒」。
  为此给 `PlayRequest` 加了 `sizeBytes`（`MediaItem` 本来就有）。
- 速率估算放 `lib/domain/services/cache_speed_meter.dart`（纯函数 + 9 条单测）。
  ⚠️ 窗口取 **8 秒**是有依据的：HLS 切片 5~10 秒，缓存量是阶梯状跳的，
  窗口窄于一个切片就平均不掉，算出来的数会在 0 和尖峰之间跳（界面上就是
  「网速在抖」的假象）。3 秒窗口实测过，压不住。
- 覆盖两段：等首帧（`_awaitingFrame`，画面本来全黑 → 不透明底色）和播放中
  卡住（`_buffering`，那一帧还在 → 半透明）。整层 `IgnorePointer`。

### 最重要的一条实测（夸克自己就有封面）

用本机夸克登录态打 PC 网关（脚本见下），**列目录返回的视频项自带三个
缩略图地址**：

| 字段 | 端点 | 实测尺寸 | 体积 |
|---|---|---|---|
| `thumbnail` | `/1/clouddrive/file/video/thumbnail?fid=` | 178×100 | 1 964 B |
| `big_thumbnail` | `/1/clouddrive/file/video/quick?fid=` | 533×300 | 7 892 B |
| `preview_url` | `/1/clouddrive/file/video/preview?fid=` | 640×360 | 12 194 B |

三档都是 WebP。**「没配 TMDB 就一墙灰块」根本不需要刮削来解决**。

取图的 Cookie 规则（三种头实测）：
- 裸链 → `401 code=31001 auth not found`
- **过期**的 `__puus` → `401 auth expired`
- 当前会话 → `200 image/webp`

⚠️ 夸克在每个响应的 `Set-Cookie` 里轮换 `__puus`。实测同一进程里
**先打一次列目录拿新 `__puus`，再打缩略图才 200**；用启动时读到的旧值 401。
所以图片请求头必须**每次现取**，不能拼进地址缓存。

字段覆盖率：全盘搜索视频前 100 条里 **71 条有 `thumbnail`**、53 条有
`duration`。所以**字段缺失时不要自己拼 URL** —— 拼出来只会 401/404。

其它可用字段（评估文档第 6 节列了优先级）：`video_width/height`（真实
分辨率，比文件名推断可靠）、`fps`、`last_play_info`（夸克自己的播放进度，
可做跨设备续播）、`cover_face_boundary`（人脸框）。

### 顺手修掉的一个既有缺口（挺严重）

`PosterCache` 判断「缓存命中」靠的是库里 `MediaWork.posterFile`，但
**全项目没有任何代码把下载结果写回那一列**（`relativeNameOf` 定义了却没人
调）。于是**每次启动应用、每张海报都重下一遍**。对 TMDB 海报只是慢；
对本轮新加的网盘缩略图就是「启动后一千次带 Cookie 的请求」。
改成「盘上有同名文件就直接用」（文件名里带 URL 散列，所以安全），

### 设计决定（都有理由，别回退）

1. **分类与 MediaKind 是两个轴**。`MediaKind` 由文件名**结构**决定
   （有没有 SxxExx），分类由**内容语义**决定。合成一个枚举会立刻撞上
   「动漫也有剧场版电影」。
2. **离线关键词判定的顺序不能反**：先关键词、后结构。综艺的文件名是
   `奔跑吧.2026-09-27.第12期.mkv`，解析器提不出季集号（`kind == unknown`），
   先按 kind 落到「其他」的话关键词表永远没机会生效。
3. **ASCII 关键词必须卡词边界**（`(?<![a-z0-9])…(?![a-z0-9])`）。
   不卡的话 `ova` 命中 `Nova`、`bbc` 命中 `abBc`。漏判只是分类不准，
   **误判是「我的电影不见了」**。
4. **「最近的一集」= 最近播过且还留着续播点的那一集**；已看完的
   （续播点被清）就播它自己，**不猜下一集** —— `lastPlayedAt` 有值但
   没续播点，既可能「看完了」也可能「点开 3 秒就关」，猜错代价大得多。
5. **`mergeWorkForUpsert` 里分类永远取新值**，不能放进 `protect` 分支：
   否则第一次判成「其他」的作品以后永远修不回来。
6. **海报地址永不为空**：本次算不出就保留旧的。网盘缩略图是「扫描那一刻
   服务端有没有生成」的快照，某次没拿到就写 null 会让海报从墙上消失。
7. **`MediaCategory` 落库时空串 ≠ other**。空串 = 「还没判定过」，
   由 `backfillWorkCategories()` 补算（只需要标题 + kind，不联网）。
   混在一起的话回填会把真正的「其他」作品反复重算。

### 迁移与老库

schema **v2 → v3**：`media_items.thumbUrl`、`media_works.category`
（`DEFAULT ''`，SQLite 的 `ADD COLUMN` 会把旧行一并填成空串）。
老库靠 `categoryBackfillProvider` 在**第一次打开媒体库时**修好，
不需要重扫网盘。
