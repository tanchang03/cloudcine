# 2026-10-09

## 修「百度扫码成功、手机授权后 PC 端仍未授权」

**现象**（`cloudcine-2026-10-08.log` L1218–1227）：`qrbdusslogin → 200` 已下发真凭证
（`Set-Cookie: BDUSS`=192B、`STOKEN`、`PTOKEN`、`BAIDUID`…），紧接着
`GET pan.baidu.com/api/account/uinfo → 200`，但 body `errno=-6`，随后
`[会话] 百度凭证校验失败，已丢弃` ⇒ 页面停在未授权。

**定位**（对照能跑通的社区实现 `baidu_pcs.py` + 网盘 API 速查 + 一篇踩同款坑的运维博客）：

1. **请求形状缺 `Origin`**：日志里发往 `/api/account/uinfo` 的头是
   `[User-Agent, Accept, Accept-Language, Referer, Cookie]`，**没有 `Origin`**。
   夸克 adapter 一直带 `Origin`，只有百度漏了 ⇒ 这是与参考实现唯一的结构性差异。
2. **扫码三跳没共享会话**：第 1 跳 `getqrcode` 下发的 `BAIDUID` 必须带回第 2、3 跳
   （参考实现明确写「第 3 步不带回 Cookie 就拿不到正式 BDUSS」），我们发了三次
   互不相干的干净请求。
3. `channel_v.u` 可能为空 ⇒ 空 `u` 会让服务端按「无落点」签发。
4. 顺带确认：百度**读接口不需要** `sign`/`timestamp`（`bdstoken` 只有写才要）；
   `errno=-6` 是**一码三义**（没带 Cookie / Cookie 失效 / 账号级临时风控），
   只能靠服务端原话 `show_msg` 区分。

**改动**（4 个文件，均在 Flutter PC 端）：

- `lib/data/remote/baidu/baidu_endpoints.dart`：新增 `static const String origin = 'https://pan.baidu.com'`。
- `lib/data/remote/baidu/baidu_adapter.dart`：
  - `_headers()` 补 `'Origin': BaiduEndpoints.origin`；
  - `_describe()` 追加 `raw=<show_msg>`，让 `-6` 的三种含义在下一次实测里可分辨。
- `lib/data/auth/baidu_qr_login.dart`：加会话 Cookie 罐 `_jar` + `_cookieHeaders` / `_absorbCookies`；
  `start()` 清罐、三跳都带罐并吸收 `Set-Cookie`；`_exchangeVia` 的 `u` 为空时退回
  `BaiduEndpoints.postLoginUrl`；返回值改为 `cookies: {..._jar}`（保证 `BAIDUID` 落进凭证）。
- 测试：`test/data/baidu_qr_login_test.dart`、`test/data/baidu_adapter_test.dart` —— 两个 `FakeHttp`
  开始记录请求头；新增「`u` 为空退回 postLoginUrl」「会话连续（BAIDUID 跨三跳）」3 例、
  「网盘请求必带 Origin」1 例。

**验证**：`flutter test test/data/baidu_qr_login_test.dart test/data/baidu_adapter_test.dart`
→ **All tests passed! (+86)**；`flutter analyze lib/data/remote/baidu lib/data/auth <两个测试文件>`
→ **No issues found!**。

**未决**：`-6` 的确切成因（上述 1/2 已修 vs 账号级临时风控）**离线无法 100% 证伪**，
需真实账号再扫一次；本次已让诊断行输出 `show_msg` 原话以便下次一眼定性。**未提交**（等审计）。

**本机踩坑记录**：macOS 自带 BSD `grep` **不支持 `\|` 交替**，`grep "A\|B" file`
会静默匹配字面量 `A|B` 并返回空 —— 排查时误判过「代码没改」。要用 `grep -E "A|B"`。

## 二修：真实账号复测仍失败 ⇒ 对照逆向客户端，发现**换票走错了分支**

**复测结果**（`cloudcine-2026-10-09.log` L326–344）：上一轮的两处修复**都已生效** ——
`getqrcode` 下发的 `BAIDUID` 被带回第 2/3 跳（`请求带Cookie键=[BAIDUID, BAIDUID_BFESS]`），
`uinfo` 请求头里也有了 `Origin`。**但 `uinfo` 依旧回 `errno=-6`**，而且响应体里
**连 `show_msg` 都没有**（只有裸 `{"errno":-6}`）⇒ 说明服务端根本没把它当登录请求看。

**用户指路**：「主要参考逆向百度网盘 app 逻辑」⇒ 回去读 `2026-10-08.md` §「逆向百度网盘
Mac 客户端」的结论，发现**换票那一跳我们把两条分支弄反了**：

| 客户端（逆向原文） | 我们当时的实现 |
|---|---|
| **主线**：`GET /v2/api/bdusslogin?tt&bduss&u&qrcode=1&tpl=netdisk`（**无 `loginVersion`**） | 排在**最后**当兜底 |
| **风控分支**（仅 `errno 400023` 走）：`POST /v3/login/main/qrbdusslogin` + `loginVersion:'v4'` + `authsid` | 当成**主线**，且送 `loginVersion:'v5'` |
| `loginVersion:'v5'` 实际属于**小程序分支** `/v3/api/mini/qrlogin` | 送给了 `qrbdusslogin` |

⇒ 用一个服务端从没见过的参数组合去换票，它**照样回 200 并下发整套 `Set-Cookie`**
（`BDUSS`/`STOKEN`/`PTOKEN`…），看起来完全成功，但**签发的会话网盘侧不认**，
下一步就是 `-6`。这解释了「手机显示授权成功、PC 端却登录状态无效」的全部现象。

**同时补齐客户端登录链里我们缺的三步**（逆向文档第 5/6/7 步）：

- 第 5 步：`GET passport.baidu.com/v3/login/api/auth?bduss=&ptoken=` → `data.stoken_list.netdisk`（netdisk 专用 STOKEN，best-effort 覆盖）。

  （兜底 `/api/get/template`）取 **`bdstoken`** —— 它是 `/api/*` 的**会话令牌**，
  客户端**每条**请求都带；缺了服务端同样回 `-6`。⚠️ 这推翻了上一轮
  「`bdstoken` 只写要」的结论：**读也要**。

**改动**：

  `qrBdussLogin` 改注为**风控分支**；新增 `stokenAuth = '/v3/login/api/auth'` 与 `templateFields`。
- `baidu_qr_login.dart`：`exchange()` 改为**主线优先**（`GET /v2/api/bdusslogin`，query 只送

- `baidu_adapter.dart`：新增 `_bdstoken` 字段 + `_ensureBdstoken()`（两条来源轮试、按会话缓存、
  换账号/登出清空）；`_get(..., withBdstoken)` 注入 `bdstoken`；`_request` 在 `unauthorized`
  且尚未取过令牌时**补令牌重试一次**（`allowBdstokenRetry` 防递归）；新增 `_logBody()`

- 测试：`FakeHttp` 增加 `methods` 记录与 `post` 路由；换票组重写为「主线优先」并新增
  「主线**不带 `loginVersion`**」「主线是 GET、风控才是 POST」；新增 `netdisk STOKEN` 组 3 例、
  `bdstoken` 组 4 例（含「补令牌重试一次」「取令牌的请求自己不带令牌」「两条来源都失败 ⇒ 不无限重试」）。

## 三修：定位到「换票后没落地网盘域」⇒ 手动跟 302 到 `pan.baidu.com`

**复测**（`cloudcine-2026-10-09.log` L379–400）：二修的**主线换票已生效** ——
`GET passport.baidu.com/v2/api/bdusslogin → 302`，`Set-Cookie` 里
`STOKEN/BDUSS/PTOKEN` 一应俱全（192B 真 BDUSS）。**但紧接着 `uinfo` 仍回
`{"errno":-6,"request_id":…}`**，`gettemplatevariable` 也 `-6`、`get/template` `errno=2`。

**根因**：换票回的是 **302**，`u` 参数就是落点；**逆向客户端的 WebView 会跟着跳到
`pan.baidu.com`**，而它的 Cookie 域过滤表是
`^\.baidu\.com$|^\.pan\.baidu\.com$|^\.passport\.baidu\.com$|^\.pcs\.baidu\.com$`
—— **网盘域那一项只可能由这一跳下发**。我们为了拿到 302 的 `Set-Cookie` 而
`followRedirects: false`，于是**没有任何人访问落点**：手里只有 passport 域的凭证，
网盘侧不认 ⇒ `-6`。这同时解释了 09:34 那次（`qrbdusslogin` 回 200、无 302）为何也 -6：
**两次都没落地**（一次无 302、一次 302 没跟）。

**改动**：

- `lib/data/auth/baidu_qr_login.dart`：
  - 新增 `_settleOnPan(location)`（登录链第 4 步）：从 302 的 `Location`（无则
    `postLoginUrl`）出发，**手动逐跳**走重定向链、每跳吸收 `Set-Cookie`
    （⛔ 不能用 `followRedirects: true` —— dio 只留最后一跳的头，中途 Cookie 全丢）；
    页面头（`pageAccept`）+ 逐跳更新 `Referer`；⛔ **只跟 `baidu.com` 域**
    （防伪造 `Location` 把凭据带去外站）；最多 5 跳防环；失败只记日志、绝不让登录失败。
  - `_exchangeVia` 改返回 `_ExchangeOutcome = ({setCookie, location})`；凭证改为
    **落地 + 换 STOKEN 之后**才组装（提前组装会漏掉网盘域那批 Cookie）。
  - `BaiduQrLoginCookies` 新增 `panCookieNames`；`filterBaiduCookiesForCredential`
    新增 `extraNames` —— ⛔ 落地收到的 `PANWEB`/`PANPSC` **不在** `knownCookieNames`，
    不显式放行就等于白做（现象与没做**一模一样**：依旧 `-6`，日志上也看不出差别）。
- `lib/data/remote/baidu/baidu_endpoints.dart`：新增 `pageAccept`（页面导航而非 XHR）。
- `lib/data/auth/baidu_qr_driver.dart`：`exchange()` 把 `result.panCookieNames`
  传进过滤器。

**测试**（先写红再实现）：新增 6 例 —— 302 必须跟到 `/` 并收下网盘域 Cookie、
落地请求要带 `BDUSS`、无 Location 也走一趟 `postLoginUrl`、外站 Location 不跟、
落地失败不影响登录、落地早于换 STOKEN；另加「过滤器按名字放行 `extraNames`」
与「凭证里必须要有 `PANWEB`」2 例。

**验证**：`flutter test test/data/baidu_{qr_login,adapter,models}_test.dart
test/ui/pages/auth_qr_login_page_test.dart` → **All tests passed! (+155)**；
`flutter analyze`（改动范围）→ **No issues found!**。**未提交**（等审计）。

**仍未证**：本机无真实账号，只能保证「与逆向客户端的链路逐跳一致」。
若这次仍 `-6`，下一个怀疑对象是**账号级风控**（`-6` 一码多义，而响应体里连
`show_msg` 都没有）。

## 四修：百度下载硬 403 —— 直链 UA 必须按「取链路由」分两种方言

**现象**（用户报「登录成功了，但是下载文件失败了」，`cloudcine-2026-10-09.log`
L528–555）：`取链成功：https://d.pcs.baidu.com/file/72977883ct01d6c8740aa3c12d39ae11`
之后立刻 `[下载] 失败：VID_….mp4 —— urlExpired 分块下载失败：HTTP 403`（连试两次）。

**定位链**（三跳，每跳都有日志证据）：

1. `GET /rest/2.0/xpan/multimedia` → **`{"errno":9019,"errmsg":"need verify"}`**。
   该路由是**官方 Open Platform** 形状，要 `access_token`；我们走的是扫码 Cookie
   会话，**没有 access_token** ⇒ 这条路由对本项目**恒不可用**（不是配置问题）。
2. 降级到 ② `/api/filemetas?dlink=1&web=5&origin=dlna` → 200 且解析出 dlink
   ⇒ ② 是**网页 crack** 形状的直链。
3. 票据却对**所有**路由统一发 `User-Agent: pan.baidu.com` ⇒ 取文件被 CDN 拒。

**真因**：crack 直链的 CDN 判据是「**百度自家客户端 UA**」，不是 `pan.baidu.com`。
证据两条独立来源：

- AList `alist-util.go`：`linkOfficial` 用 `pan.baidu.com`，而 `linkCrack` /
  `linkCrackVideo` 用 `d.CustomCrackUA`；`alist-meta.go` 里它的
  `default:"netdisk"`。**同一份代码里两条路由写死了两个不同的 UA**。
- 客户端自身 UA 构造器（`v888js/main.js`、`v888js/renderer.js`）：
  `"netdisk;"+版本+";PC;PC-"+客户端号+";"+系统版本+";UniBaiduYunGuanJia"`
  —— 是 **`netdisk` 族**，全文没有把 `pan.baidu.com` 当 UA 用过。

**为什么这条坑特别贵**：`31326/31360/31362` 这类业务错是 **HTTP 200 + JSON**，
而 CDN 边缘的拒绝是**硬 403** ⇒ 说明它在**业务层之前**就拒了。叠加上
`StreamTicket.redactedUrl` 会丢掉 query，日志里连「dlink 有没有签名」都看不到，
于是现象长得像「直链过期」（我们自己的 `_typeForStatus` 也正好把 403 判成
`urlExpired`，把人往错方向带）。

**改动**（3 个 lib 文件 + 2 个测试文件）：

- `baidu_endpoints.dart`：`dlinkUserAgent` 拆成
  `officialDlinkUserAgent = 'pan.baidu.com'` 与
  `netdiskDlinkUserAgent = 'netdisk'`，并把「路由 → UA」做成表。
  ⚠️ 刻意用**裸 `netdisk`**：AList 用裸值能跑通 ⇒ CDN 判据不含「必须 `netdisk;`
  开头」，裸值在「全等」与「包含」两种判据下都成立，是严格更安全的选法。
- `baidu_models.dart`：`toStreamTicket` 新增 **required** `userAgent`。
  刻意不给默认值 —— 默认值会让「以后加路由忘给 UA」变成**静默**线上故障，
  required 会直接变成编译错误。
- `baidu_adapter.dart`：① 用官方 UA；②③ 用 netdisk UA。成功日志补
  `查询键=[fid,sign,time,…]` 与 `UA=…` 两项 —— **下次现场取证不用再改代码**。

**验证**（先写红）：新用例先失败于
`Expected: 'netdisk' / Actual: 'pan.baidu.com'`（正是线上那个 bug）⇒ 改后
`flutter test test/data/baidu_{adapter,models,qr_login}_test.dart` → **All tests
passed! (+151)**；`flutter analyze lib/data/remote/baidu test/data/baidu_*_test.dart`
→ **No issues found!**。**未提交**（等审计）。

**仍未证 / 下一步**：本次修复基于「AList 的 crack 路由 + 客户端 UA 构造器」两条
**外部证据**，本机无法复现真机下载 ⇒ 需用户真机再跑一次下载确认（预期分块拿到
**206**）。若仍 403，下一条线索看新日志里的 `查询键=` —— 若不含 `sign`，
说明 `parseDlink` 取错了字段而不是 UA 问题。

## 五修：仍 403 —— 上一轮「crack 直链要 netdisk」**被证伪** ⇒ 改成运行时探针实测

**现象**：真机重跑，`01.mp4`（265.4 MB，`/我的资源`）依旧
`urlExpired 分块下载失败：HTTP 403`（L665 / L682）。

**上一轮的结论被证伪**（本轮最重要的信息）。日志 L664 正是上一轮加的取证字段：

```
百度取链成功：https://d.pcs.baidu.com/file/b1ee5dd84s631b2295240b1a9072df87，
查询键=[chkbd,chkv,clienttype,dp-callid,dp-logid,dstime,expires,fid,origin,r,rt,sign,vuk]，
UA=netdisk，档位=[origin]
```

⇒ dlink **带 `sign`**（不是解析错字段），UA **确实已经是 `netdisk`**，**照样 403**。
叠加上一轮：`pan.baidu.com` 也 403。**两个 UA 都被证伪** ⇒ 问题不在 UA，
或不在「只换 UA」。上一轮那句「crack 路由必须 netdisk」是**错的**，已从
`MEMORY.md` 改掉。

**顺带纠正另一条旧结论**：日志里每个 `pan.baidu.com` 响应都带
`← set-cookie: PANPSC` ⇒ **百度会下发/刷新 Cookie**，不是「完全不轮换」。
（适配器目前刻意不吸收，见 `baidu_adapter.dart` 的注释；先记为待查。）

**改动（不再猜，改成实测）**：

- `baidu_endpoints.dart`：加 `dlinkClientUserAgent`（客户端完整 UA
  `netdisk;1099a;PC;PC-21;21.6.0;UniBaiduYunGuanJia`）。
- `baidu_models.dart`：`toStreamTicket` 改成收 **`headers`**（形状决策权交给
  调用方），新增 `dlinkHeaders(userAgent, cookieHeader, includeCookie,
  includeReferer)`。关键是后两个开关 ——「少带一个头」现在和「换 UA」一样是
  候选假设（AList 的 crack 路由**两个都不带**）。
- `baidu_adapter.dart`：新增**直链形状探针** `_probeDlinkShape`：对 5 条候选各发
  一次 **1 字节 `Range: bytes=0-0`**，谁先回 206/200 就用谁，结果进日志
  （`百度直链探测「…」→ HTTP 403` / `206 ✓ 采用`）。形状**按会话缓存**
  （**实例**字段而非 `static` —— static 会让单测互相污染）。
  候选顺序：①铸造时同 UA（浏览器 UA）+Cookie+Referer（因为 dlink 查询串里有
  `chkbd`/`chkv`/`vuk` 三个疑似**校验位**，而客户端每次 `/api/*` 都用同一个 UA
  ⇒「取链与取文件必须同 UA」是**同等合理**的假设，上一轮只试了「换客户端 UA」
  就是漏在这里）②裸 netdisk（AList 形状，无 Cookie/Referer）③裸 netdisk+Cookie
  ④完整客户端 UA+Cookie ⑤官方 UA+Cookie。
- `drive_download.dart`：⛔ **非 206 时先留 300 字节响应体再报错**
  （`_readBodySnippet`）。理由：业务错是 HTTP 200 + JSON，而「形状不对」的 403
  **体里往往有线索**；只报 `HTTP 403` 会把「形状不对」误判成「直链过期」——
  我们正是这么被误导两轮的。

**验证**（先红后绿）：新用例先失败于 `Expected: 'bytes=0-0' / Actual: <null>`
（断言打在了最后一次请求上，而那是 ③ 不是探针），以及探针把 `/api/*` 也拦了
（`FakeHttp.headerHandler` 改成「返回 `null` = 不归我管」才修好）；改后

### 对照实验（真实账号 + 真实直链 + curl 三方对照）

`Dart/x.y (dart:io)`**（`Range`/`Referer` 会保留，`Cookie` 也会丢）。
于是：第一跳 302 → 第二跳带着 `Dart/…` ⇒ **必然 31362**，
而下载层把 403 归成 `urlExpired` ⇒ 现场看到的永远是「直链过期了」。

**顺带证伪两条**（都做过对照）：
- 直链 `sign` 里的**小写百分号转义**（`%2fk%3d`）被 Dart 大写化（`%2Fk%3D`）
  —— CDN **不介意**，两种串都 302/206。**不是**原因。
- 「expires 太短」：取链成功到下载失败只隔 0.7 s。**不是**原因。

## 追问：百度能不能靠「8 连接分块」下快？（实测，未改代码）

用户问「百度下载好慢，是否支持多线程分块，比如 8 连接」。先回答事实：**代码早就支持** ——
`kDownloadConnections = 8`、`kDownloadChunkSize = 2 MiB`，`ticket.connectionsFor()` 没钉上限时
大文件自动走 `_downloadChunked`。问题不在「有没有」，而在「百度让不让」。

用真实凭证 + 真实 `BaiduAdapter` 实测（`test/tmp_baidu_multiconn_test.dart`，跑完即删），
区间一律**闭区间非重叠**（第一版用 `bytes=start-` 开区间，结果各连接互相重叠、数据作废）：

### ① 多文件并行（4 个不同 PDF，各 1 连接，12 s 窗口）

```
4 文件 × 1 连接 → 合计 1503 KB = 98 KB/s | 每文件[1024/0/479/0]KB
```

⛔ 其中 **2 个文件 12 秒里一个字节都没收到**（HTTP 206 拿到了响应头，包体不来，
且不算「报错」——`_stallGuarded` 要 30 s 才判超时）。并行**不成倍叠加**。

### ② 单文件多连接（同一 PDF 43.98 MB，非重叠区间，12 s 窗口）

| 连接 | 窗口内合计 | 吞吐 | 每连接 KB |
|---|---|---|---|
| 1 | 400 KB | 31 KB/s | 400 |
| 2 | 912 KB | 70 KB/s | 512/400 |
| 4 | 1099 KB | 76 KB/s | 300/159/400/240 |
| 8 | 920 KB | 65 KB/s | 240/0/0/200/0/0/240/240 |

⇒ **天花板 ~70-80 KB/s，与连接数无关**；1→2 有提升，2→4→8 不再涨、8 条里 **3 条收 0 字节**。
（另一次跑 1 连接是 78 KB/s、2 连接 70 KB/s —— 跑间方差比「加连接」的效应还大，
所以**不能**据此说 2 连接更好；1 连接是唯一从不被掐的值，维持现状。）

### ③ 视频 dlna 快通道（完整下载 5.33 MB）

| 连接 | 墙钟 | 吞吐 |
|---|---|---|
| 1 | 1601 ms | 3252 KB/s |
| 4 | 1789 ms | 2911 KB/s |
| 8 | 1358 ms | 3834 KB/s |

⇒ 快通道**单连接就 3.2 MB/s**；8 连接只快 18%（文件太小，建连 + Range 协商吃掉收益）。
「dlna 多连接能叠加」这个结论仍然只由 10-09 凌晨 `baidu_conc_probe` 的 1→1151/2→2062/
4→3109/8→4142 KB/s 支撑，今天这条小文件测不出来。

### 结论（对外口径）

- **非媒体（文档/压缩包/图片…）：加连接无效。** 限速是**按账号/文件**算的 ~30-100 KB/s，
  把配额切开只会让每条都慢到被掐断 —— 这正是上次「卡 0%、7 分钟后才报错」的根因。
  所以 `maxConnections: 1` 是对的，**不改**。
- **媒体（视频/音频）：走 dlna 快通道，已经不限并发**，单连接就 3 MB/s 量级。
- 客户端**没有**别的提速手段：文档带 `origin=dlna` 会被 CDN `403 31329`（已实测），
  其余 `origin` 全在 40-90 KB/s。要更快只能靠百度会员侧加速。
- 「同时下载的文件数」调大**不会**变快（4 个并行合计 98 KB/s，还有 2 个颗粒无收）；
  默认 5 可以降到 2-3 以减少饥饿，但这属于行为改动，未做。

## 续查：连接数到底是不是提速杠杆？（**结论修正，仍未改代码**）

上一节的「单文件多连接」表里我写了「1→2 有提升，2→4→8 不再涨」，
并据此怀疑 `_slowChannelConnections = 1` 定小了。**这个怀疑是错的**，
是短窗口 + 固定顺序造成的假象。补了四轮实验才看清：

### 实验一：10 s 窗口，固定顺序 1→2→4（3 轮）

| 连接 | 三次 | 均值 | 相对 1 | 异常 |
|---|---|---|---|---|
| 1 | 879 / 287 / 127 KB | 431 | 1.00× | — |
| 2 | 590 / 634 / 623 KB | 615 | 1.43× | — |
| 4 | 770 / 759 / 748 KB | 759 | 1.76× | — |

⚠️ 「1 连接」单调衰减（879→287→127）而 2/4 稳定 ⇒ 像**顺序混淆**
（4 连接的突发把账号带进冷却，下一轮的第一个——总是 1 连接——正好撞上）。

### 实验二：10 s 窗口，**轮转顺序** + 臂间静默 6 s

| 连接 | 三次 | 均值 | 相对 1 | 异常 |
|---|---|---|---|---|
| 1 | 0 / 895 / 895 KB | 597 | 1.00× | ⚠ **零字节 1、掐断 1** |
| 2 | 1312 / 276 / 1112 KB | 900 | 1.51× | 无 |
| 4 | 1788 / 1721 / 1027 KB | 1512 | **2.53×** | 无 |

看起来 4 连接赢麻了 —— 但**这是 10 s 窗口的假象**。

### 实验三：持续 120/180 s（两个方向各跑一次）

| 运行 | 顺序 | 1 连接 | 4 连接 |
|---|---|---|---|
| A（180 s/臂） | 1 先、4 后 | **79 KB/s** | 65 KB/s |
| B（120 s/臂） | 4 先、1 后 | **16 KB/s** | 93 KB/s |

⇒ 同一配置两次跑出 **79 和 16 KB/s（差 5 倍）**，且方向一换结论就翻。
**10 s 窗口的 2.53× 是 TCP 慢启动的突发**，长期被同一个限速吃掉。

### 实验四（决定性）：同一时间段内**交替** 1↔4，各 60 s × 3 组

```
#1 1 连接 | 0-30s  80 → 30-60s  85 KB/s
#2 4 连接 | 0-30s 111 → 30-60s  87 KB/s
#3 1 连接 | 0-30s  13 → 30-60s  14 KB/s
#4 4 连接 |  0 KB/s  ⚠ 有连接报错
#5 1 连接 |  0 KB/s  ⚠ 有连接报错
#6 4 连接 |  0 KB/s  ⚠ 有连接报错
```

前两臂合计约 **11.6 MB** 之后，**1 连接与 4 连接一起归零**。
⇒ 不是连接数的问题，是**账号侧额度用尽**。

★★ 交叉印证：最初那个 bug 的 `.part` 冻在 **10485760 字节 = 正好 10 MiB** ——
与这里「跑了 ~10 MiB 就被掐」是同一个现象。当时我归因于「8 连接打一条慢通道」，
**那只是表象**；真因是**服务端对非会员非媒体下载的账号级额度/限速**。

### 决定

- ⛔ **`_slowChannelConnections` 保持 1，不改。** 依据：连接数在持续测量里
  **没有可复现的正收益**（1 与 4 互有胜负，且方向随顺序翻转）；而 8 连接在
  3 次观测里**每次都出现零字节/被掐连接**，4 连接是把服务端并发面扩大 4 倍，
  收益不确定、风险确定。1 是并发面最小、从不更差的值。
- ⛔ **不要再去追「多连接给百度文档提速」** —— 这个杠杆在客户端不存在。
  能做的只有：把「静默挂死」变成「及时报错」（`stallTimeout`，已在），
  以及如实告诉用户这是账号侧限速。
- ★ 媒体（视频/音频）的 dlna 快通道多连接**确实**能叠加，那条不受影响。

### 方法学教训（下次直接用）

1. **10 s 窗口测带宽不可信** —— TCP 慢启动会让多连接虚高 2-3 倍。
   要看**后 30 秒**，或直接测「下完 N 字节要多久」。
2. **固定顺序 = 混淆**。臂与臂之间必须轮转或交替，否则「谁后跑谁吃亏」。
3. **长跑会改变账号状态**。同一会话里越往后测越慢，跨会话对比也会被前一次污染。
4. 判据要写进日志：`⚠ 零字节 / 掐断` 这类**可用性**信号比吞吐更能说明问题。

## 十六修：百度视频**一播就 Failed to open** —— 中继分块取块漏了客户端级 UA

### 现场

用户报 `/我的资源/VID_20261007_170446.mp4`（fs_id `79763014313388`，1.27 GiB）无法播放。
日志（16:41:32）：

```
[取链] 百度走 dlna 快通道（category=1）
[取链] 百度取链成功：https://d.pcs.baidu.com/file/72977883ct01d6c8740aa3c12d39ae11 …UA=netdisk
[中继] 已接管 s1 … 1.27 GiB，8 连接 × 2 MiB 块，预取 256 MiB
[中继] 取块 4 失败：上游返回 403
[中继] 取块 5 失败：上游返回 403        ← 一共 18304 条
[中继] 会话 s1 读取器 #1 结束：已下发 0 字节（连接中断）
[播放窗口] mpv 报错：Failed to open
```

★★ 历史对照（一眼看出是回归）：**10-02 到 10-08 共 163 次中继接管，`403 取块` 0 次；
10-09 的 2 次接管，403 取块 18304 次。**

### 根因（实测钉死）

`LocalStreamRelay._fetchChunk` 把票据头**逐条 set 到 `request.headers`**，
而 **`dart:io` 跟随 302 时会把请求头上的 `User-Agent` 换成客户端级默认值**
（`Dart/3.7 (dart:io)`）。百度 `origin=dlna` 直链**第二跳的 `sign` 是按 UA 签的**。

用真实凭证 + 真实直链实测（同一张票据、同一个 Range）：

```
A) 中继贴头方式（只 set 到 request.headers）→ HTTP 403 → yq01-cm01.baidupcs.com
   体 = {"error_code":31362,"error_msg":"sign error"}
B) applyTicketHeaders 方式（额外设 client.userAgent）→ HTTP 206 → whzj-cm01.baidupcs.com
对照：HttpClient 默认 UA = Dart/3.7 (dart:io)
```

⇒ 是中继**分块取块**这一条路径漏了；同文件的**透传路径**（`_pipeUpstream`）早就调了
`applyTicketHeaders`（注释都写着「与下载层同一条坑」），**只有它没调**。

### 性质：这是今天下午那次修复的**不完整落地**

下午把视频从「无 origin 慢通道」挪回 `origin=dlna` 快通道时，只验证了**下载**路径
（`drive_download.dart` 两处都调 `applyTicketHeaders`，E2E 1192 KB/s ✅），
**没有验证播放路径**。慢通道第二跳不挑 UA，所以之前能播（只是慢）；
换成 dlna 之后第二跳挑 UA，中继立刻全 403 —— 「能下不能播」。

### 改动

| 文件 | 改动 |
|---|---|
| `lib/core/utils/ticket_headers.dart` | 把「设客户端级 UA」抽成 **`applyTicketUserAgent(client, headers)`**，`applyTicketHeaders` 改为调它。文档写明「手工贴头时必须额外调这个」 |
| `lib/data/stream/local_stream_relay.dart` | `_fetchChunk` 在手工贴头之后补 `applyTicketUserAgent(client, headers)`，并写清 18304 次 403 的现场 |
| `test/data/stream/local_stream_relay_test.dart` | 新增 `票据 UA 必须熬过 302` —— 本地「302 → CDN」两跳复刻，断言**第二跳**看到的 UA 仍是 `netdisk` |

抽出 `applyTicketUserAgent` 而不是内联复制：**同一个不变量散在多处就一定会漏一处**
（这次就是这么漏的）。排查后 4 个消费票据的地方全部覆盖：
`drive_download` 单连接 / 分块、中继透传 / 分块。

### 验证

- **红**：先摘掉修复跑新用例 → 失败，报「第二跳看到的 UA 是 `{Dart/3.7 (dart:io)}`」。
- **绿**：恢复修复 → `flutter analyze` **No issues found**；
  `flutter test`（中继 + 百度 + 下载 6 个文件）→ **All tests passed!（+172）**。
- ⚠️ **未做**：真机/真 App 播放实测 —— 按约定由用户自己起服务验证。
  机制层面已被单测 + 真实直链 A/B 双重钉死。

### 教训

「票据头」是一个**跨层不变量**（下载层、中继透传、中继分块、以后可能还有 HLS 分片）。
今天下午我只测了改动点所在的层，就漏了另外两层之一。
**改不变量时，要按「所有消费方」列清单逐个确认，而不是只测自己改的那个调用点。**

**顺带排除的第二个疑虑（Windows job 会不会因平台差异再挂）**：
`SecretBackend.forPlatform` 在 macOS 走 `EncryptedFileSecretBackend`、其他平台走
`FlutterSecureStorageBackend` —— 但 `flutter test` 会设 `FLUTTER_TEST`，
`defaultTargetPlatform` 被**强制成 `android`** ⇒ **测试里两个 job 走同一条分支**；
且 `FlutterSecureStorageBackend()` 的构造函数是**纯 Dart**（只建一个
`const FlutterSecureStorage(...)` 配置对象），通道只在 `read/write/delete` 里碰，
而页面链路根本不读凭证。⇒ 不引入平台差异，不需要额外加固。

### 教训（与十六修互为两面）
十六修：「改**跨层不变量**要按消费方列清单」。
十七修是它的另一面：**页面新增一条 `ref.watch`，就等于给「页面级测试」新增一条隐式依赖。**
`test/ui/pages/` 下那些裸铺页面的用例，override 清单是**手工维护**的、不会自己跟上 ——
加 `watch` 时顺手扫一眼谁在铺这个页面。

## 十八修：同一类漏洞的第二、三处 —— 按消费方清单穷举出来的

**起因**：十七修的自省是「改跨层不变量要按消费方列清单」。那就真的列一遍：
把 `lib/` 里所有**手工往请求上贴头**的地方机械地捞出来
（`headers.forEach(request.headers.set)` / `for (final e in headers.entries)`），
逐个问「这个请求会不会打到网盘直链」。

**结果**：7 个构造点里上一轮只覆盖了 4 个，**还剩 3 个漏的**：

| 位置 | 打不打直链 | 状态 |
|---|---|---|
| `local_stream_relay` 透传 | 是 | 早已覆盖 ✓ |
| `local_stream_relay` 取块 | 是 | 十六修补上 ✓ |
| `drive_download` 单连接 | 是 | 早已覆盖 ✓ |
| `drive_download` 分块 | 是 | 早已覆盖 ✓ |
| **`dolby_vision_probe.fetchHeadBytesDirect`** | **是** | **本轮修** |
| **`player_window_app._probeHlsPlaylist`** | 诊断路径 | **本轮修** |
| **`player_window_app._probeFirstSegment`** | 诊断路径 | **本轮修** |
| `dio_http_client._headerSummary` | 只读头做日志脱敏 | 不是构造点，不用改 |

**杜比视界探测那条最要紧（用户可见）**：
`player_window_app.dart` 里 `selectFor` 上方**它自己的注释**就写着
「探测用的是**上游**地址与请求头（`uri` / `headers`），不是中继那条
`127.0.0.1` 地址」—— 即探测**故意**打网盘直链。而 `fetchHeadBytesDirect` 是
`headers.forEach(request.headers.set)`、没设客户端级 UA ⇒ 302 之后 UA 变成
`Dart/3.7 (dart:io)` ⇒ 百度 dlna 直链第二跳 `403 31362 sign error` ⇒
探测按「不是 DV」返回 `null` ⇒ **DV P5 片源不换 fvp 内核、用 mpv 渲染偏绿**，
而且**日志里一条错误都没有**（`null` 与「不是 DV」在接口上无法区分）。
平台范围：`dolbyVisionProbe` 只在 `Platform.isMacOS || (isAndroid && tv)` 接上，
macOS 上必然命中；Android TV 上 P5 那条判据也会失效（`videoHeight >= 2048`
那条不依赖探测，所以 4K 路由本身不受影响）。

**两处诊断路径**（`_probeHlsPlaylist` / `_probeFirstSegment`）：只在已经出事时各抓
一次 m3u8 / `.ts`，且都是 HLS 转码档。危害不是播放，而是**给出假结论** ——
这两条自检存在的全部意义就是分开「我们给的凭证不对」和「播放器读不动这条流」，
一个不带 UA 的请求会把 403 答成前者。

**做法**：仍然先红后绿。
- 新用例加在 `test/data/stream/dolby_vision_probe_test.dart`：
  「⛔ 票据 UA 必须熬过 302 —— 否则 dlna 直链第二跳回 403，探测静默变 null」。
  本地两跳（edge 302 → cdn 206），CDN **按 UA 校验**、UA 不对就回 403 31362
  （复刻真实行为，让用例真的复现故障，而不只是比对字符串）。
- **红**：`第二跳看到的 UA 是 {Dart/3.7 (dart:io)}` —— 与十六修现场**同一个签名**。
- **绿**：`dolby_vision_probe.dart` 补 `applyTicketUserAgent(client, headers)` +
  import；`player_window_app.dart` 两处各补一行 + import。

**验证**：探测文件 → **All tests passed!（+12）**；
`test/data/stream/` + `drive_download_test` → **+82**；
`flutter analyze` → **No issues found**；全量 → 见下。

### 教训
十六修只修了「当时手上那一条」。十八修证明：**不变量必须按清单穷举，而且清单要
机械地捞（grep 所有贴头点），不能靠回忆。** 漏掉的 3 处里有 1 处用户可见（偏绿）、
2 处会误导排查 —— 都藏了将近一周，因为它们**全都不报错**。

### 附：第四条路（Dio）—— 机制已证、影响未证、**未改**

把清单继续推到「所有 HTTP 客户端构造点」时又发现一条。这条与前三条**性质不同**，
所以只记录不改：

- **机制已证**：`DioHttpClient.getBytes` 同样会在 302 后丢 UA。本地两跳实测
  （临时探针，已删）：
  `PROBE_RESULT secondHopUAs=[Dart/3.7 (dart:io)] bytes=3`
  —— Dio 默认的 `IOHttpClientAdapter` 内部也是 `dart:io HttpClient`，同病。
- **暴露面已证**：`readFileBytes` 走 `_http.getBytes(ticket.url, headers: ticket.headers)`
  —— `lib/data/remote/baidu/baidu_adapter.dart:936`、
  `lib/data/remote/quark/quark_adapter.dart:709`。调用方 3 处，读的都是**非媒体**文件：
  `library_backup_service`（读 `.ccbak` 备份）、`app_providers`（外挂字幕）、
  `player_bridge_host`（字幕）。
- **影响未证**：非媒体文件 `category` 是 4/5/6 ⇒ `canUseDlna` 为假 ⇒
  `resolveStream` 给的是**非 dlna** 直链。而「第二跳 `sign` 按 UA 签」目前只在
  **dlna** 通道上被实测证过（十六修那次 A/B）。非 dlna 通道是否同样按 UA 签 ——
  **没有证据**。现场也取不到：`cloudcine-2026-10-08.log` 里连一条 403/412 都没有，
  也没有任何百度字幕/备份读取的痕迹（这个功能大概还没被用过）。

**为什么不顺手修**：前三条都有「**已证**会打到按 UA 签名的跳」的路径，修它等于
关掉一个已证的故障。这条只到「机制已证 + 暴露面已证」，直接证据缺一环；
而且修法不再是加一行 —— `DioHttpClient` 是**所有 API 调用**共用的通用客户端，
全局改它的 UA 行为风险明显更大；更该做的是把 `readFileBytes` 改走
`fetchHeadBytesDirect` 那条 `dart:io` 路（但语义要重新对齐：`maxBytes` 截断
vs 超限报错）。⇒ **留给用户决定，不擅自改。**
