## 排查：TV 恢复备份后部分作品显示的是网盘截图、不是刮削海报

**现象**：macOS 上传备份 → TV 恢复 → 「生死时限」「阿凡达：火与烬」等在 macOS 上是 TMDB 海报，TV 上是网盘视频截图。

**取证链**（可复用）
- macOS 库在 `~/Library/Application Support/com.cloudcine.cloudcine/`（**HOME 被沙箱改写，`~` 找不到，要用绝对路径**）。`sqlite3` 查 `media_works.poster_url` / `poster_file`。
- TV 上 `run-as` 不可用（release 包 not debuggable）、无 `su`。**改用 logcat**：`adb logcat -d --pid <pid>`。关键行 `媒体库：N 部 … 海报索引 X 个文件 · 命中 Y`（`LibraryActivity.loadWorks`）。
- 用 Python 复算 `PosterNaming.hash8/sanitize` 对齐 PC 的 `PosterCache._sanitize`，确认文件名。

**结论**：根因是 **TV 上装的构建里 `PosterStore.fileFor` 没有第 ② 步**（按当前 `poster_url` 现算文件名）。旧口径只有 ①`poster_file`（PC 刮的为空）+ ③目录索引，而索引对每个键**只留 `listFiles()` 里第一个** ⇒ 一个键下有多张图时随便挑。实测 378 个海报文件 / 314 个键，其中 **58 部作品的键下有 2~3 张图**（网盘截图 + 刮削海报各一张），所以不止那两部。
**判据**：`javap -p -c` 反编译 `android/app/build/tmp/kotlin-classes/release/.../PosterStore.class`，`fileFor` 里没有 `PosterNaming.fileNameFor` 调用 ⇒ 该 release 产物无第 ② 步（debug 产物有，说明工作区已改、只是没装机）。
**修**：`PosterStore.fileFor` 加第 ② 步（工作区已改，2026-10-07 07:31，未提交）。重新出包装机即可，**不用重新恢复/重新刮削**（海报文件本来就在 TV 上）。
**⛔ 附带发现**：`adb backup -noapk` 在 MiTV 上弹确认框后 `input keyevent` 推不动按钮，产物恒 0 字节 —— 别指望这条路取 TV 数据。

### 2. 两个关键设计判断

- **两行胶囊刻意不合并**：动作行回答「对这一部作品做什么」，排序行回答「这一页
  的列表怎么排」。合成一行的话「▶ 播放」会和「修改时间倒序」并排，用户按 ←→
  路过时分不清哪颗是动作。于是有 `actionsFocused` / `itemsSortFocused` 两套光标态。
- **焦点始终留在 `itemsList` 上，胶囊只吃光标态**（与一级导航带 / 状态行同一套
  语言）：焦点一挪到胶囊上，底下列表那行的高亮就没了，用户会以为列表被清空了。
  ⛔ 各 `focus*` 必须互相清标志位，漏清 = 两行同时发光。
  上下层照物理位置：动作行 ↑↓ → 排序行 ↑↓ → 列表；**排序行上的 ↑ 从「回作品墙」
  改成了「到动作行」**，只有动作行上的 ↑/返回才退出这一页。

### 3. ⛔ 顺手修掉一个**不报错**的真 bug

`openWork` 里原来是：

```kotlin
items.clear()
items.addAll(list ?: emptyList())
…
items.clear()                                     // ← 又清了一次
items.addAll(sortItems(items, itemsSortMode))      // ← 排的是空列表
```

⇒ **剧集列表永远是空的**，不报任何错，只是「点进去什么都没有」。改成
`items.clear(); items.addAll(sortItems(list ?: emptyList(), itemsSortMode))`。

### 4. 文案口径下沉成纯函数 + 单测

新增 `library/WorkDetailFormat.kt`（`object`，纯函数）+ `WorkDetailFormatTest`（13 例）。
理由：每一条都是跨端口径，写错**全都不会报错**，而 `LibraryActivity` 里的东西
JVM 单测跑不起来（与 `PlayTarget` / `PosterNaming` 同一套做法）。钉住四条：

| 口径 | 写错的后果 |
|---|---|
| 「已刮削」= `source == "online"`，**不是**「有海报」 | 刮了没下到图的作品写「未刮削」，再刮一遍还是这样 |
| 季数门槛 `>= 2` | 每部电影 / 单季剧多一个「1 季」，像分类判错了 |
| 类型最多 4 个 | 折成两排，把简介正文挤出屏幕 |
| 原名 `!= title` 才画 | 中文片名没刮到时标题连着印两遍 |

**第三个「测试自己写错了」的实例**：我断言「什么都没刮到时 `metaLine` 返回空串」，
实际是 `"其他 · 未刮削"` —— 分类（兜底「其他」）与来源两项恒在，这一行永不为空。
改对断言之后，顺带把 `paintDetailHead` 里多余的 `if (text.isEmpty()) GONE` 也删了。

## 追剧 / 更新提醒 —— 场景设计（只出方案，未动代码）

产出：`docs/追剧-更新提醒-设计方案.md`（约 400 行）。两端同一套数据契约，UI 各自设计。

**核心决策（下次接着做时先看这几条）**：

1. **加 4 列到 `media_works`**（不新建表）：`followed` / `follow_started_at` /
   `follow_checked_at` / `new_item_count`。schema **16 → 17**，两端同时改，
   **无回填**（默认值恰好表达「没追剧」）。
2. **三条判据全靠已有的 `media_items.first_seen_at` 做差**：
   ①本次新增 = `first_seen_at > follow_checked_at` → 角标增量累加；
   ②追剧以来新增 = `first_seen_at > follow_started_at`；
   ③`max_position_ms IS NULL`。②∧③ = 剧集行 NEW 标签（播过自动消失，零额外写入）。
   ⛔ **刻意不用 `modified_at`**：替换文件（换更高码率）会误报「有新集」。
3. **检查 = 复用现成的局部发现**（PC `MediaDiscoveryService` / Android
   `LibraryScanner.discover`），只对已追剧作品名下的目录跑，`recursive=true`。
   ⛔ 绝不调全盘 `scan()`（会写游标 + prune 子树）。
4. ⛔⛔ **自动检查不写 `media_works.updated_at`**。`libraryModifiedAt` 是同步 LWW 判据，
   写了就会「本地永远看起来更新 → 无条件上传 → 盖掉另一台设备的进度」。

## 第二轮现场：恢复**成功**之后崩溃（`LateInitializationError`）

### 现象与日志复核
用户截图：`LateInitializationError: Field '_queue@218433218' has already been initialized.`
日志 11:40:50 那次恢复其实**已经成功**：
```
11:40:50.118 [数据库] 索引库已升级到 v17（追剧 / 更新提醒）
11:40:50.122 [备份] 数据库已写入 …（已换新连接，迁移随之完成）
11:40:50.189 [备份] 海报缓存已恢复 378 个文件
11:40:50.297 [媒体库] 列表就绪：129 部
```
⇒ 崩溃发生在**恢复完成之后的下游重建**，与恢复本身无关。
（对比 11:15 / 11:27 那四次：日志都停在「数据库 1884160 字节」之后 —— 那是上一轮
`reopenDatabase()` 走不通留下的旧现场。）

### 根因
`lib/ui/providers/download_providers.dart` 的 `DownloadQueueController` 把队列存进
`late final DownloadQueue _queue`。Riverpod 在依赖变化时**复用同一个 Notifier 实例**
再调一次 `build()` ⇒ 第二次赋值直接抛。触发链：
`DatabaseHandle.swap` → `databaseProvider` → `downloadTaskStoreProvider` → `downloadQueueProvider`。
★ 22 个 Notifier 子类里**只有它**是一次性初始化；`FollowController` / `ScanController` /
`LibraryScrapeController` 早就按「可重建」写（`_disposed = false` 复位那一套）。

**修**：`DownloadQueue? _queue` + `DownloadQueue get _q => _queue!`；
`build()` 开头 `_queue?.dispose(); _disposed = false;`；
`ref.onDispose` 里 `queue.dispose()` 捕获**局部变量**（读 `_queue` 会把新队列收掉）。

### 上一轮「换实例」方案补的两颗雷
1. ⛔⛔ `DatabaseHandle.build()` 里写 `return _initial` ⇒ 持有者**自己**被重建一次
   （`ref.invalidate` / 热重载 / 依赖变化）就把刚换上的新库**退回给那个已经
   `close()` 的旧实例**，之后到处 `Can't re-open a database after closing it`，
   而且是在「恢复成功」之后才炸。改成 `_current ?? _initial`，`swap` 同时写 `_current`。
2. ⛔ `DownloadQueue.init()` 是 `build()` 里 `unawaited` 出去的，`dispose()` 可能在它
   跑到一半时发生 ⇒ 还没落地的 `loadAll` 撞上已关连接 ⇒ unhandled async error。
   修：每步之间查 `_disposed`；`on StateError` 只在 `_disposed` 为真时吞（否则 rethrow）。
   ★ 机制：Drift 的 `ensureOpen` 是**异步**的（`_runRequest` 里 await）⇒
   **「调用时库还开着」不等于「执行时库还开着」**。这条是排查这类竞态的总钥匙。

### 新增守卫测试
- `test/ui/providers/restore_backup_rebuild_test.dart`：
  ① 换库 → 下游确实重建、且不抛 `LateInitializationError`；
  ② 持有者重建后仍给出**换上的那一个**。
  ★ ②已离线验证：把 `build()` 退回 `return _initial` 立刻变红（`Expected: true / Actual: false`）。
- `test/data/db_swap_after_restore_test.dart`（上一轮）+ `database_swap_wiring_test.dart`（静态读源码）。
- 回归：`test/domain test/data test/ui/providers` = **1388 例全绿**；
  `flutter analyze lib test` 只剩既有 `player_page.dart:997 WillPopScope`。

### 顺带修掉的假日志
`AppDatabase.openFile` 现在**自己**写 `_openRequestedAt`（原来只有 `openAppDatabase()` 写）
⇒ 恢复备份那条路不再打出「从申请打开起 **19846ms**（含迁移）」这种把启动后半小时
都算进去的假数字。`openAppDatabase()` 里那句冗余赋值已删。

## 第三轮现场：追剧「说有 2 个更新，但简介的文件列表里找不到」（macOS）

用户原话：
> 「遮天这部动画片设置为追剧后，点击更新后发现有 2 个更新，但是并没有在简介的
>   文件列表中发现这俩文件，要求是发现有更新的追剧，自动更新到媒体库并在列表中
>   进行醒目标记直到点击后去除醒目标记」
> 「**可能是因为没有刷新缓存，点击一下刷新可以看到 2 个新文件**」

★ 最后这句**推翻了**我第一轮的判断（我当时以为是「新集落在未被选中的季格」）。
三方对齐（日志 / 用户库 / 源码）之后的真根因在**信号接线**上。

### 根因（按重要性排序）

**① 真根因：`workDetailProvider` 没订阅 `libraryWriteSignalProvider`**
- 文件：`lib/ui/providers/library_providers.dart` 的 `workDetailProvider`。
- 它当时只 `ref.watch(playbackProgressSignalProvider)`（播放进度）。而写库的几条路径
  （扫描 / 发现 / **追更检查** / 批量刮削）推的是 `libraryWriteSignalProvider`。
  ⇒ 追更检查把新集写进库了，**详情页不在那条链的下游**，不重查。
- 为什么难查：库**写对了**（日志 `[发现] 媒体 13（新增 2 / 已有 11）`、
  `[追剧] 检查结束：… 新增 2`，库里 `new_item_count = 2`），点一下页头「刷新」
  立刻就对 ⇒ 既不像「写失败」也不像「查询错」。
- **修**：加 `ref.watch(libraryWriteSignalProvider);`。
- ★ 一般化：**任何「读库的视图」都必须 watch 写库信号**；漏掉的表现是「点了按钮
  毫无反应」，而 `FollowController._refreshAfterWrite` 的注释早就反复强调过这一条 ——
  这次漏掉的是**文件列表本身**。

**② `clearFollowBadge` 在 2026-10-07 之前全工程没有调用点** ⇒ 海报上的「更新 N」
   永远不会消失，用户没有任何办法清掉它。
- **修**：`workDetailProvider` 里判「这一部下已经没有任何『追剧后新增且没播过』的
  条目」时清掉。判据必须与行级 `■ NEW` **同源**（同一个 `isNewSinceFollow` +
  `maxPositions`），否则会出现「列表里一条 NEW 都没有、海报上还挂着 2」。
- ⛔ **用 `maxPositions` 而不是 `resumePositionMs`**：后者看完会被清成 NULL。
- 清角标只清 `new_item_count` 一列（`follow_started_at` / `follow_checked_at` /
  `updated_at` 都不能动，理由见 `clearFollowBadge` 的注释）。

**③ `183 4K.mp4` 提不出集号**（`lib/core/utils/filename_parser.dart` 的 `_parseDotted`）
- `183` 被当片名（`_isStandaloneRelease` 允许纯数字当名字，为《65》那部电影），
  紧接着「目录名作为系列名」那条规则用目录名顶掉 `title` 时**连季集号一起清掉** ⇒
  它成了库里的独立作品，而详情页按「作品 = 遮天」查文件，永远查不到。
- **修**：`_parseDotted` 加 `bareEpisode` —— 三条守卫同时成立才算：
  ① `title` 是纯数字（`^\d{1,4}$`）；② 编号与第一个技术标记之间**只隔空格**
  （`markerStart > 0`，点号不算）；③ **没有年份**。命中后 `title = null`
  （让目录名兜底），`kind = episode`，`episode = bareEpisode`。
- 回归样本全部不变：`65.2023.2160p…`（片名《65》）、`159.mkv`、`183.mp4`、
  `182.格力空调显示E6如何维修.mp4`。

### 顺带做的可见性改进（用户三选一里选的「格子角标 + 提示条」）
`lib/ui/pages/work_detail_page.dart`：
- 季/部 chip 上加「N 新」小胶囊 `_NewCountBadge`（**品牌色**，不跟选中态走）；
- 当前格一条新的都没有、而别处有时，选择器下面挂一条整条可点的指路条
  `_NewItemsHint`（「有 N 集更新在「X」里 · 去看看」），点一下 `setState` 切格。
- ⛔ 角标与行级 `■ NEW` 必须用**同一个** `isNewItem` 判据。

### ⛔ 踩到的坑：`ref.invalidateSelf()` 不能在 `FutureProvider` body 里用
清角标之后我原本写 `ref.invalidateSelf()` 把 `work` 刷成 `newItemCount = 0`。
结果单测直接**超时 30 秒**，Riverpod 抛：
`Bad state: The provider … was disposed during loading state, yet no value could be
emitted.` —— 本次计算产出的那个 future **永远不完成**，而详情页正是靠它拿数据的。
- **修**：直接 `work = owner.copyWith(newItemCount: 0);` 改手上这一份。
  既省掉一次四查询，也不会把状态推回 loading（值本来就已知）。
  顺带避开「万一 `clearFollowBadge` 没写成功 ⇒ 自我作废变无限重建」的隐患。
- ★ 一般化：**在 provider 自己的 body 里作废自己，等于把当前这次计算的 future 丢掉。**

## 第四轮现场：「点了 NEW 不消失」+「『更新 2』不动」（macOS）

用户两句话：
> 「看到了简介页面的 new 标记的列表，但是点击后，new 标记不消失，并且媒体库
>   列表中的『更新 2』标记也没有相应的调整」
> 「**调整逻辑，无论播放了多长时间，只要点击了，就去掉 new 标记**」

### ① 真根因：「已读」只认 `max_position_ms`，而它只在**整十秒边界**上报
三方对齐取证（日志 + 用户库 + 源码）：

- 日志：`12:32:30.697 播放请求已被播放窗口取走：Z 遮 天 E184` →
  `12:32:33.674 收到窗口关闭通知`（**3 秒**）；`E183` 同理 **2 秒**。
  **期间一次进度回报都没有。**
- 用户库直查（`/Users/tandy/Library/Application Support/com.cloudcine.cloudcine/
  cloudcine.sqlite`）：`183 4K.mp4` / `EP184.mkv` 的 `max_position_ms` /
  `last_played_at` / `resume_position_ms` **三列全 NULL**。
- 源码：`player_protocol.dart` 的 `ProgressThrottle.accept` ——
  `second <= 0` 或 `second % 10 != 0` 直接返回 null ⇒ **播放 < 10 秒 = 库里一个字
  都没写**。而关窗时 `_releasePlayer()` 先 `sub.cancel()` 再 stop、且
  `_currentRequest = null`，**不补最后一笔**（Android 端 `onDestroy` 是补的，
  这就是两端差异的来源）。

★ 钥匙：`max_position_ms` 是「**看到哪儿了**」，而「**有没有点过**」是另一件事。
拿前者当后者的判据，就要求「至少看满 10 秒」，而用户的口径是「点一下就算」。

### ② 修法（四处 + 一个新叶子文件）
- **新建 `lib/domain/services/follow_read.dart`**：
  ```dart
  bool isItemWatched(MediaItem item, Map<String, Duration> maxPositions) =>
      maxPositions[item.id] != null || item.lastPlayedAt != null;   // 两条取或
  Future<int> syncFollowReadCount(MediaRepository repo, String workKey) { … }
  ```
  ⛔ **起播不写 `max_position_ms`**：写假极小值会让每一行点过的条目画出一条
  **0% 进度槽**（`_WatchedBar` 的槽是**不透明**的 `panel2`，看得见），而且与
  「播了不足 1 秒 = 从没播过」的定义自相矛盾。**已读回执归 `last_played_at`，
  位置归 `max_position_ms`。**
- **`ui/widgets/play_action.dart`**：新增 `_markOpened(ref, item)`，在 `playItem`
  的**两条**返回路径上 `unawaited` 调用（独立窗口成功开窗后 / 退回内置页
  `context.push` 之前）。它做三件事：`repo.markPlayed(item.id, now)` →
  `syncFollowReadCount(repo, item.groupKey)` → 推 `playbackProgressSignal` +
  `libraryListSignal`。
  - ⛔ **三个 `ref.read` 必须在第一个 `await` 之前**：内置页那条路紧接着
    `context.push` 换页，之后再碰 `ref` 会抛
    「Cannot use ref after the widget was disposed」。
  - ⛔ **刻意不推 `libraryWriteSignalProvider`**：它下游挂着 `folderTreeProvider`
    （每次读全表两万行），而播放只写播放记录。与 `onPositionTick` 同一套口径。
- **接口改名**：`clearFollowBadge(key)` → **`setFollowNewItemCount(key, count)`**
  （语义泛化成「写成给定值」，因为现在要写的不只是 0）。三处实现/注释同步。
- **`ui/providers/library_providers.dart`** 的 `workDetailProvider`：判据换成
  `isItemWatched`，条件从 `remainingNew == 0 && owner.newItemCount > 0`
  改成 **`remainingNew < owner.newItemCount`（只下调）**。
- **`ui/pages/work_detail_page.dart`** 的 `isNewItem` 也换成 `isItemWatched`。

### ③ ⛔⛔ 只下调、绝不上调
从「未读集合」重算的口径**比 `applyFollowCheck` 的累加更宽**（包含「追剧之后、
但被**全盘扫描**而不是追更检查发现的集」）。上调会让**打开一次详情页就凭空
冒出角标**。上调的唯一入口是 `applyFollowCheck`；下调永远安全。

### ④ ⛔⛔ 新发现的真 bug：`item.groupKey` 在**归一之后不是作品 key**
`_markOpened` 手里只有 `MediaItem`，能给的只有 `groupKey`。但刮削归一之后：
```
media_items.group_key = 'z遮天'          ← 文件名解析出来的归组键
media_works.key       = 'shroudingtheheavens'   ← 归一目标（追剧状态挂在这行）
media_works['z遮天'].merged_into = 'shroudingtheheavens'   ← 别名行
```
直接拿 `groupKey` 去 `workByKey` 会落在**别名行**上，而那行 `followed == false`
⇒ 提前 return ⇒ **角标永远降不下来，且不报错**。

**修**：`syncFollowReadCount` 自己顺着 `mergedInto` 走到目标（与
`workDetailProvider` 同一口径；只走一跳，因为折叠不允许成链）。
离线验证：把这一步 `if (false)` 掉 ⇒ `Expected: <1> / Actual: <0>`。

## ⑧ CI 红：`flutter analyze` 报 128 条 `uri_does_not_exist`（14:40 修）

**为什么本地没见过**：本地一直跑的是窄口径 `flutter analyze lib test`；
CI（`.github/workflows/ci.yml`）跑的是**裸 `flutter analyze`**（分析整个仓库），
于是炸在 vendored 包上。**口径不一致**才是真凶。

**根因**：`packages/video_player_android` 是 `dependency_overrides` 里的 **path 依赖**。
**path 依赖的 `dev_dependencies` 不会被安装** ⇒ 它自己的 `pigeons/messages.dart`
（`package:pigeon/pigeon.dart`）与 `test/android_video_player_test.dart` /
`.mocks.dart`（`package:mockito/…`）全解析不到 ⇒ 128 条
`uri_does_not_exist` / `undefined_annotation` / `undefined_named_parameter` /
`non_abstract_class_inherits_abstract_member`。
**不是本仓库的代码问题，也不该靠补 mockito/pigeon 解决**
（`.mocks.dart` 是过期产物，就算装上 mockito 也还有一批错）。

**修**：根 `analysis_options.yaml` 加

```yaml
analyzer:
  exclude:
    - packages/video_player_android/**
```

理由：该包 Dart 层是**上游原样代码**，我们只改它 Android 侧的 ExoPlayer 缓冲；
真正的编译校验由 `flutter build` 承担（windows-build job 会整包编译），
静态分析不必重复。

**顺带（同一份报错里的唯一 info）**：`flutter analyze` **只要有任何 issue（含 info 级）
就 exit 1**。`lib/ui/pages/player_page.dart` 那个刻意的 `WillPopScope` 也占一份 ⇒
加 `// ignore: deprecated_member_use`。**刻意不迁移** `PopScope`：会改真机返回键行为
（原注释已实测过 `onPopInvokedWithResult` 在电视上不触发）。

**验证**：`flutter analyze` → `No issues found!`，exit 0。

**教训**：以后本地复现 CI，一律跑**裸** `flutter analyze`，别用 `lib test` 窄口径。
