## 排查：TV 恢复备份后部分作品显示的是网盘截图、不是刮削海报

**现象**：macOS 上传备份 → TV 恢复 → 「生死时限」「阿凡达：火与烬」等在 macOS 上是 TMDB 海报，TV 上是网盘视频截图。

**取证链**（可复用）
- macOS 库在 `~/Library/Application Support/com.cloudcine.cloudcine/`（**HOME 被沙箱改写，`~` 找不到，要用绝对路径**）。`sqlite3` 查 `media_works.poster_url` / `poster_file`。
- TV 上 `run-as` 不可用（release 包 not debuggable）、无 `su`。**改用 logcat**：`adb logcat -d --pid <pid>`。关键行 `媒体库：N 部 … 海报索引 X 个文件 · 命中 Y`（`LibraryActivity.loadWorks`）。
- 用 Python 复算 `PosterNaming.hash8/sanitize` 对齐 PC 的 `PosterCache._sanitize`，确认文件名。

**结论**：根因是 **TV 上装的构建里 `PosterStore.fileFor` 没有第 ② 步**（按当前 `poster_url` 现算文件名）。旧口径只有 ①`poster_file`（PC 刮的为空）+ ③目录索引，而索引对每个键**只留 `listFiles()` 里第一个** ⇒ 一个键下有多张图时随便挑。实测 378 个海报文件 / 314 个键，其中 **58 部作品的键下有 2~3 张图**（网盘截图 + 刮削海报各一张），所以不止那两部。
**判据**：`javap -p -c` 反编译 `android/app/build/tmp/kotlin-classes/release/.../PosterStore.class`，`fileFor` 里没有 `PosterNaming.fileNameFor` 调用 ⇒ 该 release 产物无第 ② 步（debug 产物有，说明工作区已改、只是没装机）。
**修**：`PosterStore.fileFor` 加第 ② 步（工作区已改，2026-10-07 07:31，未提交）。重新出包装机即可，**不用重新恢复/重新刮削**（海报文件本来就在 TV 上）。
**⛔ 附带发现**：`adb backup -noapk` 在 MiTV 上弹确认框后 `input keyevent` 推不动按钮，产物恒 0 字节 —— 别指望这条路取 TV 数据。

### 3. 凭证随备份恢复 —— 结论：**不需要新的备份代码**

备份包装的是整个 `cloudcine.sqlite` 字节，`settings` 表随之走。只要值写进 `settings`（**不是** `AppPrefs`）、键名与 PC `SettingKeys` 逐字一致即可。键名：`tmdb_api_key`·`tmdb_api_base`·`tmdb_image_base`·`douban_cookie`。

**⛔ 顺手修掉 PC 端一个真 bug**：`SettingsStore` 有进程内 `_cache`，而 `importBackup` 换掉整个库文件 ⇒ 缓存不知道。触发路径：新机器先打开设置页（缓存记下「Key 为空」）→ 从网盘恢复 → **设置页还是空的、刮削走匿名额度，要重启才对**。修法两条缺一不可：
1. `SettingsStore.invalidate()` + `LibraryBackupService` 新参数 `onLibraryReplaced`（`importBackup` 末尾无条件同步调用）+ 组合根接 `ref.read(settingsStoreProvider).invalidate()`。
2. `settings_page._refreshLibraryViews()` 加 `ref.invalidate(settingsProvider)`。

Android 端天然满足（`ScraperPipeline.fromSettings` 每次刮削重建）。

## 需求 4：点作品卡片先进入「作品简介页」（不再直接播）

**用户原话**：「媒体文件无法进入简介页面，点击媒体文件应该先进入简介页面，在简介页面支持手动刮削和播放和选集播放的相关功能，对标pc端简介页面」。

### 1. 做了什么

`LibraryActivity` 的 `Level.ITEMS` 头部整块重做，自上而下：

```
detailHead      海报 96×144 + 标题 / 原名 / 元数据行 / 简介（最多 3 行）
actionsScroll   ▶ 播放(续播) · 手动刮削 · 刮削设置 · 选集（N）
itemsSortScroll 修改时间倒序 · 剧集顺序 · 标题     （原有，未动）
itemsList       剧集列表                          （原有，未动）
hintBar         按键提示（随层级换文案）
```

- `onWorkRow` 由 `playWork(it)` 改成 `openWork(it)`。「直接续播」降级成简介页的
  第一颗胶囊 + 作品墙 MENU 里的一项（两条路都还在）。
- `openWork` 里：`paintDetailHead()` + `buildDetailActions()` + 两行胶囊 VISIBLE
  + `itemsList.requestFocus()` + `focusDetailActions()`（**焦点给列表、光标给动作行**）。
- `backToWorks` / `applyWorks` 里把 `detailHead` / `actionsScroll` 转 `GONE`
  并清 `actionsFocused`。
- `refreshAfterScrape` 里补 `paintDetailHead()` + `buildDetailActions()`（刮削改了
  标题 / 年份 / 类型 / 简介 / 海报，不重画就是「刮成功了页面上还是旧的」）。
- 新增 `hintBar` 字段替换原来写死的那句「OK 直接播放」。
- 类文档重写（三层导航 + 两张 ASCII 界面图 + 简介页按键说明）。

### 2. 两个关键设计判断

- **两行胶囊刻意不合并**：动作行回答「对这一部作品做什么」，排序行回答「这一页
  的列表怎么排」。合成一行的话「▶ 播放」会和「修改时间倒序」并排，用户按 ←→
  路过时分不清哪颗是动作。于是有 `actionsFocused` / `itemsSortFocused` 两套光标态。
- **焦点始终留在 `itemsList` 上，胶囊只吃光标态**（与一级导航带 / 状态行同一套
  语言）：焦点一挪到胶囊上，底下列表那行的高亮就没了，用户会以为列表被清空了。
  ⛔ 各 `focus*` 必须互相清标志位，漏清 = 两行同时发光。
  上下层照物理位置：动作行 ↑↓ → 排序行 ↑↓ → 列表；**排序行上的 ↑ 从「回作品墙」
  改成了「到动作行」**，只有动作行上的 ↑/返回才退出这一页。

### 3. ⛔ 顺手修掉一个**不报错**的真 bug

`openWork` 里原来是：

```kotlin
items.clear()
items.addAll(list ?: emptyList())
…
items.clear()                                     // ← 又清了一次
items.addAll(sortItems(items, itemsSortMode))      // ← 排的是空列表
```

⇒ **剧集列表永远是空的**，不报任何错，只是「点进去什么都没有」。改成
`items.clear(); items.addAll(sortItems(list ?: emptyList(), itemsSortMode))`。

### 4. 文案口径下沉成纯函数 + 单测

新增 `library/WorkDetailFormat.kt`（`object`，纯函数）+ `WorkDetailFormatTest`（13 例）。
理由：每一条都是跨端口径，写错**全都不会报错**，而 `LibraryActivity` 里的东西
JVM 单测跑不起来（与 `PlayTarget` / `PosterNaming` 同一套做法）。钉住四条：

| 口径 | 写错的后果 |
|---|---|
| 「已刮削」= `source == "online"`，**不是**「有海报」 | 刮了没下到图的作品写「未刮削」，再刮一遍还是这样 |
| 季数门槛 `>= 2` | 每部电影 / 单季剧多一个「1 季」，像分类判错了 |
| 类型最多 4 个 | 折成两排，把简介正文挤出屏幕 |
| 原名 `!= title` 才画 | 中文片名没刮到时标题连着印两遍 |

**第三个「测试自己写错了」的实例**：我断言「什么都没刮到时 `metaLine` 返回空串」，
实际是 `"其他 · 未刮削"` —— 分类（兜底「其他」）与来源两项恒在，这一行永不为空。
改对断言之后，顺带把 `paintDetailHead` 里多余的 `if (text.isEmpty()) GONE` 也删了。

### 5. 海报解码的三个约束（与海报墙不同）

- 解码走 `Bg.run`（不能主线程），与 `WorksAdapter` 同一套流程。
- ⛔ 解完**只重画这一块**，**不能** `notifyDataSetChanged()` 海报墙 —— 那会连带
  重绑整个 `GridView`，而用户正在看详情页。
- ⛔ 解完必须核对 `currentWork?.key == 解码时那个 key`：这段时间里用户可能已经
  退出 / 进了别的作品，无条件画上去就是**别人的海报**。
