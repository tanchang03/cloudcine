## 播放器窗口底部控制栏右簇不贴右（用户反馈「没有右对齐」）

- 症状：独立播放窗口（`lib/ui/windows/player_window_app.dart` 的 `_buildButtonRow`）
  底部控制栏**右簇**（画质 / 字幕 / 音轨 / 刷新 / 置顶 / 自检 / 全屏 / 关闭）
  在宽窗下缩在中间，右边空一大块。1280 宽窗口实测最右按钮（「停止并关闭」）
  右沿只到 **978**，右边空 302px。
- 根因：原写法 `const Spacer()` + `Flexible(child: SingleChildScrollView(...))`。
  两者**各是 flex 1** → 剩余宽度被**对半**分；而 `SingleChildScrollView` 在主轴
  上是**收缩**的（宽 = 内容宽）、`Flexible` 又是 loose fit → 分到的那一半填不满，
  多出来的部分留在末尾。另外 `mainAxisAlignment: end` 在滚动视图给子 Row 的
  **无界**宽度下**不起作用**。
  - 附带缺陷：右簇只拿到一半可用宽度 → 更早触发横向滚动。
- 修法：去掉 `Spacer`，`Flexible` → `Expanded`，内层加
  `Align(alignment: Alignment.centerRight)`。`Expanded` 是 tight fit → 视口撑满
  分配宽度；内容窄时 `Align` 把内容贴到右边缘，内容宽时视口宽度即可用宽度、
  横向滚动照常生效。注释已写在方法里（含「为什么不能用 Spacer+Flexible」）。
- 内置播放页 `player_page.dart` **不受影响**：那边是 `const Spacer()` + 普通 `Row`，
  Spacer 独占剩余、右簇紧跟其后，本来就贴右。

## 菜单开着时控制栏被收走（用户反馈「点画质弹菜单，播放控制栏整体消失」）

- 根因：`showAnchoredMenu` 走 `PopupRoute`，挂在 **Overlay** 上，位置在播放页
  那个 `MouseRegion`（`_buildPlayer` 最外层）**之外**。用户点开画质后必然把鼠标
  移到菜单上去选 —— 那一刻 `MouseRegion.onExit` 判定「指针离开了窗口内容」，
  **直接**调 `_hideChrome()`。`_cancelHide()` 挡不住这条路径：它只取消**倒计时**，
  而 `onExit` 是**即时**调用。于是菜单还开着、底部控制栏先没了。
- 修法：加 `int _menuDepth`（**计数**不是 bool —— 字幕菜单会重开：搜完在线字幕 /
  挑完本地文件都再弹一次）+ `_pinnedMenu()` 包住 4 处 `showAnchoredMenu`
  （画质 / 片头 / 音轨 / 字幕）；`_hideChrome()` 与 `_pokeChrome` 的倒计时回调
  都加 `if (_menuDepth > 0) return;`。
- ⚠️ **内置播放页 `player_page.dart` 不需要改**：它的 `_scheduleControlsHide`
  开头就是 `if (!AppTheme.isTvLayout(context)) return;`（桌面 / 手机根本不挂
  倒计时），而 TV 上焦点会移到菜单、`shouldAutoHideControls` 的 `stageFocused`
  变 false。**只有独立窗口是「桌面 + 鼠标静止即收」**，所以只有它需要守卫。
- 验证：新增用例「菜单开着时鼠标移出去，控制栏不该跟着消失」。
  - ⚠️ 测试里**不能**先用 `showChrome()` 再自己建鼠标指针：`MouseTracker` 按
    **设备**记账，一个测试里建两个鼠标指针会直接踩框架断言
    `(event is PointerAddedEvent) == (lastEvent is PointerRemovedEvent)`。
    自己建一个 pointer，先 `moveTo` 控制栏（浮层显示）再 `moveTo` 窗口外。
  - 先还原 HEAD 版跑 → 红（`菜单还开着，控制栏不该先没了`）；改后 → 绿。
- 全量 `flutter test`：1542 例全过（exit 0）。

## 已识别但**未修**的两处相邻问题（2026-10-03，用户选择先实测再定）

1. `_toast` 用默认 `SnackBar`（`behavior: fixed`）贴底 → 提示弹出时会**盖住控制栏**
   约 4 秒（`test/ui/windows/player_window_app_test.dart` 的 `drainTimers` 注释里
   也记着这件事）。改法：`behavior: floating` + 底部留出控制栏高度。
2. 独立窗口的控制栏倒计时（`_chromeIdleTimeout` = 3 秒）只看鼠标是否静止，
   **暂停时照样收**；内置播放页有「`playing` 为假就不藏」的约定
   （`shouldAutoHideControls`），独立窗口缺这一条。

排查结论：Overlay 类浮层里只有 4 个 anchored 菜单会踩「鼠标移上去被判成移出窗口」；
剧集面板与边缘条在 `_buildPlayer` 的 `MouseRegion` **内部**，诊断页是页面内切换，都不受影响。

## 「至臻画质」≠ 原画：差异与卡顿根因分析（只分析，未改代码）

- 结论：**至臻画质是服务端转码梯度里的高档位**（`play/info` 的 `video_list`），
  **不是原文件**；我们的「原画」是 `/file/audioplay` 返回的**原文件本身**
  （`quark_adapter.dart:518` / `quark_play_routes.dart:29-52` 已记：`video_list`
  里没有原画，原画那档是我们自己造的）。用户黑暗荣耀单集 5G / 4K SDR MKV。
- 卡顿三因叠加：① 码率差一个数量级（原画均 ~13 Mbps、峰值 30-50 Mbps；转码档
  4-8 Mbps）；② 原画是**源站冷数据回源**单条 TCP 顺序读，转码档是 **CDN 边缘预转码
  分片**可并发；③ 该目录来自「分享」，可能还有额外限流。
- **「缓冲条很满却照卡」是 mpv 的口径问题**：`demuxer-cache-time` 对未完整扫描的
  网络流是「缓存字节 ÷ **估算码率**」换算的，VBR 4K 上会严重高估（200MB 按 7.7Mbps
  报 207 秒，实际 35Mbps 只有 45 秒）→ 缓冲层虚高、45 秒后 underrun。
  真实速率已在 `mpv_cache_state.dart` 用 `raw-input-rate` 取到，可直接对比码率判定。
- 未落地的建议（等用户定）：① 先切「超清 1080P」档做零成本判定实验；
  ② `buffering==true` 时缓冲层要联动（两端已监听 `player.stream.buffering`，
  没和进度条联动）；③ 根治 = 本地 HTTP 代理多线程 Range 拉流喂给 mpv。
  mpv 侧 `bufferSize=1GB` / `readahead=9999s` 已调满，别再往上加。
