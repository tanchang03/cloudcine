## 下载带宽未占满原因分析

- **根因**：`drive_download.dart` 每个文件只用**单条 TCP 连接**顺序读（`await for (chunk in response)`），无分块、无多连接。夸克对单连接有限速（`local_stream_relay.dart` 头注释已实测确认），单连接约 3-5 MB/s。
- **错误假设**：`download_task.dart` 第 6-8 行注释认为"每个任务自己就能把带宽吃满"，因此只在**文件级**做并发（默认 5、上限 10），没做文件内并发。
- **对比**：播放路径 `LocalStreamRelay` 已有 8 连接 × 2 MiB 分块并发 + Range 请求，绕过了单连接限速；但 `drive_download.dart` 第 24-28 行注释明确说"不走本地中继"。
- **服务端支持分块**：`/file/audioplay` 端点实测返回 206 + `Accept-Ranges: bytes`（`quark_endpoints.dart` 第 96-98 行），具备多连接分块下载能力，只是客户端没利用。
- **其他次要因素**：下载用 `dart:io HttpClient` 无 buffer/socket 调优；取链令牌桶 `linkQps=1.0` 只延迟下载开始，不影响传输速率。

## 下载多连接分块整改落地

- **改动文件**：`drive_download.dart`（主改动）、`download_task.dart`（注释修正）、`drive_download_test.dart`（+6 测试）。
- **实现**：`DriveDownloadService` 新增 `_downloadChunked`：N worker 各持一条 keep-alive 连接从共享 `nextFetch` 计数器取块，发 `Range: bytes=a-b`，数据放入有界内存 buffer；单 writer 按 `nextWrite` 顺序从 buffer 取块追加写入 `.part`——`.part` 始终是连续前缀，断点续传语义不变。
- **参数**：`connections=8`、`chunkSize=2MiB`（与 `LocalStreamRelay` 同口径）；阈值 `chunkSize*4=8MiB`，小文件自动走单连接。
- **降级**：服务端回 200 而非 206 → 抛 `_RangeNotSupportedException` → `download` catch 后 `offset=0` 调 `_downloadSingle`。
- **关键约束**：`.part` 唯一真源、暂停保留/取消删除、`autoUncompress=false`+`identity`+`DIRECT` 全钉住；背压：buffer 满时 worker 轮询等待。
- **测试**：6 个新测试（分块正确性/续传/Range 降级/暂停/取消/小文件单连接）；全量测试通过。

## 播放器窗口底部控制栏右簇不贴右（用户反馈「没有右对齐」）

- 症状：独立播放窗口（`lib/ui/windows/player_window_app.dart` 的 `_buildButtonRow`）
  底部控制栏**右簇**（画质 / 字幕 / 音轨 / 刷新 / 置顶 / 自检 / 全屏 / 关闭）
  在宽窗下缩在中间，右边空一大块。1280 宽窗口实测最右按钮（「停止并关闭」）
  右沿只到 **978**，右边空 302px。
- 根因：原写法 `const Spacer()` + `Flexible(child: SingleChildScrollView(...))`。
  两者**各是 flex 1** → 剩余宽度被**对半**分；而 `SingleChildScrollView` 在主轴
  上是**收缩**的（宽 = 内容宽）、`Flexible` 又是 loose fit → 分到的那一半填不满，
  多出来的部分留在末尾。另外 `mainAxisAlignment: end` 在滚动视图给子 Row 的
  **无界**宽度下**不起作用**。
  - 附带缺陷：右簇只拿到一半可用宽度 → 更早触发横向滚动。
- 修法：去掉 `Spacer`，`Flexible` → `Expanded`，内层加
  `Align(alignment: Alignment.centerRight)`。`Expanded` 是 tight fit → 视口撑满
  分配宽度；内容窄时 `Align` 把内容贴到右边缘，内容宽时视口宽度即可用宽度、
  横向滚动照常生效。注释已写在方法里（含「为什么不能用 Spacer+Flexible」）。
- 内置播放页 `player_page.dart` **不受影响**：那边是 `const Spacer()` + 普通 `Row`，
  Spacer 独占剩余、右簇紧跟其后，本来就贴右。

## 菜单开着时控制栏被收走（用户反馈「点画质弹菜单，播放控制栏整体消失」）

- 根因：`showAnchoredMenu` 走 `PopupRoute`，挂在 **Overlay** 上，位置在播放页
  那个 `MouseRegion`（`_buildPlayer` 最外层）**之外**。用户点开画质后必然把鼠标
  移到菜单上去选 —— 那一刻 `MouseRegion.onExit` 判定「指针离开了窗口内容」，
  **直接**调 `_hideChrome()`。`_cancelHide()` 挡不住这条路径：它只取消**倒计时**，
  而 `onExit` 是**即时**调用。于是菜单还开着、底部控制栏先没了。
- 修法：加 `int _menuDepth`（**计数**不是 bool —— 字幕菜单会重开：搜完在线字幕 /
  挑完本地文件都再弹一次）+ `_pinnedMenu()` 包住 4 处 `showAnchoredMenu`
  （画质 / 片头 / 音轨 / 字幕）；`_hideChrome()` 与 `_pokeChrome` 的倒计时回调
  都加 `if (_menuDepth > 0) return;`。
- ⚠️ **内置播放页 `player_page.dart` 不需要改**：它的 `_scheduleControlsHide`
  开头就是 `if (!AppTheme.isTvLayout(context)) return;`（桌面 / 手机根本不挂
  倒计时），而 TV 上焦点会移到菜单、`shouldAutoHideControls` 的 `stageFocused`
  变 false。**只有独立窗口是「桌面 + 鼠标静止即收」**，所以只有它需要守卫。
- 验证：新增用例「菜单开着时鼠标移出去，控制栏不该跟着消失」。
  - ⚠️ 测试里**不能**先用 `showChrome()` 再自己建鼠标指针：`MouseTracker` 按
    **设备**记账，一个测试里建两个鼠标指针会直接踩框架断言
    `(event is PointerAddedEvent) == (lastEvent is PointerRemovedEvent)`。
    自己建一个 pointer，先 `moveTo` 控制栏（浮层显示）再 `moveTo` 窗口外。
  - 先还原 HEAD 版跑 → 红（`菜单还开着，控制栏不该先没了`）；改后 → 绿。
- 全量 `flutter test`：1542 例全过（exit 0）。

## 「至臻画质」≠ 原画：差异与卡顿根因分析（只分析，未改代码）

- 结论：**至臻画质是服务端转码梯度里的高档位**（`play/info` 的 `video_list`），
  **不是原文件**；我们的「原画」是 `/file/audioplay` 返回的**原文件本身**
  （`quark_adapter.dart:518` / `quark_play_routes.dart:29-52` 已记：`video_list`
  里没有原画，原画那档是我们自己造的）。用户黑暗荣耀单集 5G / 4K SDR MKV。
- 卡顿三因叠加：① 码率差一个数量级（原画均 ~13 Mbps、峰值 30-50 Mbps；转码档
  4-8 Mbps）；② 原画是**源站冷数据回源**单条 TCP 顺序读，转码档是 **CDN 边缘预转码
  分片**可并发；③ 该目录来自「分享」，可能还有额外限流。
- **「缓冲条很满却照卡」是 mpv 的口径问题**：`demuxer-cache-time` 对未完整扫描的
  网络流是「缓存字节 ÷ **估算码率**」换算的，VBR 4K 上会严重高估（200MB 按 7.7Mbps
  报 207 秒，实际 35Mbps 只有 45 秒）→ 缓冲层虚高、45 秒后 underrun。
  真实速率已在 `mpv_cache_state.dart` 用 `raw-input-rate` 取到，可直接对比码率判定。
- 未落地的建议（等用户定）：① 先切「超清 1080P」档做零成本判定实验；
  ② `buffering==true` 时缓冲层要联动（两端已监听 `player.stream.buffering`，
  没和进度条联动）；③ 根治 = 本地 HTTP 代理多线程 Range 拉流喂给 mpv。
  mpv 侧 `bufferSize=1GB` / `readahead=9999s` 已调满，别再往上加。

## 已落地：本地多路中继（用户要求「1:1 复刻夸克网盘方案」）

### 新增（全部在 `lib/data/stream/` + 两个纯函数文件）
- `core/utils/http_range.dart`：Range 解析 / 裁剪 / `Content-Range`。
  ⚠️ `bytes=0-` 在**长度未知**时必须返回 null（无从换算终点）；`clampRange`
  起点已越界必须返回 null（夹成「最后一字节」会让客户端以为拿对了数据）。
- `data/stream/chunk_layout.dart`：字节偏移 ↔ 块序号，**闭区间**，末块截断。
- `data/stream/chunk_cache.dart`：按块 LRU。⚠️ **刚 put 的那块绝不淘汰** ——
  单块超上限时淘汰它 = 下载 / 删除 / 再下载死循环。
- `data/stream/local_stream_relay.dart`：loopback HttpServer + N 路并发 Range
  预取 + LRU + **插队**（播放器此刻要的块优先）。默认 8 连接 × 2 MiB 块、
  预取 256 MiB、缓存 256 MiB。
  - ⚠️⚠️ **`Completer.sync()` 是雷**：`complete()` 会**同步**跑被唤醒 worker 的
    后续代码，而那一刻 `_notifyWorkers` 还在遍历 `_idleWorkers` → 抛
    `Concurrent modification`，**worker 全死且不报错**（只表现为「不再预取」）。
    修法：worker 用异步 `Completer()`，notify 前先 `toList()` 再 clear。
    这个 bug 是端到端单测抓到的。
  - ⚠️ 上游 HttpClient 必须 `findProxy = DIRECT`：`dart:io` 默认读 `http_proxy`，
    会把网盘直链也代理掉 → 「扫描正常、播放奇慢」，看不出原因。
  - ⚠️ 必须 `Accept-Encoding: identity`：Range + gzip 拿到的是压缩流的片段。
- `domain/adapters/stream_relay.dart`：抽象 + `RelayStats` + `isRelayableUrl`。
  ⚠️ **HLS（`.m3u8`）必须排除**：m3u8 里是相对地址，中继把基准改成
  `127.0.0.1` → 转码档直接播不了。顺带说明：原画=直链（可中继），
  转码档=HLS（本来就分片并发，不需要中继）—— **中继只服务原画**。

### 接入（两处，各一份）
- `PlaybackController`：构造加 `relay`；`_prepareSource` 在 `_loadIntoPlayer` 里
  换成中继地址。⚠️ `_releaseRelay` 必须在**每次**换源时关旧会话 —— 切清晰度
  走的也是 `_loadIntoPlayer`。⚠️ 走中继时 **headers 必须清空**（Cookie 由中继自己带）。
- `player_window_app`：同构，`_openStream` 里 `_prepareSource`（返回 record）。
  中继跑在**播放窗口自己的引擎**里（够不到主进程 provider），配置**随每条请求投过来**
  （见下「Task #7」）。
- 设置：`SettingKeys.streamRelay`（默认开，判据 `!= 'false'`）+ `relayConnections`
  （1..16，默认 8）；设置页加了开关 + 滑块。
- ⚠️ 设置同步**不能**让 `streamRelayProvider` 自己 `watch(settingsProvider)`：
  设置一变就重建中继对象 → dispose → 关掉所有会话 → 掐断 mpv 正在读的流。
  最终做法：`streamRelayProvider` 只建对象、**刻意不读设置**（读了就会把
  `settingsProvider` 的异步 + 数据库依赖拖进任何「只想看一眼中继状态」的地方，
  诊断页和单测都会炸）；设置由**副作用 provider `relayConfigSyncProvider`**
  推过来（`ref.watch(streamRelayProvider)` + `ref.watch(settingsProvider)`，
  再 `relay.configure(...)` 就地改，不重建）。
  ⚠️ 副作用 provider **不产出值 → 必须在 `CloudCineApp.build` 里 watch 一次**，
  漏了的表现是「设置页开关点了没反应」，且**没有任何报错**。

### 缓冲条诚实化
`PlayerBufferProgress.fraction(stalled:)`：mpv 报 `paused-for-cache`
（`stream.buffering`）时，缓冲层**收回播放头**。这是修正而不是保守 ——
`demuxer-cache-time` 是「字节 ÷ **估算码率**」，VBR 4K 上严重虚高。
两个调用点（`bufferedFraction` / 独立窗口）都传了。

### 诊断页可见性
`diagnostics_page.dart` 插 `RelayStatusPanel`（`LogPathRow` 与日志列表之间）：
显示「N 条连接在拉」+ 进度条 + 源标签 + 缓存字节 + 上游请求/失败数。
⚠️ 定时器**只在真有会话时**才 1Hz 起（`aggregateStats != null`），否则空转；
进度条 value 给 `progress ?? 0`（给 null 会变**无限动画**）。空态文案要说清
「未启用，或播的是转码档 / 本地文件」—— 不然用户会以为坏了。

### Task #7：独立播放窗口的中继配置统一
- 问题：独立窗口在**另一个引擎**里，读不到设置库。不把配置投过去的话，
  「设置页关掉中继」只对内置播放页生效 —— 用户不可能知道这两条路是分开的，
  只会觉得开关**时灵时不灵**。
- 做法：`PlayRequest` 加 `streamRelay` / `relayConnections`（含 `toJson`/`fromJson`/
  `==`/`hashCode`）；`desktop_play.dart` 从设置库读并算好随请求投过去；
  `player_window_app._prepareSource` 每次开流前先 `_relay.configure(...)` 再关旧会话。
- ⚠️ `desktop_play` 里的判据与 `AppSettings.fromValues` **必须逐字一致**
  （缺失即开 / 缺失即 8，且同样 clamp 1..16）。不一致不报错，只表现成
  「设置页显示 8 条，实际按别的数跑」。

## PGS（图形）字幕不显示：根因与修复（用户反馈「字幕加载不出来」）

### 症状
`/来自：分享/黑暗荣耀 全2季 … 内封sup简体中字 单集5G/` 的 The Glory S01E01
（4.73 GiB MKV，内封一条 `hdmv_pgs_subtitle`，菜单显示「简体中文 / PGS 图形 /
默认轨」）：**列得出来、也打得勾**（勾来自 mpv 的 `stream.track` 回报，
不是乐观更新），画面上一个字都没有。夸克播放器能显示。

### 根因：macOS 预编译 libmpv 的 FFmpeg 里**没有 `pgssub` 解码器**
- `media_kit_libs_macos_video` **1.1.4（2023-09-27，pub 上至今最新）** 内置的
  `Avcodec.xcframework` 用 `--disable-all` + 显式白名单；白名单有
  `subrip/ass/ssa/webvtt/dvdsub/dvbsub`，**唯独漏了 `pgssub`**。
- 本机实测（`strings` 产物里的 Avcodec）：`pgssub` **0 次**；对照组
  `subrip` 4 / `ass` 66 / `ssa` 12 / `webvtt` 4 / `dvdsub` 8 / `dvbsub` 6。
  `hdmv_pgs_subtitle` 这个**名字**在（所以轨道能识别、菜单能显示「PGS 图形」），
  但**解码器不在** → 「能选中、不显示」。
- 上游已修：`libmpv-darwin-build` **v0.7.3（2026-09-14）** 的发布说明就是
  `fix(ffmpeg): enable PGS subtitle decoder #55`。但 pub 包停在 v0.6.0 的构建
  （Makefile 里 `MPV_XCFRAMEWORKS_VERSION=v0.6.0` 硬编码），从没跟进。
- 相关 issue：media-kit#1228（macOS PGS 不显示）、libmpv-darwin-build#54（根因）。

### 修法（本机已落地；⚠️ 机器本地，**不在仓库里**）
只换 **Avcodec.xcframework 一个**（v0.7.3 的 `macos-universal-video-default` 变体）：
- v0.7.3 的 Avcodec 与我们的**同为 FFmpeg 6.1 ABI**（Avcodec `60.3.100` /
  Avutil `58.2.100` / Swresample `4.10.100` / Dav1d `6.0.0`），其余解码器计数
  **逐项一致**，唯一差别就是多了 `pgssub` → 只换它**不动 Mpv.framework**，
  零版本混用风险。换整套反而把 mpv 从 v0.6.0 跳到 v0.7.3，行为风险大得多。
- 落地路径：`~/.pub-cache/hosted/pub.dev/media_kit_libs_macos_video-1.1.4/`
  `macos/Frameworks/Avcodec.xcframework`（原版备份在 `/tmp/avcodec-v060-backup`，
  权威还原源是 `.cache/xcframeworks/libmpv-xcframeworks-v0.6.0-macos-universal.tar.gz`）。
- 已验证：产物 `build/macos/Build/Products/Debug/CloudCine.app/…/Avcodec` 里
  `pgssub` 在，且 adhoc 签名正常（`✓ Built`）。
- ⛔ **会被静默还原**：`flutter pub cache repair`、`make clean`、或删掉
  `.cache/xcframeworks/` 之后 `pod install` → make 会重新解 v0.6.0 覆盖回来。
  **还没做成仓库可复现的补丁**（候选落点：`macos/Podfile` 的 `post_install`，
  那里已经有两个同类 upstream 补丁）。

### 诊断日志的缺口（一并修了）

`Could not find subtitle decoder for format 'hdmv_pgs_subtitle'.`

#### 真正的根因：`sub-visibility=no`

media_kit 的 `PlayerConfiguration.libass` **默认 `false`**，而它一口气翻三个属性
（`media_kit-1.2.6/lib/src/player/native/player/real.dart`）：

```dart
'sub-ass':                  configuration.libass ? 'yes' : 'no',
'sub-visibility':           configuration.libass ? 'yes' : 'no',
'secondary-sub-visibility': configuration.libass ? 'yes' : 'no',
```

mpv 0.36 手册（`--sub-visibility`）原文：

> Can be used to disable display of subtitles, but still select and decode them.

**与观察到的现象逐字对应**：选了、解了、不显示、不报错。

关掉 mpv 的渲染之后，字幕改由 Flutter 层画：`media_kit_video` 的 `Video`
组件内部自带 `SubtitleView`，读 `player.stream.subtitle` ——
**`List<String>`，纯文本**。文字字幕（srt/ass/vtt）能走通，
**位图字幕（PGS）没有文字可提取，永远无路可走**。

顺带排掉一个怀疑对象：`osd-level=0`（`osc: false` 时 media_kit 会设）**不影响
字幕** —— 手册原文 `:0: OSD completely disabled (subtitles only)`。

#### 修法

新增 `core/utils/player_subtitle_config.dart`（`PlayerSubtitleConfig.useLibass`），

「两播放器共用真源」约定。`Video` 组件**已经内置**互斥判断
（`video_texture.dart`：`!(...configuration.libass ?? false)` 时才挂
`SubtitleView`），所以不会出现双份字幕。用户实测：字幕正常显示。

#### 逆向夸克：它也是**在播放器内核里画**

拆 `/Applications/Quark.app`（7.3.5.1009，Electron + 原生播放器）：

- `Libraries/libapolloffmpeg.dylib` 的构建串里明确有
  `--enable-decoder=pgssub --enable-demuxer=sup`，字符串里也有
  `PGS subtitle decoder` / `S_HDMV/PGS` / `hdmv_pgs_subtitle`；
- `Libraries/libu3player.dylib` 里文字与图形是**两条独立渲染路径**：
  `directRenderForText` / `directRenderForGraphic`、
  `getGraphicSubtitleSourceVideoSize`、「graphic subtitle video size fallback」
  （位图拿不到自身尺寸时回退用视频尺寸）；文字那条走静态链进去的 libass

- 另有 ONNX 硬字幕检测 + ASR（`libasr.dylib`）+ 字幕语言检测 —— 那是
  **AI 字幕 / 翻译**那条线（JS 里 `subtitle_url` 取 `{lang, data}` JSON），
  与内嵌字幕无关；
- 全库没有任何「提取内嵌字幕」的接口（`grep subtitle app.asar` 只有
  `FILE_EXT.video_subtitle` 这类文件类型与 AI 字幕相关的东西）。

**结论：夸克不在服务端烧录/提取内嵌字幕**，就是本地解码 + 本地渲染。
我们的方向（补 `pgssub` + 让 mpv 画）与它一致。

## 缓冲进度算错：`demuxer-cache-time` 是绝对时间戳，不是「前面多少秒」

用户反馈「每次点击进度后直接缓存了一大截，可画面照样卡」。

`PlayerBufferProgress` 原来写的是 `缓冲位置 = 播放头 + demuxer-cache-time` ——
**方向反了**。mpv 0.36 手册原文：

> Approximate time of video buffered in the demuxer, in seconds. Same as
> `demuxer-cache-duration` but returns the **last timestamp** of buffered data.

源码同样明确：`player/command.c` 返回 `s.ts_end`；`demux/demux.h` 里
`double ts_end; // approx. timestamp of end of buffered range`；
`demux/demux.c` 里 `ts_duration = ts_end - ts_reader`，且 `ts_reader` 与
`ts_end` **加的是同一个 `in->ts_offset`** —— 所以 `ts_end` 与 `time-pos`
同一参照系，可以直接当位置用。

于是每跳一次进度条，缓冲层就凭空多出**一整个播放头**那么长。用户实测
《黑暗荣耀》47:17 播到 12:07：正确是缓存到 13:20（28.2%），旧算法画到
25:5x（53.8%）。**不报错**，只在进度条上悄悄画错。

修法：`positionOf` 直接返回 `cacheEnd`（只在非正、或落在播放头**后面**时退回
`position` —— seek 期间 mpv 把 `ts_duration` 置 0，但 `ts_end` 不跟着清零，
会短暂报出旧位置的戳）。参数名 `cacheAhead` → `cacheEnd`，让语义在签名上
就看得出来。

另外两处一起改：

- 「已缓存 X」那行（缓冲浮层里）原来印的是 `_cacheEnd` 本身 —— 一个跟总时长
  同量级的**绝对时间戳**。改成 `_cacheEnd − position`，才是「还能撑多久」。
- 窗口新增 `_seek()` 统一入口（5 个 seek 调用点全改走它）：**向前** seek 会让
  `demuxer-cache-time` **整体跳升**，`CacheSpeedMeter` 的容差只处理「变小」
  挡不住，会被算成几百倍速的假尖峰并挂满 5 秒（`_cacheRateStaleAfter`）。
  该文件文档里本来就写着「seek 时要 reset」，代码只在换源时做了 —— 这次补上。
  顺带把算好的 `_cacheRate` 也清掉（`reset()` 只清样本，旧值还会靠宽限显示）。

单测：`test/core/player_buffer_progress_test.dart` 重写，加了一条回归断言
（用上面那组真实数字，同时断言「不等于 `(position+cacheEnd)/total`」），
让「加播放头」那个写法再也回不来。

## 诊断：Extraction 2「切 4K 档」黑屏卡死 = 中继按错体积取块（真 bug，**未修**）

用户报 `惊天营救2 (2023) … DV.HDR.H.265-FLUX[TGx].mkv` 原画播放「有缓冲、黑屏卡死、拖不动」。

**结论：不是杜比视界解码问题，是切「4K」转码档后中继越界取块 → 上游 416 → mpv 断流。**
- 两次 416 风暴（12:41:40 起 11 次、13:09:15 起 20+ 次）**都紧跟 `切换清晰度 → 4K` + `已接管 …（4K）`**；
  两次正常播放（13:05:32、13:10:14）都是「原画」档。
- 块号对得上：4K 档 `play_info` 声明体积 **4,703,134,338 B**（4.38 GiB），
  块 2243 起始 = 2243×2 MiB = **4,703,911,936 > 4,703,134,338** → 越界 416；
  块 2242 = 4,701,814,784 < 该值 → 正常。3300/3101/3265（6 GiB+）更不用说。
- 体积来源错在哪：`player_window_app.dart:1677` `final size = _currentRequest?.sizeBytes;`
  —— `PlayRequest.sizeBytes` 是**库内原画大小（17.09 GiB）**；切档走「刷新直链」通道（`TicketRefreshRequest`），
  `_currentRequest` **不更新** → 中继按 17.09 GiB 算块，却去请求只有 4.38 GiB 的转码流。
- 为何「能解析、不能播」：头部块正常，mpv 能解容器、能列 38 条 `subrip` 字幕轨；但 MKV 的 Cues 在文件尾，
  取尾部即越界 → `_fetchChunk` 抛 `HttpException` → `read()` 断连 → 黑屏卡死。
- `isRelayableUrl` 只排 `.m3u8`，转码档直链（`video-play-*.drive.quark.cn/<token>/…`，无扩展名）被放行，
  与 `stream_relay.dart:66-71` 注释「中继只服务原画」的**本意相悖**。

**修法方向（未实施，等用户定）**：① 中继 size 改用**本次票据声明的 contentLength**（需把 ticket 传进 `_prepareSource`）；
② 或转码档干脆不中继；③ 兜底：请求偏移 ≥ 实际长度时**返回 EOF 而非抛异常**，别让 mpv 断流。

## 原画「播一会卡一会」根因：实测量化（细化当天早些的推测）

用户再问同一片「原画」为什么播一会卡一会、而夸克「杜比视界」流畅。
当天早些的 `至臻≠原画` 条把原画卡顿猜成「源站冷数据回源 / 分享目录限流 / 码率差数量级」——
**实测推翻了前两条**：

- 片源 `meta`：**19.74 Mbps** = **2.47 MiB/s**（不是早先猜的 ~13 Mbps）；DV Profile 8。
- 夸克按连接限速实测：**单连 ~2.43 MiB/s（已贴码率线）**，**8 并发 ~7.46 MiB/s**。
  → 带宽充足，瓶颈是**单连接限速**，不是总带宽、也不是分享目录限流。
- 云影中继（`local_stream_relay.dart:431`）**每块 2 MiB 都 `HttpClient()` 新建 + `close(force)`**，
  ~8500 次 TLS 握手 → 净喂流是「burst→idle/握手」锯齿，稳态有效吞吐贴着甚至低于 2.47。
- 本地复现 `mpv_compare.py`（真实票据）：中继开 → mpv 63s 流畅 0 卡顿、缓冲领先 147s；
  但中继后台累计 **1.80 MiB/s（含空闲）< 片源 2.47** → 长片稳态必被追平 → 周期卡。
  直连组（A/B）因旋转 Cookie 失效探针没加载，**没能直接量直连**。

**结论**：杜比视界==原画（同一原始文件）；卡顿 = 取流模型差异，中继「每 2MiB 重连」把可用带宽切碎成锯齿。
**最高优先修复**：中继改连接复用（每 worker 持有一条 keep-alive HttpClient 连发 Range），消除握手间隙 0 吞吐。
完整报告：`/tmp/qk/夸克与云影_原画卡顿分析报告.md`（用户本次主动要的报告，已交付）。

⚠️ 当天早些 `至臻≠原画` 条里的「源站冷数据回源 / 分享目录限流」两条推测**作废**，以本实测为准。

### 已落地：中继连接复用（用户要求「建议整改项全部落地」）

**根因定量**：稳态吞吐实测（`/tmp/qk/measure_sustained.py`，顺序 2 MiB Range）——
**单连 3.36 MiB/s**、**8 连 7.83 MiB/s**；片源 19.74 Mbps = 2.47 MiB/s。
即**一条复用连接就有 1.36× 余量** → 复用足以让缓冲不再被追平。
（早先记的「单连 2.43」是短促突发，非稳态，已作废。）

**改法**（`local_stream_relay.dart`）：
- `_worker()` 改为**每个 worker 长期持有一条 `HttpClient`**，逐块复用（keep-alive），
  不再「每 2 MiB 新建 + `close(force)`」。`_fetch` 改返回 `bool`（连接是否仍可用）；
  `_fetchChunk` 接收 client、不再自建自毁。
- 新增 `_openClient()`（`findProxy=DIRECT` / `connectionTimeout=20s` / `idleTimeout=30s`）
  与私有 `_UpstreamException`（区分「上游给了响应但状态/长度不对」=连接是好的，
  不该连累连接池；socket/TLS/读中断才重建连接）。
- 新增可观测 `RelayStats.upstreamConnects`（新建连接数，复用生效时应远小于
  `upstreamRequests`）；诊断页显示「连接 M 条」，头部 `N 条连接在拉` → `N 路在拉`。
- ⛔ 记住：**每块新建 HttpClient = 每 2 MiB 一次 TLS 握手**，是把可用带宽切成锯齿的元凶。
- 缓存/预取窗口（256 MiB ≈ 103 s 领先）**没动**：单连 1.36× 余量下领先会自然涨满并维持，不需要加大。

**验证**：`flutter analyze` → No issues found；`flutter test` → **1626 例全过**（基线 1626，未新增用例，只在既有端到端用例里加了连接复用断言：`upstreamConnects ≤ 4` 且上游**不同远端端口数 ≤ 4**，10 次取块）。
**未实测**：真机长片流畅度（需用户起应用实播）。⚠️ 与该片相关的**另一个未修 bug** 仍在：切「4K」转码档时中继按原画体积（17.09 GiB）算块、却取 4.38 GiB 转码流 → 越界 416 → 黑屏（见上方 12:xx 条），本次未动。

### 切字幕 / 切音轨 / 切画质 不中断播放（三条优化 + 一个黑屏真因）

**用户诉求**：切字幕会「重新缓存加载」，体验糟糕；要求切字幕/音轨/画质尽量不中断播放，对标夸克播放器（逆向看它怎么做）。

**先做的定性（读码，非实测）**：
- 字幕 / 音轨**本来就不重载媒体**：走 mpv 的 `sid` / `aid` / `sub-add` / `audio-add`（media_kit 的 `setSubtitleTrack` / `setAudioTrack`），不碰 `Player.open()`。用户感到的「重缓存」来自 ① 网盘字幕要**先下载字节再解码**（一次网络往返）② `sub-add` 换渲染器那一拍。
- 只有**切画质**真的重载：夸克各档是**同一 fid 的不同转码产物** = 换 URL，项目里没有 `setVideoTrack`，只能 `player.open()`。夸克播放器（WebView + 原生引擎）对**文件源**也不是真无缝：要么 HLS 主播放列表自适应，要么快速重载 + 恢复位置；关键在「旧帧不消失」。

**改动（两条播放器路径各一份：`playback_controller.dart` 与 `player_window_app.dart`）**：

### 逐影片播放设置持久化与还原（新功能）

**用户诉求**：「播放影片时的所有设置，都需要记录下来，比如画质，字幕设置，音轨，音效等配置都应该被记录下来，下次再次播放该影片时，应该还原所有相关播放设置」。
两个已确认的设计决策：**记忆粒度 = 单集独立 + 同剧继承**；**记录范围 = 不记音量/倍速（保持全局）**，只记 画质/字幕/音轨/音效/字幕开关。

**数据模型**：新增 `lib/domain/entities/playback_preference.dart`
- `TrackPreference`（`trackId`/`language`/`title`/`index`）—— 轨道存**特征**不存 id，因为内嵌轨号是 mpv 给**这一条流**编的号，换一集必然对不上。
  `scoreAgainst` 四级打分 **100**（id 相同）/**80**（语言+标题）/**60**（仅语言）/**40**（仅序号）/**0**（不匹配）；`bestIndex` 取最高分、并列取**先出现的**。
  `normalizeLanguage` 把 `chi`/`zho`/`zh`/`chs`/`cht`/`zh-Hans`/`cmn` → `zh`（不同发布组/不同 mkvmerge 版本写法不一致，不归一的话「跨集继承」会**时灵时不灵**）。
  ⛔ **四级都不中就当没存过**，退回默认 —— **绝不硬套**一条语言都对不上的轨（那比没记住更糟）。
- `PlaybackPreference`（`qualityId`/`audio`/`subtitle`/`subtitlesEnabled`/`audioEffect`）。`subtitlesEnabled` 缺失即 `true`（判据 `raw['subtitlesEnabled'] != false`；写成 `== true` 会让老库全部变成「字幕关着」）。
  ⚠️ `subtitlesEnabled` 与 `subtitle == null` **不是一回事**：前者区分「用户主动关掉」与「没记过」。

**表与迁移**：`PlaybackPrefs`（`itemId` 主键 / `groupKey` / `prefs` JSON `DEFAULT '{}'` / `updatedAt`），drift **v13 → v14**。
⛔ **刻意不往 `media_items` 加列** —— 那些列会被重扫的 upsert 冲掉，用户的选择会「自己变回去」。

**仓储**（`MediaRepository` 接口 + drift 实现 + `InMemoryMediaRepository`，三处口径必须一致）
- `playbackPreferenceFor(itemId, {groupKey})` 两级：**本文件** → 同 `groupKey` 按 `updated_at DESC` 取**非空**最新（`isEmpty` 的行当「没记过」，因为 `prefs` 列有 `DEFAULT '{}'`）。回退**只限同一部作品**（跨作品串味最难查）。排序必须在 SQL 里做（每开一次播放页都走这里）。
- `savePlaybackPreference` **整条覆盖写**（不合并）—— 「清掉某一项」只有覆盖写表达得出来。
- 删除路径清理：`deleteItem` / `deleteWork` / `deleteItemsNotIn` 都连带删 `playback_prefs`（否则留下永远读不到的孤儿行）。

**两个播放器各一份还原**（`player_page.dart` 内置页 · `player_window_app.dart` 独立窗口）
- 内置页：`_openItem` 读偏好 → 选档 `widget.qualityId ?? pref.qualityId ?? 全局`；`_savePref` 先改本地再写库（值没变则跳过）。控制器 `open(preference:)` → `_autoLoadSubtitle` 用 `bestIndex` 匹配；`_onTracksChanged` 末尾 `_maybeRestoreAudio()`（**一次性闸**，直接 `player.setAudioTrack` 避免 `notifyListeners` 重入）。
- 独立窗口：`_pref` 在 `_adoptRequest` 里**换片才播种**（刷新直链不能重取，否则把用户刚改的顶回去）；`_restoreFromPreference()` 在 `_onTracks` 里触发，音轨/字幕**各只做一次**；`_savePreference` → 通道 `PlayerBridgeMethod.savePlaybackPreference`（窗口**不碰库**，`groupKey` 由主窗口 `player_bridge_host.dart` 翻）。
- 字幕 id **统一口径**（两个播放器读同一个库）：内嵌 `embedded#<sid>`、网盘 `'<itemId>#<fileId>'`。前缀用来分辨来源 —— 少了它「上次选的是网盘 ASS」会被当成「内嵌第 N 条」还原成图形字幕。

**四条硬约束（做错都不报错）**
1. ⛔ **只记用户改过的项**：**别把画质/音效「对齐到本次实际在用的值」再写回** —— 本次实际在用的大多数时候只是**全局默认**，写进库等于钉死成这部片的覆盖值，之后改全局默认这部片再也不跟着变。
2. ⛔ **失败不记**：画质要等 `activeQualityId == id`、字幕要等 `activeSubtitleId == track.id` 才记（否则下次打开会**再失败一次**，用户只看到「字幕总是加载不上」）。音轨例外：候选全来自 mpv 自己的清单，切一条存在的轨不会失败。
3. ⛔ **在线/本地字幕不记**：在线按次计费（自动还原=替用户烧额度）；本地 id 是 `local#<微秒时间戳>`（每挑一次都变，永远匹配不回去，靠序号兜底只会记成另一条不相干的轨）。
4. ⛔ 窗口侧 `_pref` **只播种、不改写**：请求里那份本来就是主窗口从库里读出来的，所以「整份覆盖写」不会丢任何用户没动过的项。

## seek 卡顿根因定位 + 修复（中继预取锚点争抢）

**用户问题**：起播已经不卡了（雷一连接复用生效），但**一拖进度条就「看一会卡一会」**，
问这两种场景有什么区别。

**实测定位**（真中继 + 真夸克直链 + 真 libmpv + 记录型 loopback 代理；90s、第 20 秒 seek 到 1500s）：

- 一条会话上 mpv **同时挂 3~4 个读取器**，且 **seek 不关旧连接** —— 4 次 `SERVE-start`，
  seek 时**没有一次** `SERVE-end`（全部到测试结束才断）。旧读取器留在原地继续被喂。
- 预取锚点原本是**会话唯一**的一个，谁请求谁覆盖 → seek 后在新旧位置反复拉锯
  （`ENSURE 1779 anchor=1779` → `ENSURE 92 anchor=92` → `ENSURE 1797` → `ENSURE 134`）。
- 量化：seek 后 **81% 上游带宽（318 MiB）喂给已不看的位置**，新位置只有 0.87 MiB/s
  （片源需 2.37）→ 位置在 1500.000000 上**冻住 34 秒**、6 次 `paused-for-cache`。
- 顺手排除一个猜测：`cache=no` **不是**原因（`cache=auto` 同样冻 34 秒）。
- **起播为什么不卡**：那时只有一条读取器，锚点没得争。这就是两个场景的唯一区别。

**修复**（三处一起才有效）：
1. 新增 `lib/data/stream/relay_reader_arbiter.dart` —— 纯函数状态机，按**请求范围长度**
   认「在放片子」（≥ 一个预取窗口；MKV `Cues` 探针只有 ~0.86 MiB → 探索引，**永不推锚点**）。
   最新到达的「在放片子」读取器 = 当前读取器（seek 一定新开连接，所以「最新」就是「刚拖到的位置」）。
2. `local_stream_relay.dart`：`_onRequest` 给每个 HTTP 请求编号（`_readerSeq`），
   `_serve/read/_ensure` 全链路带 `reader`；新增 `_stale` **低优先队列**（旧读取器需求
   **降级不丢** —— 丢了 `_ensure` 会永远吊着）；`_take()` 三段顺序：主队列 → 窗口扫描 → 旧读取器。
   `_onAnchorJumped` 三件事一起做：旧位置排队降级、`cache.clear()`、新窗口等待提升回主队列。
3. 文档：类注释加「⚠️ 预取窗口必须跟着正在播的那条流」一节（含实测 trace）。

**修复后同一实测**：旧位置占比 81% → **13%**；新位置 0.87 → **3.36 MiB/s**；
最长不动 34s → **10s**（正常重缓冲）；卡顿 6 → **1** 次；70 秒内推进 13.1s → **57.9s**。

- 空态判据从「视频为空」改成「**三组全空**」—— 否则一个只有 `.srt` 的目录会一边
  列着字幕、一边说「这一层没有视频」。

### 二、下载（`domain/services/drive_download.dart`）

- **取链复用 `adapter.resolveStream`**，没有自己打 `/file/download`。理由：夸克那条
  字面意义上的「下载」接口 **>50MiB 直接 `code=23018`**，而 `resolveStream` 内部降级链
  的第一条 `GET /file/audioplay?fid=` 实测对任意 fid 都回原文件且不限体积 ——
  「哪条接口能拿到这个文件的字节」这份知识只在适配器内部，抄第二遍会抄歪。
- **原子落盘**：全程写 `<目标>.part`，**校验体积通过才 rename**。声明了体积就核对
  （CDN 抖动时连接会「正常」结束而包体是短的）。取消/失败一律不留残文件。
- 与本地中继同一口径的三条：`findProxy=DIRECT`、`Accept-Encoding: identity`、
  `autoUncompress=false`（最后一条是新增的：开着透明解压时 `contentLength` 是压缩后
  的长度，进度会超 100%、体积校验永远不等）。
- 403 判成 `urlExpired` 而不是 `permissionDenied`：网盘直链带签名，过期后 CDN 回的正是
  403，判成权限错会把用户引到「去检查权限」而正确动作是「重新取一次链」。

### 三、UI 侧（`ui/widgets/download_action.dart`）

- 保存位置：`defaultTargetPlatform` 是 macOS/Win/Linux → `getSaveLocation` 弹系统面板；
  其余（Android/TV）→ `defaultDownloadDir()`（系统下载目录 → Android 应用外部目录 →
  `appSupport/downloads` 兜底）再过 `dedupePath` 去重。**判据用 `defaultTargetPlatform`
  而不是 `dart:io Platform`**，否则桌面那一支在 `flutter test` 里永远走不到。
- `dedupePath` 单独抽出来可测：撞名时不改名不会抛任何异常（`openWrite` 默认覆盖），
  只是**静默替换掉用户上一次下载的那个文件**。
- 进度用模态 `AlertDialog` + `ValueNotifier`，带「取消」；总长未知时进度条是不确定态
  （不拿 `received` 编百分比）。完成后 SnackBar 给完整路径 + 「复制路径」。
- entitlements：两份都补了 `files.user-selected.read-write`（`getSaveLocation` 选中的位置
  要往里写）。沙箱已关所以实际不受约束，写进去是为了「万一以后重开沙箱」。

## 详情页「文件」列表：显示网盘修改时间 + 三档排序

需求原话：「媒体文件简介页面中的文件列表，需要显示对应的网盘文件的修改时间，并支持排序
能力 按修改时间排序（正序倒序，默认倒序）」。动手前问了三个岔口，用户答：
**①保留「剧集顺序」做第三档 ②排序落库到设置 ③播放按钮与默认高亮不跟排序走**。

### 一、数据早就有，缺的只是「显示」与「排序」

`MediaItem.modifiedAt` 从扫描第一天起就落库了（`tables.dart:56` → `media_repository_impl`
的 `_toItem`/写入两处），所以这次**一行 DB 改动都没有**。`DriveEntry.modifiedAt` 也早就在
目录视图里用了。

### 二、三档而不是「一个方向开关」

只给「正序 / 倒序」等于把原有的「季 → 部 → 集」弄丢 —— 看剧时最常用的动作会变成
「每次进详情页先手动切一次」。所以 `episodeOrder` 是一个**真正的选项**，且它的实现是
**原样返回**：那条排序规则的唯一实现在仓储层 `itemsForWork`，在 UI 侧再排一遍就是抄
第二份，两处一旦分叉会出现「选择器高亮 Part.1、列表第一行却是 Part.2」而不报错。

新增 `domain/services/item_sort.dart`（纯函数）：
- `ItemSortMode`：`episodeOrder` / `modifiedDesc`（**默认**）/ `modifiedAsc`；
  `parse` 读不懂一律退回默认（与 `FolderSortMode.parse` 同一套，落库用枚举名本身）。
- `sortItems` + `compareItemsByTime`，边界口径**刻意与 `folder_sort.dart` 的
  `compareEntries` 对齐**：`modifiedAt == null` **两个方向都垫底**（「不知道」≠「最旧」，
  正序时把它当最小值会排到第一行）；时间相同按 `naturalCompare(name)` 定序（网盘对一次
  批量上传只给到秒，不定序 = 每次重开详情页都可能换位置）。

### 三、排序**只改显示**，不改 `primary`

`_DetailBodyState.build` 里 `primary`（点播放会播哪一条）必须在 `sortItems` **之前**算。
顺序反过来的后果是「切一次时间倒序 → 点播放播最新上传的那个文件」，而用户要的是续播
那一集 / 第一集。默认高亮哪一季看的是 `WorkDetail.primary`（provider 层，同样没被排序
碰过），所以「第二季那一集最新」时打开详情页仍停在第 1 季 —— 这条专门写了一个 widget
测试钉住（把 `primary` 挪到排序之后算就会红）。

### 四、时间列抽成共用 widget

`folder_browser.dart` 里那个私有的 `_ModifiedColumn` 提成
`ui/widgets/modified_time_column.dart` 的 `ModifiedTimeColumn`：详情页与目录视图是**两套
数据结构、两套行布局**（刻意不共用），但「时间该怎么显示」不是布局问题 —— 一处写
`3 天前`、另一处写 `2026-10-03 16:41`，用户会以为是两个不同的字段。固定 90px 右对齐、
相对时间 + tooltip 给完整时刻、`null` 显示 `—`。目录视图三处调用点与一条测试注释同步改了。

### 五、设置：`SettingKeys.itemSortMode`，**与目录视图分开存**

`folderSortMode` / `itemSortMode` 两个键刻意不合并：排的是两种东西（网盘实时目录 /
已入库的媒体文件），合并后用户在目录视图切成「名称」，回详情页就会看到按文件名排的集，
而集号在文件名里未必是自然序。新增 `itemSortModeProvider`（`library_providers.dart`，
挨着 `workDetailProvider`），模式与 `folderSortModeProvider` 同构：设置没读出来时先退回
默认，不让列表按错的顺序闪一下。

**没有**在设置页加对应的一行：详情页那个排序开关就是唯一入口，加一行「默认值」只会多出
一个「改了这里、那里没变」的困惑。用户要的话随时可以补。

### 六、UI 细节

- 排序开关放在「文件」一节的标题行右侧（`PopupMenuButton`，与页头 / 目录视图那两个排序

### 五条「做错不报错、只悄悄坏数据」的约束

1. **`.part` 是断点的唯一真源**。`startOffset` 只是提示，一律用 `.part` 实际长度
   校正：库里那个按秒节流的快照偏大会撞 **416**（表现「点了继续直接失败」）、
   偏小会重复写一段（文件坏掉但**不报错**）。
2. **服务端忽略 Range 回 200 时必须从 0 重写**。不判这一下会把整份**追加**到
   `.part` 后面 → 长度翻倍，而体积校验**会通过**（received 从 0 重算）——
   唯一一条「下载器自己写坏文件还报成功」的路径。
3. **暂停保留 `.part`、取消 / 失败删除**。`DownloadQueue.dispose()` 用 `pause()`
   而不是 `cancel()`，否则「关一次应用，下了一半的 20 GB 白下了」。
4. **`init()` 先把库里 `downloading` 归一成 `paused`，且刻意不自动续传** ——
   不改的话一开应用就闷头下几十 GB，界面还挂着一条永远不动的「下载中」。
   `DownloadStatus.parse` 读不懂退回 **paused**（退 queued 会让未知状态自动开下）。
5. **`enqueue` 对已存在的记录**：同 savePath 且未完成 → 保留断点；已完成的 →
   **归零**（否则续传从文件末尾要 Range → 416）；**换了保存位置 → 归零**。

## 21:05 批量删除的复核：改了三处注释 + 一个未实施的限流缺口

对刚做完的多选批量删除做了一轮自查。**只改了注释，没改行为。**

### 1. `deleteFiles` 的返回值是**入参回显**（已改注释）
`QuarkAdapter.deleteFiles` 只认信封 `code==0`，然后 `return fileIds` ——
把**入参原样返回**。逐条结果在响应里没有可读的（参考实现无文档，也没翻 `data`）。
但两处注释把它说成「服务端核实过」：
- `CloudDriveAdapter.deleteFiles`（抽象层）原文是「返回被删除的 fid 列表
  （**供调用方核对**）」—— 回显没有任何可供核对的信息，这句是误导；
- `DriveCleanupController._purgeLibrary` 原文「只处理**服务端确认删掉**的那些」
  —— 实际是「请求成功」，不是「逐条确认」。
三处（抽象层 / Quark 实现 / `_purgeLibrary`）已改成如实描述，并写明
**别改成「删完立刻重列目录来核对」**：删除在服务端未必立刻可见，刚删完重列
很可能仍然看得到 → 会把成功报成失败，比少报更糟。`_purgeLibrary` 另补了
「宁可清早不可清晚」的不对称理由（清早了下次扫描会重建；清晚了要等用户
点到那条死索引才暴露）。

### 2. 限流：适配器里有两个桶，但**都只包读接口**
实测（`grep _listBucket|_linkBucket`）：
- `_listBucket`（3 QPS）只包 `listDirectory`、`search`；
- `_linkBucket`（1 QPS, burst 2）只包 4 条取链路由；
- **所有写操作走裸 `_request`**：`deleteFiles`(778)、`createDirectory`(748)、
  `uploadFile` 的 pre/hash/auth/finish(817/860/927/1043/1075)、`moveFiles`。
所以「删除没有节流」与 `createDirectory` / `uploadFile` 是**一致的** —— 项目既有
口径是「被循环调用的**读**接口才进桶」，写接口都是用户单次触发。
`DriveCleanupController` 的批次循环是这个口径下的**第一个例外**：一个写操作被
循环 N 次（`maxIdsPerRequest=100`，3000 项 = 30 次连发、无任何间隔）。
- 已有兜底：`rateLimited` 是**可续**的按批失败（controller 只对
  `unauthorized` / `network` 提前 break），所以顶到限流的后果是「部分失败 +
  如实提示 + 刷新后剩下的还在、可重选重试」，**不是**数据损坏。
- 若补，架构上一致的位置是**适配器里加第三个桶**（与 `_listBucket`/`_linkBucket`
  同层），而不是在 controller 里用 `RequestThrottle` —— 后者类文档明写自己是
  「列目录请求的最小间隔节流器」。代价：3000 项从 ~6-12s（自然往返）变成
  有 ~10s 硬下限。**未实施，等用户拍板。**

**21:12 用户拍板：先不加。** 理由与我的倾向一致 —— 现实批量（几百项 = 几批）
的自然往返耗时已经接近 3 QPS，节流加不了多少保护；顶到限流的后果是
「部分失败 + 如实提示 + 刷新后剩下的还在、可重选重试」，不是数据损坏。
真要补时，位置按上面那条（适配器第三个桶），**别**用 `RequestThrottle`。

### 3. 排查过、确认无问题的两处
- `_delete`（`folder_browser.dart:619`）在 `await` **之前**就取好
  `ScaffoldMessenger.of(context)`，await 之后只用 `messenger` —— 删除中途
  离开页面不会往已销毁的 context 上弹提示。
- 被删的条目若正在下载队列里：`download_queue.dart:488` 把
  `DriveErrorType.notFound` 映射成「这个文件已经不在网盘上了」，且失败是终态，
  不会变成静默重试循环。
